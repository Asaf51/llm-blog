Tools: NumPy, PyTorch & Hugging Face, the workbench behind every Build it

Every project in this book is a few hundred lines of Python sitting on a deep stack: NumPy and PyTorch for arrays, gradients and GPUs, and Hugging Face for models and their files. This chapter teaches that stack from the bottom up, with every snippet run and every timing measured, so that the first line of Chapter 1's project is not also your first line of PyTorch.

In this chapter
  • Python decides what to compute; compiled kernels compute it. A Python loop costs about 22 ns per element, one library call 0.3–0.6 µs, one GPU kernel launch about 3 µs, so the craft is making each call do a lot of work.
  • A NumPy array is a buffer plus shape, dtype and strides. Reductions remove the axis you name (keepdims=True keeps it as length 1); slices are views of the same bytes, while masks and index arrays copy.
  • Broadcasting aligns shapes at the right and stretches length-1 axes without copying. It also turns (N, 1) − (N,) into (N, N) without a word: a mean squared error of 0.125 became 2.125.
  • A dot product of 1,000,000 floats takes 22 ms as a Python loop, 0.088 ms in np.dot on one core and about 0.015 ms in torch.dot on 14 cores: interpreter overhead, then SIMD, then threads.
  • PyTorch tensors add a device and autograd. GPU work is queued, not finished, when Python moves on: a 4096 × 4096 matmul "took" 0.02 ms without torch.cuda.synchronize() and really took 24.2 ms.
  • backward() adds into .grad (6, then 12 if you forget zero_grad). nn.Linear(in, out) stores a [out, in] weight and computes xWT + b; state_dict names are the keys in checkpoint files.
  • The training loop is always batch, forward, loss, zero_grad, backward, step, then validation under eval() and no_grad and a checkpoint. Saving the RNG state makes a resumed run bit-identical.
  • hf auth login and hf download (one pattern per --include) fill a cache under HF_HOME; gated models such as Llama 3.1 need an accepted license. Twenty lines of transformers give SmolLM2-135M's next-token distribution for "The cat sat on the": ␣bed 7.22%.

The stack: from a line of Python to a GPU kernel

Every Build it in this book starts with pip install torch transformers and then writes lines like logits = model(ids) and loss.backward(). Each of those lines runs thousands of lines of C++ and CUDA you never see. When the code is slow, runs out of memory or returns a subtly wrong number, you need a picture of what sits underneath. The good news is that the picture has a familiar shape: a user program calling a library, the library calling a driver, the driver feeding hardware.

Read it top to bottom:

  • Your script. Python is an interpreter. Every + goes through bytecode dispatch and works on boxed, heap-allocated objects. That is fine for control flow and terrible for arithmetic on millions of numbers.
  • The library's Python API. torch.Tensor, torch.nn, numpy.ndarray and transformers are mostly thin Python layers that check arguments and call into C.
  • The dispatcher. PyTorch's C++ core (called ATen) looks at the inputs' device (CPU or GPU) and dtype (float32, bfloat16, …) and picks the matching kernel. If gradients are being tracked, it also records the operation for backward() (see Autograd below).
  • Kernels. A kernel is the compiled function that does the actual arithmetic over a whole array. On a CPU these are SIMD loops and BLAS libraries (Basic Linear Algebra Subprograms: tuned matrix-multiply code). On an NVIDIA GPU they are cuBLAS, cuDNN, PyTorch's own CUDA code and code generated by Triton (a compiler that writes GPU kernels from Python). Chapter 2 owns kernels and how a GPU runs them.
  • Runtime and driver. The CUDA runtime libraries (cuBLAS, cuDNN and friends) arrive with PyTorch as pip dependencies (nvidia-* packages). Only the kernel-mode driver is installed on the system, and nvidia-smi talks to it. See Getting a GPU.
  • Hardware. CPU cores with SIMD units and DRAM, or GPU streaming multiprocessors with tensor cores and VRAM, joined by a PCIe link (Chapter 2).

The cost model that falls out has two terms: a fixed overhead per call (interpreter, dispatch, kernel launch: microseconds) and the work inside the kernel (proportional to the data: fractions of a nanosecond per element). Array programming, the subject of the next three sections, is the craft of making the second term dominate.

Systems analogy: syscalls and write buffering

A call from Python into a kernel is like a syscall: a fixed toll to cross a boundary, after which the real work runs at full speed. You would never write() a file one byte at a time; you fill a buffer and make one call. Array code is the same discipline. Hand the library a million elements per call, not one element per call. The analogy stops at one point: a GPU launch does not wait for its result (PyTorch tensors, below), so the toll and the work can overlap.

The ecosystem map

The book uses a small set of libraries, each with one job. Figure P5.2 shows who talks to whom.

  • PyTorch adds what NumPy lacks for deep learning: GPUs, automatic gradients, layers (nn) and optimizers (optim). Nearly all open-weight model code is PyTorch.
  • Hugging Face is a company and a set of libraries. Key takeaway

Python orchestrates and compiled kernels compute. Every performance rule in this chapter, from vectorization to "do not call .item() in the loop", is the same rule seen from a different layer: cross the expensive boundary rarely, and carry a lot of data each time.

NumPy arrays: shape, dtype, indexing and axes

A model's weights, activations (the intermediate values computed inside it) and logits (its output scores) are big blocks of numbers that all have the same type. A Python list is the wrong container for them. Each element of [0.5, 1.25, …] is a separate 24-byte heap object reached through a pointer, so a million floats cost about 32 MB of objects and pointers instead of 4 MB of data, scattered across memory.

The idea of an array library is one contiguous buffer of raw numbers plus a small description of how to read it. NumPy's ndarray is exactly that: a pointer to the buffer, a dtype (the type of every element, such as float32), a shape (the length of each axis) and strides (how many bytes to jump per step along each axis). An axis is one of the directions you can index along: a matrix has axis 0 (rows) and axis 1 (columns). Chapter 2 owns the memory layout (row-major order and strides); this section is about using arrays.

import numpy as np
x = np.arange(12, dtype=np.float32).reshape(3, 4)
x.shape, x.ndim, x.dtype        # (3, 4)  2  float32
x.size, x.nbytes, x.strides     # 12  48  (16, 4): byte steps per row, column

Indexing and slicing

Indexing has one slot per axis, separated by commas. Each slot is a number (pick one position, the axis disappears), a slice start:stop:step (keep a range, the axis stays), or one of two shortcuts: : means "all of this axis" and ... means "all the leading axes, however many there are". Negative numbers count from the end.

x[0, 1]       # 1.0                    one element
x[-1]         # [ 8.  9. 10. 11.]      the last row
x[:, 2]       # [ 2.  6. 10.]          column 2 of every row
x[1:, ::2]    # [[ 4.  6.] [ 8. 10.]]  rows 1.., every 2nd column
x[..., -1]    # [ 3.  7. 11.]          last element, last axis
x[x > 6]      # [ 7.  8.  9. 10. 11.]  boolean mask: a 1-D copy
x[[0, 2]]     # rows 0 and 2           index array ("fancy")

The ... form is everywhere in model code because it works for any number of batch axes: h[..., -1, :] takes the last token's vector whether h is [n, d] (n tokens, d numbers each) or [B, n, d] (a batch of B such sequences).

Reductions along an axis

A reduction combines many numbers into one: sum, mean, max, argmax (the index of the maximum). With axis=k it runs separately for every position of the other axes, and axis k disappears from the shape. Figure P5.3 shows both directions on the 3 × 4 example. The one argument worth memorizing is keepdims=True: it keeps the reduced axis with length 1, so the result lines up with the original for the next operation. That is how a softmax, which turns a row of scores into probabilities, is written in one line per step for every row at once (the softmax itself is Chapter 4's). Here each row holds the logits of one position, n = 2 rows, over a toy vocabulary of V = 3 tokens:

logits = np.array([[2.0, 1.0, 0.1],           # [n, V] = [2, 3]
                   [0.5, 2.5, 0.3]], dtype=np.float32)
logits.argmax(axis=-1)                        # [0 1]: greedy token per row
m = logits.max(axis=-1, keepdims=True)        # shape (2, 1): [[2.], [2.5]]
e = np.exp(logits - m)                        # (2, 3) - (2, 1): broadcasting
p = e / e.sum(axis=-1, keepdims=True)         # rows: [0.659 0.2424 0.0986]
                                              #       [0.1086 0.8025 0.0889]

Views and copies

Many operations do not copy any numbers. They return a view: a new array header (shape, strides, offset) over the same buffer, the way two pointers can point into one malloc'd block. Writing through a view changes the original. Other operations must gather scattered elements and therefore return a fresh copy. I checked each case below with np.shares_memory:

Common misconception: "a slice is a copy"

In plain Python, lst[1:3] copies. In NumPy and PyTorch, x[1:3] is a view, and an in-place update of it (v += 1, v[...] = 0) writes into x. Copy explicitly when you mean it. The reverse surprise exists too: assigning to a fancy-indexed result (x[[0, 2]][0] = 5) changes only a temporary copy and is silently lost.

dtypes and their defaults

NumPy creates float64 and int64 arrays unless told otherwise (np.array([1.0, 2.0]).dtype is float64). Models run in float32 or lower, so pass dtype=np.float32 when you build arrays that will meet model weights. When dtypes mix, the result is promoted to the wider one: float32 plus a float64 array gives float64, while float32 plus a plain Python number stays float32. Integers wrap around silently: np.array([127], np.int8) + 1 is -128. And float32 runs out of integer precision at 224: np.float32(16777216) + 1 is still 16,777,216 (why is Chapter 2's topic).

Key takeaway

An array is a buffer plus shape, dtype and strides. Index with one slot per axis, reduce with axis= (that axis disappears, unless keepdims=True), and know which operations return views of the same bytes and which return copies.

Broadcasting: how arrays of different shapes combine

Model code constantly combines arrays of different shapes. A linear layer adds one bias vector of length d to every row of an [n, d] batch. A softmax subtracts each row's maximum, shape [n, 1], from logits of shape [n, V]. Attention (Chapter 5) adds one [n, n] causal mask to scores of shape [B, h, n, n], for B sequences and h attention heads. Writing a Python loop for each would be slow, and copying the small array to the big shape first would waste memory.

Broadcasting is the rule that makes these combinations work directly. Elementwise operations (+ - * /, comparisons, np.maximum, …) accept two arrays of different shapes whenever the shapes are compatible, and they reuse the smaller array along the missing or length-1 axes. The rule has three parts:

  1. Align the shapes at the right. Compare the last axes first, then the second-to-last, and so on. If one shape is shorter, pad it on the left with 1s.
  2. Check each axis. Two sizes are compatible if they are equal, or if one of them is 1. Anything else is an error.
  3. Take the larger size. The result has the larger size on every axis. An input of size 1 along an axis is reused for every position along it. Nothing is copied: the reused axis gets stride 0, so every step along it reads the same bytes (for the int64 B of Figure P5.4, np.broadcast_to(B, (3, 4)).strides is (0, 8)).

Gotcha: broadcasting that should have failed

Broadcasting never asks whether you meant it. Predictions of shape (N, 1) minus targets of shape (N,) broadcast to (N, N): every prediction minus every target. With four predictions [1, 2, 3, 4] and targets [1.5, 2, 2.5, 4], the mean squared error comes out 2.125 instead of the correct 0.125. PyTorch's F.mse_loss prints a warning ("Using a target size … that is different to the input size") but still returns 2.125. Plain arithmetic does not even warn. Assert shapes at the boundaries of your functions: assert pred.shape == y.shape.

Vectorization: why a Python loop is hundreds of times slower

Every layer of an LLM is dot products: one row of weights times one input vector, summed (Primer 2). So the dot product is the right benchmark. Here are three ways to compute the dot product of two arrays of 1,000,000 float32 numbers, timed on this chapter's test laptop:

rng = np.random.default_rng(0)
N = 1_000_000
a = rng.standard_normal(N).astype(np.float32)
b = rng.standard_normal(N).astype(np.float32)
la, lb = a.tolist(), b.tolist()                 # same numbers, Python floats

def py_loop():                                  # 22 ms
    s = 0.0
    for i in range(N):
        s += la[i] * lb[i]
    return s

np.dot(a, b)                                    # 0.088 ms, one core: 250x faster
ta, tb = torch.from_numpy(a), torch.from_numpy(b)
torch.dot(ta, tb)                               # about 0.015 ms on 14 cores

The gap has three causes, and each one is a lesson.

  1. Interpreter overhead. The loop body compiles to 13 bytecode instructions (dis.dis(py_loop) shows them). Each is decoded and dispatched by the interpreter, and each * and + checks the types of its operands and allocates a new float object for the result. About 22 ns per element is over a hundred clock cycles at 5.4 GHz, spent to do one multiply-add.
  2. SIMD. NumPy's loop is compiled C that walks two contiguous buffers. With AVX2, one fused multiply-add instruction processes 8 float32 values at once (Chapter 2 covers SIMD and why GPUs take the same idea much further). At 0.088 ns per element on one core, the limit is moving data, not arithmetic: 8 MB of input in 0.088 ms is 91 GB/s, served from the 24 MB L3 cache that holds both arrays between runs, while the multiply-adds alone would take about 12 µs at two 8-wide FMAs per cycle.
  3. Threads. PyTorch split the same work over 14 cores and finished in about 0.015 ms (0.012–0.03 ms from run to run). Libraries parallelize large operations for you; a Python loop never will.

Two more measurements sharpen the picture. First, the slowest bar: looping in Python over a NumPy array is 5× worse than looping over a list, because every a[i] must create a new boxed np.float32 scalar object (about 110 ns per indexed multiply in isolation). Arrays are fast only when the library does the looping. Second, (a * b).sum() is 3.3× slower than np.dot: it writes a temporary 4 MB array of products and then reads it back. Fewer passes over memory win, which is the whole idea behind kernel fusion (Chapter 15).

Low-level view: the per-call toll

A library call has its own fixed cost, separate from the per-element cost. On the test laptop, np.dot on two 8-element arrays takes about 0.34 µs and torch.dot about 0.6 µs (best case): argument parsing, dtype and device checks, dispatch, allocating the result. For 8 elements that is all overhead. For 1,000,000 elements it is noise. So vectorize at the largest granularity you can: one matmul over a whole batch, not one per example. A GPU raises the toll (a kernel launch) and lowers the per-element cost, which makes the same rule matter even more.

How to vectorize

The recipe is to describe the whole computation as array operations and let the library run the loops:

  • Elementwise math on whole arrays: np.exp(x), x * w + b, np.maximum(x, 0).
  • Reductions with an axis: x.sum(axis=-1), x.argmax(axis=-1).
  • Masks instead of if: np.where(x > 0, x, 0.01 * x) computes both branches and selects.
  • Matrix products instead of loops of dot products: X @ W.T for a whole batch, or np.einsum for anything with named axes (Primer 2 teaches einsum notation).
  • Broadcasting instead of tiling: add a [d] bias to an [n, d] batch directly.

A useful smell test: if you are writing for i in range(n) over the elements of an array, there is probably an array expression for it. Python loops stay the right tool for the things that really are sequential, such as training steps, epochs and the token-by-token generation loop of Chapter 1.

Key takeaway

A Python-level loop costs about 20 ns per element; a vectorized kernel costs well under 1 ns. The difference is interpreter overhead plus SIMD plus threads. Push loops over data into the library, one big call at a time.

PyTorch tensors: NumPy arrays with a device

NumPy has no GPU support and cannot compute gradients, and training a neural network needs both. PyTorch's torch.Tensor keeps NumPy's model of an array (a buffer plus shape, strides and dtype) and adds two fields: a device saying which memory the buffer lives in, and autograd bookkeeping (next section). The everyday API is deliberately close to NumPy's, so everything in the last three sections carries over: indexing, reductions, broadcasting, views.

import torch
x = torch.arange(12.).reshape(3, 4)
x.shape, x.stride(), x.dtype, x.device        # torch.Size([3, 4]) (4, 1)
                                              # torch.float32 cpu
x.sum(dim=0)                                  # tensor([12., 15., 18., 21.])
x.sum(1, keepdim=True).shape                  # torch.Size([3, 1])

Three differences bite NumPy users:

  • Default float type. PyTorch creates float32 by default; NumPy creates float64. torch.from_numpy keeps NumPy's dtype, so a float64 array becomes a float64 tensor, and feeding it to a float32 layer fails with mat1 and mat2 must have the same dtype, but got Double and Float. Convert with .float() or build the array as float32.
  • Shared memory. torch.from_numpy(a) and t.numpy() (CPU only) share one buffer, like a view: after a[0] = 42, the tensor reads 42 too. torch.tensor(a) copies.
  • Names. PyTorch says dim and keepdim where NumPy says axis and keepdims (PyTorch 2.15 also accepts the NumPy spellings, but docs and model code use its own), .clone() where NumPy says .copy(), and unsqueeze(i) for inserting a length-1 axis.

Devices, and the price of moving data

A tensor's device is cpu, cuda:0 (the first NVIDIA or AMD GPU), mps (Apple silicon) or another accelerator. Operations run where their inputs live, and all inputs must live in the same place. Mixing them is one of the most common errors you will see:

device = "cuda" if torch.cuda.is_available() else "cpu"
model = model.to(device)                    # moves every parameter, once
x = torch.randn(32, 2, device=device)       # create data where it is used
model(torch.ones(4, 2))                     # CPU input, GPU weights:
# RuntimeError: Expected all tensors to be on the same device, but got mat1
#   is on cpu, different from other tensors on cuda:0 (when checking argument
#   in method wrapper_CUDA_addmm)

Moving data is an explicit copy, and on a discrete GPU it crosses the PCIe link, which is far slower than either side's own memory (Figure P5.6). So move the model once, keep batches on the GPU, and fetch results back only when you need them.

Two details matter for speed. Pinned (page-locked) CPU memory lets the GPU's copy engine read the buffer directly, and allows x.to("cuda", non_blocking=True) to overlap the copy with computation; DataLoader(..., pin_memory=True) sets this up for training batches. And some calls copy back to the CPU without saying so: .item(), .tolist(), .cpu(), .numpy(), print(t), and Python if t > 0: on a GPU tensor. Each one also forces the CPU to wait for the GPU, which is the subject of the next subsection.

The GPU runs behind your back: asynchronous launches

When Python executes c = a @ b on GPU tensors, PyTorch does not wait for the matrix multiply. It enqueues the kernel on a CUDA stream, a first-in first-out queue of work for the GPU, and returns as soon as the launch is recorded. The CPU races ahead to the next line while the GPU works through the queue. This is what lets the CPU's per-launch overhead overlap with the GPU's work. It also means a naive timer measures the wrong thing.

The correct timing harness is short. Warm up first, because the very first matmul in a process also initializes cuBLAS (it took 55 ms here, against 24 ms for the kernel itself):

def gpu_time_ms(fn, reps=20):
    for _ in range(3): fn()              # warm-up: library init, allocator
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()
    for _ in range(reps): fn()
    end.record()
    torch.cuda.synchronize()             # wait until both events happened
    return start.elapsed_time(end) / reps  # ms per call

With this harness the test laptop's GPU did a 4096 × 4096 matmul in 24.2 ms in float32 (5.7 TFLOPS, trillions of floating-point operations per second, counting 2n3 for an n × n matmul; PyTorch's default float32 matmul does not use the faster TF32 mode) and in 5.6 ms in bfloat16 (24.3 TFLOPS, on tensor cores). The CPU, 14 cores, took 249 ms for the float32 version (0.55 TFLOPS). Turning such measurements into a roofline is the Chapter 2 project.

Low-level view: the launch toll on a GPU

A loop of 2,000 tiny z.add_(1) calls on a one-element GPU tensor took about 3 µs per kernel on the test laptop, almost all of it CPU-side launch work: the GPU sat idle between kernels. Recording the same 100 adds once as a CUDA Graph and replaying it cost 0.95 µs per add. With .item() after every add, each step took 9.6 µs. That gap is why generating text one token at a time (decode, Chapter 11), which launches hundreds of small kernels per token, is attacked with fusion and CUDA Graphs (Chapter 15). Chapter 2 puts launch overhead at a few microseconds; when the CPU is busy with other work it grows, because launching is CPU work.

Key takeaway

A tensor is an array with a device and a dtype. Keep data on one device and cross PCIe rarely. GPU work is queued, not executed, when Python reaches the line: time it with torch.cuda.synchronize() or CUDA events after a warm-up, and keep .item() and print out of hot loops.

Autograd: gradients without writing backward

Training needs the derivative of the loss with respect to every parameter: how much the loss would change if that one number moved a little. Primer 1 explains why the optimizer needs it, and Primer 3 built a small engine that computes it for scalars by recording a graph of operations and walking it backwards with the chain rule. PyTorch's autograd is the same idea for tensors, with a hand-written backward rule for every one of its operations.

You use it in three moves. Mark the tensors you want gradients for with requires_grad=True (layer weights are marked for you). Compute a scalar loss with ordinary tensor code. Call loss.backward(), and each marked tensor's .grad now holds the derivative of the loss with respect to it, with the same shape as the tensor itself.

w = torch.tensor(2.0, requires_grad=True)   # a parameter: a "leaf"
x, target = torch.tensor(3.0), torch.tensor(5.0)
loss = (w * x - target) ** 2      # tensor(1., grad_fn=<PowBackward0>)
loss.backward()
w.grad                            # tensor(6.)

Check it by hand with the chain rule. The prediction is y = w·x = 6, and the loss is (y − 5)2 = 1. The loss changes with y at rate 2(y − 5) = 2, and y changes with w at rate x = 3, so the loss changes with w at rate 2 × 3 = 6. Figure P5.8 shows the graph PyTorch recorded to get the same answer.

.grad accumulates

backward() does not overwrite .grad; it adds to it. Run the forward pass and backward() a second time without clearing and w.grad becomes 12. This is deliberate. A parameter used in several places must receive the sum of all its contributions (the fan-out rule of Primer 3), and summing gradients over several small batches before one update is a standard trick for simulating a large batch (gradient accumulation, Chapter 8). The price is that you must clear gradients yourself at every step: optimizer.zero_grad(), which sets every .grad to None. Forgetting it is a classic bug: training still runs, but each step uses the sum of all past gradients. Deleting that one line from the two-moons script in The training loop makes its training loss climb from 0.57 to 52 over 20 epochs instead of falling to 0.037.

Turning autograd off

Recording the graph costs time and, above all, memory: every intermediate tensor that a backward rule needs stays alive until backward() runs. For a large model these saved activations can outweigh the weights (Chapter 8). When you do not need gradients, say so:

  • with torch.no_grad(): nothing inside is recorded. Use it for validation, and for updating weights by hand (w -= lr * w.grad must not itself become part of the graph).
  • with torch.inference_mode(): (or @torch.inference_mode() on a function) is a stricter, slightly faster version for pure inference. Tensors created inside cannot be used later in a computation that autograd records (clone them first); trying gives "Inference tensors cannot be saved for backward". Chapter 1's next_token_probs uses it.
  • t.detach() returns a view of t cut off from the graph: the same numbers, treated as a constant.

Two more rules complete the picture. The graph is freed by backward() to release that memory, so calling backward() twice on the same graph fails with "Trying to backward through the graph a second time"; rebuild it with a new forward pass. And you can test any gradient against finite differences, the check Primer 3 teaches: torch.autograd.gradcheck(f, inputs) does it in float64 and returned True for (A @ B).tanh().sum(). How backprop works for whole matrix layers, and what it costs, is Chapter 8's.

Key takeaway

Autograd records every operation on tensors that require gradients, and backward() replays the record in reverse to add derivatives into .grad. Clear gradients every step, wrap anything that does not need gradients in no_grad or inference_mode, and trust but verify with gradcheck.

nn.Module: parameters, state_dict and the [out, in] weight

A real model has hundreds of weight tensors: 291 in Llama 3.1 8B, 272 in the small SmolLM2-135M used later in this chapter. You need to move all of them to a device in one call, hand all of them to an optimizer, and save and load them by name. Keeping them in loose variables would be hopeless.

PyTorch's answer is torch.nn.Module, a base class for anything with learnable state. A module holds parameters, other modules and a forward method. Any nn.Parameter (a tensor with requires_grad=True) or module that you assign as an attribute in __init__ is registered automatically, so the container can find it later. Calling model(x) runs forward(x) plus any hooks.

import torch.nn as nn

class MLP(nn.Module):
    def __init__(self, d_in=2, d_hidden=16, d_out=2):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(d_in, d_hidden), nn.Tanh(),
                                 nn.Linear(d_hidden, d_hidden), nn.Tanh(),
                                 nn.Linear(d_hidden, d_out))
    def forward(self, x):                  # x: [batch, 2] -> [batch, 2]
        return self.net(x)

model = MLP()
for name, p in model.named_parameters():
    print(name, tuple(p.shape))        # net.0.weight (16, 2), net.0.bias
                                       # (16,), ... net.4.bias (2,)
sum(p.numel() for p in model.parameters())     # 354

nn.Sequential is itself a module: it calls its children in order, each one's output feeding the next. nn.Tanh applies tanh to every element, the nonlinearity of Primer 3's MLP, and has no parameters.

nn.Linear stores its weight as [out, in]

nn.Linear(in_features, out_features) holds a weight of shape [out_features, in_features] and a bias of shape [out_features], and computes y = xWT + b for a batch x of shape [batch, in_features]. I checked that lin(x) equals x @ lin.weight.T + lin.bias. The orientation puts the weights of one output neuron in one contiguous row. Primer 2 explains the math of this convention and Chapter 4 its memory layout. So Llama's gate_proj, which maps 4,096 numbers to 14,336, is an nn.Linear(4096, 14336, bias=False) whose weight has shape [14336, 4096]: 58,720,256 numbers. When a shape in a model file looks transposed, this is usually why.

state_dict: the model as a dictionary

model.state_dict() returns an ordered dictionary from each parameter's dotted name to its tensor (Figure P5.9). It is the unit of saving and loading:

torch.save(model.state_dict(), "mlp.pt")
model2 = MLP()
model2.load_state_dict(torch.load("mlp.pt"))  # <All keys matched successfully>
# with one key missing, strict loading refuses:
# RuntimeError: Error(s) in loading state_dict for MLP:
#     Missing key(s) in state_dict: "net.4.bias".

Loading is strict by default: every key must match a parameter by name and shape, which catches most "wrong checkpoint for this architecture" mistakes. strict=False instead reports the mismatches, as _IncompatibleKeys(missing_keys=['net.4.bias'], unexpected_keys=[]), which is useful when you put a new output layer (a "head") on a pretrained model. Since PyTorch 2.6, torch.load defaults to weights_only=True and refuses to unpickle arbitrary Python objects, because a pickle can run code; Chapter 6 explains why published models use safetensors instead.

The rest of the Module toolkit

  • model.to(device), model.to(torch.bfloat16) move or cast every parameter and buffer in one call.
  • model.train() and model.eval() flip a flag that changes how some layers behave. Dropout in training mode zeroes random elements and scales the rest by 1/(1 − p) (with p = 0.5, eight ones became [2, 2, 2, 2, 0, 2, 2, 0]); in eval mode it passes values through unchanged. The flag has nothing to do with gradients: eval() does not turn off autograd, and no_grad() does not turn off dropout. You usually want both.
  • Buffers (self.register_buffer("inv_freq", t, persistent=False)) are tensors that move with the model but are not learned, such as RoPE's frequency table (Chapter 5). Non-persistent buffers are left out of the state_dict.
  • Hooks (m.register_forward_hook(fn)) call fn(module, inputs, output) after a submodule runs. They are how you capture intermediate activations without editing model code, as the logit lens of Chapter 6 does. Keep the returned handle and call .remove() when done.
Key takeaway

A module is a tree of named parameters with a forward. parameters() feeds the optimizer, state_dict() is what goes to disk, and nn.Linear(in, out) stores a [out, in] weight and computes xWT + b.

The training loop

Everything so far comes together in one loop that every PyTorch training script shares, from a two-input toy to Chapter 8's mini-Llama. Primer 1 owns the ideas (batches, epochs, train and validation splits, overfitting) and Primer 3 owns the gradients. This section is the code. It needs three more pieces of PyTorch:

  • A Dataset answers two questions: how many examples (__len__) and what is example i (__getitem__). TensorDataset(X, y) wraps tensors that are already in memory; a custom subclass can read files lazily.
  • A DataLoader turns a dataset into an iterator of batches: it shuffles the indices each epoch (with shuffle=True), collects batch_size examples and stacks them into batch tensors. With num_workers > 0 it loads batches in background processes, and pin_memory=True prepares them for fast GPU copies.
  • An optimizer from torch.optim holds references to the parameters and updates them from their .grad. Plain SGD does w ← w − lr·w.grad (Primer 1); AdamW, the one LLMs use, is Chapter 8's.

A complete, runnable example

Here is the whole program for the two-moons problem: classify 2-D points that lie on two interleaved half-circles, a task no straight line can solve. It is the same MLP as in Figure P5.9 (written as one nn.Sequential), trained with plain SGD. It runs in under two seconds on the test laptop's CPU (1.7 s).

import math, torch, torch.nn as nn
from torch.utils.data import TensorDataset, DataLoader

def make_moons(n, noise=0.15, seed=0):        # two interleaved half-circles
    g = torch.Generator().manual_seed(seed)
    t = torch.rand(n, generator=g) * math.pi
    y = torch.randint(0, 2, (n,), generator=g)
    top = torch.stack([torch.cos(t), torch.sin(t)], dim=1)
    bottom = torch.stack([1 - torch.cos(t), 0.5 - torch.sin(t)], dim=1)
    x = torch.where(y[:, None] == 1, bottom, top)
    return x + noise * torch.randn(n, 2, generator=g), y

torch.manual_seed(0)                          # seeds the weight init
X, y = make_moons(1200)
train_ds = TensorDataset(X[:1000], y[:1000])  # 1,000 train / 200 validation
val_X, val_y = X[1000:], y[1000:]
g = torch.Generator().manual_seed(0)          # seeds the shuffling
loader = DataLoader(train_ds, batch_size=32, shuffle=True, generator=g)

model = nn.Sequential(nn.Linear(2, 16), nn.Tanh(),
                      nn.Linear(16, 16), nn.Tanh(),
                      nn.Linear(16, 2))
opt = torch.optim.SGD(model.parameters(), lr=0.3)
loss_fn = nn.CrossEntropyLoss()

for epoch in range(20):
    model.train()
    total = 0.0
    for xb, yb in loader:                     # 32 batches per epoch
        logits = model(xb)                    # forward: [32, 2]
        loss = loss_fn(logits, yb)            # one number
        opt.zero_grad()                       # clear old .grad
        loss.backward()                       # fill .grad
        opt.step()                            # w -= lr * w.grad
        total += loss.item() * len(xb)
    model.eval()
    with torch.no_grad():                     # validation: no graph
        val_logits = model(val_X)
        val_loss = loss_fn(val_logits, val_y).item()
        val_acc = (val_logits.argmax(dim=1) == val_y).float().mean().item()
    print(f"epoch {epoch:2d}  train {total / len(train_ds):.4f}  "
          f"val {val_loss:.4f}  acc {val_acc:.3f}")
    torch.save({"epoch": epoch, "model": model.state_dict(),
                "opt": opt.state_dict(), "rng": g.get_state()}, "ckpt.pt")

Its output (selected epochs):

epoch  0  train 0.3783  val 0.3458  acc 0.830
epoch  7  train 0.2151  val 0.2068  acc 0.915
epoch 14  train 0.0611  val 0.0818  acc 0.970
epoch 16  train 0.0865  val 0.5014  acc 0.805      # a bad step: SGD is noisy
epoch 19  train 0.0371  val 0.0673  acc 0.975

Read the log the way Primer 1 teaches. After the first epoch, for six epochs (1 to 6) the training loss hovers between 0.25 and 0.29, which is what a purely linear classifier reaches on this data (I trained one the same way: training loss 0.269, 86% validation accuracy). Then the network learns to bend its boundary and the loss falls fast. Validation follows training closely, so there is no overfitting at this size. Epoch 16 is a reminder that a single SGD step with a large learning rate can make things worse for a while, which is why long runs save the best checkpoint by validation loss, not just the last. The loss.item() inside the loop forces a synchronization on every step; that is harmless on a CPU, while on a GPU you would sum the losses into a tensor and call .item() once per epoch.

Checkpoints, resuming and seeds

A checkpoint must hold everything that influences the future of the run: the model's state_dict, the optimizer's state_dict (empty for plain SGD, but AdamW keeps two tensors per parameter), the epoch counter and the random number generator state that decides the shuffling. Resuming loads them all back:

ckpt = torch.load("ckpt.pt")
model.load_state_dict(ckpt["model"])
opt.load_state_dict(ckpt["opt"])
g.set_state(ckpt["rng"])             # same shuffles as an uninterrupted run
start_epoch = ckpt["epoch"] + 1

I tested this: 10 epochs, stop, resume for 10 more, gives final weights that are bit-for-bit identical to 20 uninterrupted epochs (validation loss 0.0672665983 both times). Leave out the g.set_state line and the resumed run replays epoch 0's shuffles instead: its weights differ by up to 0.085 and its validation loss ends at 0.0715. Seeds work the same way at the start of a run: torch.manual_seed(0) fixes the initial weights and the generator passed to the DataLoader fixes the batch order. Exact reproducibility holds for the same code, library versions and hardware; across GPUs and library versions, floating-point reductions may run in a different order (Chapter 14 explains why).

Key takeaway

The loop is always the same: batch, forward, loss, zero_grad, backward, step; then eval, validate without gradients, checkpoint. Save the optimizer and RNG state along with the weights, and a resumed run is the same run.

Getting a GPU: drivers, memory and out-of-memory errors

Nothing in the six primers needs a GPU. Most Build-its from Chapter 1 on say "1 GPU, 24 GB+", because they run Llama 3.1 8B in bfloat16, and most offer a small-model fallback that runs anywhere. This section covers how to get a GPU working, how to read its memory, and what to do when it runs out.

The options

  • A local NVIDIA GPU. Install NVIDIA's driver through your operating system or NVIDIA's installer. That is the only system-level piece. The CUDA runtime libraries arrive inside the PyTorch wheel: on Linux, a plain pip install torch of version 2.15.0 pulls the CUDA 13.2 libraries (cuBLAS, cuDNN, NCCL and others, several GB of nvidia-* packages). You need the separate CUDA toolkit with its nvcc compiler only to compile your own CUDA code, as Chapter 2's Build it does.
  • An AMD GPU. PyTorch publishes ROCm builds. They keep the torch.cuda API and the "cuda" device string, so most code runs unchanged.
  • Apple silicon. The mps device runs PyTorch on the Mac's GPU, which shares one memory pool with the CPU (Chapter 2). There is no float64 on mps, and some operations are missing; PYTORCH_ENABLE_MPS_FALLBACK=1 runs those on the CPU instead of failing. llama.cpp is often the faster way to run LLMs on a Mac (Chapter 11).
  • A rented GPU. Hosted notebooks offer small GPUs for free or cheaply, and GPU clouds and the large cloud providers rent single GPUs up to 8-GPU servers by the hour. Pick a machine image with the NVIDIA driver preinstalled, check nvidia-smi first, attach enough disk (every copy of Llama 3.1 8B is 16 GB) and point HF_HOME at it, run long jobs inside tmux, and stop the instance when you finish, because billing usually runs while it is idle.

Reading GPU memory: allocated, reserved, and what nvidia-smi shows

PyTorch does not return freed GPU memory to the driver. Its caching allocator keeps freed blocks and reuses them, because asking the driver for memory (cudaMalloc) is slow and can synchronize the device: the same reason malloc keeps a free list instead of calling mmap every time. So there are three different numbers, and they disagree. Measured on the test laptop:

memory_allocated() counts bytes in live tensors. memory_reserved() counts what the allocator holds, live or cached. nvidia-smi adds the CUDA context and libraries (about 100 MiB here, more once cuBLAS and cuDNN load) and anything other processes use. A high nvidia-smi number after a del is therefore normal, not a leak. For a peak figure, use torch.cuda.max_memory_allocated(); for a breakdown, torch.cuda.memory_summary().

When it runs out

Asking for more than is free raises torch.OutOfMemoryError (a subclass of RuntimeError). The message is informative; here it is for a 12 GiB request on the 8 GB laptop GPU:

torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 12.00 GiB.
GPU 0 has a total capacity of 7.62 GiB of which 7.51 GiB is free.
Including non-PyTorch memory, this process has 96.00 MiB memory in use.
Of the allocated memory 512 bytes is allocated by PyTorch, and 2.00 MiB
is reserved by PyTorch but unallocated. If reserved but unallocated memory
is large try setting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True to

What to try, roughly in order of how often it is the fix:

  1. Find the leak first. The classic one is losses.append(loss) instead of losses.append(loss.item()): each stored loss keeps its whole autograd graph, with all its activations, alive.
  2. Turn off gradients for inference (inference_mode), so no activations are kept.
  3. Shrink the batch or the sequence length. Activation memory grows with both.
  4. Use a smaller dtype. Loading a model in bfloat16 instead of float32 halves its weights.
  5. For training, use gradient accumulation and activation checkpointing (Chapter 8) or LoRA and QLoRA (Chapter 9). For inference, quantize (Chapter 13).
  6. Against fragmentation, when "reserved but unallocated" is large, set PYTORCH_ALLOC_CONF=expandable_segments:True. That is the current name of the variable; the message above still prints its older alias, PYTORCH_CUDA_ALLOC_CONF, which also works.

Gated models and access tokens

Some repos are gated: you must be logged in and accept the license on the model page before the files will download. meta-llama/Llama-3.1-8B is gated with manual approval, and an anonymous download attempt fails immediately:

The fix has three steps. Create a Hugging Face account. Open the model's page, fill in the access form and wait for approval (the page shows its status). Then authenticate your machine:

export HF_TOKEN=hf_...  # servers and CI: the token in an env variable

The projects that use Llama also name an ungated fallback (SmolLM2 or Qwen2.5), so you can start before approval arrives.

The cache

Without --local-dir, files go to a shared cache that every Hugging Face library uses, so from_pretrained on a model you already downloaded fetches nothing again (it only asks the Hub whether main moved). Its location is $HF_HOME/hub (override just the hub part with HF_HUB_CACHE). Set HF_HOME to a large disk before downloading big models, and set HF_HUB_OFFLINE=1 to forbid network access entirely. The layout is content-addressed, like git's object store:

transformers: a language model in 20 lines

Chapter 1 describes an LLM as one function f from a sequence of tokens to a probability for every possible next token. With the transformers library you can call that function on a real model in about 20 lines. The model here is SmolLM2-135M: a Llama-style architecture with 134,515,008 parameters, small enough to run on any CPU in float32 (0.54 GB).

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

name = "HuggingFaceTB/SmolLM2-135M"
tok = AutoTokenizer.from_pretrained(name)            # reads tokenizer.json
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32)
model.eval()                                         # already the default

enc = tok("The cat sat on the", return_tensors="pt")
enc["input_ids"]        # tensor([[ 504, 2644, 2643,  335,  260]])
with torch.inference_mode():
    logits = model(**enc).logits     # [1, 5, 49152]: batch, position, vocab
probs = torch.softmax(logits[0, -1], dim=-1)   # the next-token distribution
top = torch.topk(probs, 5)
for p, i in zip(top.values, top.indices):
    print(f"{p.item():.2%}  {tok.decode(i)!r}")
# 7.22%  ' bed'    4.47%  ' edge'    3.29%  ' window'
# 3.22%  ' table'  2.43%  ' tree'

Each line maps onto Chapter 1's picture. The tokenizer turns text into 5 token IDs (Chapter 3). The model returns logits of shape [batch, positions, vocabulary]: it scores every possible next token at every position at once, which is how training gets one prediction per position from a single pass (Chapter 8). For generation only the last row matters, so logits[0, -1] picks batch item 0, last position, and a softmax over its 49,152 scores gives the probabilities (Chapter 4). That vector is f.

Generating text

model.generate runs Chapter 1's loop for you: call f, pick a token, append it, repeat, with a KV cache (Chapter 12) so it does not recompute the prefix.

# greedy: always take the top token
out = model.generate(**enc, max_new_tokens=20, do_sample=False)
tok.decode(out[0])
# 'The cat sat on the bed, and the cat sat on the bed.\n\n
#  The cat sat on the bed.\n'

A small base model, decoding greedily, falls straight into the repetition trap that Chapter 14 explains; do_sample=True with a temperature is that chapter's subject too.

Chat models and the chat template

An instruction-tuned model (one fine-tuned to answer requests, Chapter 9) expects its input wrapped in a specific format of role markers and special tokens. Each repo ships that format as a chat template, and apply_chat_template applies it (Chapter 3 owns templates):

path = "models/SmolLM2-135M-Instruct"    # a local folder works like a repo id
tok = AutoTokenizer.from_pretrained(path)
model = AutoModelForCausalLM.from_pretrained(path, dtype=torch.float32)
messages = [{"role": "user", "content": "What is the capital of France?"}]
enc = tok.apply_chat_template(messages, add_generation_prompt=True,
                              return_tensors="pt")
out = model.generate(**enc, max_new_tokens=40, do_sample=False)
tok.decode(out[0, enc["input_ids"].shape[1]:], skip_special_tokens=True)
# 'The capital of France is Paris.'

With tokenize=False the same call returns the text the model actually sees, 37 tokens for this one question, including a system prompt the template inserts when you give none: '<|im_start|>system\nYou are a helpful AI assistant named SmolLM, trained by Hugging Face<|im_end|>\n<|im_start|>user\nWhat is the capital of France?<|im_end|>\n<|im_start|>assistant\n'. Slicing off the prompt tokens before decoding leaves only the answer.

What from_pretrained does, and the arguments that matter

from_pretrained resolves the name (cache, local folder, or download), reads config.json to choose and size the architecture (LlamaForCausalLM here, from the architectures field), builds the module tree, loads the safetensors weights into its state_dict (all 272 tensors; the LM head is tied to the embedding, as Chapter 6 explains), casts to the requested dtype and returns the model in eval mode. Three arguments do most of the work:

  • dtype= chooses the precision: torch.float32, torch.bfloat16 or "auto". In transformers 5.x the default is "auto": leaving it out loads the dtype stored in the checkpoint (bfloat16 for SmolLM2). Every 4.x version instead loaded float32 unless told otherwise, so the same line gives different numbers and twice the memory on an older install. The argument itself was called torch_dtype= until transformers 4.56; versions before that need the old name, and current ones still accept it with the warning "torch_dtype is deprecated! Use dtype instead!".
  • device_map="auto" places the weights on the available GPUs (spilling to CPU if needed) as they load. It needs the accelerate package; without it the call fails with "requires accelerate". For one device, .to("cuda") after loading also works.
  • revision= pins the repo commit, as with hf download.

In transformers 5.x, apply_chat_template(..., return_tensors="pt") returns a dictionary with input_ids and attention_mask, hence the **enc; 4.x versions returned a bare tensor of IDs unless you passed return_dict=True, so model.generate(**enc) fails there; old code that does model.generate(enc) needs return_dict=False in 5.x.

Key takeaway

AutoTokenizer plus AutoModelForCausalLM.from_pretrained(name, dtype=...) gives you Chapter 1's f: the softmax of logits[0, -1] is the next-token distribution. generate is the loop around it, and apply_chat_template is the formatting a chat model needs.

Environments, versions and the pitfalls table

Every result in this chapter carries a version label, because the stack moves quickly. The transformers library renamed torch_dtype to dtype (4.56) and then changed its default from float32 to the checkpoint's own dtype (5.0). Between huggingface_hub 0.x and 2.x, the CLI was renamed and --include changed shape. A PyTorch wheel fixes its CUDA version. So treat the environment as part of the experiment: one isolated environment per project, with versions pinned and recorded.

Three rules prevent most environment pain:

  • Give inference engines their own environment. vLLM pins an exact PyTorch version and ships CUDA kernels compiled against it, so installing it into your research environment can silently replace your torch. Make a separate venv for vLLM (Chapters 10, 15 and 16 use it as a reference engine), and treat llama.cpp as a separate C++ build with its own Python conversion tools (Chapter 13).
  • Match the CUDA build to the driver, not the other way around: the driver's maximum CUDA version (top right of nvidia-smi) must be at least the wheel's major version (Getting a GPU).
  • Print the versions in every report. torch.__version__, torch.version.cuda, transformers.__version__, the GPU name and the model's commit hash take one line and explain most "it worked yesterday" mysteries.

Milestones

  1. A pinned environment and a benchmark that explains itself

    Write env.py so that every later report can start with one line of versions and hardware. Then reproduce Figure P5.5: time the dot product of two 1,000,000-element float32 arrays as a Python loop over lists, a Python loop over the NumPy array, np.dot on one thread (OPENBLAS_NUM_THREADS=1) and torch.dot on all cores. Take the minimum of several runs, as Vectorization does, and also time an 8-element np.dot to measure the per-call toll.

    def env_report() -> dict: ...         # versions, CUDA, CPU, GPU or None
def best_of(fn, reps: int, warmup: int = 3) -> float: ...  # min seconds
def bench_dot(n: int = 1_000_000) -> dict[str, float]: ...

    The Python loop costs tens of nanoseconds per element (22 ns on the test laptop's performance cores), the NumPy element loop is about 5× worse (109 ms), np.dot is 100–2,000× faster than the list loop, and the 8-element call costs a fraction of a microsecond (0.34 µs). All four results agree to float32 rounding (the test laptop got −204.349 from the float64 loop and −204.341 from float32 np.dot).

  2. Gradients you have checked three ways

    Port Primer 3's small MLP to matrices: 2 inputs and 16 tanh hidden units, but 2 output logits with a cross-entropy loss instead of one sigmoid output, over a batch of 8. Write its backward pass by hand in NumPy float64 (the gradient of the loss with respect to the logits is p − y, the softmax probabilities minus 1 at the true class, divided by the batch size; Chapter 8 derives it). Compare it with PyTorch autograd on the same numbers, and with central finite differences at two step sizes in float64 and in float32.

    def forward(params, X, y) -> float: ...               # NumPy float64
def backward(params, X, y) -> list[np.ndarray]: ...    # shapes of params
def finite_diff(params, X, y, eps: float, dtype) -> list[np.ndarray]: ...

    Hand-written and autograd gradients agree to about 10−16 (8.3×10−17 on the test laptop), and torch.autograd.gradcheck returns True. Finite differences in float64 match to a relative error of 5×10−10 at eps = 10−6 and 4×10−7 at 10−3. In float32, eps = 10−3 gives 4×10−4 and eps = 10−6 gives 0.45: the subtraction cancels almost every bit, as Primer 3 warns.

  3. A training loop that resumes exactly

    Start from the program in The training loop and add a command line: --epochs, --resume, --seed. Save model, optimizer, epoch and the shuffling generator's state at the end of every epoch, plus a separate best-by-validation checkpoint. Plot training and validation loss per epoch.

    def save_ckpt(path, model, opt, epoch: int, gen: torch.Generator): ...

    # returns the next epoch
def train(epochs: int, resume: bool, seed: int = 0) -> dict: ...

    With seed 0 and the same versions, epoch 19 prints validation loss 0.0673 and accuracy 0.975; the plateau near 0.27 for the first epochs and the spike at epoch 16 (0.5014) appear too. 10 epochs plus a resumed 10 give weights bit-identical to 20 straight (torch.equal on every tensor), and dropping the generator state breaks that, as the chapter measured (final validation loss 0.0715 instead of 0.0673).

  4. A timer that does not lie

    Time square matmuls of size 256, 512, 1024, 2048 and 4096 three ways: perf_counter around the call alone, perf_counter with torch.cuda.synchronize(), and CUDA events, each after a warm-up. Do it in float32 and bfloat16 on the GPU if you have one, and in float32 on the CPU regardless. Convert to TFLOPS with 2n3 FLOPs per matmul. While a long run is going, look at nvidia-smi -q -d PERFORMANCE to see whether power or thermal limits are active.

    def time_naive(fn) -> float: ...
def time_synced(fn, reps: int = 20) -> float: ...
def time_events(fn, reps: int = 20) -> float: ...   # ms per call

    The naive timer stays at a fraction of a millisecond for every size (5–50 µs on the test laptop), while synchronized and event times agree within a few percent and grow about 8× per doubling of n once the GPU is busy (0.44, 2.9, 24.2 ms for 1024, 2048, 4096 in float32 there). The first call in a process is slower (55 ms there, cuBLAS initialization). bfloat16 is several times faster than float32 on tensor-core GPUs (24.3 vs 5.7 TFLOPS at 4096 on the test laptop). Chapter 2's roofline lab picks up from here.

  5. Hello, LLM: count it, call it, chat with it

    Count SmolLM2-135M's parameters from the safetensors file using safetensors.safe_open (names, shapes and dtypes only, no tensor data), and compare with sum(p.numel() for p in model.parameters()) after from_pretrained. Hints (open only when stuck)
  • The Python loop takes forever: time it a handful of times, not a thousand. One run of 1,000,000 iterations is already tens of milliseconds.
  • Your np.dot looks slow: check np.show_config(). The test laptop's system NumPy (1.26, linked to the distribution's generic BLAS) took 0.37 ms for the same dot product instead of the venv wheel's 0.088 ms. Also pin single-threaded runs to one core (taskset -c 0 on Linux): hybrid CPUs have fast and slow cores.
  • Hand-written and autograd gradients differ by a constant factor: you forgot to divide by the batch size, or PyTorch's cross_entropy averages over the batch and your loss sums.
  • Resume is close but not identical: you created a new DataLoader generator instead of restoring the saved state, or you use num_workers > 0 without seeding the workers (pass worker_init_fn and a generator).
  • GPU numbers are far below the card's specification: laptops cap GPU power when the CPU is hot. While other jobs kept the test laptop's CPU busy, its GPU dropped to about 750 MHz under a 20 W cap and the float32 matmul took 82 ms instead of 24 ms; nvidia-smi -q -d PERFORMANCE shows "SW Power Cap" when this happens.
  • hf download says "File not found" for *.safetensors: you passed two patterns to one --include; repeat the flag.
  • Your top-5 digits differ slightly: you loaded the default dtype, which in transformers 5 is the checkpoint's bfloat16 (␣bed 7.49%); pass dtype=torch.float32.
