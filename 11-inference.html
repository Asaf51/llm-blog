Part IV · Chapter 11

Inference: Prefill, Decode & Memory

Running a trained model is a loop of forward passes. This chapter shows exactly what one pass does on the hardware, why the first token and every later token are limited by different things, and how to predict speed and memory for any model on any machine.

In this chapter
  • Why prefill (reading the prompt) is a big matrix-matrix multiply bound by compute, and decode (writing the answer) is a matrix-vector multiply bound by memory bandwidth.
  • One decode step of Llama 3.1 8B on an H100, kernel by kernel: 436 MB and about 130 µs per layer, 15 GB and 4.5 ms per token.
  • The roofline applied to LLMs: decode does about B FLOPs per byte, so you need a batch of hundreds before the GPU's compute matters.
  • Latency metrics (TTFT, TPOT, E2E, goodput) and the one formula that predicts decode speed: bandwidth ÷ bytes read per token.
  • The full VRAM budget, what happens when a model does not fit (CPU offload, mmap, unified memory), multi-GPU splits, cold starts, and why output tokens cost more than input tokens.
  • Build it: a predict-then-measure profiler that checks this chapter's formulas (decode bound, roofline knee, TTFT/TPOT, batching curve, VRAM edge, offload, cold start) against your own GPU and Llama 3.1 8B.

Inference is a forward pass in a loop

Training searched for good weights. Inference uses them. Once a model is trained, its weights are frozen: nothing about them changes when you send a request. Every request runs the same fixed function, the forward pass from Chapter 6, again and again inside the generation loop from Chapter 1 (predict, sample, append, repeat).

That makes inference much lighter than training in one way. There is no backward pass, no gradients and no optimizer state. Training needs about 16 bytes per parameter (Chapter 8). Inference in BF16 needs 2 bytes per parameter for the weights, plus some per-request state. For Llama 3.1 8B that is 16.06 GB of weights instead of about 128 GB of training state.

But inference is heavy in another way: it is a loop, and every iteration reads every weight matrix. Three kinds of data live in GPU memory while a model serves requests:

  • Weights: read-only, shared by every request, and read in full on every forward pass.
  • The KV cache: per request. For each token already processed, every layer stores that token's key and value vectors so they never have to be recomputed. It grows by one entry per token (Chapter 12 owns it; here we only need its size: 128 KiB per token for Llama 3.1 8B in BF16).
  • Activations: scratch space for the current pass, reused every step.

A request goes through two phases. Prefill runs the whole prompt through the model in one pass and produces the first output token. Decode then produces the remaining tokens one per pass. The two phases run the same layers with the same weights, yet they stress the hardware in opposite ways. Most of this chapter is about that difference.

Intuition: a full table scan per token

Think of the weights as a 16 GB read-only table with no index. Every forward pass is a full table scan. Prefill is one scan that serves all 2,000 prompt rows at once. Decode is a fresh full scan for every single output token, because the next token's input is not known until the previous scan finishes. You cannot pipeline across tokens of the same sequence. You can only make each scan serve more rows (batching), make the table smaller (quantization), or make the scan faster (more bandwidth).

Prefill and decode: the same layers, two different shapes

The problem. A transformer layer is mostly matrix multiplications against weight matrices (Chapter 2). How expensive a matmul is depends on its shape, and the shape depends on how many tokens you push through at once. Prefill and decode push very different numbers of tokens.

Prefill. All prompt tokens are known up front. Stack their vectors into a matrix X with n rows (one per token) and d = 4,096 columns. Every linear layer then computes X·WT for all rows in one call: a GEMM (general matrix-matrix multiply). Causal masking (Chapter 5) is what makes this legal: each position only looks at earlier positions, so all n positions can be computed in parallel and still give the same answer as one at a time. Prefill produces two things: the K and V vectors of every prompt token at every layer (written into the KV cache), and the logits for the last position, from which the first output token is sampled. Engines only run the LM head on that last row; the other n−1 rows never need logits.

Decode. From then on, exactly one token per sequence is new. Its vector is a single row x of shape [1 × 4,096]. Every linear layer becomes a GEMV (matrix-vector multiply). Attention needs the keys and values of all earlier tokens, and those are already in the KV cache, so the new token computes only its own q, k, v, appends k and v, and attends over everything cached.

The FLOPs per token are the same in both phases: about 2N ≈ 16 GFLOP for the weight matmuls, plus a small attention term that grows with position (Chapter 6). What differs is how many tokens share each weight read. That single ratio decides which hardware limit you hit.

Common misconception

“Long prompts are slow because the model does more work per token.” Per token, prefill does the same weight math as decode. It is just far more efficient, because thousands of tokens share each byte read from memory. On an H100, Llama 3.1 8B processes a 2,000-token prompt in about the time it takes to generate 10 tokens one by one (both are computed below). Only the attention part grows faster than linearly, and that matters only for very long prompts.

One decode step, byte by byte

Let us follow one decode step of Llama 3.1 8B in BF16 on one H100 at batch size 1, and count every byte. The model's 16.06 GB of weights sit in HBM (the GPU's main memory). The H100 can stream at most 3.35 TB/s from HBM into its 132 streaming multiprocessors (SMs). Its 50 MB L2 cache cannot help: a single layer is 436 MB, so by the time the next step needs layer 1 again, layer 1 was evicted long ago. Every step streams every weight from HBM. (Hardware terms are defined in Chapter 2.)

Inside one layer, the step runs a short, fixed sequence of GPU kernels. Here they are with the bytes each must read and the minimum time at full bandwidth:

Multiply by 32 layers: 13.96 GB and 4.17 ms. Add the LM head (1.05 GB, 314 µs) and the sampler. The embedding table is the one weight tensor that is not streamed: the step gathers a single 8 KiB row out of its 1.05 GB. Total: 15.01 GB per token, 4.48 ms at the very best, so at most 223 tokens per second. Meanwhile the math is about 15 GFLOP, which the tensor cores could finish in 15 µs. They sit idle more than 99% of the step.

223 or 209? Most other chapters quote a simpler version of the same bound, which divides bandwidth by the whole model size: 3.35 TB/s ÷ 16.06 GB ≈ 209 tok/s (4.8 ms per token). The only difference is the embedding table. The shortcut counts it as streamed; the strict count above does not, because only one row of it is read. So for models with untied embeddings the shortcut is slightly pessimistic (by the table's share of the bytes: 7% here, 1.5% for the 70B), and for models with tied embeddings, where that table is also the LM head and is read in full, it is exact. Use either for estimates: real efficiency moves the answer far more than 7%. This chapter uses the strict count.

Measured reality. Independent benchmarks of Llama 3.1 8B in BF16 on one H100 report about 152 tokens/s at concurrency 1 with vLLM or TensorRT-LLM (see Further reading). That is 6.6 ms per token, or about 68% of the 223 tok/s ceiling. The missing third goes to:

  • Gaps between kernels. A step launches a few hundred small kernels (roughly 8–10 per layer after fusion). Each has a startup cost and a tail where the last thread blocks finish while the rest of the GPU idles. Engines record the whole step as a CUDA Graph to cut CPU launch overhead (Chapter 15), but the tails remain.
  • Kernels that cannot saturate HBM. The 33.5 MB output projection takes 10 µs at full speed. Ramping 132 SMs up and down around it costs a noticeable fraction of that.
  • Synchronization with the CPU for sampling, stop checks and scheduling the next step.

A useful efficiency metric is model bandwidth utilization (MBU), defined by Databricks as achieved bandwidth ÷ peak bandwidth, where achieved bandwidth = (weight bytes + KV bytes read per step) ÷ TPOT. The H100 example runs at an MBU of about 68%. Good engines on big models reach 60–80%. Tiny models on very fast GPUs do worse, because each kernel moves so few bytes that fixed costs dominate.

Key takeaway

At batch 1, a decode step is a memory copy in disguise: stream every weight byte once, do 2 FLOPs per weight on the way. Its time is set by bytes ÷ bandwidth, not by FLOPs. Per layer of Llama 3.1 8B: 436 MB and about 130 µs on an H100. Per token: 15 GB and 4.5 ms.

The roofline, applied to LLMs

Chapter 2 introduced the roofline model: a kernel's speed is the smaller of peak compute and (arithmetic intensity × bandwidth), where arithmetic intensity I is FLOPs per byte moved. The crossover, the ridge point, is 295 FLOPs/byte for an H100 in BF16. Now we apply it to the two phases of inference.

Decode: intensity equals batch size

Take a decode step with B sequences in the batch. Each weight is a number of b bytes, read once per step. Each sequence uses it for one multiply and one add: 2 FLOPs. So:

Idecode ≈ 2 · N · Bb · N = 2Bb where N = parameters read per step, B = sequences in the batch, b = bytes per weight (2 for BF16, 1 for FP8, about 0.5 for 4-bit). In BF16 the intensity is simply I ≈ B FLOPs per byte.

So decode becomes compute-bound only when 2B/b reaches the ridge, at a batch of B* = ridge × b/2:

  • H100, BF16 weights and math: B* = 295 × 2/2 = 295 sequences.
  • H100, FP8 weights and FP8 math: half the bytes but also twice the FLOP/s (ridge 591), so B* = 591 × 1/2 ≈ 295 again. FP8 makes every step about twice as fast; it does not change where the knee is.
  • H100, 4-bit weights with BF16 math (“W4A16”, Chapter 13): B* = 295 × 0.5/2 ≈ 74. Weight-only quantization reaches the compute roof at much smaller batches.
  • RTX 4090, BF16: ridge about 164, so B* ≈ 164. Apple M5 Max: ridge about 95, so B* ≈ 95.

The catch: the KV cache does not batch

Weights are shared by every sequence in the batch. KV caches are not: each sequence's attention reads its own history. For one sequence at context length c, per layer, attention does 4·d·c FLOPs (scores and weighted sum over 32 query heads of 128 dimensions) and reads c × 4 KiB of K and V. That is 4 FLOPs per byte for Llama 3.1 8B, because each cached KV head serves 4 query heads (GQA; Chapter 5 derives this). In general it is about h/hkv FLOPs per byte in BF16, no matter how large the batch.

Worked example: B = 128 sequences, each with 2,048 tokens of context. Weights: 15.0 GB. KV: 128 × 2,048 × 128 KiB = 34.4 GB. FLOPs: 128 × (15.0 GFLOP of weight matmuls + 1.07 GFLOP of attention) = 2.06 TFLOP. Intensity = 2.06e12 / 49.4e9 ≈ 42 FLOPs/byte, far below the ridge, even though the weight matmuls alone would be at 122. With realistic contexts, decode on an H100 stays memory-bound at every batch size that fits in memory. Shrinking the KV cache (GQA, MLA, KV quantization) attacks exactly this; Chapter 12 covers it.

Prefill: intensity equals chunk length

In prefill the “batch” is the n tokens of the prompt (or of the chunk processed in one pass). By the same argument the weight matmuls do about n FLOPs per byte in BF16, until the activation traffic (which also grows with n) starts to count. For the query projection with n = 2,000: 2·2000·4096·4096 FLOPs over 2·(4096·4096 + 2·2000·4096) bytes ≈ 1,010 FLOPs/byte. Any prompt chunk above a few hundred tokens is compute-bound on an H100. A short prompt of 30 tokens is not; it behaves like a batch-30 decode step.

Key takeaway

Decode intensity ≈ 2B/b for the weights, and only about h/hkv for the KV cache. Prefill intensity ≈ chunk length. So prefill saturates compute with one request, while decode needs hundreds of concurrent sequences to approach compute limits, and long contexts push it back to the memory roof anyway.

Latency: TTFT, TPOT and the shape of a response

Because the two phases are limited by different things, one number cannot describe inference speed. The industry uses a small set of metrics. Tools differ slightly in their exact definitions (for example whether network time counts), so always check what a benchmark measured.

  • Time to first token (TTFT): from sending the request to receiving the first output token. It includes network, queueing, tokenization, the whole prefill, and sampling the first token. Long prompts and busy servers raise it.
  • Time per output token (TPOT): the average gap between output tokens after the first one: (E2E − TTFT) / (nout − 1). Inter-token latency (ITL) is the individual gaps; their distribution matters, because a gap spikes when the server squeezes another request's prefill between your decode steps (Chapter 15).
  • End-to-end latency (E2E): the whole response.
  • Throughput: per user it is 1/TPOT (what one reader sees). Aggregate throughput is total output tokens per second across all users on the machine (what the operator pays for).
  • Goodput: aggregate throughput counting only requests that met their service-level objectives, for example TTFT ≤ 500 ms and TPOT ≤ 50 ms. A server can raise raw throughput by batching harder while its goodput falls.
E2E = TTFT + (nout − 1) · TPOT where nout = number of output tokens. TTFT is dominated by prefill (compute-bound); TPOT by decode (memory-bound).

Worked example. Llama 3.1 8B in BF16 on one idle H100, a 2,000-token prompt, 500 output tokens.

  • Prefill FLOPs. The 32 layers hold 6.98 B parameters, so the weight matmuls cost 2 × 6.98e9 × 2,000 = 27.9 TFLOP. Attention adds about 2·L·d·n2 = 2 × 32 × 4,096 × 2,0002 = 1.05 TFLOP (the causal half of the n × n score and value products). The LM head runs on one row only. Total ≈ 29.0 TFLOP.
  • Prefill time. At an assumed 50% of the 989 TFLOP/s peak (a typical model FLOPs utilization, MFU, for prefill): 29.0e12 / 4.95e14 ≈ 59 ms. With a few milliseconds of network and scheduling, TTFT ≈ 62 ms.
  • Decode. At the measured ~152 tok/s, TPOT ≈ 6.6 ms.
  • E2E = 0.062 + 499 × 0.0066 ≈ 3.36 s. Decode is 98% of the wall time even though the prompt was four times longer than the answer.

For reference: a TPOT of 50 ms is 20 tok/s, faster than most people read. Reasoning models change the picture, because their hidden thinking tokens are output tokens too: thousands of them can pass before the first visible word, so the user-perceived “TTFT” becomes TTFT plus nthink × TPOT (Chapter 10).

The decode speed limit: bandwidth ÷ bytes per token

Everything so far collapses into one formula that predicts decode speed on any hardware, for any dense model, at batch 1:

tokens/s ≤ memory bandwidthWread + c · skv     expected ≈ η × that bound, η ≈ 0.6–0.8 Wread = weight bytes streamed per token (≈ model size; for MoE only the active experts, see Chapter 7); c = tokens already in the context; skv = KV-cache bytes per token (128 KiB for Llama 3.1 8B in BF16); η = achieved fraction of peak bandwidth (MBU).

It is an upper bound because it ignores everything except memory traffic. Real systems land at 60–80% of it. Let us check it against measurements. The llama.cpp project keeps public scoreboards that run the same model (Llama 2 7B) on many devices; that makes them a clean calibration set.

The bound works well, with one pattern worth understanding: small models on very fast GPUs fall far short (the H100 at 32% with a 3.8 GB model). Each token there takes about 3.6 ms, split into hundreds of kernels that each move only a few megabytes. Worked examples

  1. Llama 3.1 8B, BF16, H100: 3.35 TB/s ÷ 15.0 GB = 223 tok/s bound; ~152 measured.
  2. Llama 3.1 8B, 4-bit (Q4_K_M, about 4.9 GB), RTX 4090: 1.01 TB/s ÷ 4.92 GB = 205 tok/s bound; expect about 140 at 70%. The 4-bit file is 3.3× smaller than BF16, so the decode bound is 3.3× higher on the same card. Measured gains are somewhat lower, but this is the main reason people quantize for local use (Chapter 13 covers both).
  3. Llama 3.1 70B across 2 GPUs. In BF16 it streams 139 GB per token (141 GB minus the 2.1 GB embedding table). Split with tensor parallelism over 2 H100s, each GPU streams half, 69.5 GB, in parallel: 20.7 ms, so about 48 tok/s bound, minus a little for communication (later section), about 33 tok/s at 70%. In FP8 the bound doubles to about 96. Split by layers instead (as llama.cpp does by default across consumer GPUs), the GPUs take turns, so their bandwidths do not add: the 2×3090 row in the table gets 24 tok/s bound from one card's 936 GB/s.
  4. Apple M5 Max (614 GB/s, up to 128 GB): Llama 3.1 8B in BF16 → 41 tok/s bound; 70B at Q4_K_M (42.5 GB) → 14.4 bound, about 11 expected. The M5 Ultra (1.2 TB/s, up to 512 GB) doubles both, and can even hold 70B in BF16 (139 GB → 8.6 tok/s bound).
  5. Desktop CPU with dual-channel DDR5-6000 (2 channels × 8 B × 6,000 MT/s = 96 GB/s theoretical, typically 70–80 measured): 8B Q4_K_M → 19.5 tok/s bound; 70B Q4_K_M → 2.3 tok/s bound. Usable for small models, painful for big ones.

Context length adds the second term. At 32K tokens of context, Llama 3.1 8B reads 32,768 × 128 KiB = 4.3 GB of KV per token on top of the 15 GB of weights, so the H100 bound drops from 223 to 173 tok/s. At 128K context the KV read (17.2 GB) exceeds the weights. Chapter 12 charts this.

Batching: one weight read, many tokens

The problem. At batch 1 an H100 does useful math less than 1% of the time. Serving one user per GPU would be absurdly expensive. The idea: run the decode steps of many independent requests together. They all need the same weights, so one stream of 15 GB serves every sequence in the batch (Figure 11.2, step 6). It is the same trick as a database answering many queries with one shared scan.

A simple model of one decode step with B sequences, each holding c tokens of context:

T(B) ≈ max( Wread + B·c·skvη·BW , B·(2N + 4Ldc)MFU·P ) + tfixed Per-user speed = 1/T(B). Aggregate throughput = B/T(B). P = peak FLOP/s; tfixed = launch and scheduling overhead per step.

Plug in Llama 3.1 8B on an H100 with c = 1,024, η = 0.75, MFU = 0.6 and tfixed = 0.4 ms (illustrative but calibrated: it gives about 156 tok/s at batch 1, close to the measured 152). Batch 64 then gives about 6,500 tok/s in total and about 102 tok/s per user. Batch 256 gives about 12,800 tok/s in total, but each user sees about 50 tok/s. Throughput rose about 80-fold; each user's speed fell about 3-fold. A public benchmark of exactly this setup reports 13,771 tok/s at concurrency 128 with vLLM, the same order (its requests had shorter contexts, which the model reproduces: with c = 512 it predicts about 13,000).

Three things limit how far up the curve a server can go:

  • Memory for the KV cache. Every sequence in the batch keeps its whole KV cache resident. With 55 GiB free after the weights, Llama 3.1 8B fits about 450K tokens of cache: 442 sequences of 1,024 tokens, but only 55 sequences of 8,192 tokens. This, more than compute, usually caps the batch (Chapter 12).
  • Latency targets. Each added sequence slows every other one a little. The operator picks the largest batch that still meets the TPOT objective; that is the goodput-maximizing point.
  • Arrival patterns. Requests start and finish at different times. Keeping the batch full requires swapping sequences in and out at every step, which is continuous batching (Chapter 15).
Key takeaway

In decode, the weight read is a fixed cost per step and the batch shares it. Batching turns idle tensor cores into throughput at the price of per-user speed, until memory for KV caches or the latency target says stop. This one trade-off sets the economics of every LLM service.

The VRAM budget

The problem. “Will it fit?” is the first question for any deployment, and “model size ≤ GPU memory” is the wrong test. Five things share the card:

  1. Weights: N × bits/8. Llama 3.1 8B in BF16: 16.06 GB = 14.96 GiB. Fixed.
  2. KV cache: B × c × skv, with skv = 2·L·hkv·dh·bytes. Grows with every sequence and every token. Usually the largest variable term.
  3. Activations and workspace: scratch for the current step. It scales with the number of tokens processed in one step (the prefill chunk), not with the total context, because modern attention kernels never materialize the n × n score matrix (Chapter 15). For Llama 3.1 8B a step of 8,192 tokens peaks around 1–2 GiB: the gate and up projections alone produce 8,192 × 28,672 BF16 values (470 MB). Add a logits buffer of B × 128,256 FP32 values for the sampled rows.
  4. Runtime overhead outside the tensor allocator: the CUDA context (a few hundred MiB for the driver state and loaded kernel images), library workspaces (cuBLAS, attention backends), NCCL buffers when several GPUs talk (NCCL is NVIDIA's GPU-to-GPU communication library), and memory pools for captured CUDA graphs. Typically 0.5–2 GiB per GPU.
  5. Fragmentation and headroom: allocator slack, alignment, and a safety margin so a rare large step does not crash the server.

How vLLM sizes it

vLLM does not guess these numbers; it measures them at startup, then hands everything left over to the KV cache:

  1. Record free memory, load the weights.
  2. Run a dummy forward pass with the largest number of tokens a step may contain, and record PyTorch's peak allocation: that is the activation reserve.
  3. Record how much memory appeared outside PyTorch (NCCL, CUDA context, attention-backend buffers).
  4. KV budget = gpu_memory_utilization × total memory − (weights + peak activations + non-PyTorch memory).
  5. Cut the budget into fixed-size KV blocks and allocate them all immediately. The log reports how many tokens of KV fit and the maximum concurrency at the configured context length.

gpu_memory_utilization is the fraction of the whole GPU this instance may use: 0.92 by default in current releases (older releases used 0.9). Two consequences surprise people. First, nvidia-smi shows the GPU about 92% full right after startup with zero requests; that is the pre-allocated KV pool, not a leak. Second, the setting is per instance, so two vLLM processes on one GPU must split it (for example 0.45 each). Engines that allocate lazily (llama.cpp allocates the KV cache for the configured -c context at load time; Hugging Face transformers grows it on demand) show different numbers for the same model.

When the model does not fit: VRAM, RAM and disk

The problem. Llama 3.1 70B at 4 bits (Q4_K_M) is 42.5 GB. An RTX 4090 has 24 GB. Something has to give. The decode-speed formula tells you what the options cost, because every byte of weights must reach a compute unit once per token, from wherever it lives. Each memory tier has a bandwidth, and the time to stream 42.5 GB from it is the minimum time per token if the weights live there:

The options, in the order you should consider them:

  1. Make the model smaller: a lower-bit quantization or a smaller model (Chapter 13).
  2. Get more fast memory: a bigger GPU, more GPUs (later section), or a machine with large unified memory.
  3. Split the model between GPU and CPU and accept the speed of the slow part.
  4. For MoE models, split by access pattern: always-used weights on the GPU, rarely-used experts in system RAM (Chapter 7).

Layer offload in llama.cpp

llama.cpp's -ngl N (--n-gpu-layers) stores the weights of N transformer layers in VRAM. The rest stay in system RAM, and the CPU computes those layers itself. Per token, the GPU runs its layers, the 4,096- or 8,192-element hidden state (8–16 KiB) crosses PCIe, the CPU runs the remaining layers, and so on. The phases run one after the other, so their times add:

ttoken ≈ WGPUBWGPU + WCPUBWDDR WGPU, WCPU = weight bytes resident on each side; BW = achieved bandwidth of that memory.

70B Q4_K_M on an RTX 4090 plus dual-channel DDR5, at 75% of peak on both sides: put about 20 GB on the GPU (leaving room for KV cache and buffers) and 22.5 GB in RAM. GPU part: 20 GB ÷ 756 GB/s = 26 ms. CPU part: 22.5 GB ÷ 72 GB/s = 312 ms. Total 339 ms, about 3 tok/s. Running everything on the CPU would take 591 ms (1.7 tok/s). Moving half the model to a GPU that is 10× faster only made the whole thing 1.75× faster. It is Amdahl's law: the slow tier dominates.

Why not stream the missing weights to the GPU for every token? Because PCIe 5.0 x16 moves at most about 64 GB/s, less than the CPU can read its own DRAM, and the bytes must be read from DRAM anyway to be sent. For decode it never pays. For prefill it does: one transfer of a layer's weights serves a whole batch of prompt tokens (llama.cpp's default physical batch is 512), so the transfer cost is amortized 512 ways while the GPU's compute does the heavy GEMMs. llama.cpp does exactly this by default (--op-offload), which is why its documentation notes that the GPU may still accelerate parts of the computation even with -ngl 0.

Recent llama.cpp builds automate the placement: -ngl defaults to auto, and a --fit pass (on by default) adjusts unset options, such as the number of GPU layers and the context size, so that everything fits with about 1 GiB to spare per device. The load log prints what landed where.

mmap: when RAM is the cache and the SSD is the backing store

GGUF and safetensors files are laid out so they can be memory-mapped (Chapter 6). By default llama.cpp maps the model file instead of reading it (--load-mode, default auto = mmap where supported). Startup is fast because nothing is read until it is touched; the first token faults the pages in; CPU-resident layers are computed straight out of the page cache with no copy. The OS treats the model like any file: if RAM runs short, it evicts clean model pages and re-reads them from the SSD later. That is the failure mode to recognize: a model somewhat larger than free RAM does not crash, it slows to disk speed. Re-reading 42.5 GB per token from a 7 GB/s NVMe drive is about 6 seconds per token. The mlock load modes ask the OS to pin the pages in RAM to prevent this.

Unified memory: Apple silicon and friends

On Apple's M-series chips the CPU and GPU share one pool of LPDDR memory on a wide bus. There is no VRAM/RAM split and no PCIe copy: the GPU reads the weights where they lie, at full memory bandwidth (614 GB/s on an M5 Max, 1.2 TB/s on an M5 Ultra). That is why a 128 GB laptop runs 70B models at 4 bits at a usable 10+ tok/s, something no single consumer GPU can do. By default macOS lets the GPU wire only part of the memory (around three quarters on large configurations, according to llama.cpp maintainers; it can be raised with a sysctl on recent macOS). The trade-off is compute: these GPUs have a fraction of an H100's FLOP/s, so prefill of long prompts is several times slower even when decode is fine. NVIDIA's DGX Spark (128 GB, 273 GB/s) and AMD's Ryzen AI Max machines follow the same unified design at lower bandwidth.

Common misconception

“It runs, so it fits.” A model that spills into system RAM or into swap still produces correct tokens, just 10–1,000× slower. When local inference is mysteriously slow, check where the bytes live before blaming the GPU.

Loading a model: cold starts

Before the first token, the weights have to travel from wherever they are stored into GPU memory, and the engine has to prepare. A cold start has four stages:

  1. Fetch the files to the machine, if they are not already on local disk (object storage, a model hub, a network file system).
  2. Read them from local disk. Safetensors and GGUF need no parsing beyond a small header, so this runs at disk speed (Chapter 6).
  3. Copy host to GPU over PCIe, ideally from pinned memory and to several GPUs in parallel.
  4. Warm up: allocate and profile memory (previous section), compile or select kernels, capture CUDA graphs for common batch sizes. Depending on engine and model this takes from seconds to minutes the first time; engines cache the compiled artifacts so later starts are faster.

The lesson is that a cold start is dominated by the slowest hop, usually the network. A 70B model takes about two minutes just to download at 10 Gbit/s. Production systems therefore keep weights on local NVMe or in RAM, keep replicas warm, and use engine features that snapshot or “sleep” a loaded model so it can resume in seconds. Scaling a fleet up and down around these costs is a serving problem (Chapter 15).

One model, many GPUs

The problem. Llama 3.1 70B in BF16 is 141 GB; one H100 holds 80. And even when a model fits, one GPU's bandwidth caps decode speed. There are two basic ways to spread one model over several GPUs, and they behave very differently during decode.

Pipeline parallelism (PP) gives each GPU a contiguous range of layers. A token's hidden state (8,192 BF16 values = 16 KiB for the 70B) passes from stage to stage. Communication is tiny and happens once per stage boundary, so PP works even across machines over ordinary networks. But at batch 1 the stages run one after another: GPU 1 waits while GPU 0 works. Memory capacity adds up; bandwidth does not. To keep all stages busy you need several independent sequences in flight, like an instruction pipeline needs independent instructions.

Tensor parallelism (TP) splits every layer across the GPUs, Megatron-style (Chapter 8 shows the column/row split): each GPU owns a slice of the attention heads and a slice of the FFN columns in every layer. All GPUs work on the same token at the same time, each streaming only its share of the weights, so bandwidths add and batch-1 decode gets faster. The price is synchronization: after the attention block and after the FFN block, the partial results must be summed across GPUs with an all-reduce (Chapter 2). That is 2 all-reduces per layer, 160 per token for the 70B.

Practical rules that follow:

  • TP inside a server, over NVLink. TP degree is usually 2, 4 or 8, and it should divide the number of KV heads (8 for all Llama 3.1 models) so that each GPU holds whole KV heads; with more GPUs than KV heads the KV cache must be replicated. Beyond the speedup, TP also splits the KV cache, which raises the possible batch size.
  • PP across servers. Llama 3.1 405B in BF16 (812 GB) does not fit in one 8×H100 server (640 GB); a common layout is TP = 8 within each server and PP = 2 across two servers. In FP8 (406 GB) it fits in one server.
  • Consumer GPUs over PCIe (two RTX 4090s) usually use layer splitting (llama.cpp's default --split-mode layer): capacity adds, speed stays that of one card, as the 2×3090 row in the earlier table showed.
  • Data parallelism (independent replicas) scales throughput linearly with no communication, if the model fits on each replica. Expert parallelism spreads MoE experts across GPUs with all-to-all traffic (Chapter 7). Combining these at scale is Chapter 15.

Why output tokens cost more than input tokens

API prices almost always charge several times more per output token than per input token (Chapter 15 covers actual prices). The compute view explains why. Both kinds of token cost about the same FLOPs. What differs is how efficiently the hardware can produce them, i.e. how much GPU time each one occupies:

  • An input token is processed in prefill, inside a big GEMM that runs near the compute roof. At 50% MFU an H100 prefills Llama 3.1 8B at about 34,000 tokens/s: about 29 µs of GPU time per input token.
  • An output token needs its own decode step, which is memory-bound. Even at a large batch, each output token occupies several times more GPU time, and at small batches far more. It also keeps its KV cache resident in scarce GPU memory for the whole generation, which limits how many other requests can share the GPU.

Even a well-batched server spends roughly 3–5× more GPU time per output token than per input token, and that ratio is in the same range as typical price ratios. Cached input tokens, whose KV is reused instead of recomputed, are cheaper still (Chapter 12). Reasoning tokens are output tokens, with all of the above costs (Chapter 10).

CPUs, phones and the edge

The same formula governs every device: decode speed ≈ memory bandwidth ÷ bytes per token; prefill speed ≈ usable FLOP/s ÷ 2N.

  • Desktop CPUs have plenty of RAM but only 60–100 GB/s of bandwidth on two DDR5 channels. They decode small quantized models (1–8B at 4 bits) at a few to 20 tok/s. Prefill is the weak spot: a CPU has one to two orders of magnitude fewer FLOP/s than a GPU, so long prompts take a long time. llama.cpp uses SIMD dot products on packed low-bit weights (AVX2/AVX-512, ARM NEON/SVE, plus matrix extensions such as AMX or SME where present).
  • Server CPUs with 12 DDR5 channels per socket reach roughly 460–600 GB/s theoretical (12 × 8 B × 4,800–6,000 MT/s), comparable to an M5 Max, with terabytes of capacity. That is enough to decode large MoE models whose active parameters are small.
  • Phones and laptops run 1–8B models at 4 bits on LPDDR memory (tens of GB/s up to a few hundred), using the GPU or an NPU. Memory capacity is the binding limit: the OS, apps and the model share 8–16 GB. Energy matters as much as speed, and moving bytes from DRAM costs far more energy than the arithmetic, which is one more reason low-bit weights dominate on-device.

Key takeaway

Three numbers answer almost every inference question: bytes of weights (does it fit, and how fast can decode be: bandwidth ÷ bytes), KV bytes per token (how much context and concurrency fit), and FLOP/s (how fast prefill and large batches run). Everything else is efficiency.

./build/bin/llama-bench -m l8b-q4_k_m.gguf -ngl 0-33+3 -p 512 -n 128 -o json > ngl.json

    The intermediate -ngl points fall within 15% of your two-point prediction, and moving half the layers to the GPU buys less than 2× even though the GPU is more than 10× faster (Amdahl, as the 70B example showed). As layers leave the GPU, pp512 falls by a much smaller factor than tg128, because prompt batches still have their weights shipped to the GPU and computed there (the --op-offload behaviour). The accelerate TPOT is within 25% of WCPU ÷ your host-to-device bandwidth (plus the GPU part), and per CPU-resident byte it is slower than llama.cpp computing in place. In the cold-start ledger every hop is within 25% of bytes ÷ that link's measured bandwidth, and you can name the hop that dominates.

Hints (open only when stuck)
  • Timing. Kernel launches are asynchronous, so time.perf_counter() without a synchronize measures the launch, not the work. Use CUDA events, warm up first (cuBLAS picks algorithms and the allocator grows on the first calls), and report the median.
  • Faster than HBM? A 33.6 MB matrix timed in a loop stays in L2 (50 MB on an H100, 72 MB on a 4090) and reports impossible bandwidth. Cycle through the 32 layers' copies so each call touches cold memory, as the real model does.
  • Counting bytes. A copy of N bytes moves 2N. Write x @ W.T for weights stored as (out, in); calling W.t().contiguous() inside the timed region adds a full extra read and write of the matrix.
  • Prefill OOM in your own loop. A plain forward computes logits for every position: n × 128,256 values, which is 16.8 GB in FP32 for 64 × 512 prompt tokens. Recent transformers versions accept logits_to_keep=1 (older ones call it num_logits_to_keep). That buffer is the “logits” line of the VRAM budget.
  • KV slope too steep? Write down the bytes each step actually moves. A cache that appends with torch.cat copies the whole layer cache every step. An attention path that expands 8 KV heads to 32 (repeat_kv in the HF Llama code; its SDPA path does that whenever an explicit mask is passed) reads 4× the bytes. A static cache may scan its whole preallocated length, so size max_cache_len to the context of each measurement point.
  • Compiled timings. mode="reduce-overhead" captures CUDA graphs per input shape, so the first call at every new (B, cache length) recompiles. Warm up each shape before timing. Leave compile time out of TPOT and put it in the cold-start ledger.
  • Binary-searching OOM. After catching torch.cuda.OutOfMemoryError, drop every reference and call torch.cuda.empty_cache(), or the next trial starts with a fragmented pool. The peak includes the prefill activations, so the edge depends on whether you prefill all B prompts in one pass or one at a time. State which.
  • Cold disk reads without root. os.posix_fadvise(fd, 0, 0, os.POSIX_FADV_DONTNEED) on each shard evicts its clean pages from the page cache. If your “cold” read runs at 20+ GB/s, it was not cold.
  • llama-bench. -ngl counts the output layer too, so 33 means everything for a 32-layer model. Set -t to your physical core count; the CPU side is bandwidth-bound, and extra threads only add noise.

Stretch goals

  • Two GPUs. Rent a 2-GPU box and run vLLM with --tensor-parallel-size 2 and then --pipeline-parallel-size 2 at batch 1 and batch 32. Add 2 all-reduces per layer to your predictor, fit their latency, and check One model, many GPUs: TP speeds up batch-1 decode by 1.5–2×, PP does not, and PP's aggregate throughput rises once several sequences are in flight.
  • The edge. Run the Milestone 6 llama.cpp sweep on a laptop, a Mac or a single-board computer, and add your rows (bandwidth, bound, measured, MBU) to the calibration table in The decode speed limit. Then run Qwen2.5-0.5B on your big GPU and watch MBU collapse, the “small models on very fast GPUs” effect.
  • Precision moves the speed, not the knee. Repeat the Milestone 3 sweep with an FP8 library GEMM (for example torch._scaled_mm on Hopper or Ada) and, if you can, a W4A16 kernel from a quantization library. Check that FP8 halves the step time but keeps B* near 295, while W4A16 moves it to about 74 (The roofline, applied to LLMs; the formats are Chapter 13's).
  • A planner. Wrap predict.py and machine.json in a speedlimit plan --model ... --gpu ... CLI that reproduces every row of What hardware do I need?. Then predict a model you have never run (say Qwen3-32B at 4 bits), run it, and score your prediction.
