Tokens: how text becomes numbers

A model never sees letters. It sees a list of integers, and each integer picks one row from a big table of learned vectors. This chapter shows how those integers are chosen, what they cost, and why so many strange model behaviors start here.

Why not characters, why not words?

A neural network is arithmetic on arrays of numbers. Text is a string. So the first step of every LLM is a conversion: cut the string into pieces from a fixed, finite list, and replace each piece by its index in that list. The pieces are tokens. The list is the vocabulary, of size V. The index is the token ID, an integer in [0, V). The program that does the cutting is the tokenizer. It is not a neural network. It is a deterministic algorithm with a data file, built once before the model is trained and then frozen forever.

How big should the pieces be? There are two obvious answers, and both are bad.

Characters (or bytes). The vocabulary is tiny: 256 possible byte values cover every string in every language. Nothing is ever unknown. But sequences get long. The cat sat on the is 18 bytes. The model does a full forward pass for every token it generates (Chapter 1), and attention cost grows with the square of the sequence length (Chapter 5). Four to five times more tokens means four to five times more decode steps and a much larger cache of past tokens. The model also has to spend its capacity learning to spell before it can learn anything else.

Whole words. Sequences are short: 5 tokens. But the vocabulary explodes. English alone has hundreds of thousands of word forms (run, runs, running, runner), plus names, typos, URLs, code identifiers and every other language. Any word not in the list has no ID at all and becomes a generic [UNK] ("unknown") token, so the model cannot even repeat it back. Languages without spaces, like Chinese or Japanese, have no obvious "word" to cut at. (Primer 6 measures how sparse word-level statistics get.)

Subwords sit in between. Frequent strings get their own token (␣the, ␣cat). Rare strings are split into frequent pieces (␣tokenizationally). Worst case, a string falls back to single bytes, so nothing is ever unknown.

Intuition: a compression dictionary

A subword tokenizer is a dictionary-based compressor, like the dictionary in LZW or a static Huffman table built from a training corpus. Frequent strings get a single short code; rare strings are spelled out from smaller codes. The goal is the same as in compression: a short encoding for typical input. The difference is that the codes are not bits on disk. Each one becomes a step of expensive computation.

Look at where the spaces went in Figure 3.1: ␣cat, not cat␣. In GPT-style and Llama 3 tokenizers the leading space belongs to the following word. So the at the start of a text and ␣the in the middle of a sentence are two different tokens with two different IDs (1820 and 279 in Llama 3). This one convention explains several odd behaviors later in the chapter.

Key takeaway

Tokenization is a fixed lookup scheme chosen before training. It trades vocabulary size against sequence length. Subword tokens give roughly 4–5 characters of English per token while still covering every possible string.

Byte Pair Encoding: learning a vocabulary by merging

Which subwords should be in the vocabulary? Nobody writes the list by hand. It is learned from a large sample of text by a simple greedy algorithm called Byte Pair Encoding (BPE). BPE started as a 1994 data-compression trick and was adapted for neural machine translation by Sennrich, Haddow and Birch in 2016. GPT-2, GPT-4, Llama 3, Qwen and most other modern LLMs use a variant of it.

The idea in one sentence: start with single symbols, and repeatedly glue together the pair of neighbors that occurs most often. Each glue operation is a merge. Each merge adds one new token to the vocabulary. You stop when the vocabulary reaches the size you want.

The training loop

  1. Split the training text into words (more precisely, into chunks; see the regex section below) and count how often each distinct chunk occurs. Work on the distinct chunks with their counts, not on the raw text. This is much faster.
  2. Write each chunk as a sequence of base symbols (characters in the toy example, bytes in real tokenizers).
  3. Count every adjacent pair of symbols, weighted by the chunk's count.
  4. Take the most frequent pair (a, b). Create a new symbol ab. Record the rule "a + b → ab" as merge number r. This number is the merge's rank.
  5. Replace every occurrence of a b in every chunk by ab. Go back to step 3.

The output of training is just two things: the base symbols, and the ordered list of merges. That ordered list is the tokenizer.

The whole trainer fits in a few lines. Here is the core, matching the widget later in this chapter:

def train_bpe(chunk_counts, n_merges):        # {"low": 5, "lower": 2, ...}
    words = {tuple(c.encode("utf-8")): f for c, f in chunk_counts.items()}
    merges = []                                    # ordered list = the tokenizer
    for r in range(n_merges):
        pairs = Counter()
        for w, f in words.items():
            for a, b in zip(w, w[1:]):
                pairs[(a, b)] += f                 # weighted by chunk frequency
        if not pairs: break
        best = max(pairs, key=pairs.get)          # first-seen wins ties
        new_id = 256 + r                         # IDs 0..255 are the raw bytes
        merges.append((best, new_id))
        words = {replace_pair(w, best, new_id): f for w, f in words.items()}
    return merges
Low-level: what training a real tokenizer costs

The naive loop above recounts every pair after every merge: O(merges × corpus symbols). For 128K merges over gigabytes of text that is too slow. Production trainers (Hugging Face tokenizers in Rust, SentencePiece in C++) keep a pair → count table plus an index from each pair to the chunks containing it. After merging (a, b) they update only the counts of pairs touching the new symbol, and use a priority queue to find the next maximum. Training a 100K-entry vocabulary on a few GB of text then takes minutes to hours on a multi-core CPU, depending on data size: tiny next to training the model. But the result is frozen. Changing the tokenizer later means retraining the model, or at least surgery on its embedding and output layers, because the learned weights are tied to these exact IDs.

Encoding: applying merges in rank order

Once training is done, how do you tokenize new text? You do not search for the "best" split. You replay the merges. For each chunk:

  1. Start from the base symbols (bytes).
  2. Look at all adjacent pairs. Among the pairs that have a merge rule, pick the one with the lowest rank (the rule learned earliest).
  3. Merge it. Repeat until no adjacent pair has a rule.

This reproduces exactly what training would have done to that chunk. It is greedy and deterministic: the same text always gives the same tokens. Figure 3.3 shows the real Llama 3 tokenizer encoding ␣strawberry.

Low-level: how tiktoken stores merges

OpenAI's tiktoken (which Llama 3's tokenizer is built on) does not store a merge list at all. Its data file has one line per token: the token's bytes in base64 and its rank. A pair (a, b) is mergeable if the concatenated bytes a‖b are in the table, and its priority is the rank of a‖b. Since tokens were added in merge order, rank = token ID. The encoder is a small Rust loop over the bytes of each chunk. If the whole chunk is already a token (common words like ␣the), one hash lookup finds it and no merging happens. Hugging Face's implementation also memoizes recently encoded chunks in a cache. The Hugging Face conversion of the same vocabulary lists 280,147 explicit merges, because it spells out every pair that can produce each token.

Encoding cost is small. A chunk of m bytes needs at most m − 1 merges, each scanning O(m) pairs, and chunks are short. In a quick test on this chapter's corpus repeated to 100,000 tokens (486 KB), tiktoken took about 40 ms and the Hugging Face Rust tokenizer about 200 ms. That is small next to the GPU work it feeds, but not free: inference servers often run tokenization in separate CPU worker processes so it never stalls the GPU.

    Key takeaway

    BPE training = repeatedly merge the most frequent adjacent pair and record the merge. BPE encoding = replay those merges on new text, lowest rank first. The tokenizer file is a vocabulary plus that priority order.

    Byte-level BPE: why nothing is ever out of vocabulary

    The toy example started from characters. Which characters, though? Unicode has about 150,000 assigned code points. Starting from all of them wastes vocabulary on characters that almost never occur, and any character missing from the base set would still be unknown.

    Byte-level BPE, introduced with GPT-2 in 2019, solves this by starting from bytes. Text is first encoded as UTF-8. The 256 possible byte values are the base vocabulary. Every string, in every language, including emoji, binary garbage and code, is a sequence of bytes, so every string can be encoded. In the worst case each byte is its own token. There is no [UNK].

    UTF-8 is a variable-length encoding: ASCII characters take 1 byte, accented Latin, Greek, Cyrillic, Hebrew and Arabic letters take 2, most Chinese, Japanese, Korean and Hindi characters take 3, and emoji take 4. BPE merges bytes into larger tokens without caring where character boundaries are. A token can hold half a character, or the end of one character and the start of the next.

    The bottom row of Figure 3.4 looks like garbage, and you will see it if you ever open a tokenizer.json file: Ġ everywhere, Ã© for é. This is a storage trick from GPT-2. Many bytes (space, newline, control bytes, bytes 0x80–0xFF) are not printable on their own, and BPE libraries of the time worked on Unicode strings. So GPT-2 maps each of the 256 bytes to a printable Unicode character: printable ASCII maps to itself, and the rest are shifted to code points 256 and up. Space (0x20) becomes Ġ (U+0120), newline (0x0A) becomes Ċ, and the two bytes of é (C3 A9) become Ã and ©. It is a display encoding only. The tokenizer converts back to raw bytes when decoding.

    Optional deep dive: byte IDs are not byte values

    In Llama 3 (and in OpenAI's cl100k), the 256 single-byte tokens occupy IDs 0–255, but in the order of that printable mapping, not in byte order. Printable ASCII comes first: ! (0x21) is ID 0, A is ID 32, a is ID 64. The byte 0xA6 is ID 99, and the space byte is ID 220. So a token ID is an opaque index; you cannot read a byte value from it. The "decoder" is a table from ID to byte string, and decoding is a concatenation of byte strings followed by UTF-8 decoding.

    Common misconception

    "The model reads characters." It does not. It reads token IDs, and a single character can be split over several tokens. A model "knows" that token 99 followed by token 247 completes an emoji only because it saw that pattern during training.

    Pre-tokenization: the regex that runs before BPE

    If you run BPE on raw text, it happily learns merges across word boundaries and across punctuation: dog., dog!, dog? and .␣The all become separate tokens. The vocabulary fills up with near-duplicates. So before BPE, every tokenizer in the GPT family first splits the text into chunks with a regular expression. BPE then runs inside each chunk, and merges never cross a chunk boundary.

    This is the Llama 3 pattern. It is essentially GPT-4's cl100k_base pattern (tiktoken's copy uses possessive quantifiers for speed):

    (?i:'s|'t|'re|'ve|'m|'ll|'d)|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}{1,3}| ?[^\s\p{L}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+

    \p{L} means "any Unicode letter" and \p{N} "any Unicode digit". The alternatives are tried left to right at each position, and the first one that matches wins.

    Each alternative encodes a design decision:

    • Leading space joins the word ([^\r\n\p{L}\p{N}]?\p{L}+). So ␣cat is one chunk, and the vocabulary does not need separate "word" and "space" tokens for every word.
    • Digits in groups of at most 3 (\p{N}{1,3}). This caps how many number tokens can exist (1,110 strings of 1–3 digits) instead of learning arbitrary numbers like 2019 or 1234. GPT-2's older pattern had ?\p{N}+, which allowed any digit run, so its vocabulary contains many arbitrary multi-digit numbers.
    • Whitespace is kept, not thrown away. Runs of spaces become tokens (important for code indentation), and \s+(?!\S) leaves the last space of a run to attach to the next word.
    • Contractions are split from their word, case-insensitively.

    GPT-4o's o200k_base uses a longer pattern that also splits words at case changes (so CamelCase identifiers split into Camel + Case chunks) and attaches contractions to the word. Other tokenizers choose differently: Llama 2, Qwen3 and Gemma 3 split every digit into its own token.

    Low-level: regex speed matters

    The regex runs over every byte of every prompt, and Unicode property classes like \p{L} need table lookups, not a simple byte range. tiktoken uses the Rust fancy-regex crate, because the lookahead (?!\S) is not supported by pure finite-automaton engines like Rust's standard regex. Backtracking engines are slower, so pre-tokenization is a significant share of encoding time, and fast tokenizers spend real engineering effort on it.

    Other tokenizer families: SentencePiece, Unigram, WordPiece

    Byte-level BPE with a regex is today's most common design, but you will meet three others.

    SentencePiece (Kudo & Richardson, 2018) is a library, not an algorithm. It treats the input as a raw stream of Unicode characters with no regex pre-split. Spaces are replaced by the visible character ▁ (U+2581) and become part of tokens, so decoding is exact. It can train either BPE or Unigram models. Llama 2 used SentencePiece BPE with 32,000 tokens and byte fallback: characters not in the vocabulary are emitted as byte tokens <0x00>…<0xFF> (IDs 3–258). So Llama 2 also never produces [UNK], but it reaches bytes only as a last resort. The llama emoji costs Llama 2 five tokens (▁ plus four byte tokens) versus three in Llama 3. Gemma 3 also uses SentencePiece, with a 262K vocabulary.

    Unigram (Kudo, 2018) works in the opposite direction from BPE. It starts with a huge candidate vocabulary and repeatedly removes the tokens whose removal hurts the likelihood of the training text the least, using a simple probabilistic model where each token has a probability. To encode, it finds the most probable segmentation with dynamic programming (the Viterbi algorithm), instead of replaying merges. Because it has probabilities, it can also sample different segmentations of the same word during training ("subword regularization"), which makes models more robust. T5 and ALBERT used Unigram.

    WordPiece (BERT) is BPE-like, but picks the merge that most increases training-data likelihood rather than raw pair frequency, and marks word-internal pieces with ##. It is mostly seen in encoder models.

    How big should the vocabulary be?

    The number of merges is a free choice. More merges mean a bigger vocabulary V. What does that buy, and what does it cost?

    Benefits of a bigger V: each token covers more text on average, so the same text becomes fewer tokens. Every token you remove saves one full forward pass when generating, one entry in the cache of past tokens (the KV cache, Chapter 12), and some attention work. More text also fits in a fixed context window. Most of the gain comes in languages, scripts and domains that a small vocabulary served badly.

    Costs of a bigger V:

    • The embedding table has one row of d numbers per token: V × d parameters (next section).
    • The LM head, the last matrix of the model, turns the final vector into one score per vocabulary entry (Chapter 6). It is another V × d matrix, and it costs 2·V·d FLOPs for every token position it is applied to.
    • The softmax that turns those V scores into probabilities (Chapter 4) runs over V entries per position. In training, where every position gets its own V scores, that adds up to gigabytes per sequence (Chapter 4 has the numbers).
    • Rare tokens are undertrained. A row of the embedding table is only updated when its token appears in the training data. With a huge vocabulary, the tail tokens get few updates.
    embedding params = LM-head params = V · d     LM-head FLOPs per token = 2 · V · d V = vocabulary size, d = model width (d_model). Llama 3.1 8B: 128,256 × 4,096 = 525,336,576 parameters per matrix (1.05 GB in BF16), and 2 × 525.3M ≈ 1.05 GFLOP per token for the head, about 6.5% of the ≈16 GFLOP a full forward pass costs per token.
    Worked example: Llama 2 (32K) → Llama 3 (128K)

    Meta reports that the Llama 3 tokenizer encodes English at 3.94 characters per token, versus 3.17 for Llama 2's. For the same English text that is 3.17 / 3.94 = 0.80 of the tokens: about 20% fewer forward passes, 20% less KV cache.

    The price: at d = 4,096, the LM head grows from 2 × 32,000 × 4,096 = 0.26 GFLOP to 1.05 GFLOP per token, an extra 0.79 GFLOP, or about 5% of the ≈16 GFLOP per token. Net compute for a fixed English text: 0.80 × 1.05 ≈ 0.84, roughly 16% less. (Simplified: it ignores everything else that changed between the two models.) Memory: the two V × d matrices grow from 2 × 0.26 GB to 2 × 1.05 GB in BF16.

    For small models the table dominates. Gemma 3 1B has a 262K vocabulary and d = 1,152: 302M of its 1B parameters are the embedding table (the Gemma 3 report lists 302M embedding vs 698M non-embedding parameters). Gemma shares that table with the LM head ("tied embeddings", Chapter 6), otherwise it would be even worse. For a 400B model, the same table would be a rounding error. That is why vocabulary sizes grew as models grew: 32K was normal in 2023, 128K–262K is normal now.

    Why do config files say 151,936 when Qwen3 only uses 151,669 tokens? The embedding and LM-head matrices are often padded to a multiple of 64 or 128 rows. Matrix-multiply kernels and tensor-parallel splits across GPUs run best when dimensions are multiples of the hardware tile size (Chapter 2). The padding rows are never produced by the tokenizer. Llama 3's 128,256 happens to be 1,002 × 128 already.

    Key takeaway

    Vocabulary size trades a V × d table (twice, if untied) and 2·V·d head FLOPs per token against shorter sequences. For big models, large vocabularies are cheap and the shorter sequences win.

    Token IDs and the embedding lookup

    After tokenization, the running sentence is an array of integers. With the real Llama 3 tokenizer:

    The 791   ␣cat 8415   ␣sat 7731   ␣on 389   ␣the 279

    An ID is a label, not a quantity. Token 8415 is not "bigger" than token 389 in any useful sense, so the model must not do arithmetic on IDs directly. Instead, every ID selects a learned vector. The model holds an embedding table E with V rows and d columns. Row i is the embedding of token i: a list of d = 4,096 numbers that the model learned during training. These vectors are the model's internal representation of each token; Chapter 4 explains what such vectors can mean. The first operation of the model is simply:

    X[t] = E[ idt ]    for t = 0 … n−1 E ∈ ℝV×d is the embedding table (128,256 × 4,096 for Llama 3.1 8B), idt is the token ID at position t, and X ∈ ℝn×d is the input to the first transformer layer. For our sentence n = 5, so X is 5 × 4,096.

    Mathematically, this is the same as multiplying a one-hot vector (all zeros except a 1 at position id) by E: the 1 picks out exactly one row. Textbooks often write it that way. No real implementation does it, because the matmul would waste 2·V·d ≈ 1.05 GFLOP per token on multiplying zeros and would read the whole table. The real operation is a gather: compute an address, copy a row.

    Low-level: the gather kernel

    In PyTorch this is torch.nn.functional.embedding(ids, E); in llama.cpp it is the GGML_OP_GET_ROWS op. On a GPU, a typical kernel assigns one thread block per token: the block reads one ID, computes base + id * d * sizeof(bf16), and its threads copy the row with wide, coalesced 16-byte loads (8,192 bytes = 512 such loads). It is purely memory-bound and tiny: even a 100,000-token prompt gathers 100,000 × 8 KiB ≈ 0.82 GB, a fraction of a millisecond of H100 bandwidth. During decoding, it is one 8 KiB row per sequence per step, negligible next to reading the 16 GB of weights (Chapter 11). If the table is quantized (Chapter 13), the kernel dequantizes the row as it copies it.

    In training, the gradient of a gather is a scatter-add: the gradient for X[t] is added into row idt of the table's gradient, and rows of tokens that did not occur get zero. That is why rare tokens learn slowly (Chapter 8).

    The table is also why every model is welded to its tokenizer. Row 8415 means ␣cat only because that is what the tokenizer emitted during training. Feed the same model IDs from a different tokenizer and every input is the wrong vector. At the other end of the model, the LM head produces one score per row of its own V × d matrix, so the model can only ever output IDs from this same vocabulary.

    Key takeaway

    Token IDs are row indices. The embedding "layer" is a gather of n rows of d numbers: for Llama 3.1 8B, 8 KiB per token from a 1.05 GB table. It is free in FLOPs; its cost is the memory the table occupies.

    Special tokens

    Some tokens are not text at all. They are control signals: "a document starts here", "this turn is over", "the next words are a role name". These special tokens are added to the vocabulary by hand, after BPE training, at reserved IDs. Llama 3 has 256 of them, IDs 128,000–128,255:

    TokenIDMeaning
    <|begin_of_text|>128000BOS ("beginning of sequence"): first token of every input
    <|end_of_text|>128001end of a document in pretraining; a base model stops here
    <|start_header_id|>, <|end_header_id|>128006, 128007wrap a role name: system, user, assistant, ipython
    <|eot_id|>128009end of turn: the message is finished. The chat model emits it when its answer is done
    <|eom_id|>128008end of message, but the model expects a tool result before continuing
    <|python_tag|>128010starts a call to a built-in tool (search, Wolfram Alpha, code interpreter)
    <|finetune_right_pad_id|>128004padding
    <|reserved_special_token_N|>the rest248 unused placeholders for future use

    The inference engine stops generating when the model samples one of the stop tokens. Llama 3.1 Instruct's generation_config.json lists three: 128001, 128008 and 128009. The engine checks the sampled ID with an integer compare; the token's text is never looked at. (Stop strings supplied by the user are a different, text-level mechanism; see Chapter 14.)

    Security: special tokens must not be typeable

    Special tokens have text names like <|eot_id|>, but ordinary text must never be encoded into them. If a user types the string <|eot_id|><|start_header_id|>system and your code tokenizes it with special-token parsing enabled, the user has forged a turn boundary and a fake system message. tiktoken refuses by default: encode() raises an error if the text contains a special token's name. Hugging Face tokenizers, by default, do parse them (encoding the string <|eot_id|> gives ID 128009). Encode untrusted text with special-token parsing off, and let only the template insert real special tokens.

    One more subtlety: the 248 reserved tokens never appeared in training, so their embedding rows never received a gradient update and stay near their random initialization. If you fine-tune a model and start using a reserved token, its embedding has to be learned from scratch.

    Chat templates: messages become one flat sequence

    A chat API takes a structured list of messages. The model takes one flat list of token IDs. A chat template converts one into the other. There is no "message" object inside the model: roles, turn boundaries, tools and tool results are all just tokens in a single sequence, marked by special tokens that the model learned to respect during post-training (Chapter 9).

    Here is a short request:

    [ { "role": "system", "content": "You are a helpful assistant." },
  { "role": "user",   "content": "Finish the sentence: The cat sat on the" } ]

    The Llama 3.1 template renders it to this exact string (special tokens highlighted; ↵ marks each newline character, and the line breaks are those newlines):

    <|begin_of_text|><|start_header_id|>system<|end_header_id|>↵
↵

    Two things you did not write appeared. The template injected two lines of date information into the system message (the date defaults to "26 Jul 2024" unless the caller passes one). And the string ends with an open assistant header. That trailing header is the generation prompt: it tells the model "now the assistant speaks", so its most likely next tokens are an answer, not another user message.

    Where templates live

    The template is a Jinja program stored in the model's tokenizer_config.json under the key chat_template. In Hugging Face Transformers, tokenizer.apply_chat_template(messages, add_generation_prompt=True) runs it. Inference servers like vLLM, SGLang, llama.cpp and Ollama run it for you when you call their OpenAI-compatible /v1/chat/completions endpoint. Closed APIs (OpenAI, Anthropic, Google) apply their own private templates on the server; you never see those tokens, but you are billed for them.

    Different model families use different templates. ChatML, used by Qwen and many open models, looks like this (Qwen3 IDs: <|im_start|> = 151644, <|im_end|> = 151645):

    <|im_start|>system↵
You are a helpful assistant.<|im_end|>↵
<|im_start|>user↵
Finish the sentence: The cat sat on the<|im_end|>↵
<|im_start|>assistant↵

    OpenAI's open-weight gpt-oss models use the harmony format, which adds named channels so that reasoning and final answers are separate messages: <|start|>assistant<|channel|>final<|message|>…<|return|>. How reasoning tokens are marked and handled is Chapter 10's topic.

    Template bugs are silent

    A model given the wrong template does not crash. It just gets worse, because it sees a token pattern it was never trained on. Two classic mistakes: (1) rendering the template to a string and then tokenizing it with add_special_tokens=True, which prepends a second <|begin_of_text|>; (2) using one family's template (say ChatML) on another family's model. When a fine-tuned or quantized model "feels dumber" than it should, check the exact token sequence first.

    Tools are tokens too

    Tool (function) definitions do not go into a separate channel either. The Llama 3.1 template serializes each JSON schema with 4-space indentation and pastes it, with a paragraph of instructions, into the first user message. Adding one small get_weather(city) tool to the request above grows it from 50 to 195 input tokens. The model answers with a JSON tool call as ordinary text; the runtime executes the call and appends the result as a new message under an ipython header; the model continues (Chapter 9 covers the mechanics). After one call-and-result round trip, the next request in this example is 238 tokens. Every tool definition is paid for on every request, as input.

    Input tokens and output tokens

    APIs bill and limit two counts: input tokens and output tokens. At the token level the rule is simple:

    • Input tokens = everything in the sequence before generation starts: template tokens, system prompt, tool definitions, all previous messages, tool results, images (see below). They are processed in parallel in one pass, called prefill (Chapter 11).
    • Output tokens = the tokens the model samples, one decode step each (the stop token costs a step too), including hidden reasoning tokens for reasoning models (Chapter 10).

    The model has no memory between requests. Chat APIs are stateless: to continue a conversation, the client resends the whole history, so last turn's output becomes this turn's input.

    Input therefore grows linearly with the conversation length, and the total input billed over a conversation grows roughly quadratically: turn k resends about k turns. Two mechanisms soften this. Prompt caching reuses the stored attention state of an unchanged prefix, so repeated input is processed and billed more cheaply (Chapter 12). And input tokens are cheaper than output tokens in the first place, because prefill processes them in parallel while decode produces output one step at a time (Chapter 11; prices in Chapter 15).

    Key takeaway

    The model sees one flat token sequence. Roles, tools and history are template tokens inside it. Everything already in the sequence is input; everything sampled is output; and a stateless API resends the whole history, so input grows every turn.

    Tokens per word, and why language matters

    For English prose, OpenAI's rule of thumb is about 4 characters or ¾ of a word per token, so 100 tokens ≈ 75 words. Our own measurement on the widget corpus (211 words of plain English) with the Llama 3 tokenizer: 250 tokens, 1.18 tokens per word, 4.86 characters per token. Technical text, code, numbers and rare names cost more per word.

    Other languages can cost far more. A tokenizer is trained mostly on whatever data dominates its corpus, usually English and code, so other scripts get fewer and shorter merges. The extreme case is a script that barely appears: its characters stay as 2–3 byte tokens each.

    Petrov et al. (NeurIPS 2023) measured this across many languages and found the same text can need up to 15× more tokens depending on the language. Since tokens drive everything, a speaker of a poorly tokenized language pays more per request, waits longer for each answer, and fits less text into the context window. It also affects quality: a model that spends three tokens per character has less "room" per thought. This is a major reason recent vocabularies grew to 128K–262K: the extra entries mostly go to non-English scripts.

    Key takeaway

    Use about 1.3 tokens per English word, or 4 characters per token, as a rough estimate. For anything else, measure with the actual tokenizer: the ratio can be 1× to 3× English with modern tokenizers, and much worse with old ones.

    Artifacts: numbers, spelling, code and glitch tokens

    Many famous LLM failures are tokenization effects. Once you know that the model sees IDs, not characters, they stop being mysterious.

    Spelling and letter counting. "How many r's are in strawberry?" asks about characters, but the model receives ID 73700. It can only answer from facts it memorized about that ID (that its spelling is s-t-r-a-w-b-e-r-r-y), which it learned indirectly, from text that happened to spell words out. Reversing a word, counting letters and making rhymes all have this problem. Models do much better when they first write the word out letter by letter, because then each letter becomes its own token.

    Arithmetic. Llama 3 splits digit strings into groups of three from the left: 1234567 → 1234567. The groups do not line up with place value: in 12,345 + 67,890 the "thousands" are inside different tokens in the two numbers. Singh & Strouse (2024) showed that GPT-3.5 and GPT-4 do better at addition when numbers are written with commas, which forces right-aligned groups of three. Llama 2, Qwen3 and Gemma 3 use one token per digit, which aligns digits but makes numbers long. Notice also that ␣67890 starts with a bare space token: the regex never attaches a space to a digit.

    Case and spacing. hello, Hello, ␣hello and HELLO are unrelated IDs. The model must learn from data that they mean the same thing. All-caps text is usually split into more, rarer pieces.

    Trailing spaces. Since the space belongs to the next word, a prompt ending in "on the␣" ends with a lone space token (ID 220). During training, " mat" almost always arrived as the single token ␣mat, so a lone space followed by mat is a rare pattern, and completions get worse. Some libraries fix this with token healing: they remove the last token of the prompt and force the first generated token to start with the removed text.

    Code. Indentation, brackets and newlines are tokens. The Llama 3 regex turns a 4-space indent into ␣␣␣ + ␣return; the punctuation-plus-newline ):↵ is one token. On four small JavaScript and Python files we measured 2.9–3.8 characters per token with Llama 3, versus 4.9 for the English widget corpus: code costs more tokens per byte than prose.

    Glitch tokens. The tokenizer and the model are trained on different data. GPT-2's tokenizer data included Reddit usernames such as SolidGoldMagikarp, which became a single token (ID 43453). The model's training data barely contained it, so its embedding row was almost never updated. In 2023, researchers found that GPT-3-era models, which shared that tokenizer, behaved bizarrely when asked to repeat such tokens: evasions, insults, unrelated words. Newer tokenizers are built on data closer to the model's, and teams now check for under-trained tokens, but the failure mode remains: a token that is common in the tokenizer's data and rare in the model's data has a junk embedding.

    Common misconception

    "The model is bad at math and spelling because it is not smart enough." Partly. But much of the difficulty comes from the input format: the information needed (digit positions, letters) is not directly in the tokens. Fix the representation, by spelling out, adding digit separators, or calling a calculator tool, and accuracy jumps.

    Detokenization and streaming

    Going back from IDs to text is simple: look up each ID's byte string, concatenate, decode as UTF-8. The catch is streaming. Chat UIs show the answer as it is generated, one token at a time. But a token is a byte string, not a character string, and it can end in the middle of a multi-byte character (Figure 3.4). If you decode each token on its own, the half character becomes the replacement character �.

    The fix is an incremental UTF-8 decoder: append each token's bytes to a buffer, and emit the longest prefix that is complete UTF-8. The lead byte tells you how long the character is (0xxxxxxx = 1 byte, 110xxxxx = 2, 1110xxxx = 3, 11110xxx = 4). Python's codecs.getincrementaldecoder and JavaScript's TextDecoder with {stream: true} do exactly this. Servers that stream over Server-Sent Events do it before sending. So one streamed "chunk" can contain zero, one or several tokens. SentencePiece tokenizers add one more wrinkle: tokens carry a leading ▁ that must become a space, except at the very start of the text. Stop sequences that span token boundaries are Chapter 14's problem.

    Beyond text: images and audio as tokens

    Multimodal models accept images (and sometimes audio and video) in the same sequence as text. They do not use BPE for pixels. Instead:

    1. The image is resized and cut into a grid of square patches, typically 14–32 pixels on a side.
    2. A vision encoder, usually a Vision Transformer (ViT), turns each patch into a vector, letting patches exchange information along the way.
    3. A small projector (a linear layer or small MLP) maps those vectors to the language model's width d. Some models also pool neighboring patches to cut the count.
    4. The resulting vectors are inserted into the sequence, between special marker tokens, exactly where the image appeared in the message. They skip the embedding table: there are no IDs, the vectors go straight into X.

    From then on the transformer treats them like any other positions. They take attention compute, KV-cache memory and context-window space, and APIs bill them as input tokens.

    How many tokens is an image? Each API has its own rule (checked October 2026):

    ProviderRule1024 × 1024 image
    OpenAI (current GPT-5.x / GPT-6 models, patch-based)⌈w/32⌉ × ⌈h/32⌉ patches × model multiplier (1.2 for current models), after resizing to the detail level's budget1,024 patches → 1,229
    Anthropic (Claude)⌈w/28⌉ × ⌈h/28⌉ visual tokens; larger images downscaled to a cap (1,568 tokens standard; 4,784 on high-resolution models)37 × 37 = 1,369
    Google (Gemini 3 / 4)fixed budget per image set by media_resolution: low 280, medium 560, high 1,120 (default), ultra-high 2,2401,120 (default)

    Audio works the same way: an audio encoder turns short frames of sound into vectors. Gemini 3 and 4 count 25 tokens per second of audio. A one-hour recording is about 90,000 tokens.

    Key takeaway

    "Token" really means "one position in the sequence". Text positions come from a table lookup; image and audio positions come from an encoder. All of them cost the same per position once inside the transformer.

    • Whole-chunk lookup is not just a speedup. tiktoken checks the whole chunk first, and Llama 3's tokenizer.json asks Hugging Face to do the same (look for ignore_merges). Do it too, so you match by construction rather than by luck.
    • Fast trainer divergence: count pairs exactly as the naive loop does (a run like aaa adds 2 to (a, a) in both, although only one merge fits), and merge left to right without overlap, like replace_pair. Stale entries in the pair → chunks index are fine if you rescan each chunk. For the heap, use lazy deletion: push (−count, pair) whenever a count changes, and skip popped entries whose count no longer matches the table.
    • Comparing with BpeTrainer: its vocab_size includes the 256 base bytes. Use pre_tokenizers.Sequence([Split(Regex(PATTERN), behavior="isolated"), ByteLevel(add_prefix_space=False, use_regex=False)]) with initial_alphabet=pre_tokenizers.ByteLevel.alphabet(), then map its vocabulary keys back to bytes with your milestone 1 map.
    • A diff against Hugging Face on web text that contains a literal special-token name is the security callout in action: Hugging Face parsed it as a special token. Log those documents as a finding; do not "fix" your encoder.
    • Template diffs: compare repr() of both strings first. The usual culprits are the double newline after each header, the injected date lines and whitespace handling in the Jinja source (look for filters such as trim).
    • Streaming: bytes 10xxxxxx are continuation bytes. Scan back at most 3 bytes from the end of the buffer for a lead byte, and hold the tail only if it is an incomplete but valid start of a character. Bytes that can never complete (a stray continuation byte, 0xFF) should come out as U+FFFD at once, not sit in the buffer forever. generate(..., streamer=...) accepts any object with put() and end(); its first put carries the whole prompt.
    • The widget corpus repeated 400 times is 400 copies of the same chunks, so a chunk cache flatters it. That is why you also benchmark held-out text.
    • NumPy has no bfloat16. Read the row as uint16 and widen it: (u.astype(np.uint32) << 16).view(np.float32). Or let PyTorch do it.
