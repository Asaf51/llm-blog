Numbers & the Machine: tensors, floats, GPUs

An LLM is a small program that pushes billions of numbers through matrix multiplications. This chapter covers what those numbers are, down to the bits, what one matrix multiplication costs, and how a GPU runs it. After this, every later chapter can talk in bytes, FLOPs and bandwidth.

In this chapter
  • All data in an LLM is a tensor: a typed block of numbers with a shape, stored row-major in flat memory.
  • Multiplying an (m×k) matrix by a (k×n) matrix costs 2·m·n·k FLOPs. Almost all LLM compute is matmuls. GEMV (one vector) and GEMM (many vectors) behave very differently.
  • Number formats at the bit level: FP32, FP16, BF16, FP8 (E4M3, E5M2), FP4 (E2M1), INT8, INT4. Exponent bits buy range, mantissa bits buy precision. Why BF16 won, and why sums are kept in FP32.
  • A GPU is a throughput machine. An H100 has 132 SMs, warps of 32 threads, tensor cores, a software-managed SRAM, and HBM at 3.35 TB/s.
  • Tiling a matmul through shared memory reuses each loaded byte many times. FlashAttention uses the same trick later.
  • Memory and links: HBM vs GDDR vs DDR5, VRAM vs RAM vs disk, PCIe vs NVLink, Apple unified memory, collective operations.
  • The roofline model: arithmetic intensity (FLOPs per byte) tells you if a kernel is limited by compute or by memory. A batch-1 GEMV does about 1 FLOP per byte. An H100 needs about 295 to keep its tensor cores busy.
  • Build it: a roofline lab: a float codec that matches PyTorch bit for bit on all 232 FP32 inputs, a ladder of CUDA and Triton matmul kernels, and your own GPU's measured roofline with every kernel placed on it.

Tensors: shaped blocks of numbers

An LLM has only one data structure. The input token IDs, the learned weights, the intermediate values (called activations) and the cache of past keys and values are all tensors. A tensor is a block of numbers that all have one type, arranged in a grid with some number of axes. If you have used NumPy, a tensor is an ndarray.

  • A scalar has no axes: one number, such as a sampling temperature of 0.7.
  • A vector has one axis. The hidden state of one token in Llama 3.1 8B is a vector of d = 4,096 numbers. (What the hidden state means is the topic of Chapter 4.)
  • A matrix has two axes. The query projection weight Wq of one layer has shape [4096, 4096].
  • A tensor with three or more axes is usually just called a tensor. A batch of activations has shape [B, n, d]: B sequences, n tokens each, d numbers per token.

The number of axes is the rank (also "number of dimensions"). The list of axis lengths is the shape. The element type is the dtype (for example bfloat16). Two facts follow directly:

elements = product of the shape      bytes = elements × bytes per element Example: Wq has 4096 × 4096 = 16,777,216 elements. In BF16 (2 bytes each) that is 33,554,432 B = 33.6 MB = exactly 32 MiB.

Row-major layout and strides

Memory is a flat array of bytes. A tensor library must map each multi-index to one offset. Nearly all deep-learning code uses row-major (C order) layout: the last axis is contiguous. For a matrix with C columns, element [i, j] lives at offset i·C + j. The numbers you multiply the indices by are called strides. For a [B, n, d] tensor the strides are (n·d, d, 1), so token t of sequence b starts at offset b·n·d + t·d, and its 4,096 numbers are consecutive.

This is the same thing as a C array float a[3][4]. In PyTorch a tensor is a pointer to storage plus shape, strides, dtype and device. Operations like transpose, slicing or view often just create new strides over the same bytes: no copy. The catch is contiguity. Fast GPU loads want neighboring threads to read neighboring addresses (we come back to this in the kernel section). So a library will sometimes copy a strided view into a fresh contiguous buffer before a heavy operation. A .contiguous() call is a real memory copy.

A convention that trips people up

PyTorch's nn.Linear stores its weight as [out_features, in_features] and computes y = x·WT. Model files store weights in that orientation. When this blog writes x·W with W of shape [k, n], it means the math, not the storage layout. The cost is the same either way.

Matrix multiplication: where the FLOPs go

Almost every learned operation in a transformer is "multiply a block of token vectors by a weight matrix". So the cost of an LLM is mostly the cost of matrix multiplication. Let us count it exactly.

Take A with shape [m, k] and B with shape [k, n]. The product C = A·B has shape [m, n], and each output is a dot product of a row of A with a column of B:

Cij = ∑p=0k−1 Aip · Bpj   ⇒   FLOPs = 2 · m · n · k m = rows of A (in LLMs: the number of tokens being processed), k = the shared inner dimension, n = columns of B. Each output needs k multiplies and k adds. Hardware does them as k fused multiply-adds (FMA), and by convention one FMA counts as 2 FLOPs. There are m·n outputs.

Why matmuls dominate an LLM

A transformer layer has two kinds of work (Chapter 6 walks through every op):

  • Matmuls with weight matrices: projections to queries/keys/values, the output projection, and the three MLP matrices. For n tokens they cost about 2·n·(parameters in the layer) FLOPs, which scales as n·d2.
  • Everything else: normalization, activation functions, adding residuals, rotary position math, softmax. These touch each activation a few times, so they scale as n·d. With d = 4,096 they are thousands of times cheaper in FLOPs.

Attention scores are matmuls too (Chapter 5). Since every weight takes part in exactly one multiply-add per token, a forward pass costs about 2N FLOPs per token, where N is the parameter count. For Llama 3.1 8B that is about 16 GFLOP per token. Chapter 6 derives it exactly.

The "everything else" ops are cheap in FLOPs but not cheap in time. Each one reads and writes whole activation tensors and does almost no math per byte. They are limited by memory bandwidth, which is why engines fuse them into neighboring kernels. The roofline model at the end of this chapter makes this precise; Chapter 4 profiles each kind of op and Chapter 15 covers fusion.

GEMV vs GEMM

Linear-algebra libraries (BLAS) name the two cases. GEMV (general matrix-vector multiply) has m = 1: one vector times a matrix. GEMM (general matrix-matrix multiply) has many rows. In an LLM the weight matrix is the same either way. What changes is how many token vectors we push through it in one go.

Look at the bytes. In the GEMV, the 4096×4096 weight matrix (32 MiB) must come in from memory to produce one tiny output vector. It does 33.6 million FLOPs on 33.6 MB: about 1 FLOP per byte. In the GEMM with 2,048 rows, the same 32 MiB of weights is read once and reused by every row. FLOPs grow 2,048 times, but bytes only double, so the ratio climbs to about 1,024 FLOPs per byte. In general, when m is much smaller than k and n, a BF16 matmul does roughly m FLOPs per byte. Hold on to this. Generating text one token at a time is a stream of GEMVs. Reading a whole prompt at once is a GEMM. Chapter 11 builds on exactly this.

Key takeaway

FLOPs of a matmul = 2·m·n·k. Bytes ≥ (m·k + k·n + m·n) × bytes per element. Their ratio, FLOPs per byte, is small for GEMV (≈ 1 in BF16) and large for big GEMMs. Hardware has to be fed bytes before it can do FLOPs.

Number formats at the bit level

Every weight and activation is stored in some number format. The format sets three things you will meet again and again: how many bytes the model takes, how fast the hardware can multiply, and how much error creeps in. Fewer bits mean smaller and faster, but coarser. This section shows exactly what each format can and cannot represent.

How a float stores a number

A binary floating-point number is scientific notation in base 2 with a fixed number of digits. It has three bit fields:

  • a sign bit s (0 = positive),
  • an exponent field e of E bits, stored with a bias so it can be negative,
  • a mantissa (fraction) field f of M bits: the digits after the binary point.
value = (−1)s × 2e − bias × (1 + f / 2M) For normal numbers the leading "1." is implicit, so it costs no bit. When e = 0 the number is subnormal: value = (−1)s × 21 − bias × (f / 2M). Subnormals fill the gap between the smallest normal number and zero. In IEEE-style formats the all-ones exponent is reserved for infinity (f = 0) and NaN (f ≠ 0).

Worked example: 0.1 in FP32. FP32 has E = 8, M = 23, bias 127. Since 0.1 = 1.6 × 2−4, the stored exponent is −4 + 127 = 123 = 01111011. The mantissa should be 0.6 × 223 = 5,033,164.8, which rounds to 5,033,165 = 0x4CCCCD. The bit pattern is 0x3DCCCCCD, and it decodes to 0.100000001490116… The error is 1.5 × 10−9, a relative error of 1.5 × 10−8. You can check this in the explorer below.

Range vs precision

The two fields buy different things:

  • Exponent bits buy range. Each exponent value is one "binade", the interval [2p, 2p+1). With E bits you get about 2E binades. FP32 and BF16 both span about 10−38 to 1038. FP16 only spans about 6 × 10−5 to 65,504 for normal numbers.
  • Mantissa bits buy precision. Inside one binade there are 2M evenly spaced values. The gap between neighbors, relative to the number, is 2−M. Rounding to the nearest value makes a relative error of at most half of that. This is the same at 0.001 and at 1,000: floats have constant relative precision, not constant absolute precision.

A small example makes precision concrete. In BF16 (M = 7) the neighbors of 256 are 254 and 258. So 256 + 1 = 257 is a tie, which rounds to the even mantissa: 256 + 1 = 256 in BF16. Hardware rounds with round-to-nearest, ties-to-even (RNE) by default. Ties go to the neighbor whose last mantissa bit is 0, so ties do not bias sums upward.

FP16 vs BF16: why BF16 won

Both are 16 bits. They split them differently. FP16 (IEEE half precision) keeps 10 mantissa bits but only 5 exponent bits. Its largest value is 65,504, and anything below about 6 × 10−8 becomes zero. Neural-network values span a wide range. Gradients in training are often tiny, and a few activations can be large. In FP16 the tiny ones underflow to zero and the large ones overflow to infinity. Training in FP16 therefore needs loss scaling: multiply the loss by a large constant so gradients move into FP16's range, then divide it out later (Chapter 8).

BF16 ("brain float", designed by Google Brain for TPUs) keeps FP32's 8-bit exponent and cuts the mantissa to 7 bits. It won for four reasons:

  1. Same range as FP32. No overflow or underflow surprises and no loss scaling. Networks tolerate coarse values far better than they tolerate infinities.
  2. Trivial conversion. A BF16 value is the top 16 bits of an FP32 value. Converting is a shift plus a rounding step. Converting back just appends 16 zero bits.
  3. Cheaper multipliers. A multiplier's area grows roughly with the square of the significand width. BF16 multiplies 8-bit significands (counting the implicit 1). FP16 multiplies 11-bit ones, FP32 multiplies 24-bit ones.
  4. Precision is rarely the problem. About 2–3 significant digits per value is enough when sums are kept in higher precision (see below).

Today BF16 is the default format for training and for released weights. Llama 3.1 ships its weights in BF16.

TF32: a format you never store

NVIDIA tensor cores also support TF32: FP32's 8-bit exponent with a 10-bit mantissa (19 bits used inside a 32-bit register). It lets "FP32" matmuls run on tensor cores at reduced input precision. It is an internal compute mode, not a storage format.

FP8: E4M3 and E5M2

FP8 halves the bytes again and doubles tensor-core throughput on Hopper and later GPUs (H100: about 1,979 dense FP8 TFLOPS vs 989 for BF16). With 7 non-sign bits there is no good single split, so there are two standard formats, defined by the Open Compute Project's 8-bit floating point (OFP8) spec:

  • E4M3: 4 exponent bits, 3 mantissa bits, bias 7. It drops infinities to win back range. Only S.1111.111 is NaN, so S.1111.000 through S.1111.110 are normal numbers, and the max is 1.75 × 28 = 448. PyTorch calls it float8_e4m3fn, "fn" meaning finite only. More precision, less range. It is typically used for weights and activations.
  • E5M2: 5 exponent bits, 2 mantissa bits, bias 15. It follows IEEE rules: Inf and NaN exist and the max is 1.75 × 215 = 57,344. More range, less precision. It is typically used for gradients in FP8 training.

When a value is too big, conversion either produces Inf/NaN or saturates to the largest finite value. CUDA exposes both behaviors, and ML code nearly always saturates. With only 8 bits, the values must also be scaled into the format's sweet spot first. Choosing those scales is quantization's job (Chapter 13).

FP4 only works when small blocks of values share a scale factor (MXFP4, NVFP4). Those block formats belong to Chapter 13. Blackwell GPUs (B200, RTX 50-series) run FP4 matmuls natively, faster than FP8 (twice the FP8 rate on a B200).

Integers: INT8 and INT4

INT8 and INT4 are ordinary two's-complement integers: −128…127 and −8…7. Their grid is uniform: the gap between neighbors is always 1. To store real-valued weights in them you pick a scale and store round(w / scale). The math (scales, zero points, group sizes, outliers) is Chapter 13's job. At the hardware level, integer multiply-accumulate is simple and cheap: INT8 products are summed into INT32 accumulators. On an H100, dense INT8 runs at the same rate as FP8.

Multiply in low precision, add in FP32

A matmul output is a long sum. In Llama 3.1 8B each output of the MLP down-projection adds up 14,336 products. Long sums are where low precision really hurts. Once the running total is large, a small addend falls below half a step of the total's grid and vanishes. This is called swamping.

The fix is built into the hardware. Tensor cores take BF16 (or FP16, FP8, FP4) inputs, form exact or near-exact products, and add them into an FP32 accumulator. The product of two BF16 values has at most 16 significant bits, so it fits in FP32's 24 exactly. Only when the finished sum is written back is it rounded to BF16. That is why spec sheets say "BF16 with FP32 accumulate". Long sums elsewhere, such as the mean of squares inside a normalization or the denominator of a softmax, are also computed in FP32 in good kernels. FP8 is subtler. DeepSeek reported that the accumulation inside H800 FP8 tensor-core GEMMs keeps only about 14 bits. They periodically moved partial sums out to FP32 registers to compensate (DeepSeek-V3 report).

Key takeaway

Store and multiply in as few bits as quality allows. Accumulate in FP32. Range failures (overflow to Inf, underflow to 0) are worse than coarse rounding, which is why BF16 beat FP16 and why low-bit formats need scale factors.

CPU vs GPU: latency machine vs throughput machine

You know how a modern CPU core works. It is built to finish one instruction stream as fast as possible. It has a deep out-of-order window, branch prediction, speculation, prefetchers and large private caches. Most of the die goes to control logic and cache. The arithmetic units are a small part. That is the right design when the next instruction depends on the last one and you cannot wait for memory.

A GPU makes the opposite bet. It assumes there are millions of independent, identical small tasks, and that it is fine if each one is slow. It spends its transistors on arithmetic units and on keeping huge numbers of threads in flight. It drops the machinery that makes a single thread fast.

Some numbers. Take a 16-core desktop CPU with full-width AVX-512 (for example AMD Zen 5). Each core can issue two 512-bit FMAs per cycle: 2 × 16 FP32 lanes × 2 FLOPs = 64 FLOPs per cycle. At about 5 GHz that is roughly 16 × 64 × 5 × 109 ≈ 5 TFLOPS FP32 peak, fed by dual-channel DDR5-6000 at 96 GB/s. An H100 SXM has 16,896 FP32 lanes (NVIDIA calls them "CUDA cores") for about 67 TFLOPS of plain FP32. Its tensor cores add 989 TFLOPS of dense BF16, fed by 3,350 GB/s of HBM. That is roughly 200× the CPU's peak (comparing the GPU's BF16 tensor math with the CPU's FP32 vector math) and 35× the bandwidth.

Hiding latency with parallelism

Both machines wait hundreds of nanoseconds for DRAM. A CPU fights the latency with caches, prefetching and out-of-order execution, so the one thread rarely waits. A GPU accepts the latency and hides it. Each SM keeps many warps (groups of 32 threads, explained next) resident at once. Every warp's registers live in the SM's large register file all the time. Switching from one warp to another is therefore free: the scheduler simply issues, on the next clock, an instruction from any warp whose operands are ready. If you know SMT (hyper-threading), this is SMT with 16 hardware threads per scheduler instead of 2 per core.

Little's law gives the scale. To keep 3.35 TB/s flowing with a memory latency of roughly 500 ns, about 3.35 × 1012 × 5 × 10−7 ≈ 1.7 MB of loads must be in flight at every moment. That is about 13 KB per SM, outstanding at all times. Only thousands of concurrent threads, or deep asynchronous copy pipelines, can generate that much. (The latency figure is approximate. The conclusion holds for any realistic value.)

Inside an H100: SMs, warps, tensor cores

An H100 SXM is a hierarchy of copies. The chip has 8 GPCs (graphics processing clusters). Together they hold 144 SM slots, and 132 of them are enabled on the SXM product. All SMs share a 50 MB L2 cache, split into two partitions. Five HBM3 stacks sit beside the die, driven by ten 512-bit memory controllers. The SM (streaming multiprocessor) is the unit that matters for programming.

Threads, warps and SIMT

CUDA code is written for one thread, like ordinary scalar C. The hardware groups 32 consecutive threads into a warp. A warp has one instruction stream: each clock, a sub-partition's scheduler picks one ready warp and issues one instruction for all 32 lanes. NVIDIA calls this SIMT (single instruction, multiple threads). It is a 32-wide SIMD unit where each lane looks like its own thread with its own registers.

Compared with AVX-512: in SIMD you write vector instructions and manage masks. In SIMT the compiler and hardware do it for you. If threads of one warp take different sides of an if, the warp runs both sides one after the other with inactive lanes masked off. This is divergence, and it wastes lanes. Matmul code has almost none.

Resources limit how many warps can be resident, which is called occupancy. An H100 SM holds at most 64 warps (2,048 threads) and has 65,536 32-bit registers. If each thread of a kernel needs 128 registers, only 65,536 / 128 = 512 threads (16 warps) fit, no matter what else you do. Shared memory per block limits it the same way. Matmul kernels deliberately trade occupancy for big per-thread register tiles.

Tensor cores: matrix-multiply hardware

The FP32 lanes do one FMA on one pair of numbers per clock. A tensor core does a whole small matrix multiply-accumulate (MMA) at once. Software reaches it through warp-level instructions. In PTX (NVIDIA's virtual assembly) one example is:

// one warp: D[16x8] = A[16x16] * B[16x8] + C[16x8], BF16 inputs, FP32 accumulators
mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32  {d0,d1,d2,d3}, {a0,a1,a2,a3}, {b0,b1}, {c0,c1,c2,c3};
// 2*16*8*16 = 4,096 FLOPs per instruction; operands are spread across the 32 threads' registers

Hopper adds wgmma ("warpgroup MMA"). Four warps (128 threads) issue one asynchronous m64·N·k16 multiply, with N up to 256, and the operands can be read straight from shared memory. Per clock, the four tensor cores of an H100 SM together complete 2,048 dense BF16 FMAs, which is 4,096 FLOPs. Multiply by 132 SMs and by the roughly 1.83 GHz clock that NVIDIA's figure implies: 132 × 4,096 × 1.83 × 109 ≈ 989 TFLOPS. The same SM's 128 FP32 lanes do only 256 FLOPs per clock. Tensor cores supply about 94% of the chip's math, and only for matrix multiplies. FP8 inputs double the per-clock rate (1,979 TFLOPS). Blackwell (B200) goes further: 148 SMs, FP4 and FP6 support, and a dedicated 256 KB "tensor memory" per SM that holds accumulators.

Key takeaway

On a modern GPU, "fast" means "expressed as matmuls on tensor cores, in low precision". Anything else, such as elementwise math, reductions or branches, runs on a much smaller part of the chip. This is a big reason transformers are built almost entirely from matmuls.

The tensor cores can only multiply data that is already sitting in registers or shared memory, a few hundred kilobytes per SM. The weights live in HBM, gigabytes away. Between the two is a ladder of memories. Each step up the ladder is smaller and faster.

How this differs from the CPU caches you know

  • The fast level is a scratchpad, not a cache. On a CPU you issue loads, and the hardware decides what stays in L1/L2 while prefetchers guess. On a GPU, matmul kernels do not rely on luck. Code explicitly copies a tile from HBM into shared memory, synchronizes the threads of the block, and then all of them read it many times. It is like a DSP's local store, or a cache you manage by hand. (The same SRAM can also act as a normal hardware L1.)
  • The register file is the biggest fast memory. 256 KB per SM, more than the shared memory. A CPU core's architectural vector registers total about 2 KB (32 × 64 B for AVX-512). The GPU needs it because thousands of threads keep their state resident to make warp switching free.
  • Coherence is weak and explicit. There is no snooping between SMs' L1s. Threads in a block synchronize with barriers. Across blocks you use atomics, or you end the kernel.
  • Bandwidth is the scarce resource, not latency. HBM delivers 3.35 TB/s, but the tensor cores could consume operands far faster than that. The whole art of GPU kernels is to load each byte from HBM once and reuse it many times from SRAM and registers.

Kernels: how work is launched on a GPU

A kernel is a function that runs on the GPU (the device), launched by code on the CPU (the host). One launch starts a grid of thread blocks, and every thread runs the same function. Built-in variables tell each thread where it is: blockIdx for its block in the grid and threadIdx for its position in the block. The rules are simple and strict:

  • A block has at most 1,024 threads. It runs entirely on one SM and never migrates. Its threads can share that SM's shared memory and wait for each other with __syncthreads().
  • Blocks are independent. The hardware may run them in any order, many at a time. That is why the same program scales from a 128-SM RTX 4090 to a 148-SM B200 without changes.
  • Inside a block, every 32 consecutive threads form a warp.

Here is the simplest possible matmul kernel. Each thread computes one element of C:

// C[M,N] = A[M,K] * B[K,N], row-major, FP32. One thread per output element.
__global__ void matmul_naive(const float* A, const float* B, float* C, int M, int N, int K) {
  int row = blockIdx.y * blockDim.y + threadIdx.y;
  int col = blockIdx.x * blockDim.x + threadIdx.x;   // neighbors in a warp get neighboring columns
  if (row >= M || col >= N) return;
  float acc = 0.0f;
  for (int p = 0; p < K; ++p)
    acc += A[row * K + p] * B[p * N + col];             // 2 global loads per FMA
  C[row * N + col] = acc;
}

Notice coalescing. With 32×8 blocks (the launch line in Figure 2.11), the 32 threads of a warp share one row and have consecutive col values, so in each iteration they read 32 consecutive floats of B. The memory system merges those into one 128-byte transaction, the GPU version of "use the whole cache line". All 32 threads read the same element of A, which is broadcast. If neighboring threads instead touched addresses far apart, each load would cost its own transaction and the effective bandwidth would collapse. This is where row-major layout and strides become performance questions.

Launch overhead

A kernel launch is not free. The CPU, the driver and the GPU's front end need on the order of a few microseconds per launch (approximate; it depends on the system). Launches are asynchronous, so this only hurts when kernels are short. Then the GPU finishes each kernel before the CPU has issued the next one and sits idle in between. That is exactly the situation in LLM decoding at batch size 1: one step runs a handful of kernels per layer times 32 layers, several hundred launches, each doing very little work. A few hundred launches at a few microseconds each is around a millisecond, a big share of the roughly 5 ms that one token of Llama 3.1 8B can take on an H100. Small kernels also cannot fill 132 SMs. Serving engines fight this with kernel fusion (one kernel does several ops) and CUDA Graphs (record a whole sequence of launches once, then replay it with a single launch). Both are covered in Chapter 15.

Tiled matmul through shared memory

The naive kernel is correct and slow. Each FMA needs two loads from global memory, so for a 4096×4096×4096 BF16 matmul it would request 2·40963 elements × 2 bytes ≈ 275 GB of traffic. Even at 3.35 TB/s that takes 82 ms. The math itself is 2·40963 = 137 GFLOP, which takes 0.14 ms at 989 TFLOPS. The ideal minimum traffic (read A and B once, write C once) is only 3 × 40962 × 2 B ≈ 101 MB, or 30 µs. Caches recover part of the gap, but nowhere near enough. The fix is the same as cache blocking for CPU matmul, done explicitly.

The idea: give each thread block one T×T tile of C. To compute it, the block needs a horizontal strip of A and a vertical strip of B. It walks along K one chunk at a time. For each chunk it loads one tile of A and one tile of B into shared memory, synchronizes, multiplies the two tiles, and adds the result to an accumulator in registers. Every element brought in from global memory is now used T times instead of once.

global traffic ≈ 2 · m · n · kT elements    (vs 2·m·n·k for the naive kernel) Each of the m·n/T2 output tiles reads a T×k strip of A and a k×T strip of B: 2·T·k elements. With T = 128 on the 40963 example, traffic from L2 drops from 275 GB to about 2.1 GB. L2 then catches most re-reads between neighboring blocks, so HBM traffic ends up within a small factor of the 101 MB minimum.

Real kernels (cuBLAS, CUTLASS, Triton) stack this idea at every level of the hierarchy:

  • Block tiles in shared memory, for example 128×256 of C per block, with K chunks of 64.
  • Warp tiles in registers. Each warp computes a sub-tile such as 64×64 from fragments it loads from shared memory. Each shared-memory read is reused again.
  • Tensor-core MMAs at the bottom, consuming those fragments.
  • Pipelining. While the tensor cores work on chunk k, chunk k+1 is already being copied. On Hopper the TMA unit does these bulk copies asynchronously. Kernels often specialize warps: "producer" warps issue copies and "consumer" warps do math. If you have written double-buffered DMA code on an embedded system, this is the same pattern.
  • Tile scheduling. The order in which blocks are launched is chosen so that blocks running at the same time share strips of A and B in L2.

With all of this, large GEMMs reach a large fraction of peak tensor throughput. The roofline section shows why that is possible for big matmuls and impossible for GEMV. The same tiling idea, applied to attention so the big score matrix never leaves SRAM, is FlashAttention (Chapter 15).

VRAM vs system RAM vs disk

The model must be somewhere, and every place has a price in bandwidth. A useful mental unit: how long does it take to read Llama 3.1 8B's 16.06 GB of BF16 weights once?

Three conclusions follow, and Chapter 11 uses all of them. Weights that are read for every token must sit in the fastest memory that can hold them. Streaming weights over PCIe for each token is hopeless: 251 ms per token. And when a model does not fit in VRAM, running part of it on the CPU from DDR5 is bounded by DDR5's bandwidth, not by CPU FLOPs.

Links: PCIe and NVLink

PCIe connects a GPU to the host. PCIe 5.0 runs 32 GT/s per lane over 16 lanes with 128b/130b encoding: about 63 GB/s in each direction (NVIDIA's "128 GB/s" counts both directions). The RTX 4090 uses PCIe 4.0, half that. The RTX 5090 and H100 use PCIe 5.0.

NVLink connects GPUs directly. An H100 SXM has 18 NVLink 4 links of 25 GB/s per direction each: 450 GB/s each way, 900 GB/s total, about 7× PCIe 5.0. In an 8-GPU HGX/DGX server, NVSwitch chips give every GPU that full speed to every other GPU. Blackwell's NVLink 5 doubles it to 1.8 TB/s per GPU. Between servers, traffic goes over InfiniBand or Ethernet NICs, typically one 400 Gb/s NIC per GPU (about 50 GB/s each way), roughly 9× less than NVLink. That ratio decides how a big model is split across GPUs (Chapter 8, Chapter 11).

Apple unified memory

On Apple silicon the CPU, GPU and Neural Engine share one pool of LPDDR5X through a common memory fabric. There is no separate VRAM and no PCIe copy: a weight file that is memory-mapped by the CPU can be read directly by the GPU. In 2026 an M5 Max offers up to 128 GB at 614 GB/s, and an M5 Ultra up to 512 GB at 1.2 TB/s. That is far more capacity than any single consumer GPU, with bandwidth between an RTX 4090 and an H100. The weak side is compute. Apple does not publish matmul TFLOPS. Community measurements put an M5 Max GPU around 55–60 TFLOPS of FP16 on large matmuls, with the per-core "Neural Accelerators" new in the M5 generation, versus 989 for an H100. So a Mac can hold big models and stream their weights at a decent rate, which suits generating tokens one at a time. It is much slower at compute-heavy work such as reading a long prompt. The roofline model below says exactly that.

Collective operations: GPUs working together

When a model or its training is spread over several GPUs, they must exchange tensors. The exchanges follow a few standard patterns called collectives. Libraries such as NCCL implement them on top of NVLink and the network. The concepts are below. When and why each parallelism strategy uses them is covered in Chapter 8 (training), Chapter 11 (inference) and Chapter 7 (MoE).

Cost. The standard bandwidth-optimal all-reduce is the ring. The p GPUs form a ring, each tensor is cut into p chunks, and chunks circulate twice: once to reduce (a reduce-scatter) and once to share the results (an all-gather). Each GPU sends and receives

bytes per GPU = 2 · p − 1p · S   ⇒   time ≈ 2 · p − 1p · Slink bandwidth + latency terms S = tensor size in bytes. Example: all-reducing 16.06 GB of BF16 gradients (one per Llama 3.1 8B parameter) across 8 H100s over NVLink at 450 GB/s each way: 2 × 7/8 × 16.06 GB ÷ 450 GB/s ≈ 62 ms. Over PCIe 5.0 (~63 GB/s): about 0.45 s. A small tensor, such as one token's 8 KB activation vector, is instead dominated by per-message latency (microseconds).

Note that the per-GPU traffic barely grows with p: 2(p−1)/p approaches 2. That is why ring and tree algorithms scale to thousands of GPUs. The tensor size S and the slowest link in the ring set the time.

Arithmetic intensity and the roofline model

We now have all the pieces for the most useful performance model in this blog. A kernel needs two resources: arithmetic and memory traffic. Which one runs out first?

Arithmetic intensity is the number of FLOPs a kernel does per byte it moves to or from a given memory level (here: HBM or DRAM):

I = FLOPsbytes moved     time ≥ max( FLOPsP , bytesBW )     attainable FLOP/s = min( P , I · BW ) P = peak compute (FLOP/s) for the precision used; BW = memory bandwidth (bytes/s). The two bounds are equal at the ridge point I* = P / BW. For an H100 in BF16: 989 × 1012 / 3.35 × 1012 ≈ 295 FLOPs per byte.

Plot attainable FLOP/s against I on log-log axes. You get a slanted line (the bandwidth roof, slope 1) that hits a flat line (the compute roof) at the ridge. That shape is the roofline (Williams, Waterman and Patterson, 2009). A kernel left of the ridge is memory-bound: the tensor cores wait for bytes, and buying more FLOPs does nothing. A kernel right of the ridge is compute-bound: bytes arrive faster than they can be used. The ridge says how many FLOPs you must squeeze out of every byte to keep the chip busy. An H100 needs 295. That is a demanding number.

Now apply it to the operations from this chapter, in BF16 on an H100:

  • Elementwise add of two vectors: 1 FLOP per element, 6 bytes moved (read 2 + 2, write 2). I ≈ 0.17, so at most about 0.56 TFLOP/s, or 0.06% of peak. Normalization, activation and residual ops live here, which is why they get fused into neighboring kernels.
  • GEMV at batch 1 (one token through the 4096×4096 Wq): I ≈ 1. At most 3.35 TFLOP/s, 0.34% of peak. The 33.6 MB of weights take 10 µs to stream, and the math would take 0.03 µs. Generating text one token at a time is made of exactly these.
  • GEMM with m rows: I ≈ m when m is much smaller than k and n. So about 300 rows are needed before the H100 stops being memory-bound. With 64 rows, I ≈ 62 and the kernel is still memory-bound.
  • Big square GEMM (40963): I = 2·40963 / (3·40962·2 B) ≈ 1,365. Compute-bound, and tiling makes it possible to approach the compute roof.

Ridge points differ a lot between machines. An RTX 4090 needs about 164 FLOPs per byte (BF16), an RTX 5090 about 117, an M5 Max about 94, and a desktop CPU in FP32 about 53. Lower precision moves both sides: FP8 halves the bytes per weight (a GEMV becomes about 2 FLOPs per byte) but also doubles peak FLOPs (H100 ridge 591). So FP8 decoding is still memory-bound, but twice as fast, because half as many bytes must move.

What the roofline leaves out

Real kernels reach perhaps 60–80% of the compute roof on big GEMMs and 80–90% of the bandwidth roof on streaming kernels (rough figures that vary by kernel and shape). Every memory level has its own roofline: L2 and shared memory are much faster than HBM, which is exactly what tiling exploits. Bytes that hit in cache do not count against HBM. The model also ignores launch overhead and communication. It is still the first question to ask about any kernel: which roof am I under?

Key takeaway

Performance = min(compute, intensity × bandwidth). A batch-1 GEMV does about 1 FLOP per byte, which is hundreds of times below the ridge of any GPU. So token-by-token generation is limited by how fast weights stream from memory, not by FLOPs. Processing many tokens at once raises the intensity. Chapter 11 applies this to prefill and decode, where the intensity of decode turns out to be about equal to the batch size.

Hints (open only when stuck)
  • Rounding with integers. Shift away the low bits you drop. Call them d and the halfway value h = 1 << (shift − 1). Round up if d > h, or if d = h and the lowest kept bit is 1. Add the round-up to the combined exponent-and-mantissa integer, not to the mantissa alone. The carry then moves 1.111…1 up to the next power of two, and pushes the largest finite value into overflow, for free.
  • Subnormal outputs. When the exponent is below the target's minimum normal exponent, put the implicit 1 back in front of the 23 mantissa bits and shift right by the extra amount before rounding. A subnormal that rounds up into the smallest normal number is handled by the same carry.
  • Sign extension. >> on negative int32 tensors copies the sign bit. Do all bit work in int64 and mask with 0xFFFFFFFF.
  • NaN and overflow. PyTorch returns one canonical NaN pattern, so for NaN inputs only check "is it NaN". For overflow, probe PyTorch with inputs just above the largest finite value, at the halfway point to the next value the format would have, and far above. E4M3 has no Inf, so something else has to come out. ml_dtypes.float4_e2m1fn saturates to ±6.
  • Timing traps. The first call includes Triton compilation, autotuning and cuBLAS heuristics, so warm up. GPUs boost and then throttle as they heat up, so run for at least a second and report the median. Cross-check your bench against triton.testing.do_bench, which also flushes L2 between runs.
  • The L2 trap. Wq in BF16 is 33.6 MB, which fits in an H100's 50 MB L2 and an RTX 4090's 72 MB. Run a GEMV twice on the same weights and the second run reads from L2 and "beats" HBM. Rotate through enough weight copies to exceed 2× the L2 size, or flush between runs.
  • Shared-memory kernel. It needs two __syncthreads() per K step: one before the FMAs (the tile is fully loaded) and one after them (no thread still reads the tile you are about to overwrite). Without the second you get wrong answers only sometimes. Keep threadIdx.x walking columns so the loads into shared memory stay coalesced.
  • Register tiling. The plain shared-memory kernel does 2 shared-memory loads per FMA, so shared memory becomes the new wall. With an 8×8 thread tile, each thread loads 8 values of an A column and 8 of a B row into registers and does 64 FMAs: 16 loads per 64 FMAs. If ncu reports shared-memory bank conflicts (32 banks of 4 bytes), store the A tile transposed or pad each row by one element.
  • No nvcc, or no counters? cupy.RawKernel compiles the same CUDA C++ at runtime with NVRTC and runs on PyTorch tensors through cupy.asarray (zero-copy). If ncu fails with ERR_NVGPUCTRPERM, the machine does not let you read performance counters, which is common in cloud containers. Skip the traffic checks, not the milestone.
  • Triton. Block sizes must be powers of two and at least 16 for tl.dot. Start at 128×128×64 with num_warps 4 or 8 and num_stages 3 or 4, then let triton.autotune choose among a handful of configs.
  • FP8 with torch._scaled_mm. Both dimensions of each operand must be multiples of 16, the second operand must be column-major (store it as [n, k] and pass .t()), and the scales are FP32 tensors (1.0 is fine for unit-scale random data). For a "GEMV", pad m = 1 to 16 rows. The weight bytes dominate, so the intensity barely changes.
  • Fair FP32 baseline. Call torch.set_float32_matmul_precision("highest") so cuBLAS does not quietly use TF32 tensor cores while your kernels use the FP32 lanes.
