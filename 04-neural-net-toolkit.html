Part I · Chapter 4

The Neural-Net Toolkit: vectors, layers, softmax

An LLM is built from very few kinds of operation: dot products, matrix multiplies, a few nonlinear functions, softmax, normalization and plain addition. This chapter covers each one: what it does, why it exists, its exact math with Llama 3.1 8B shapes, and what it costs on real hardware. After this chapter you can read transformer math.

In this chapter
  • A token's meaning is a vector of 4,096 numbers. Similarity is a dot product or a cosine. Concepts are directions, and high-dimensional space has room for far more nearly-orthogonal directions than it has dimensions. This is called superposition.
  • A linear layer y = Wx is one dot product per output row, which is a loop of fused multiply-adds (FMAs). With many tokens at once it becomes a matrix multiply Y = XWT. Each Llama MLP matrix holds 14,336 × 4,096 = 58.7 M weights.
  • Without a nonlinearity between them, any stack of linear layers collapses into a single linear layer. ReLU, GELU and SiLU bend space. SwiGLU multiplies a SiLU "gate" by a second linear projection.
  • Softmax turns logits into probabilities. You must subtract the maximum first: in FP32, exp(89) is already infinity.
  • Cross-entropy is −log p(correct token). An untrained Llama 3 model starts near ln 128,256 ≈ 11.76.
  • RMSNorm rescales each vector to a standard size (root-mean-square 1). Residual connections add a layer's output to its input. Matmuls are compute-heavy; almost everything else is memory-bound, which is why inference engines fuse kernels.
  • Build it: write every op in this chapter by hand, forward and backward, make it reproduce a real Llama 3.1 8B layer and its loss, time it on your GPU, then build a 32-layer MLP language model from it and knock out the nonlinearity, the gate, the residuals and the norms one at a time.

Vectors as meaning

Chapter 3 turned text into integers: The, ␣cat, ␣sat… become token IDs. An ID is just a row number. ID 8415 and ID 8416 are no more related than ID 8415 and ID 90. Arithmetic on IDs means nothing. The network needs a representation where "similar" is something you can compute.

The idea is to give each token a point in space. A vector is an ordered list of numbers, and you can read it as the coordinates of a point (or an arrow from the origin to that point). Llama 3.1 8B gives every token a vector of d = 4,096 numbers. That vector is the token's embedding. The lookup from ID to vector is a row read from a big table (owned by Chapter 3). Everything after that lookup is math on vectors.

Training places these points so that tokens used in similar ways land close together. Nobody designs the layout by hand; it falls out of training on next-token prediction. The result behaves like a map of meaning: animals in one region, furniture in another, past-tense verbs in another.

Dimensions as features

A helpful first picture: each coordinate measures one property. Coordinate 17 might be "is an animal", coordinate 940 "is plural", coordinate 2,001 "is past tense". A token's vector would then be a list of property scores, like a row in a feature table.

The real picture differs in one important way. The axes are not special. Training is free to use any direction in the 4,096-D space as a feature, and it usually does. "Animal-ness" is more likely a direction such as 0.3·axis17 − 0.2·axis940 + … spread over many coordinates. To measure how much of a feature a vector contains, you project the vector onto that feature's direction. That projection is a dot product.

Dot product and cosine similarity

The dot product of two vectors of the same length multiplies them element by element and adds the results (refresher: Primer 2):

a · b = Σi ai bi = |a| |b| cos θ where ai, bi are the i-th coordinates, |a| = √(a·a) is the length (norm) of a, and θ is the angle between the two arrows.

The two forms say the same thing. The left one is how you compute it: a loop of multiply-adds. The right one is how you read it: the dot product is large and positive when the arrows point the same way, zero when they are perpendicular (orthogonal), and negative when they point in opposite directions. It also grows with the lengths. To compare directions only, divide out the lengths. That gives the cosine similarity:

cos θ = a · b|a| |b|   ∈ [−1, 1]

Hold on to the projection picture. It is the most important piece of geometry in this blog, and it comes back again and again:

  • An attention score is the dot product of a query vector and a key vector (Chapter 5).
  • Every neuron in a linear layer computes a dot product of its weight vector with the input (below).
  • The final logits are dot products of the last hidden vector with one vector per vocabulary token (below).
Low-level: what a dot product costs

For d = 4,096 you do 4,096 multiplies and 4,095 adds, which is ≈ 8,192 FLOPs (2 per element). Each pair is one fused multiply-add (FMA) instruction. On a CPU with AVX-512, one FMA instruction handles 16 FP32 lanes, so a 4,096-long dot product is 256 vector FMAs. With BF16 inputs (2 bytes each), the two vectors are 16 KiB together. Cosine similarity needs two more dot products for the norms, then a square root and a divide. That is why vector databases usually pre-normalize stored vectors to length 1: after that, cosine is a plain dot product.

Analogy arithmetic, and its caveats

The famous demo comes from word2vec (Mikolov et al., 2013; Primer 6 tells its backstory): take the vector for King, subtract Man, add Woman, and the nearest word vector is Queen. The reading is that the difference woman − man captures a "gender" direction, and adding it to king moves you along that direction. Figure 4.1 shows this as a parallelogram.

The idea is real but oversold. Three caveats:

  1. The standard test cheats a little. The usual analogy code is not allowed to return any of the three input words. Nissim et al. (2019) removed that rule. On the standard Google analogy test set, accuracy for the usual method fell from 0.74 to 0.21. Most of the time the "answer" was simply the input word: man is to king as woman is to king.
  2. It works for some relations (capital-of, plural, verb tense) much better than others.
  3. LLM input embeddings have no context. The vector for ␣bank is the same in "river bank" and "bank loan". The model sorts out which meaning is intended later, by mixing in information from other tokens (Chapter 5). The rich, context-aware meaning lives in the vectors inside the model (the residual stream, Chapter 6), not in the input table.

The useful lesson is the linear representation idea: many concepts are stored, roughly, as directions. That is why so much of an LLM is dot products. Reading a feature is a projection, and writing a feature is adding a vector.

High-dimensional space has room for many features

The model has to represent far more concepts than it has dimensions: every topic, name, language, code construct, tone and fact. If each concept needed its own private axis, 4,096 axes would run out almost immediately. Two facts about high-dimensional geometry explain how models get around this.

Fact 1: random directions are almost orthogonal

Pick two random directions in 2-D and the angle between them can be anything. Pick two random directions in 4,096-D and they are almost always within a degree or so of perpendicular. The reason is the law of large numbers. The cosine is a sum of 4,096 small products with random signs, divided by the lengths. Those products mostly cancel. The typical size of what is left shrinks like 1/√d:

std(cos θ) ≈ 1√d   →   d = 4,096:   1/64 ≈ 0.016 For two independent random directions in d dimensions. In 2-D the spread covers the whole range [−1, 1]. At d = 4,096, a cosine of 0.1 is more than six standard deviations out (Primer 4 explains why such spreads shrink like 1/√d), so it practically never happens by chance.

Fact 2: you can pack many more nearly-orthogonal directions than dimensions

You can have only d exactly orthogonal directions in d dimensions. If you allow a small tolerance, say every pair must have |cos| below 0.1, the number of directions you can fit grows exponentially with d. This is the concentration-of-measure effect behind the Johnson–Lindenstrauss lemma. So 4,096 dimensions can hold far more than 4,096 "almost independent" feature directions.

Superposition

Elhage et al. (2022, "Toy Models of Superposition") showed that networks really do this. They trained small ReLU networks to squeeze n features through m < n dimensions and read them back out. When features were sparse, meaning only a few are active on any one input, the networks stored more features than dimensions. They arranged the feature directions in regular shapes, for example 5 features in 2-D as a pentagon. They called this superposition. The cost is interference: when feature A is active, reading feature B along B's direction gives a small nonzero value. A nonlinearity with a threshold filters that noise out.

Systems analogy: hashing with collisions

Superposition works like a hash table that is deliberately overfilled. You accept occasional collisions because most slots are empty most of the time, and a cheap check (here, a ReLU threshold) throws away false hits. It works only while the data is sparse. If many features are active at once, the interference adds up and the scheme fails.

One consequence matters for anyone trying to look inside a model. A single neuron (one coordinate) usually responds to several unrelated things. This is called being polysemantic, and it happens because features are spread across directions rather than tied to axes. Tools that recover the real feature directions, such as sparse autoencoders, get a short tour in Chapter 6.

Key takeaway

A hidden vector is a sum of many feature directions, each scaled by how strongly that feature is present. You read a feature with a dot product and write one by adding a vector. High dimension lets thousands of features share 4,096 numbers with little interference.

The neuron and the linear layer

One neuron

A neuron is the smallest unit. It takes an input vector x, computes a weighted sum, adds a constant, and passes the result through a simple function:

z = w · x + b      y = φ(z) w = the neuron's weights (one per input), b = its bias (a single number), z = the pre-activation, φ = the activation function (covered in the next section). w and b are parameters: numbers found by training and then frozen (Chapter 1).

In words: the neuron measures how much the input points along its weight vector w, shifts that by b, and squashes the result. It is a feature detector built from one dot product.

A layer is many neurons: a matrix times a vector

A layer is m neurons that all read the same input. Stack their weight vectors as the rows of a matrix W with m rows and d columns. Then all m weighted sums are one matrix–vector product:

y = W x + b      W ∈ ℝm×d,  x ∈ ℝd,  b, y ∈ ℝm ℝm×d means "a grid of real numbers with m rows and d columns" (refresher: Primer 2). Output y[i] is the dot product of row i of W with x, plus b[i].

This is called a linear layer (also "dense" or "fully connected" layer, or a "projection"). Strictly, with a bias it is affine; people say "linear" anyway. Llama's linear layers have no bias at all (its config sets attention_bias and mlp_bias to false), so for Llama, y = Wx exactly.

There is a geometric reading too. W maps a point in d-dimensional space to a point in m-dimensional space. It can rotate, stretch, squash, shear and project, but it keeps straight lines straight and keeps the origin fixed. Column j of W is where the j-th axis direction lands. Figure 4.7 below shows this on a 2-D grid.

The running example for the rest of the chapter is one of Llama 3.1 8B's MLP projections, gate_proj. It maps d = 4,096 to dff = 14,336, so W has 14,336 × 4,096 = 58,720,256 weights, or 117.4 MB in BF16.

How W sits in memory

PyTorch's nn.Linear stores its weight with shape [out_features, in_features], here [14336, 4096], in row-major order (why this is the transpose of the math notation: Primer 2). Row-major layout was covered in Chapter 2. So the 4,096 weights of one output neuron sit next to each other: one contiguous 8 KiB run. The dot product for y[i] streams through that run front to back. On a CPU this is exactly the pattern hardware prefetchers love. On a GPU, neighbouring threads read neighbouring addresses, so their loads coalesce into wide memory transactions.

Batching: from GEMV to GEMM

Feeding one token through the layer is a matrix–vector product, a GEMV. Each weight is used once, so the hardware does about 1 FLOP per byte it loads and spends nearly all its time waiting on memory (Chapter 2). Stack n token vectors as the rows of X ∈ ℝn×4096 and the same layer becomes

Y = X WT     [n × 4,096] · [4,096 × 14,336] → [n × 14,336]     FLOPs = 2 · n · 4,096 · 14,336 WT ("W transposed") swaps rows and columns. No data moves in practice: the kernel simply reads W row by row. The factor 2 counts one multiply and one add per FMA.

This is a matrix–matrix product, a GEMM. The weights are read once and reused n times, so the work per byte grows roughly in proportion to n. At n = 2,048 one projection is 240.5 GFLOP. That is about 0.24 ms at an H100's 989 TFLOPS BF16 peak, and enough reuse to be limited by compute, not memory. GPUs run GEMMs on tensor cores using the tiled scheme from Chapter 2. The gap between one-token GEMV and many-token GEMM is the whole story of prefill versus decode in Chapter 11.

Key takeaway

A linear layer is a matrix multiply: one dot product per (token, output neuron) pair, each a loop of FMAs over a contiguous weight row. Almost all of an LLM's parameters and FLOPs are in these layers. For one token they are limited by memory bandwidth; for many tokens, by compute.

Why nonlinearities

Stacking linear layers does not make a network more powerful. Two linear layers in a row are just one linear layer:

W2(W1x + b1) + b2 = (W2W1)x + (W2b1 + b2) = W′x + b′ Matrix multiplication is associative (Primer 2 covers composing linear maps), so the two matrices fold into one, W′ = W2W1. Example: W1 = [[1, 2], [0, 1]] and W2 = [[2, 0], [1, 1]] give W′ = [[2, 4], [1, 3]]. A hundred stacked linear layers still compute one linear function.

A compiler would constant-fold this, and so does the math. Geometrically, a linear map keeps grid lines straight, parallel and evenly spaced. It cannot fold, bend or cut space. But nearly every interesting function needs that: "if this feature is present, do this, otherwise do something else."

The fix is a cheap nonlinear function φ applied to each number on its own (elementwise) after a linear layer. With φ in between, stacked layers no longer collapse. A network with one hidden layer and enough neurons can approximate any continuous function on a bounded region; this result is the universal approximation theorem. With ReLU, each hidden neuron adds one "crease" (the line where it switches on), and the network becomes a piecewise-linear function with many creases. Figure 4.7 computes this live on a 2-D grid.

ReLU, GELU and SiLU

Three activation functions cover almost every LLM you will meet:

ReLU(x) = max(0, x)     GELU(x) = x · Φ(x)     SiLU(x) = x · σ(x) = x1 + e−x Φ(x) is the standard normal cumulative distribution function: the probability that a bell-curve random number is below x (bell curve: Primer 4). σ(x) = 1/(1 + e−x) is the logistic sigmoid, an S-curve from 0 to 1.
  • ReLU (rectified linear unit) passes positive values and zeroes negative ones. It costs one compare. Its weakness: for negative inputs the slope is exactly 0, so a neuron stuck in the negative region gets no learning signal. These are called "dead" neurons.
  • GELU (Hendrycks & Gimpel, 2016) multiplies x by "how likely it is to be positive-ish". It is a smooth ReLU that lets small negative values through slightly. Its minimum is about −0.170, at x ≈ −0.752. It was used by BERT and the GPT-2/GPT-3 family. A common fast form is the tanh approximation 0.5x(1 + tanh(√(2/π)(x + 0.044715x3))).
  • SiLU (sigmoid linear unit, also called Swish with β = 1) gates x by its own sigmoid. The name SiLU first appeared in the GELU paper; Elfwing et al. (2017) and Ramachandran et al. (2017, "Swish") studied it further. Its minimum is about −0.278, at x ≈ −1.278. Llama uses SiLU (its config says "hidden_act": "silu").

Why did the smooth versions win? Mostly because they trained a little better in experiments. The usual explanation is that a smooth curve with nonzero slope for slightly negative inputs gives the optimizer useful signal everywhere. That story is plausible but was found empirically, not proven.

Low-level: what an activation costs

ReLU is one max instruction. SiLU needs an exponential, an add, a reciprocal and a multiply. On NVIDIA GPUs the exponential runs on special function units through a hardware approximate base-2 exponential, so it costs about as much as a few multiplies. Either way the arithmetic is trivial: a few FLOPs per element against 2 bytes read and 2 written in BF16. Activations are memory-bound. Run as a separate kernel, they cost a full round trip through GPU memory. That is why they are almost always fused into a neighbouring kernel (see the last section).

The MLP and gated units (SwiGLU)

The classic MLP: up, activate, down

The MLP (multi-layer perceptron, also called the feed-forward network or FFN) is the workhorse that sits in every transformer block next to attention. The classic version is two linear layers with an activation between them:

MLP(x) = Wdown · φ(Wup · x)     d → dff → d Wup ∈ ℝdff×d projects up to a wider hidden size dff (classically 4d). φ acts on each of the dff numbers. Wdown ∈ ℝd×dff projects back to d.

Why go wider? Each hidden unit is one feature detector: row j of Wup is the direction it looks for. φ decides how strongly the unit fires. Column j of Wdown is the vector it writes back if it fires. More hidden units means more detectors per token. Chapter 6 develops this "detector → written vector" view into the FFN-as-key–value-memory picture. One thing to note now: the MLP processes each token independently. The same weights are applied to every position, and no information flows between tokens here. Mixing across tokens is attention's job (Chapter 5).

Gated linear units

A gated linear unit (GLU; Dauphin et al., 2016) computes two projections of the same input. One goes through a sigmoid and acts as a gate; the gate then multiplies the other projection element by element:

GLU(x) = σ(Wx) ⊙ (Vx)      SwiGLU(x) = SiLU(Wx) ⊙ (Vx) ⊙ is elementwise multiplication (the Hadamard product): element j of the result is gatej × valuej. Shazeer (2020, "GLU Variants Improve Transformer") tried other gate functions: ReGLU (ReLU), GEGLU (GELU) and SwiGLU (Swish/SiLU). Biases are omitted, as in Llama.

The gate makes the layer multiplicative: each hidden unit's output is the product of two linear functions of the input. That is a soft "if": the gate decides how much of each value passes through. Shazeer found that GLU variants, SwiGLU and GEGLU in particular, predicted text better (lower loss) than ReLU or GELU MLPs at equal parameter count. His paper honestly says it offers no explanation and attributes the success "to divine benevolence". Llama's MLP is exactly this:

FFN(x) = Wdown · ( SiLU(Wgate x) ⊙ Wup x ) Llama 3.1 8B: Wgate, Wup ∈ ℝ14336×4096, Wdown ∈ ℝ4096×14336. In Hugging Face code: down_proj(act_fn(gate_proj(x)) * up_proj(x)).

Why 14,336?

A gated MLP has three matrices instead of two. To keep the parameter count equal to a classic 4d MLP, Shazeer shrank dff by a factor of 2/3: three matrices of width (2/3)·4d hold as many weights as two of width 4d. Llama 3 starts from the same rule, then scales the result up a little and rounds it to a multiple of 1,024, which gives 14,336 = 3.5d. Chapter 6 shows the exact arithmetic.

Low-level: what SwiGLU costs

Per token per layer, the MLP is 352 MFLOP of GEMM work but only about 86 KB of intermediate activations in BF16 (two 14,336-long vectors in, one out). With many tokens the three GEMMs are compute-bound and the SiLU-and-multiply step is memory-bound. So engines run gate and up as one merged GEMM and do the SiLU-and-multiply in one fused kernel (Chapter 6; the last section of this chapter puts numbers on the saving).

Softmax: from scores to probabilities

At the end of the network, the model produces one score for every entry in the vocabulary: 128,256 real numbers for Llama 3. These scores are called logits. They can be any size and any sign. What we need is a probability distribution: every value at least 0, all values summing to 1, and a bigger score giving a bigger probability. Softmax does exactly this:

softmax(z)i = eziΣj=1V ezj z = the logit vector (length V), ez = exp(z), always positive. The denominator is the same for every i: it is the normalizer that makes the outputs sum to 1.

Why the exponential? It makes everything positive, and it turns differences of logits into ratios of probabilities: pi / pj = ezi − zj. A logit gap of 1 means a factor of e ≈ 2.72. A gap of 2.3 means about 10×.

Worked example (illustrative logits for continuations of "The cat sat on the", over just five candidates): ␣mat 4.0, ␣floor 3.2, ␣bed 2.5, ␣couch 2.1, ␣roof 0.5. Subtract the largest (4.0) to get 0, −0.8, −1.5, −1.9, −3.5. Exponentiate to get 1, 0.449, 0.223, 0.150, 0.030, which sum to 1.852. Divide by that sum to get probabilities 0.540, 0.243, 0.120, 0.081, 0.016. (The first step is explained just below.)

Four properties matter later:

  1. Shift invariance. Adding the same constant c to every logit changes nothing, because ec cancels between top and bottom. Only differences between logits matter.
  2. Order is preserved. The largest logit always gets the largest probability.
  3. Scale matters. Doubling every logit doubles every gap, so the distribution gets sharper. Halving them flattens it. Dividing logits by a number T before softmax is exactly temperature, the subject of Chapter 14.
  4. It is a "soft" argmax. With big gaps it is nearly one-hot (all mass on the top entry). Unlike argmax it is smooth, so training can push on it. That is why it also produces attention weights (Chapter 5) and MoE router weights (Chapter 7).

Numerical stability: subtract the max

The textbook formula is a trap in floating point, because ez overflows quickly:

FormatLargest finite valueexp(z) overflows when z >
FP1665,50411.09
BF16≈ 3.39 × 103888.72
FP32≈ 3.40 × 103888.72
FP64 (JavaScript numbers)≈ 1.80 × 10308709.78

Once one term is ∞, the sum is ∞ and ∞/∞ = NaN. The opposite failure happens too: if every logit is very negative (say −1,000), every ez rounds to 0 and you compute 0/0 = NaN. The fix uses shift invariance. Subtract the maximum logit m before exponentiating:

softmax(z)i = ezi − mΣj ezj − m,    m = maxj zj Every exponent is now ≤ 0, so every term lies in (0, 1] and nothing can overflow. The largest term is exactly e0 = 1, so the denominator is between 1 and V and can never be 0. The price is one extra pass over the data to find m.

Log-softmax and log-sum-exp

Training needs the logarithm of a probability (next section). Computing softmax and then taking the log is fragile: a tiny probability such as e−200 underflows to 0 in FP32 (the smallest FP32 number is about e−103), and log(0) = −∞. Instead, take the log of the formula by hand:

log pi = zi − LSE(z),     LSE(z) = log Σj ezj = m + log Σj ezj − m LSE ("log-sum-exp") is computed with the same max trick. Worked example: LSE = 4.0 + ln 1.852 = 4.616, so log p(␣mat) = 4.0 − 4.616 = −0.616, and e−0.616 = 0.540 as before. A logit 200 below the others simply gives log p ≈ −200, with no underflow.

What softmax costs

The FLOPs are negligible: about 5 per element (compare, subtract, exp, add, divide), or about 0.6 MFLOP for a 128,256-entry row. Compare that with ≈ 16 GFLOP for the whole forward pass of one token. The cost is data movement and synchronization. A straightforward GPU kernel makes three passes over the row. Each pass is a reduction or depends on one: many threads each combine their own slice, then combine across the warp with shuffle instructions, then across warps through shared memory.

Memory becomes a real problem in training. There the model computes logits for every position of every sequence at once. For a single 8,192-token sequence the logits tensor is 8,192 × 128,256 × 4 B ≈ 4.2 GB in FP32. Training frameworks therefore use fused cross-entropy kernels that compute the loss chunk by chunk and never materialize the full probability tensor (Chapter 8).

Common misconception

"Softmax probabilities are the model's confidence that its answer is true." They are the model's predicted distribution for the next token, nothing more. Whether a 0.54 really comes true 54% of the time (whether the model is calibrated) depends on how it was trained, and it says nothing about whether a multi-token answer is factually correct.

Logits and cross-entropy

Where do logits come from? The last layer of the model, the LM head, is one more linear layer, Whead ∈ ℝ128256×4096. Logit i is the dot product of the final hidden vector h with row i of Whead. In words: how much does the model's final state point toward token i's direction? That single matrix holds 525,336,576 parameters. Its place in the full architecture, and whether it shares weights with the input embedding, is covered in Chapter 6.

To train, we need one number that says how wrong a prediction was. The training text tells us what the next token actually was (say ␣mat). The cross-entropy loss for that position is

L = −log pcorrect = LSE(z) − zcorrect pcorrect = the probability the model gave the token that really came next. The second form computes the same value straight from the logits, using the stable log-sum-exp. log is the natural log, so the unit is nats (Primer 4 derives cross-entropy and its units); divide by ln 2 for bits. With p(␣mat) = 0.540: L = 0.616 nats = 0.889 bits.

Read it as surprise. If the model gave the right answer probability 1, the loss is 0. As that probability heads toward 0, the loss climbs without limit. A model that knows nothing spreads probability evenly over all 128,256 tokens, so its loss is ln 128,256 ≈ 11.76. That is roughly where an untrained Llama 3 starts. The training loss is this number averaged over every position of every training sequence. Chapter 8 turns it into perplexity.

What "learning" means, in one paragraph

The loss is a function of every weight in the model: 8.03 billion inputs, one output. The gradient is a vector with one entry per weight. Each entry says how fast the loss would change if you nudged that weight up a tiny bit. Training repeats one move: compute the loss on a batch of text, compute the gradient, and step every weight a small amount in the direction that lowers the loss, w ← w − η·g, where η is the learning rate. The algorithm that computes all 8 billion entries in one backward sweep is backpropagation; that sweep costs about twice the forward pass. For softmax plus cross-entropy the gradient with respect to the logits is very simple: p − onehot(correct). The correct token's logit is pushed up by 1 − pcorrect (0.46 for ␣mat), and every other logit is pushed down by its own probability. Everything else about training (backprop, optimizers, schedules, scale) is Chapter 8. Primer 1 (gradient descent, learning rate) and Primer 3 (how the gradient is computed) take this slowly.

Normalization: LayerNorm and RMSNorm

As a vector moves up through 32 layers, each layer adds something to it (next section). Its size drifts: some coordinates grow large, others shrink. Downstream operations care about scale. Softmax gets too sharp or too flat, and SiLU behaves very differently at 0.1 and at 100. In training this shows up as loss spikes and NaNs. We want every sublayer to see its input at a consistent size.

The idea is automatic gain control, as in a radio: before using a vector, rescale it to a standard size. Then multiply by a learned per-dimension gain, so the model can still choose whatever scale it wants for each coordinate. This is done per token, across that token's d numbers. Tokens never share statistics with each other.

LayerNorm(x) = x − μ√(σ2 + ε) ⊙ γ + β       RMSNorm(x) = x√(mean(x2) + ε) ⊙ γ μ = mean of the d entries, σ2 = their variance, mean(x2) = mean of the squared entries (the square root of it is the root mean square, RMS). ε is a tiny constant (Llama: 10−5) that prevents division by zero. γ (gain) and β (bias) are learned vectors of length d.

LayerNorm (Ba, Kiros & Hinton, 2016) re-centres the vector to mean 0 and rescales it to variance 1. RMSNorm (Zhang & Sennrich, 2019) skips the centring and the β. It only divides by the RMS. The authors' hypothesis was that re-centring is unnecessary and rescaling does the useful work. Quality turned out comparable, and RMSNorm is simpler and cheaper. Llama and most recent open models use it.

Worked example. x = [3, 5, 4, 7, 2, 6, 4, 9]. Mean μ = 5 and variance σ2 = 4.5, so σ = 2.12. LayerNorm gives [−0.94, 0, −0.47, 0.94, −1.41, 0.47, −0.47, 1.89], which has mean 0 and variance 1. The mean of squares is 236/8 = 29.5, so RMS = 5.43. RMSNorm gives [0.55, 0.92, 0.74, 1.29, 0.37, 1.10, 0.74, 1.66], which has RMS 1 but a mean of 0.92, not 0.

Low-level: RMSNorm in Llama

Llama 3.1 8B has 65 RMSNorms: two per block plus one final norm. That is 65 × 4,096 = 266,240 parameters, about 0.003% of the model. The Hugging Face implementation upcasts the vector to FP32, computes mean(x²), multiplies by rsqrt(mean + 1e-5), casts back to BF16 and multiplies by γ. A GPU kernel usually gives each token row to one thread block: one sum-of-squares reduction (the same tree as Figure 4.10), then one elementwise pass. Per token it reads 8 KB and writes 8 KB for about 16 K FLOPs, which is firmly memory-bound. Engines fuse it with the residual add that comes right before it; vLLM's kernel is called fused_add_rms_norm. Where the norms sit inside a block ("pre-norm") is covered in Chapter 6.

Residual connections

Deep stacks are hard to train. A signal that passes through 32 transformations in series is multiplied by each layer's "gain". If each layer shrinks it slightly, say by 0.9, then after 32 layers only 0.932 ≈ 0.034 of it is left. If each grows it by 1.1, it becomes 1.132 ≈ 21×. Gradients flowing backward during training compound the same way, so they vanish or explode. He et al. (2015, ResNet) observed that simply adding more plain layers made networks worse even on their training data. Their fix is used in every LLM:

out = x + f(x) x = the layer's input, f = the layer's computation (for example norm → MLP). The layer learns a correction to add, not a replacement. Example: x = [1.0, −0.5, 2.0] and f(x) = [0.1, 0.3, −0.2] give [1.1, −0.2, 1.8].

Two things follow. First, if f outputs about zero, the layer is just the identity, so adding a layer can hardly hurt. Second, the derivative of the output with respect to the input is I + ∂f/∂x. The identity term I is a direct path that carries the signal forward, and the gradient backward, through any number of layers without decay (Primer 3 shows how gradients vanish or explode otherwise).

Systems analogy

A residual connection is state += delta instead of state = transform(state): each layer writes a correction, never a replacement. Chapter 6 builds the "residual stream" picture of the whole transformer on this idea. The add itself is the cheapest operation in the model: 4,096 additions per token, reading two vectors and writing one, and engines fuse it into the RMSNorm that follows (previous section).

The compute profile: where the time goes

You now know every operation class in an LLM except attention, which Chapter 5 builds from these same parts. For performance, they fall into three classes:

ClassExamplesFLOPs per byteLimited by
Matmul (GEMM / GEMV)all linear layers: Q, K, V, O, gate, up, down, LM head; attention's score and weighted-sum products≈ n (tokens per weight load)compute when n is large; memory at n = 1
ElementwiseSiLU, ⊙, residual add, scaling, dtype casts, applying rotary position encoding≈ 0.2–1memory bandwidth
Reductionssoftmax, RMSNorm, top-k/argmax when sampling≈ 0.3–1memory bandwidth + synchronization

In FLOPs, matmuls are everything. For Llama 3.1 8B they are ≈ 16 GFLOP per token. All elementwise ops and reductions together are a few MFLOP, well under 0.1%. But FLOPs are not time. A memory-bound op runs at the speed of memory, and a GPU can do about 295 BF16 FLOPs in the time it takes to move one byte from HBM (the H100 ridge point from Chapter 2). Every separate elementwise kernel reads its inputs from HBM and writes its output back, even though the math takes almost no time. Every kernel launch also costs a few microseconds of overhead.

The cure is kernel fusion: do several consecutive memory-bound steps inside one kernel, keeping intermediate values in registers or shared memory instead of round-tripping through HBM. Figure 4.14 puts numbers on it for Llama's SwiGLU at prefill.

This pattern sets the agenda for the systems chapters. Prefill is dominated by big GEMMs and is compute-bound. Decode does one token per sequence, so its GEMMs become GEMVs and the whole step is memory-bound (Chapter 11). Serving engines win by fusing kernels, capturing whole decode steps as CUDA Graphs to remove launch overhead, and using FlashAttention, which fuses attention's matmuls and softmax into one kernel (Chapter 15).

Key takeaway

An LLM is dot products organized into matrix multiplies, with cheap elementwise and reduction glue: nonlinearities, gates, softmax, norms and residual adds. The matmuls hold the parameters and nearly all the FLOPs. The glue holds almost no FLOPs but can eat real time unless it is fused. With these parts you can read every formula in the rest of the blog. Next, Chapter 5 uses dot products and softmax to let tokens talk to each other.

Hints (open only when stuck)
  • Stable reductions. Use z.amax(dim, keepdim=True) and keep the reduced dimension so broadcasting lines up. Cross-entropy is logsumexp(z) minus the target logit picked with gather; never take the log of a softmax.
  • Linear on 3-D input. Flatten [B, T, d] to [B·T, d] before forming the weight gradient dYTX; the input gradient is dYW.
  • Activation derivatives. SiLU′(x) = σ(x)(1 + x(1 − σ(x))). GELU′(x) = Φ(x) + x·φ(x), with φ the standard normal density.
  • Norm backward. With r = 1/√(mean(x2) + ε), x̂ = x·r and g = dy ⊙ γ: dx = r·(g − x̂·mean(g ⊙ x̂)), and dγ is the sum over tokens of dy ⊙ x̂. LayerNorm adds a −mean(g) term, with x̂ built from the centred x.
  • gradcheck fails? Use float64 and shapes around 4 × 16, and pass ε as a Python float whose gradient is None. In FP32 it fails even on correct code.
  • Loss off by a lot? Logits at position t predict token t + 1, so compare logits[:, :-1] with ids[:, 1:]. Hugging Face computes the logits in BF16 and upcasts them to FP32 before the loss; do the same.
  • FP32 MLP mismatch? .float() converts a module in place, so deep-copy the MLP first. Leave TF32 off for matmuls (the PyTorch default), or your "FP32" matmuls round their inputs to a 10-bit mantissa.
  • Bandwidth too good to be true? An H100 has 50 MB of L2 cache. Repeated runs on smaller tensors are served from cache, not HBM, so rotate several input buffers. Exclude the first torch.compile call, which is the compile itself.
  • Custom Functions and mixed precision. Decorate forward and backward with torch.amp.custom_fwd(device_type="cuda") and torch.amp.custom_bwd(device_type="cuda"), or just train in FP32 with TF32 matmuls switched on; the model is small.
  • Windows for the MLP LM. ids.unfold(1, k, 1) turns [B, T] into [B, T − k + 1, k]. Embed, reshape to [B, T − k + 1, k·d_emb], and make the target of each window the token right after it.
  • Step-0 loss derivation. At initialization each logit is a zero-mean Gaussian independent of the target, so the target logit averages 0, and LSE ≈ ln(V·E[ez]), where E[ez] = eσ²/2 for a Gaussian.
  • The no-norm residual stack diverges? That is a result, not a bug: Part A predicted it. Record it, then rerun at a quarter of the learning rate for a fair comparison.
