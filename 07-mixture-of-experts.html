Part II · Chapter 7

Mixture of Experts

How a model can store a trillion parameters but spend only about 32 billion of them on each token, and what that trick does to memory, bandwidth, training, and serving.

In this chapter
  • An MoE layer replaces the single feed-forward network (FFN) with E smaller FFNs called experts, plus a tiny router that picks k of them for each token. Attention stays dense.
  • Total parameters decide how much memory you need. Active parameters decide the FLOPs per token. Mixtral 8x7B: 46.7B total, 12.9B active. DeepSeek-V3: 671B total, 37B active. We derive both numbers from the configs.
  • Left alone, routing collapses onto a few experts. Balancing losses, router z-loss, capacity limits, and DeepSeek's bias trick keep the load even.
  • Across GPUs, each MoE layer does two all-to-all exchanges (dispatch and combine). Inside a GPU, tokens are sorted by expert and run through one grouped GEMM.
  • At batch 1 a decode step reads only the chosen experts, so MoE models run fast on machines with lots of slow memory. At large batch almost every expert is touched, so MoE needs big batches and expert parallelism to pay off. A calculator lets you see both regimes.

Why mixture of experts?

In a dense model, every parameter takes part in every token. Llama 3.1 8B uses all 8.03 billion weights for each token it reads or writes, so one forward pass costs about 2N ≈ 16 GFLOP per token (derived in Chapter 6). To make the model know more, you add parameters, and the cost of every token rises with them: in training (≈ 6·N·D FLOPs, Chapter 8) and in every request after that.

But one token does not need everything the model knows. When the model processes ␣sat in "The cat sat on the", whatever it stored about tax law, Rust lifetimes, or Portuguese verbs does not help. A dense model multiplies all of it in anyway, every time.

Mixture of Experts (MoE) breaks that link. Take the FFN, the per-token MLP that holds 70–80% of a dense model's weights (Chapter 6). Keep many independent copies of it, call each copy an expert, and add a small router that decides which few experts each token visits. Total parameters grow with the number of experts E. Compute per token grows only with the number of experts each token uses, k. This is called conditional computation: which weights run depends on the input.

Intuition: a sharded key-value store with a learned router

Chapter 6 described the FFN as a big key-value memory. A dense FFN is one giant node that every request scans from end to end. An MoE layer is a cluster of E shards with a front-end router that sends each request to k shards. Capacity grows with the number of shards; the work per request does not. The twist is that the routing function is not a fixed hash. It is learned together with the shards, and both keep changing during training.

A note on the name

You will sometimes hear "model of experts". The standard name is Mixture of Experts, abbreviated MoE. Also, the "experts" are not experts in any human sense. Nobody assigns them topics. Each one is just an FFN block, and the specialization that emerges in training is mostly about token type and syntax, not subject matter (we look at the evidence below).

The idea is old. Jacobs, Jordan, Nowlan and Hinton described "adaptive mixtures of local experts" in 1991. The modern version starts with Shazeer et al. (2017), who put a sparsely-gated MoE layer with thousands of experts between LSTM layers (an older, recurrent kind of network) and reported more than 1000× gains in capacity with minor losses in computational efficiency. GShard (2020) brought top-2 MoE into Transformers and trained a 600B-parameter translation model. Switch Transformer (2021) simplified routing to a single expert per token and reached about 1.6 trillion parameters. Mixtral 8x7B (December 2023) made MoE mainstream for open models, and DeepSeek's fine-grained designs (2024) set the template most large open models follow in 2025–2026.

Key takeaway

MoE separates capacity (total parameters, which cost memory) from per-token compute (active parameters, which cost FLOPs and, at small batch, memory bandwidth). Almost everything else in this chapter is about the side effects of that separation.

Anatomy of an MoE layer

An MoE layer is a drop-in replacement for the FFN inside a Transformer block. With the pre-norm block from Chapter 6:

h = x + Attn(RMSNorm(x))  out = h + MoE(RMSNorm(h)) Attention, both norms, the embeddings and the LM head are unchanged and dense. Only the FFN slot becomes an MoE.

Inside the MoE, four things happen for each token. Call the normalized hidden state u (a vector of d numbers).

  1. Score. The router is a single linear layer with weights Wr of shape [E, d]. It produces one number per expert: the router logits z = Wru.
  2. Select. Keep the indices of the k largest logits (top-k).
  3. Weight. Turn the kept logits into gate weights g. Mixtral and gpt-oss use a softmax over just the k kept logits, so the gates sum to 1.
  4. Run and mix. Run the token through each chosen expert, an ordinary SwiGLU FFN with its own weights (Chapter 6), and add up the outputs scaled by their gates.
MoE(u) = ∑i ∈ TopK(z, k) gi · FFNi(u),  z = Wru,  g = softmax(zTopK) u ∈ ℝd: the token's hidden state after RMSNorm. Wr ∈ ℝE×d: router weights. z ∈ ℝE: router logits. TopK(z, k): the indices of the k largest logits. gi: gate weight of expert i. FFNi(u) = Wdown(i)(SiLU(Wgate(i)u) ⊙ Wup(i)u).

Worked example. Suppose the router gives the token "The" logits whose two largest entries are z3 = 1.9 and z6 = 1.2 (illustrative). Then g3 = e1.9 / (e1.9 + e1.2) = 1 / (1 + e−0.7) = 0.668 and g6 = 0.332. The output is 0.668·FFN3(u) + 0.332·FFN6(u). The other six experts do nothing for this token.

The router is tiny. In Mixtral it has 4,096 × 8 = 32,768 weights per layer and costs 2·d·E = 65,536 FLOPs per token per layer. The two experts it selects cost 2 × 2 × 176,160,768 ≈ 705 MFLOPs. The router is about 0.01% of the work.

The shapes, for a batch of tokens

Real systems route many tokens at once. With T tokens in the batch:

TensorShapeMixtral, T = 5 (Figure 7.2)
normalized hidden states U[T, d][5, 4096]
router logits Z = U·WrT[T, E][5, 8]
top-k expert ids (int32)[T, k][5, 2]
gate weights[T, k][5, 2]
rows gathered for expert e[T_e, d], ΣT_e = T·kExpert 3: [3, 4096]
expert hidden (gate, up, SiLU, ⊙)[T_e, d_ff][3, 14336]
expert output[T_e, d][3, 4096]
combined output Y[T, d][5, 4096]

A reference implementation, in numpy-style pseudocode, makes the data movement explicit. It is correct but slow; we fix the speed later.

def moe_layer(U, W_r, experts, k):          # U: [T, d]
    Z    = U @ W_r.T                         # [T, E]  router logits
    top  = argtopk(Z, k, axis=1)            # [T, k]  chosen expert ids
    G    = softmax(take(Z, top, axis=1))     # [T, k]  gates (Mixtral style)
    Y    = zeros_like(U)                     # [T, d]
    for e, (Wg, Wu, Wd) in enumerate(experts):
        rows, slot = where(top == e)         # tokens that chose e, and in which top-k slot
        if len(rows) == 0: continue          # idle expert: no FLOPs, no weight reads
        X = U[rows]                          # gather      [T_e, d]
        H = silu(X @ Wg.T) * (X @ Wu.T)      # SwiGLU      [T_e, d_ff]
        Y[rows] += G[rows, slot, None] * (H @ Wd.T)   # scatter-add [T_e, d]; rows are unique per expert
    return Y                                 # the block adds the residual: out = h + Y

Gating recipes: softmax, top-k, sigmoid

Models differ in how they turn logits into gates. Three recipes cover almost every model you will meet.

  • A. Softmax over all E, then top-k. Used by Switch Transformer, DeepSeek-V2 and Qwen3. The kept probabilities sum to less than 1. Qwen3 sets norm_topk_prob: true in its config, which divides them by their sum.
  • B. Top-k of the logits, then softmax over the k. Used by Mixtral and gpt-oss. Once A is renormalized, A and B give exactly the same gates: dividing softmax probabilities by their sum over the kept experts cancels the shared denominator. They differ in what else uses the full softmax (the balancing loss below).
  • C. Sigmoid per expert, then top-k, then normalize. Used by DeepSeek-V3, Kimi K2, GLM-5 and MiniMax-M2 (scoring_func: "sigmoid" in their configs). Each expert gets an independent score in (0, 1), with no shared denominator squeezing 256 scores toward 1/256. DeepSeek-V3 then multiplies the normalized gates by routed_scaling_factor = 2.5. DeepSeek-V4 moved to yet another score function ("sqrtsoftplus" in its config).
Why the gate weights are how the router learns

Picking the top k is a hard, discrete choice. Nudge a router weight slightly and the same experts are picked, so the choice itself has no gradient. The router learns only through the gate values that scale the expert outputs. If Expert 3's output helped lower the loss, the gradient flows back through g3 and raises z3. This is why Switch Transformer, with k = 1, scales the expert output by the full-softmax probability pi: a softmax over a single kept logit is always exactly 1, and the router would never learn. Shazeer et al. (2017) also added trainable Gaussian noise to the logits before top-k ("noisy top-k gating") to help exploration and balance.

Fine-grained experts, shared experts, and where MoE layers go

The problem with big experts. Mixtral's experts are full-size FFNs: each one is as large as Mistral 7B's FFN. With only 8 experts and top-2, there are just C(8, 2) = 28 possible pairs per layer. Each expert must cover a broad mix of patterns, and many experts end up learning the same common things (how to handle punctuation, frequent function words, and so on).

Fine-grained experts (DeepSeekMoE, 2024) split each expert into m smaller ones with 1/m of the hidden size, and activate m·k of them. Total parameters and FLOPs per token stay the same. What changes is the number of ways to combine experts. DeepSeekMoE's own example: 16 experts with top-2 give C(16, 2) = 120 combinations; splitting each into 4 gives 64 experts with top-8 and C(64, 8) = 4,426,165,368 combinations. More combinations let each token get a more precise mix.

Shared experts are experts that every token always uses, with no routing. They absorb the knowledge everybody needs, so the routed experts do not each have to relearn it. In DeepSeekMoE the shared experts come out of the same budget: some fine-grained experts are made "shared", and the number of routed experts per token drops by the same amount.

Modern experts are small. DeepSeek-V3's experts have a hidden size of 2,048 while the model width is d = 7,168. Qwen3-235B-A22B uses 1,536 with d = 4,096, and Qwen3.5-397B-A17B uses 1,024 with 512 experts. DeepSeek-V3 has a neat symmetry: 8 routed experts plus 1 shared expert give 9 × 2,048 = 18,432 active hidden units, exactly the intermediate_size of its 3 dense layers. Per token, an MoE layer does the same FFN work as a dense layer of the same model; it just chooses which 9 of 257 slices to use.

Where the MoE layers go also varies:

  • Every layer: Mixtral, Qwen3, gpt-oss.
  • Every other layer: GShard put MoE in every other FFN. Llama 4 Maverick alternates dense and MoE layers, and each MoE layer sends every token to one shared expert plus one of 128 routed experts.
  • Dense first, then MoE: DeepSeek-V3 keeps its first 3 layers dense (first_k_dense_replace: 3), Kimi K2 its first 1, GLM-5 its first 3.

Total vs active parameters: the accounting

Two numbers describe an MoE model:

  • Total parameters: everything stored in the weight files. This sets the memory you need.
  • Active parameters: the parameters one token's forward pass actually multiplies. This sets FLOPs per token (≈ 2 × active, by the same argument as Chapter 6).

Conventions differ on one detail: the input embedding table is a lookup, not a matmul, so some reports leave it out of "active". The gpt-oss model card says so explicitly: "Unembedding parameters are counted towards active, but not embeddings." Below we count both and note the difference.

Common misconception

"An MoE with 37B active parameters is as cheap to serve as a 37B dense model." It is as cheap per token in FLOPs. It is not as cheap in memory (all 671B must sit somewhere fast), and at large batch it is not as cheap in bandwidth either. The inference section below works out exactly when the "active" number is the right one to think about.

What do experts actually learn?

The name invites a picture of a biology expert, a law expert and a code expert. Measurements do not support it.

The Mixtral paper measured which experts the router picked on different parts of The Pile, a public training dataset (ArXiv, PubMed abstracts, PhilPapers, GitHub, and others). In their words: "we do not observe obvious patterns in the assignment of experts based on the topic." Expert usage on biology looked almost the same as on philosophy. Only DM Mathematics, a synthetic dataset, looked a bit different. What they did see was structure tied to syntax: the token self in Python and the word "Question" in English often went to the same expert, and indentation tokens in code were consistently assigned to the same experts, especially in the first and last layers.

They also found positional locality: consecutive tokens often pick the same expert. On ArXiv text, the next token had the same first-choice expert 14.0% of the time at layer 0, 27.9% at layer 15 and 22.7% at layer 31, against 12.5% for random assignment. This matters for systems: locality lets you cache experts, but it also means bursts of tokens can pile onto one expert and overload it.

Other studies agree on the big picture. The ST-MoE authors saw encoder experts specialize in groups of tokens or shallow concepts (for example punctuation or proper nouns), with weaker specialization in decoders. DeepSeek reports that a model balanced with their auxiliary-loss-free method (below) shows more domain-level specialization than one balanced with an auxiliary loss (Appendix C of the V3 report). So "experts" do specialize, but in ways that are statistical and mostly invisible to a human. You cannot remove the "biology expert" to shrink a model for code.

Training MoE: keeping every expert busy

The problem: routing collapse. At the start of training the router is random. Some expert happens to get slightly more tokens, so it gets more gradient updates, becomes slightly better, and the router learns to send it even more tokens. This rich-get-richer loop can end with a few experts doing all the work while the rest are dead weight that you still pay to store. It also hurts speed: with experts spread over GPUs, an overloaded expert makes its GPU the straggler that every other GPU waits for, and idle experts waste their GPU. Four tools fight this.

1. The load-balancing auxiliary loss

The standard fix, from Switch Transformer, adds a small extra term to the training loss that is smallest when the load is even:

Laux = α · E · ∑i=1E fi · Pi fi: the fraction of the batch's tokens actually sent to expert i (a hard count). Pi: the average router probability for expert i over the same tokens (softmax over all E). E: number of experts. α: a small weight; Switch used 0.01.

f comes from argmax decisions, so it has no gradient. P comes from a softmax, so it does. The product uses f as a fixed weight: the derivative with respect to Pi is α·E·fi, so the busiest expert's probability is pushed down hardest. Because probabilities sum to 1, the mass moves to the idle experts.

Worked example. E = 4, top-1. Measured loads f = [0.50, 0.25, 0.125, 0.125], average probabilities P = [0.40, 0.30, 0.15, 0.15]. Then ∑f·P = 0.200 + 0.075 + 0.019 + 0.019 = 0.3125. Times E = 4 gives 1.25, times α = 0.01 gives 0.0125. A perfectly even router has fi = Pi = 1/4, so ∑ = 4 × 1/16 = 0.25, times 4 = 1.0, times α = 0.01. The factor E makes the balanced value equal α for any number of experts. For top-k, f counts all k assignments; DeepSeek writes the same loss with the normalization folded into fi so that a balanced expert has fi = 1.

The weight is a real trade-off. Too small and experts collapse; too large and the router balances at the expense of routing well. Shipped configs show the range: Mixtral's router_aux_loss_coef is 0.02, Qwen3's is 0.001. Where you measure balance matters too: per sequence forces every document to use all experts evenly, which fights specialization. Qwen3 uses a "global-batch" balancing loss that measures f over the whole global batch, to encourage specialization.

2. Router z-loss

Large router logits cause trouble: exponentials of big numbers in low precision lose accuracy (BF16 stores only 7 mantissa bits, Chapter 2), and the routing becomes jumpy. ST-MoE added a penalty on the size of the logits:

Lz = 1T ∑t=1T ( log ∑j=1E ezt,j )2 zt,j: router logit of token t for expert j. The inner term is the log-sum-exp of the token's logits (about the size of its largest logit). T: tokens in the batch. ST-MoE weights it by cz = 0.001 in the total loss L = LCE + cBLB + czLz.

Example: logits [2.0, 1.0, 0.5, −1.0] have log-sum-exp 2.495, so the penalty is 2.4952 = 6.23. The same logits times 10 have log-sum-exp 20.00005 and penalty 400. Softmax does not change if you subtract a constant from all logits, so the model can shrink them at no cost to routing. Switch Transformer also kept the router computation in FP32 even when the rest ran in BF16 ("selective precision").

3. Capacity factor and token dropping

Early MoE systems (GShard and Switch on TPUs) needed static tensor shapes, and fixed-size buffers make the cross-device exchange simple. So each expert gets a fixed number of slots per batch, its capacity:

C = CF · T · kE T·k/E: slots per expert if the load were perfectly even. CF: the capacity factor, a safety margin. Switch Transformers worked well at CF = 1.0 to 1.25.

Tokens beyond an expert's capacity are dropped: they skip that expert, and since the MoE output for them is zero (or only the surviving expert's share, for k > 1), the residual connection carries their hidden state through unchanged. Slots that nobody fills are padding: computed and thrown away.

Modern GPU stacks mostly go dropless. MegaBlocks (2022) reformulated MoE as block-sparse matrix multiplication so that each expert can take any number of tokens, without dropping or padding. DeepSeek-V3 states that, thanks to its balancing, it "does not drop any tokens during training" and also drops none at inference. Dropping still matters to know about: it makes a token's output depend on what other tokens are in the batch, one of the sources of nondeterminism covered in Chapter 14.

4. Auxiliary-loss-free balancing (DeepSeek-V3)

Every auxiliary loss pulls the router away from what is best for the language-modelling loss. DeepSeek-V3 mostly replaced it with a feedback controller. Each expert gets a bias bi that is added to its score only when choosing the top-k:

selected = TopK( si,t + bi , k ),  gi,t = si,t∑j ∈ selected sj,t si,t = sigmoid(ut·ei): the affinity of token t for expert i (ei is a row of the router). bi: a balancing bias, not trained by gradient. The gate g uses the original s, not s + b.

After each training step, the system measures every expert's load over the whole batch. Overloaded experts get bi −= γ, underloaded ones bi += γ. DeepSeek-V3 used γ = 0.001 for the first 14.3T training tokens and 0 for the last 500B. A tiny sequence-wise auxiliary loss (α = 0.0001) remains only to prevent extreme imbalance inside a single sequence.

Intuition: a load balancer, not a fine

The auxiliary loss is like fining an application for causing hot spots: it changes the application's own goals. The bias is like a weighted load balancer in front of a server pool that lowers a backend's weight when its queue is long. It steers which expert gets a borderline token without changing how much that expert's output counts, so no gradient from the balancing mechanism interferes with learning.

What MoE costs and saves in training

Training FLOPs follow the active parameters: about 6 · Nactive · D (Chapter 8). For DeepSeek-V3 with 37B active and 14.8T tokens that is about 6 × 37e9 × 14.8e12 ≈ 3.3e24 FLOPs. A dense 671B model on the same data would need about 6.0e25, roughly 18× more. The report states 2.788M H800 GPU-hours for the full training. Memory, however, follows the total: weights, gradients and optimizer state exist for all 671B parameters, so they must be sharded across many GPUs (DeepSeek-V3 trained on 2,048 H800s with 16-way pipeline, 64-way expert and ZeRO-1 data parallelism; the general techniques are in Chapter 8). Each expert also sees only a slice of the tokens, roughly k/E of them, which is one reason MoE models need large training batches.

Expert parallelism: experts on different GPUs

The problem. DeepSeek-V3's weights are 671 GB even in FP8. No single GPU holds that. Experts are natural shards: they are independent, all the same shape, and each token needs only a few of them. Expert parallelism (EP) puts E/G experts on each of G GPUs. The dense parts (attention, norms, shared experts) are usually replicated or split with tensor parallelism, and each GPU runs attention for its own share of the tokens.

That creates a data-movement problem. After attention, token t sits on GPU 0, but its router may pick experts that live on GPUs 2 and 3. So every MoE layer runs this sequence:

  1. Route locally: every GPU computes top-k for its own tokens.
  2. Dispatch: an all-to-all exchange (the collective operation from Chapter 2) in which every GPU sends each token's hidden vector to the GPUs that own its experts, k copies per token.
  3. Compute: each GPU runs its local experts on whatever tokens arrived.
  4. Combine: a second all-to-all sends every expert output back to its token's home GPU.
  5. Weighted sum at home with the gate weights, then on to the next layer.

How many bytes move

Per token and per MoE layer, dispatch sends k copies of a d-dimensional vector, and combine returns k vectors. For DeepSeek-V3, which dispatches in FP8 and combines in BF16:

dispatch = k·d·1 B = 8 · 7168 = 57,344 B  combine = k·d·2 B = 114,688 B About 172 KB per token per MoE layer if every copy leaves the GPU (an upper bound; copies to local experts stay put). FP8 dispatch also sends small scale factors.

A training micro-batch of 4,096 tokens per GPU therefore pushes up to about 0.70 GB out of each GPU per MoE layer, forward only. At the 50 GB/s of one InfiniBand link that is about 14 ms; at the 160 GB/s of H800 NVLink, about 4.4 ms. The same layer's compute for 4,096 tokens is about 2 × 585M × 4,096 ≈ 4.8 TFLOP, a few milliseconds on an H800. Communication and compute are the same order of magnitude, so MoE training at scale lives or dies by overlapping them (DeepSeek's DualPipe schedule computes one micro-batch while another communicates).

Node-limited routing

Inside a node, GPUs talk over NVLink; between nodes, over InfiniBand, about 3.2× slower in DeepSeek's cluster (160 vs 50 GB/s). DeepSeek-V3 therefore limits each token to experts on at most M = 4 nodes. It picks the nodes first, ranking each node by the sum of the highest k/M = 2 affinity scores among its experts, then picks the top 8 experts inside those nodes. A token crosses InfiniBand once per destination node and is then forwarded over NVLink to the right GPUs. The configs encode the same idea as group-limited routing: n_group: 8, topk_group: 4 (256 experts in 8 groups; keep the best 4 groups). DeepSeek notes that a token selects 3.2 experts per node on average, and that this scheme could scale to 13 experts (4 nodes × 3.2) at the same communication cost. Only 20 of the H800's 132 SMs are reserved for communication.

Communication kernels and serving layouts

Generic all-to-all from a collective library is not ideal for MoE: message sizes depend on routing and are known only at run time. DeepSeek open-sourced DeepEP, a library of dispatch and combine kernels with two modes:

  • Normal kernels for training and prefill: high throughput, forwarding from NVLink to RDMA. DeepEP reports about 153 GB/s for dispatch within a node (EP8) and about 43–58 GB/s across nodes (EP16–64) on H800s, with 4,096 tokens, top-8, FP8 dispatch and BF16 combine.
  • Low-latency kernels for decode: pure RDMA, for small batches. With 128 tokens and top-8, dispatch takes 77 µs at EP8 and 194 µs at EP256; combine 114 µs and 360 µs.

Those latencies add up. At EP256, dispatch plus combine is about 554 µs per MoE layer, so roughly 32 ms per decode step across 58 layers if nothing overlaps. That is why production systems overlap the communication of one micro-batch with the compute of another.

In serving, EP gets very wide: DeepSeek spreads V3's decode over hundreds of GPUs with only one or two routed experts each, and duplicates the busiest experts on extra GPUs, the MoE version of replicating hot keys in a cache cluster. Those layouts, data-parallel attention and expert load balancing are Chapter 15's subject.

Inside one GPU: permute, grouped GEMM, unpermute

The problem. The reference code above loops over experts. On a GPU that means E separate small matrix multiplications per projection, each with its own kernel launch, many of them tiny or empty. Launch overhead dominates and most SMs sit idle.

The idea is the same as bucketing packets by destination port before processing: sort the work so that each expert's tokens are contiguous, then process all buckets in one pass.

  1. Route. Top-k produces a list of T·k (token, expert, gate) entries.
  2. Permute. Sort the entries by expert id. Because the keys are small integers, this is a counting sort: histogram the expert ids, take a prefix sum to get each expert's offset, then gather the hidden-state rows into one contiguous buffer of shape [T·k, d].
  3. Grouped GEMM. One kernel launch computes all experts at once. Each group is a matmul of the expert's me rows against that expert's weights. me varies per expert; N and K (the weight shapes) are fixed. Gate and up projections, SiLU and the elementwise product are typically fused, then a second grouped GEMM does the down projection.
  4. Unpermute. Scatter each output row back to its token's position, multiplied by its gate, and add. With expert parallelism this step merges into the combine.

DeepSeek's DeepGEMM library documents two layouts that map directly to the two inference phases. The "contiguous" layout concatenates each expert's tokens, with each segment padded to the GEMM block size; it is meant for training and prefill. The "masked" layout is for decode with CUDA Graphs (a recorded sequence of kernel launches that is replayed as a whole, Chapter 15), where the CPU does not know how many tokens each expert received: the kernel reads per-expert counts from GPU memory and computes only the valid rows. vLLM, SGLang and TensorRT-LLM all ship fused MoE kernels built on the same permute, grouped GEMM and unpermute pattern.

Low-level: why MoE needs far more tokens per step to be efficient

Take one expert projection with weights of shape [d, n] stored at b bytes per weight, applied to m tokens. It does 2·m·d·n FLOPs and must read d·n·b bytes of weights. Its arithmetic intensity is about 2m/b FLOPs per byte, which is just m in BF16. On an H100 the BF16 ridge point is about 295 FLOPs/byte (Chapter 2), so the expert becomes compute-bound only once it sees about 295 tokens per step. (FP8 halves the bytes but doubles the peak FLOPs, so the answer is the same.)

A dense FFN sees every token in the batch. An expert sees only about B·k/E of them. To give each expert about 295 tokens you need B ≈ 295·E/k: about 9,400 tokens per step for DeepSeek-V3 (E/k = 32), against about 295 for a dense model. At a decode batch of 128, each DeepSeek-V3 expert sees on average 128·8/256 = 4 tokens, an intensity of about 4 FLOPs/byte, some 75× below the ridge. This is the hardware reason MoE serving gathers huge global batches across many GPUs (Chapter 11 applies the same roofline reasoning to dense decode).

MoE at inference: memory, bandwidth and batch size

Decode generates one token per sequence per step and is limited by how many bytes of weights it must read from memory per step (Chapter 11 derives this). MoE changes that byte count in a way that depends strongly on the batch size. Three facts explain nearly all MoE inference behavior.

1. All experts must be resident

You do not know which experts a token needs until its router runs, and that happens layer by layer, mid-forward-pass. Fetching an expert on demand from host memory is far too slow. One DeepSeek-V3 expert is 44 MB in FP8. Over PCIe 5.0 at about 64 GB/s that takes 0.69 ms, and a token needs 8 × 58 = 464 expert visits per forward pass: about 0.32 s per token, even if everything else were free. So the full model must sit in memory the compute can read quickly. Memory capacity follows total parameters.

2. At batch 1, only the chosen experts are read

With one sequence, a decode step reads the always-used weights (attention, shared experts, dense layers, LM head, routers) plus k experts in each MoE layer, and nothing else. Bandwidth follows active parameters. This is why MoE models shine on machines with a lot of slow memory.

gpt-oss-120b on an NVIDIA DGX Spark (128 GB unified memory, 273 GB/s). Always-read weights, kept in BF16: attention 1.91 GB + LM head 1.16 GB + routers and norms ≈ 3.10 GB. Experts: 36 layers × 4 experts × 13.2 MB (24.9M weights at 4.25 bits) = 1.90 GB. Total ≈ 5.0 GB per token, so the bandwidth bound is 273 / 5.0 ≈ 55 tok/s. A dense 117B model at the same 4.25 bits would read 62 GB per token: about 4.4 tok/s. Same memory footprint, about 12× faster decode.

DeepSeek-V3 on a Mac Studio M3 Ultra (512 GB, 819 GB/s), quantized to about 4.5 bits per weight (illustrative, a typical 4-bit GGUF): the weights take 671B × 4.5 / 8 ≈ 377 GB, which fits. Each token reads 36.6B active weights × 4.5 / 8 ≈ 20.6 GB, so the bound is about 40 tok/s. Real throughput is lower because of compute, KV-cache reads and overheads, but it is the reason a 671B model is usable on a desktop at all.

3. Expert offload to CPU RAM (llama.cpp)

On a PC with a 24 GB GPU and 128 GB of DDR5, gpt-oss-120b (about 65 GB, or 60.8 GiB) does not fit in VRAM. The trick is to split by access pattern: put what every token reads (attention, LM head, KV cache) on the GPU, and put the routed experts, which are big in total but sparsely read, in system RAM, where the CPU runs them. llama.cpp supports this directly:

# all non-expert weights on the GPU (-ngl 99), all routed-expert weights in system RAM
llama-server -m gpt-oss-120b-mxfp4.gguf -ngl 99 --cpu-moe

# keep the experts of the first N layers in RAM, the rest on the GPU (tune N to fill VRAM)
llama-server -m gpt-oss-120b-mxfp4.gguf -ngl 99 --n-cpu-moe 26

# the general mechanism: put tensors whose names match a regex in CPU buffers
llama-server -m model.gguf -ngl 99 -ot "\.ffn_.*_exps\.=CPU"

The expert tensors in a GGUF file are named like blk.12.ffn_up_exps.weight, which is what the regex matches. -cmoe/--cpu-moe and -ncmoe/--n-cpu-moe N are shortcuts for such patterns. Recent builds also list a --moe-cache-mib option that keeps a GPU-side cache of CPU-resident experts, which exploits the routing locality we saw earlier.

With --n-cpu-moe 26, the experts of 10 layers move to the GPU (10 × 1.69 GB ≈ 17 GB, which fits next to the 4.3 GB of non-expert weights plus KV cache). The CPU then reads 26 × 4 × 13.2 MB ≈ 1.37 GB per token (about 17 ms) and the GPU about 3.6 GB (about 3.6 ms), so the bound rises to roughly 48 tok/s. These are upper bounds from bandwidth alone; measured speeds are lower.

4. At large batch, almost every expert gets touched

Now serve many sequences at once. Each of the B tokens in a decode step picks its own k experts. A dense model reads its weights once per step no matter how big B is; that sharing is what makes batching cheap. In an MoE, the step must read every expert that any token in the batch picked. How many is that?

Assume, as a simplification, that each token picks k distinct experts uniformly at random, independently of the other tokens. For one token, the chance that a given expert is not picked is 1 − k/E. For B independent tokens it is (1 − k/E)B. So:

expected experts touched per layer = E · ( 1 − (1 − k/E)B ) ≈ E · ( 1 − e−Bk/E ) E: routed experts per layer. k: experts per token. B: tokens in the step (in decode, one per sequence). The approximation holds for small k/E; it shows the curve depends mostly on B·k/E.

Worked numbers, DeepSeek-V3 (E = 256, k = 8, so 1 − k/E = 0.96875): at B = 1, 8 experts. At B = 32: 256 × (1 − 0.9687532) = 256 × (1 − 0.362) ≈ 163 experts, 64%. At B = 128: 256 × (1 − 0.0172) ≈ 252, 98%. Mixtral (k/E = 1/4) is at 90% by B = 8. Any prefill of a few hundred tokens touches essentially every expert.

What this means:

  • Bytes per step climb toward the whole model. DeepSeek-V3 in FP8 reads 36.6 GB per step at B = 1 but about 584 GB at B = 64. Per generated token that is 9.1 GB, while a dense 37B model at B = 64 would read about 0.6 GB per token.
  • Batching still helps, but later. Once all experts are touched, bytes per step stop growing, and each extra token rides along almost free, as in a dense model. MoE needs about E/k times more tokens per step than a dense model to reach the same weight reuse, the same factor as in the intensity argument above.
  • Real routing is not uniform. Skewed routing touches fewer unique experts than the formula predicts, but the hot experts get more tokens than average and become stragglers. Redundant experts and balancing exist for this reason.
  • Side effects. Speculative decoding verifies several draft tokens per step (Chapter 15); for a dense model the extra tokens are nearly free, but in an MoE each extra token can pull in new experts. And because a token's experts can flip on tiny numerical differences, routing is one reason temperature-0 outputs can vary between runs (Chapter 14).

Two trends stand out. Experts got more numerous and smaller (8 → 128 → 256 → 384–512), and the active fraction fell from about a quarter to 3–5%. A rough rule of thumb, folklore rather than law: an MoE tends to perform like a dense model somewhere between its active and its total size. People sometimes quote the geometric mean, which for Mixtral is √(12.9 × 46.7) ≈ 25B. Take it as a hint, not a measurement.

Key takeaways
  • An MoE layer is router → top-k → gates → k expert FFNs → weighted sum. Everything else in the Transformer stays dense.
  • Memory follows total parameters; FLOPs per token follow active parameters. Mixtral: 46.7B / 12.9B. DeepSeek-V3: 671B / 37B, with 9 × 2,048 active expert width per layer.
  • Routing must be kept balanced: auxiliary loss α·E·∑fiPi, router z-loss, capacity limits (or dropless kernels), and DeepSeek's selection-only bias.
  • At scale, experts are spread over GPUs: dispatch and combine all-to-alls every layer, grouped GEMMs inside each GPU.
  • Bytes per decode step = always-read weights + (touched experts) × (expert size), with touched ≈ E(1 − (1 − k/E)B). Small B: MoE is cheap to read. Large B: it reads nearly everything, so it needs very large batches.
