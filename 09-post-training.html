Post-Training & Fine-Tuning

Pretraining produces a model that continues documents. Post-training turns it into an assistant that answers, stops, calls tools and refuses. This chapter shows what those extra training stages optimize, token by token, and how you can fine-tune a model yourself on one GPU.

From document completer to assistant

Chapter 8 ended with a base model: a set of weights that predict the next token of internet-like text. Give it a question and it does whatever text on the web would most likely do next. That is not always "answer the question".

We tested this directly. We ran Llama 3.1 8B (base) and Llama 3.1 8B Instruct on the same three requests, using our own numpy implementation of the forward pass on the real BF16 weights and greedy decoding (always take the most likely token; see Chapter 14). The base model received the raw text after <|begin_of_text|>. The Instruct model received the same text wrapped in its chat template (Chapter 3).

The base model is not broken. A web page that says "What is the capital of France? Paris" and then a link is plausible text. So is a homework sheet that follows "Write a haiku" with grading rules, and an FAQ that restates its own question. The base model has no idea that someone is talking to it, that a question deserves an answer, or that an answer should end.

The Instruct model has the same architecture, the same tokenizer and the same 8,030,261,248 parameters. It started from these exact base weights. The only difference is a few more training stages on carefully chosen token sequences. That is post-training: everything done to the weights after pretraining.

Mechanically, nothing about the function changes. The model still maps a token sequence to a probability distribution over the next token (Chapter 1). What changes is where the probability mass goes in specific contexts. After the token pattern <|start_header_id|>assistant<|end_header_id|>↵↵, the Instruct model puts its mass on answer-shaped continuations: for the France question it gives "The" a probability of 0.9997, while the base model's top choice at the same position is "What" (0.10), the start of yet another question. After "Paris." the Instruct model puts 0.9991 on <|eot_id|>, the end-of-turn token that tells the inference engine to stop; the base model's favorite is " Paris" again (0.32). The base model never saw those tokens during pretraining. We checked the checkpoints: in the base model the embedding rows of <|start_header_id|>, <|end_header_id|> and <|eot_id|> are exactly zero. In Instruct they are non-zero (L2 norm 0.03–0.05; an ordinary token's row has a median norm of 0.69). Post-training literally taught the model what these tokens mean.

Intuition

Pretraining builds a huge library of "how text continues". Post-training does not add many books. It teaches the model which shelf to walk to when it sees a chat transcript, how to format what it finds, and when to stop talking. The LIMA paper made this point sharply: fine-tuning a 65B base model on just 1,000 carefully written examples already produced a usable assistant. Their "superficial alignment hypothesis" says knowledge comes from pretraining and post-training mostly selects behavior. That is roughly right for chat style. It is not the whole story for reasoning, where reinforcement learning adds real skill (Chapter 10).

The post-training pipeline

Modern post-training is a sequence of stages. Each one uses a different kind of data and a different loss, but all of them reuse the training machinery from Chapter 8: forward pass, loss, backward pass, AdamW update. Only the data and the loss change.

Post-training is cheap compared to pretraining, but it decides behavior. InstructGPT, the 2022 paper that defined this recipe, reports 4.9 petaflop/s-days for SFT and 60 for PPO on its 175B model, against 3,640 for pretraining GPT-3. Its 1.3B post-trained model was preferred by human raters over the 175B base GPT-3, a model 100× larger. DeepSeek-V3's post-training used about 5K GPU-hours against 2.664M for pretraining. Llama 3 ran its loop six times. Each round trained a reward model, generated 10–30 candidate answers per prompt and kept the one the reward model scored highest (rejection sampling), fine-tuned on the result, ran DPO, and averaged the weights of several runs.

Supervised fine-tuning (SFT)

The simplest way to make a model answer is to show it many conversations where an assistant answers well, and train on them with the same next-token loss as pretraining. This is supervised fine-tuning, or SFT (also called instruction tuning). "Supervised" means every training example comes with the exact output we want.

The data

SFT data is a list of conversations (system prompt, user and assistant turns, tool calls and results). Its sources have shifted from people to models:

  • Human demonstrations. InstructGPT used about 13K prompts, many answered by hired labelers. Expert answers take minutes to hours each, so this does not scale.
  • Converted datasets. FLAN (2021) rewrote more than 60 existing NLP datasets (translation, QA, sentiment) into natural-language instructions using templates.
  • Small and curated. LIMA (2023): 1,000 hand-picked examples; quality beats quantity.
  • Synthetic. Self-Instruct (2022) had GPT-3 expand 175 seed tasks into 52K instructions with answers, then trained GPT-3 on them. Today most SFT data is model-generated. In Llama 3, rejection sampling (above) supplies most answers, and specialized pipelines generate code, math, tool-use and long-context data. Their final SFT mix averages 4.7 turns and 846 tokens per example (536 of context, 310 in the final response).

Synthetic data needs aggressive cleaning. Llama 3's report lists rule-based filters for "excessive use of emojis or exclamation points" and overly apologetic phrases, plus model-based quality and difficulty scoring and semantic deduplication. The model will copy any tic that is common in its SFT data.

Loss masking: learn the answer, not the question

Each conversation is rendered with the chat template into one flat token sequence (Chapter 3) and fed through the model exactly as in pretraining: one forward pass gives a next-token prediction at every position (Chapter 8). The difference is which predictions count. We want the model to learn to produce assistant turns. We do not want it to learn to produce user messages, system prompts or tool schemas: those are given at inference time, never generated. Training on them wastes capacity, teaches the model to imitate users, and lets boilerplate that repeats across many examples (the template's date lines, a long system prompt) dominate the loss.

So each position gets a mask bit mt: 1 if the token being predicted belongs to an assistant turn (including its closing <|eot_id|>), 0 otherwise. The loss averages only over unmasked positions:

L(θ) = − ∑t mt · log pθ(xt | x<t)∑t mt xt is the token at position t, x<t all tokens before it, pθ the model's probability with weights θ, mt ∈ {0, 1} the mask. The denominator counts trained tokens.

Low-level: how masking is implemented

Frameworks build a labels array next to input_ids: a copy of the token IDs with every masked position overwritten by the sentinel −100. The loss code shifts by one (the logits at position t are scored against labels[t+1]), and PyTorch's cross_entropy(..., ignore_index=-100) skips sentinel entries both in the sum and in the count. The forward pass still runs over all 50 positions: the prompt tokens must be processed to build the context that the answer attends to, and gradients flow back through them via attention. So SFT costs about 6N FLOPs per token for every token, trained or not. What masking can save is the LM head: some trainers compute logits only at labeled positions, which avoids most of the huge logits tensor (4.2 GB in FP32 for one 8,192-token row; Chapter 8).

Packing. Examples vary from 20 to 40,000 tokens, so trainers pack several into one row, as in pretraining (Chapter 8): the causal mask becomes block-diagonal and position IDs restart at 0 for each example. Variable-length attention kernels implement this without materializing a mask: they take an array of cumulative sequence offsets (cu_seqlens) and run each segment as its own causal attention.

Cost and hyperparameters

SFT is small. Take one million examples at Llama 3's average of 846 tokens: 0.85 B tokens. For an 8B model, training compute ≈ 6 · N · D = 6 × 8.03×109 × 0.85×109 ≈ 4.1×1019 FLOPs. An H100 at 40% utilization delivers about 4×1014 FLOP/s, so this is roughly 29 GPU-hours. Pretraining the same model on 15 T tokens is about 17,700× more. Learning rates are lower than in pretraining (Llama 3 used 10−5 for SFT, against a pretraining peak of 8×10−5 for the 405B) and runs last one to a few epochs, because the goal is to adjust a good model, not to rebuild it.

What SFT cannot do

SFT only imitates. It never sees a bad answer labeled as bad, so it cannot learn "this is worse than that". It trains on someone else's text, so it never practices recovering from its own mistakes. And writing perfect answers is expensive: for many tasks, people (and models) are much better at judging which of two answers is better than at writing the best one. That gap motivates preference learning.

Key takeaway

SFT is pretraining's next-token loss on curated conversations, with a mask that zeroes the loss on every token the assistant did not write. It teaches format, persona and when to stop, cheaply: tens of GPU-hours for an 8B model.

Learning from preferences: reward models and RLHF

"Good answer" has no formula. But people can compare two answers and say which is better, quickly and fairly consistently. Reinforcement learning from human feedback (RLHF) turns those comparisons into a training signal in two moves: first fit a model that predicts human preferences, then optimize the LLM to score well under that model.

Analogy

The reward model is a benchmark harness standing in for real users. You can optimize against it millions of times, but it is a proxy: tune hard enough and the code gets faster on the benchmark and slower in production. RLHF has exactly this failure mode, and much of its machinery exists to limit it.

Step 1: collect comparisons

Take a prompt, sample several answers from the SFT model, and ask a person to rank them. InstructGPT showed labelers K = 4 to 9 answers per prompt. A ranking of K answers yields K(K−1)/2 pairs, up to 36. Llama 3 sampled two answers from two different models, asked annotators how strong their preference was (four levels, from "marginally" to "significantly" better), and sometimes had them edit the winner to make a third, even better answer. Human agreement is far from perfect: InstructGPT's labelers agreed with each other 72.6% of the time.

Step 2: train a reward model

A reward model (RM) is a transformer that reads a prompt and an answer and outputs one number, r(x, y). Architecturally it is the LLM with its LM head (a d × V matrix, 525M parameters for Llama 3.1 8B) replaced by a d → 1 head (4,096 parameters), read at the last token of the answer. It is usually initialized from the SFT model, so it starts out "understanding" text.

How do we train a scorer from comparisons that never say how good anything is in absolute terms? The Bradley–Terry model (1952, a model of paired comparisons; chess Elo ratings use the same logistic form) assumes the probability that answer yw ("winner") beats yl ("loser") depends only on the difference of their scores:

P(yw ≻ yl | x) = σ(r(x, yw) − r(x, yl)),    LRM = − log σ(rw − rl) σ(z) = 1/(1 + e−z) is the logistic sigmoid; rw, rl are the RM's scores for the preferred and the rejected answer. The loss is the cross-entropy of a two-way classification "which one did the human pick?".

Worked example: the RM scores the human's favorite 1.3 and the other answer 0.4. The difference is 0.9, σ(0.9) = 0.711, loss = −ln 0.711 = 0.341. If the scores were the other way round, σ(−0.9) = 0.289 and the loss is 1.241. The gradient of the loss with respect to rw is −(1 − σ(0.9)) = −0.289: push the winner up, the loser down, harder when the RM is more wrong. Only differences matter, so the scale has an arbitrary offset; InstructGPT shifted its RM so that human-written demonstrations average 0. Its 6B RM predicted held-out labelers' choices 69.6% of the time, close to the labelers' own agreement rate. Reward models are noisy instruments.

Step 3: optimize the policy with RL

Now treat the LLM as a policy in the reinforcement-learning sense: the state is the context so far, an action is the next token, an episode is one full answer, and the reward arrives at the end from the RM. We want answers the RM likes, but we do not want the model to wander far from the SFT model, because the RM was only trained on SFT-like answers and is unreliable elsewhere. The objective adds a penalty for drifting:

maxθ   Ex, y∼πθ [ r(x, y) ] − β · KL( πθ ‖ πref ) πθ: the model being trained. πref: a frozen copy of the SFT model. KL: the Kullback–Leibler divergence, estimated per sampled answer as ∑t [log πθ(yt | …) − log πref(yt | …)], how much more surprised the reference is than the policy by the tokens the policy chose. β sets how short the leash is (InstructGPT: 0.02).

The optimizer used for this was PPO (Proximal Policy Optimization). It is a policy-gradient method: raise the log-probability of tokens in answers that scored better than expected, lower it for worse ones, and clip the objective so there is no reward for moving any token's probability more than about ±20% (InstructGPT's clip ratio, 0.2) away from the policy that generated the samples. "Better than expected" needs an estimate of the expected reward at every token, so PPO trains a second network, the value model (critic). The clipped-ratio math is the same one GRPO uses; it is written out in Chapter 10, where GRPO removes the value model.

Reward hacking and the KL leash

The RL optimizer is good at its job: it finds whatever raises r, including the places where the RM is wrong. This is reward hacking, Goodhart's law for neural networks: when a measure becomes a target, it stops being a good measure. Classic symptoms are length (raters slightly prefer thorough answers, so the policy pads), sycophancy (raters like being agreed with, so the policy agrees with the user even when the user is wrong), style over substance (confident tone, headings and emojis win comparisons that correctness should decide), and outright exploits, odd strings that score high for no reason a person would accept.

Gao et al. (2022) measured the effect cleanly by letting a large "gold" RM play the human, training smaller proxy RMs on its labels, and optimizing against the proxy. As the policy moves away from its starting point, the proxy score keeps rising while the gold score rises, peaks and falls:

The KL term is the leash. It has a precise meaning: the policy that maximizes the objective above is known in closed form,

π*(y | x) = 1Z(x) · πref(y | x) · exp( r(x, y) / β ) Z(x) = ∑y πref(y | x) exp(r(x, y)/β) normalizes over all possible answers (an astronomically large sum nobody computes).

In words: the ideal policy is the reference policy, reweighted by exponentiated reward. An answer whose reward is 0.1 higher gets e0.1/0.02 = e5 ≈ 148× more probability at β = 0.02, but an answer the reference considers impossible stays impossible. Small β: a long leash, aggressive optimization, more hacking. Large β: the policy barely moves. Other defenses are better RMs (bigger, trained on fresher data from the current policy), ensembles of RMs, length penalties, and mixing pretraining gradients back in (InstructGPT's "PPO-ptx").

Direct Preference Optimization (DPO)

PPO-based RLHF works, but it is heavy: four models, live generation inside the training loop, a value model to train, and many sensitive hyperparameters. In 2023, Rafailov et al. showed that for the KL-regularized objective above you can skip both the separate reward model and the RL loop. Their method, Direct Preference Optimization, trains on the same (prompt, chosen, rejected) triples with one supervised-style loss.

The trick in three lines

Start from the closed-form optimal policy π* ∝ πref · exp(r/β) and solve it for the reward:

r(x, y) = β · log π*(y | x)πref(y | x) + β · log Z(x)

Now substitute this into the Bradley–Terry model. It only ever uses the difference r(x, yw) − r(x, yl), and both answers share the same prompt x, so the intractable β log Z(x) cancels. What remains is a preference probability written purely in terms of the policy. Replace π* by the model we are training, πθ, and maximize the likelihood of the human labels:

LDPO = − log σ( β log πθ(yw | x)πref(yw | x) − β log πθ(yl | x)πref(yl | x) ) log π(y | x) is the sum of per-token log-probabilities over the answer's tokens (the same masked sum as in SFT). The quantity r̂(x, y) = β log(πθ/πref) is the implicit reward: the paper's subtitle is "Your Language Model is Secretly a Reward Model". Typical β: 0.1.

In words: make the chosen answer gain log-probability, relative to the reference, faster than the rejected one does. Absolute probabilities do not matter. The rejected answer may well be more likely than the chosen one under both models; only the change since the reference counts.

The gradient makes the weighting explicit:

∇θLDPO = −β · σ(r̂l − r̂w) · [ ∇θ log πθ(yw | x) − ∇θ log πθ(yl | x) ] The bracket is "SFT on the chosen answer minus SFT on the rejected one". The factor σ(r̂l − r̂w) is near 1 when the implicit reward ranks the pair wrongly and near 0 once it is ranked right with margin.
A real measurement: Llama's implicit reward

We scored three answers to "What is the capital of France?" under both Llama 3.1 8B checkpoints, using base as πref and Instruct as πθ. This is a stand-in: Meta's DPO reference was each round's SFT model, not the base. Summed log-probabilities over the answer tokens:

  • "The capital of France is Paris." −19.34 (base) → −0.001 (Instruct): Δ = +19.3 nats, r̂ = 1.93 at β = 0.1.
  • "The capital of France is Lyon." −30.71 → −21.17: Δ = +9.5 nats, r̂ = 0.95.
  • "Paris, obviously. Everyone knows that." −38.74 → −41.41: Δ = −2.7 nats, r̂ = −0.27.

Both "Paris" and "Lyon" gained, because post-training taught the chat format they share (the base model alone spends 14.1 nats on the final <|eot_id|>). The correct answer gained twice as much, and the rude one lost ground even against the base model. Read as a Bradley–Terry model, Instruct prefers Paris over Lyon with σ(1.93 − 0.95) = 0.73. The trained policy really does carry a reward model inside it.

Why everyone adopted it, and what goes wrong

The systems profile is the selling point. DPO needs no generation during training, no reward model and no value model. Per pair it needs four forward passes: the policy on yw and yl (with gradients) and the reference on both (without). The reference log-probabilities never change, so they can be computed once, offline, and stored as two floats per pair. Then only one model is in GPU memory and DPO costs about the same as SFT on twice the tokens. Llama 3 tried PPO and chose DPO because it "required less compute for large-scale models and performed better", using β = 0.1 and a learning rate of 10−5.

Two of Llama 3's modifications reveal real failure modes. First, they masked formatting tokens (headers, <|eot_id|>) out of the DPO loss. Those tokens appear in both the chosen and the rejected answer, so the loss asks to raise and lower them at the same time, which caused "tail repetition or abruptly generating termination tokens". Second, they added an ordinary NLL (SFT) loss on the chosen answer with weight 0.2. Without it, DPO can increase the margin by pushing the rejected answer down faster than the chosen one, while both lose probability, and the freed probability mass goes to text nobody labeled. A third issue is that DPO is offline: the pairs often come from other models, not from the policy being trained. Llama 3 handled this by collecting fresh preferences on its latest models in each of its six rounds ("iterative" or "online" DPO).

Key takeaway

DPO turns preference learning into a classification-style loss on log-probability changes. Same data as RLHF, one trainable model, no sampling in the loop. Its weak spots are being offline and letting both answers' probabilities fall, which is why practical recipes add an SFT term and refresh the data every round.

AI feedback and Constitutional AI

Human labels are slow, expensive and inconsistent. If a model can judge answers reasonably well, it can produce preference labels by the million. Anthropic's Constitutional AI (Bai et al., 2022) did this for harmlessness, with human input reduced to a short list of natural-language principles, the "constitution" (16 principles in the paper's supervised phase).

The result was a model that was both less harmful and less evasive: instead of a bare refusal it explained its objection. The general pattern, RLAIF (RL from AI feedback), is now everywhere. Labs use strong models as judges to rank answers against written rubrics, to generate preference pairs, to filter SFT data and to write the critiques themselves. The trade-off is that the judge's biases (it likes long answers, its own style, confident tone) become the policy's biases, so AI labels are usually mixed with human ones and audited.

A different signal is even better than a judge when it exists: a program that checks the answer. Unit tests for code, exact match for math, a verifier for a proof. That is RL with verifiable rewards, the engine of reasoning models, covered with GRPO in Chapter 10.

Tool use and function calling

A model's knowledge stops at its training cutoff, its arithmetic is unreliable (Chapter 3 shows why), and it cannot act on anything. Tool use (also called function calling) fixes all three by letting the model ask your code to do things.

The key fact: the model never executes anything. It only emits tokens in a format it was trained to use. Some other program notices those tokens, parses them, runs the function, and pastes the result back into the context as more tokens. Then the model continues.

Analogy: a system call

A user-space program cannot touch the disk. It puts a syscall number and arguments in registers and traps into the kernel. The kernel does the work, writes a return value, and the program resumes as if a function had returned. For an LLM, the "registers" are a JSON object in its output, the "trap" is a stop token that hands control back to the runtime, and the "return value" is a tool message appended to the context.

Four details in that stream matter in practice.

  • Tool definitions are input tokens on every request. Here one small schema plus its instructions cost 148 of the 195 input tokens; fifty tools can cost thousands before the user says anything. OpenAI's docs say functions are "injected into the system message in a syntax the model has been trained on" and "billed as input tokens". Anthropic also adds a tool-use system prompt (286 tokens for its current models with tool_choice auto).
  • The stop token is the trap. With Environment: ipython in the system prompt, Llama 3.1 is trained to end a call with <|eom_id|> ("end of message, expect a tool result") instead of <|eot_id|> ("end of turn"). Both are in the engine's stop list (Chapter 3), so generation halts the moment the call is complete.
  • Parsing is ordinary string processing on the server. Open-weight servers ship per-family parsers (vLLM: --tool-call-parser llama3_json) that turn the generated text into the tool_calls array your client receives. Malformed JSON makes the parser fail. Strict modes (strict: true in OpenAI and Anthropic tool definitions) guarantee schema-valid arguments; the standard technique is constrained decoding, which masks at every decode step any token that would break the schema (Chapter 14).
  • The tool result is untrusted input. It enters the context as ordinary tokens, so a web page that says "ignore your instructions" is now inside the prompt. Teaching the model to treat tool output as data is part of the instruction hierarchy below.

How a model learns to call tools

Nothing new is needed beyond SFT and preference tuning on tool transcripts. Llama 3's recipe: have an earlier model write questions that need a tool, generate the calls, execute them for real, and write final answers from the outputs (about 30% of trajectories were dropped as unexecutable or malformed). Then multi-step trajectories, and human preferences collected per assistant message, so feedback covers both "right call?" and "used the result correctly?". Easy questions answered without tools teach the model when not to call one.

Loss masking matters here. Tool results are training input, masked out of the loss like user turns. If they were trained on, the model would learn to write tool outputs itself, which is exactly hallucinated "I checked and the weather is 14 °C". Only the call tokens and the final answer carry gradient.

Agents are loops, and MCP is the plug

An agent is this round trip in a loop: call the model; if it asked for tools, run them, append the results, and call it again; stop when it answers instead. Coding agents, research agents and computer-use agents differ mainly in their tools and their stopping rules.

messages = [system, user]
while True:
    resp = llm(messages, tools=TOOLS)       # one request: prefill + decode
    messages.append(resp.message)           # the call tokens become context
    if resp.finish_reason != "tool_calls":
        break                               # a final answer: done
    for call in resp.tool_calls:
        out = run_tool(call.name, json.loads(call.arguments))
        messages.append({"role": "tool", "tool_call_id": call.id, "content": out})

The Model Context Protocol (MCP), introduced by Anthropic in late 2024 and now an open specification (current revision 2026-07-28), standardizes the plumbing between an agent and its tools. A tool provider runs an MCP server that answers JSON-RPC 2.0 requests: tools/list returns each tool's name, description and inputSchema (a JSON Schema), and tools/call executes one with arguments and returns content blocks. The host application converts the listed schemas into whatever tool format its model API expects and forwards the model's calls. MCP changes nothing inside the model. It is a USB standard for the sockets, not a new instruction set. Every MCP tool you connect still costs prompt tokens on every request, which is why the 2026 revision asks servers to return tools in a deterministic order: a stable tool list keeps the prompt prefix stable, and that keeps prompt-cache hit rates up (Chapter 12).

Key takeaway

Function calling = schemas serialized into the prompt + a trained output format + a stop token that returns control + a runtime that executes and appends the result as a tool message. The model proposes; your code disposes. Agents are loops of this, and their input grows every iteration.

System prompts, the instruction hierarchy and safety

A system prompt is just the first message in the token sequence, under a system header (Chapter 3). Nothing in the architecture makes it special. It has authority only because post-training data taught the model to give it authority: thousands of conversations where the system message set rules and the assistant followed them, even when a later user message pushed the other way.

Once tools and documents flow into the context, "whose instructions win?" becomes a security question. A tool result, a retrieved web page or an email may contain text that looks like an instruction. This is prompt injection, and there is no hardware boundary to stop it: privilege exists only as learned behavior over token sequences. Wallace et al. (2024) proposed training an explicit instruction hierarchy: generate conversations where lower-priority text conflicts with higher-priority text, and train the model to follow the higher level and ignore the lower one. OpenAI's Model Spec writes the current order down:

The Model Spec's order is Root (rules only the spec can set), System (the platform), Developer (your system or developer message), User, Guideline (soft defaults), and then content with no authority by default: assistant and tool messages, quoted text, images and files. Whatever the exact order a lab uses, it is learned, so it is probabilistic. Treat the model like a well-trained but fallible employee: give agents least privilege, require confirmation for destructive actions, and never assume an instruction in the system prompt is a security boundary.

Safety tuning

Safety behavior is trained with the same tools. SFT data includes adversarial prompts with good refusals and, just as important, borderline prompts that look risky but are fine ("how do I kill a Python process?") with helpful answers. Preference data ranks safe-and-helpful over unsafe and over needlessly-refusing. Llama 3's safety section tracks two numbers against each other: the violation rate (harmful completions) and the false refusal rate (refusing benign requests), because pushing one down tends to push the other up. Red teams (people and automated attackers) search for jailbreaks, prompts that get around the training, and the failures become new training data. In deployed systems, separate classifier models screen inputs and outputs as well (Meta's Llama Guard is one), so safety is layered rather than resting on the weights alone.

Distillation: learning from a bigger model

Small models are cheap to serve (Chapter 11), but they learn less from raw text than large models do. Distillation trains a small student model to imitate a large teacher. Hinton et al. named it in 2015. For LLMs there are three forms, and they differ in how much of the teacher's knowledge each training token carries.

  • Sequence-level (Kim and Rush, 2016): sample text from the teacher and run plain SFT on it. Any API can be distilled this way, which is why most SFT data is now model-generated, and why small "reasoning" models are often trained on a big model's chains of thought (Chapter 10). Each position teaches one token, the one that happened to be sampled.
  • Logit-level (Hinton et al., 2015): at every position, train the student's distribution p to match the teacher's full distribution q, minimizing KL(q ‖ p) = ∑v qv log(qv/pv). The gradient with respect to the student's logits is simply p − q, the soft version of pretraining's p − y (Chapter 8). The target says not only "mat" but also "matt, hat and dog are each about 1% plausible", which carries far more information per token. Gemma 2 trained its 2B and 9B models this way during pretraining, on over 50× the compute-optimal number of tokens. It requires the teacher's weights (or full logits), so only the model's owner can do it.
  • On-policy (GKD, Agarwal et al., 2023): the student generates, and the teacher scores every token of the student's own output with a single forward pass; the per-token reverse KL, KL(p ‖ q), which penalizes the student for putting probability where the teacher puts little, is the training signal. It fixes SFT's "never practices recovering from its own mistakes" problem with RL-like dense feedback but without a reward model. Thinking Machines (2025) reported reaching a reasoning score similar to an RL-trained Qwen3-8B at 9–30× lower cost.
Low-level: the logit storage problem

A full next-token distribution for Llama 3's vocabulary is 128,256 numbers, 513 KB per position in FP32. For a distillation set of 1011 tokens that would be 51 PB. So either the teacher runs online, next to the student, with its forward pass adding roughly 2Nteacher FLOPs per token to the student's 6Nstudent, or you store only the top-k entries (say k = 64: 64 × (4 B id + 2 B prob) = 384 B per position, a 1,300× reduction) and renormalize. After "The cat sat on the", the top 5 tokens already hold 79% of the mass.

Fine-tuning it yourself: full, LoRA, QLoRA

Everything so far is what labs do. You can run the same SFT and DPO recipes on your own data with open weights. The question is memory.

Full fine-tuning and its bill

Full fine-tuning updates every weight with AdamW, which costs about 16 bytes per parameter before activations: BF16 weights and gradients, FP32 master weights, and two FP32 Adam moments (Chapter 8). For Llama 3.1 8B that is 16 × 8.03×109 = 128.5 GB, more than one 80 GB H100, so you need at least two GPUs with the optimizer state sharded (ZeRO/FSDP). For the 70B it is 1.13 TB: even a full node of 8 H100s (640 GB) is not enough without offloading to CPU memory. And every fine-tuned variant is a complete 16 GB (or 141 GB) copy to store and serve.

LoRA: train a low-rank correction

Most of that memory is optimizer state for weights that barely move. Hu et al. (2021) hypothesized that the change a weight matrix needs during adaptation has low "intrinsic rank": it can be described by a few directions. LoRA (Low-Rank Adaptation) freezes the original matrix and learns the change as the product of two thin matrices:

h = W x + αr · B (A x) W ∈ ℝdout×din is frozen. A ∈ ℝr×din projects the input down to r numbers; B ∈ ℝdout×r projects them back up. r (the rank, typically 8–64) is much smaller than d. α is a fixed scale. Only A and B are trained.

Why it works. B·A is a 4096 × 4096 matrix of rank at most 16. It can change the layer's behavior only along 16 input directions (the rows of A) mapped to 16 output directions (the columns of B). Think of it as 16 rank-1 rules of the form "when the input has a component along ai, add some output along bi". That is a strong restriction, and it turns out to be enough for most post-training-sized datasets: Thinking Machines (2025) found LoRA matching full fine-tuning on typical instruction and reasoning SFT datasets, and in RL even at very small ranks, falling behind only when the dataset carries more information than the adapter can store.

Initialization. B starts at zero and A at small random values (Gaussian in the paper, Kaiming-uniform in Hugging Face PEFT). So ΔW = 0 at step 0 and training starts from the base model's exact behavior. Both cannot be zero: the gradient for A is proportional to BT, so A would never move, and the gradient for B would be proportional to Ax = 0. With A random, B gets a gradient immediately, and A starts learning one step later.

The α/r scale keeps the update's size roughly independent of the rank, so changing r does not require re-tuning the learning rate (rsLoRA argues for α/√r at high ranks). Common settings are α = r or 2r. LoRA's best learning rate is about 10× higher than full fine-tuning's (e.g. 2×10−4 vs 2×10−5).

Which matrices. The original paper adapted only Wq and Wv. Later work (QLoRA; Thinking Machines) found that adapting all linear layers, especially the MLP ones that hold two thirds of the parameters (Chapter 6), is what lets LoRA match full fine-tuning; attention-only LoRA underperforms even with matched parameter counts.

Low-level: FLOPs, memory and kernels

Forward FLOPs. The side path costs 2r(din + dout) FLOPs per token per matrix; summed over the model at r = 16 that is 2 × 41.9M ≈ 84 MFLOP per token, 0.5% of the base model's ~16 GFLOP.

Backward FLOPs. A trained linear layer needs two gradient matmuls: one for its input (dX = dY·W) and one for its weight (dW = dYT·X). A frozen layer skips the second. So LoRA training costs about 4N FLOPs per token instead of 6N: a third less compute, not 99% less.

Memory. LoRA removes gradients and optimizer state for frozen weights, which is where the 16 B/param went. It does not remove activation memory: the adapter's own gradient dA needs the same input x that the frozen layer sees, so the stored activations are about the same as in full fine-tuning.

Kernels. Unmerged, each adapted layer runs one large GEMM (X·WT) plus two skinny ones (X·AT → n × 16, then · BT). The skinny GEMMs have low arithmetic intensity and add kernel launches, so unmerged LoRA adds noticeable latency at inference even though its FLOPs are tiny.

Merging, and serving many adapters at once

After training you can fold the adapter into the weights: W′ = W + (α/r)·B·A, computed once. W′ has exactly the shape of W, so the merged model has zero extra inference cost. Or you can keep adapters separate and serve many fine-tunes on one copy of the base model:

QLoRA: a 4-bit frozen base

With LoRA, the frozen base still costs 2 B/param in BF16: 16 GB for 8B, 141 GB for 70B. But a frozen weight is never updated, so it can be stored compressed. QLoRA (Dettmers et al., 2023) keeps the base in 4 bits and trains BF16 adapters on top. Three pieces:

  • NF4 storage. The frozen weights use the 4-bit "NormalFloat" format: blocks of 64 weights, 16 levels placed to suit normally distributed weights, and one FP32 scale per block, for 4.5 bits per weight. Chapter 13 explains the format and its error.
  • Double quantization. The FP32 block scales are themselves quantized to 8 bits, which cuts the total to 4.127 bits (0.516 bytes) per weight. On a 65B model that saves about 3 GB.
  • Paged optimizers. Adapter optimizer state lives in CUDA unified memory. When a long sequence spikes activation memory, pages are evicted to CPU RAM and faulted back in for the optimizer step: OS paging applied to GPU memory, to survive spikes instead of crashing with out-of-memory.

In the forward and backward pass, each 4-bit block is dequantized to BF16 inside the matmul kernel, used, and discarded. Gradients flow through the dequantized weights to the inputs and into the adapters; the 4-bit weights themselves receive no gradient. The paper fine-tuned a 65B model on one 48 GB GPU (16-bit full fine-tuning would need more than 780 GB) and matched 16-bit full fine-tuning and 16-bit LoRA on its benchmarks.

Fine-tune, prompt, or retrieve?

Fine-tuning is one of three ways to adapt a model, and often not the first one to try.

  • Prompting: instructions and a few examples in the system prompt. Zero training, changes take minutes. You pay for those tokens on every request (cheaper when cached; Chapter 12), and you are limited to skills the model already has.
  • Retrieval-augmented generation (RAG): at request time, search your documents and paste the most relevant chunks into the prompt. The search usually uses an embedding model that maps each text chunk to a vector, plus nearest-neighbor lookup by cosine similarity (Chapter 4), often combined with keyword search. RAG is the right tool for knowledge that is private, large, changes often, or must be cited.
  • Fine-tuning: changes the weights. It is the right tool for behavior: a strict output format, a tone, a narrow task done well by a small, cheap model, a tool-call convention, or shrinking a long prompt into the weights to cut latency and input cost. It is a poor tool for adding facts. Facts learned by fine-tuning are hard to update, hard to cite, and training on new knowledge tends to degrade behaviors learned earlier (Thinking Machines observed exactly this when teaching an assistant new documents, and used on-policy distillation to restore the lost behavior).

Catastrophic forgetting

The same weights store everything the model knows, densely overlapped (superposition; Chapter 4). A gradient step that helps your task also moves weights that other abilities depend on. Fine-tune hard on narrow data and the model can lose its chat formatting, its multilingual ability, general knowledge, or its safety behavior. That last one is easy to trigger: Qi et al. (2023) removed GPT-3.5 Turbo's safety guardrails by fine-tuning on 10 adversarial examples, for under $0.20, and found that even benign fine-tuning data erodes safety somewhat. Standard defenses: mix general data into the fine-tuning set (InstructGPT mixed in pretraining data for exactly this), use lower learning rates and fewer epochs, evaluate on general benchmarks and not only on your task, and prefer LoRA when it is enough: Biderman et al. (2024) titled their comparison "LoRA Learns Less and Forgets Less".

Model merging

Fine-tunes of the same base model can often be combined by arithmetic on their weights, with no further training. Averaging several runs that differ in data order or hyperparameters ("model soups") usually beats the best single run; Llama 3 averaged models at its RM, SFT and DPO stages. Task arithmetic treats a fine-tune as a vector, τ = θfine-tuned − θbase, and adds or subtracts such vectors to combine or remove skills. TIES and DARE improve on plain addition by dropping tiny changes and resolving sign conflicts between task vectors. This works because fine-tunes from one base tend to stay in the same low-loss basin, where points on the straight line between two solutions are also good. A LoRA adapter is literally a compact task vector, (α/r)·B·A.

How post-trained models are evaluated

Pretraining has a clean metric, held-out loss (Chapter 8). Post-training does not: we care about helpfulness, correctness, safety and style. Evaluation is therefore a portfolio of imperfect instruments.

Benchmarks are fixed question sets with automatic scoring. Families include knowledge and reasoning (MMLU-Pro, GPQA Diamond, Humanity's Last Exam), competition math (AIME), code (HumanEval; SWE-bench Verified, which applies the model's patch to a real repository and runs hidden tests), instruction following (IFEval, with checkable constraints like "answer in exactly three bullet points"), tool use (BFCL, τ-bench) and long context. Mechanically, a base model is often scored by comparing the log-likelihood it assigns to each multiple-choice option, while a chat model generates an answer that a script parses. Code is scored with pass@k, the probability that at least one of k samples passes the tests. Scores move with the prompt format, the number of few-shot examples, whether reasoning is allowed and the sampling temperature, so only compare numbers produced the same way. Benchmarks also saturate: once top models score above ~90%, the benchmark stops separating them and a harder one replaces it.

Contamination is the chronic problem. Test questions leak into web crawls, and into synthetic data generated by models that saw them. A contaminated score measures memory, not skill. Defenses are n-gram decontamination of training data (Chapter 8), canary strings embedded in benchmark files, private held-out sets, and fresh problems written after the model's training cutoff, such as each year's new AIME.

LLM-as-a-judge grades open-ended answers with a strong model, either pairwise ("which is better?") or against a rubric. The MT-Bench paper found GPT-4's judgments agreed with human preferences over 80% of the time, about as often as humans agree with each other. It also documented the judge's biases: position (favoring the first or second answer), verbosity (favoring longer answers) and self-enhancement (favoring its own outputs). Practical mitigations: judge both orders and average, control for length, and use explicit rubrics.

Arenas such as LMArena (formerly Chatbot Arena) show users two anonymous models side by side and record which answer they prefer. The votes are turned into ratings with the same Bradley–Terry model that trains reward models. Arenas use real prompts that cannot be memorized in advance, but they measure what voters like, which includes length and formatting. The "Leaderboard Illusion" study (2025) also showed how private testing distorts them: it identified 27 private variants Meta tested before the Llama 4 release, with providers able to publish only their best score.

Key takeaway

No single number captures a post-trained model. For your own use case, 50–200 real examples with an automatic check or a rubric-guided judge tell you more than any leaderboard, and they catch regressions every time you change the prompt, the model or the fine-tune.

Hints (open only when stuck)
  • Finding assistant spans. Render messages[:k] with add_generation_prompt=True and messages[:k+1], both with tokenize=True, and assert the first is a prefix of the second. The new tokens are the assistant's content plus its end-of-turn token. Templates that rewrite earlier turns break this prefix property; Llama 3.1's does not. Qwen2.5's template adds a default system prompt when you pass none and a newline after each <|im_end|>; decide whether that newline is trained and stay consistent.
  • Double BOS. apply_chat_template(..., tokenize=True) already starts with <|begin_of_text|>. Rendering to a string and then calling the tokenizer with special tokens enabled adds a second one. Assert ids[1] != ids[0] in a test.
  • Accumulation. Averaging per-micro-batch means gives every micro-batch equal weight, so tokens in short answers count more. Sum token losses and divide once by the trained tokens in the whole step. Hugging Face's Trainer had exactly this bug until a fix in late 2024.
  • Untrained rows (Milestone 4). The base model's rows for <|start_header_id|>, <|end_header_id|> and <|eot_id|> were never trained. Check whether the LM-head rows are distinct from each other and from the reserved tokens' rows: if <|eot_id|> shares its row with other tokens, their logits are tied and it can never take most of the probability. The community fix in 2024 was to set these rows to the mean of the trained rows and train them (or the whole embedding and LM head) alongside the adapters.
  • Silent zero gradients. With reentrant gradient checkpointing and frozen embeddings, nothing at the input requires grad, and the adapters can end up with no gradient at all. Use gradient_checkpointing_enable(gradient_checkpointing_kwargs={"use_reentrant": False}) or model.enable_input_require_grads(), and assert every adapter's .grad is set after the first backward.
  • Measuring memory. Call torch.cuda.reset_peak_memory_stats() between phases. nvidia-smi reads higher because it includes the CUDA context and the caching allocator's reserve. bitsandbytes' paged optimizers allocate their state outside PyTorch's allocator, so use plain AdamW while you check the formulas.
  • Where 16 B/param comes from. FP32 weights under BF16 autocast give 4 + 4 + 8 = 16 B, the same total as the chapter's BF16 weights and gradients plus FP32 master copy and moments. Load in BF16 with plain AdamW and you get 8 B/param, and updates of size ~2×10−5 on weights of size ~10−2 are smaller than half of BF16's spacing, so most of them round away (Chapter 2). For LoRA, keep A and B in FP32.
  • Reading the last token. With right padding the reward model's score is at index attention_mask.sum(-1) - 1; with left padding it is at -1. Reading a pad position gives about 50% accuracy forever.
  • DPO's step 0 is not ln 2. Compute the reference with the exact code path you use for the policy: same padding side, dtype, mask and dropout setting. Use the masked sum of log-probs; the per-token mean is SimPO's reward, not DPO's.
  • A stable judge. Ask for a single letter, A or B, and read the probabilities of those two tokens instead of parsing free text. Average over both orders and keep the flip count.
