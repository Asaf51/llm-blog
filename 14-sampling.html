Part IV · Chapter 14

Sampling & Temperature

The model only produces a probability for every possible next token. Separate code, the sampler, has to pick one of them. This chapter covers that code: the random draw, temperature, the top-k/top-p/min-p filters, penalties, stopping, why "temperature 0" still gives different answers, and how JSON schemas are enforced one token at a time.

In this chapter
  • How a uniform random number becomes a token (inverse-CDF), and how GPUs do it without sorting (Gumbel-max, rejection sampling).
  • What temperature does to the math: logits divided by T, entropy, and why a high temperature hands most of the probability to junk tokens.
  • Top-k, top-p (nucleus), min-p and typical sampling; why the order of the sampler chain changes results; repetition, frequency, presence and DRY penalties; logit bias.
  • Greedy decoding, repetition loops, beam search, stop sequences, finish_reason, seeds and RNGs.
  • Why temperature 0 is not deterministic on real servers (floating-point order, batch-dependent kernels, MoE routing), and how batch-invariant kernels fix it.
  • Constrained decoding for structured output: schema → automaton → token mask → logits set to −∞. Logprobs, and recommended settings, including the fixed temperatures of reasoning models.

The last step: from logits to a token

Every forward pass ends the same way. The LM head (Chapter 6) produces one score, a logit, for every entry in the vocabulary: 128,256 numbers for Llama 3.1 8B. Softmax (Chapter 4) turns them into a probability distribution. At this point the model has not chosen anything. It has only said how likely each token is. A separate piece of code, the sampler (also called the decoder or decoding strategy), must turn that distribution into exactly one token ID. That token is appended to the context and the generation loop from Chapter 1 runs again.

The sampler has no weights and learns nothing. It is a few hundred lines of code. Yet it decides whether the same prompt gives the same answer twice, whether text falls into a loop, whether JSON output parses, and how "creative" the output feels. Formally, a decoding strategy is a function:

token = decode(z, history, settings, random bits) z = the logit vector for the next position (length V). history = the tokens so far (needed for penalties and grammars). settings = temperature, top-p, and so on. random bits = output of a pseudo-random number generator (absent for greedy decoding).

In practice this function is built as a chain of small stages. Each stage reads the logit vector and writes a modified one: add a bias here, subtract a penalty there, divide by the temperature, cut off the unlikely tail. The last stage turns the result into probabilities and makes a random draw. Hugging Face calls these stages logits processors; llama.cpp calls them samplers in a sampler chain.

Intuition

Think of a Unix pipeline or an HTTP middleware chain. The model emits one big record (the logits). Each filter in the pipe edits or drops fields. The final stage picks one field at random, weighted by its value. Change the order of the filters and you can get a different result, exactly like reordering sort | uniq.

Low-level: what the sampler touches

The logits tensor has shape [B, V]: one row per sequence in the batch. Engines convert it to FP32 before sampling (vLLM's sampler does this explicitly), so one row is 128,256 × 4 B = 513 KB. At a batch of 256 sequences that is 131 MB, read and written by several small elementwise kernels per decode step. Compare this with the ~16 GB of weights that a decode step of Llama 3.1 8B reads (Chapter 11): sampling is a small part of the step. It is not free, though. A naive implementation launches a handful of kernels, sorts 128K values when top-p is on, and may force the GPU to wait for the CPU. The next two sections show how this is done well.

Drawing a token: inverse-CDF sampling

The problem. We have probabilities p1 … pV that sum to 1. We want to pick token i with probability exactly pi. A computer gives us only uniform random numbers: a value u anywhere in [0, 1), all values equally likely.

The idea. Lay the probabilities end to end on a ruler of length 1. Token 1 owns the segment [0, p1), token 2 owns the next p2, and so on. Drop u on the ruler. The token whose segment contains u wins. A segment of length 0.21 catches 21% of all uniform draws, so each token is chosen with exactly its probability. This is inverse transform sampling, or inverse-CDF sampling. It is a roulette wheel cut open and laid flat.

Fi = p1 + p2 + … + pi,    choose the smallest i with Fi > u Fi is the cumulative distribution function (CDF): the total probability of the first i tokens. u ~ U(0, 1) is one uniform random number. "Inverse" because we go from a height on the CDF (u) back to the token.

Worked example. The figure below uses illustrative logits for 12 continuations of "The cat sat on the" (␣mat 4.0, ␣floor 3.2, ␣bed 2.5, ␣couch 2.1, …) and, to be realistic, gives every one of the other 128,244 vocabulary tokens a logit of −12. At T = 1 the probabilities are 0.467, 0.210, 0.104, 0.070, … and the 128,244 junk tokens share 0.7%. With u = 0.62: F(mat) = 0.467 ≤ 0.62, keep walking; F(floor) = 0.676 > 0.62, stop. The sampler emits ␣floor, the second most likely token. Over many draws ␣mat wins 46.7% of the time and ␣floor 21.0%. (These numbers differ from Chapter 4's five-token example because there are more candidates.)

Ordering does not matter. The ruler can list tokens in any order: in vocabulary-ID order, sorted, or shuffled. Each token's segment still has length pi, so each token is still chosen with probability pi. Plain sampling therefore needs no sort. Only the truncation filters (top-k, top-p) need to know which tokens are the largest.

Low-level: llama.cpp's final sampler

llama.cpp's dist sampler is a direct implementation of the ruler. It finds the max logit, computes p = expf(logit − max) for each surviving token and their sum S in a double, draws rnd from a std::uniform_real_distribution<double>(0, 1), and walks the running sum until it passes S · rnd. Multiplying u by S instead of dividing every p by S saves a full pass over the vocabulary; a code comment says this single-pass version is about 3× faster on a Mac with the full gpt-oss vocabulary.

How GPUs actually sample

The ruler is perfect on a CPU. On a GPU it has two problems. A running sum is a sequential scan, and the classic library call that does it, torch.multinomial, makes the CPU wait for the GPU. vLLM's source says so directly: it avoids torch.multinomial "because torch.multinomial causes CPU-GPU synchronization". During decode the CPU is busy preparing the next step, so a sync stalls the pipeline. The fix is a different but equivalent way to draw.

The Gumbel-max trick, or the exponential race

Idea. Give every token its own random alarm clock. Token i's clock rings after a random time that is exponentially distributed with rate pi: likely tokens have fast clocks. The token whose clock rings first wins. For exponential clocks, the chance that clock i rings first is exactly pi / Σpj. So the race is a correct sampler, and it is a single parallel argmax instead of a sequential scan.

token = argmaxi  pi / qi,   qi ~ Exp(1)   ⇔   token = argmaxi ( zi/T + gi ),   gi = −ln(−ln Ui) qi = one exponential random number per token (−ln of a uniform). qi/pi is token i's ring time, so the largest pi/qi rings first. Taking logs gives the second form: add independent Gumbel noise gi to every scaled logit and take the argmax. Neither form needs the probabilities to be normalized, and the second needs no softmax at all.

Worked example with two tokens, p = 0.467 for ␣mat and 0.210 for ␣floor. Suppose the noise draws are q = 1.30 and 0.40. Scores: 0.467/1.30 = 0.359 and 0.210/0.40 = 0.525, so ␣floor wins this race. Over many races ␣mat wins 0.467/(0.467+0.210) = 69% of the head-to-head contests, exactly as the ruler would give.

vLLM's default PyTorch path does exactly this: fill a [B, V] tensor with exponential_() noise, divide the probabilities by it in place, and take argmax. That costs 128,256 random numbers per sequence per step instead of one, but GPU random number generation is cheap (see the seeds section) and the whole thing is two fused, fully parallel passes with no sort and no sync.

Selecting the top tokens without a full sort

Truncation filters need the largest tokens. Sorting 128,256 floats per sequence per step is wasteful when you need the top 40. Engines use partial methods instead:

  • Bucketing. llama.cpp's top-k drops every logit into one of 128 buckets spanning [−10, 10], builds a histogram, finds the bucket where the running count reaches k, and runs std::partial_sort only inside that boundary bucket. It is a radix-select in spirit.
  • Radix select on GPU. Finding the k-th largest value digit by digit, with a histogram per pass, then keeping everything above it.
  • Rejection sampling with pivots. FlashInfer (used by vLLM and SGLang on NVIDIA GPUs) never sorts. It samples with a ruler pass over tokens above a pivot probability, checks whether the sampled token satisfies the top-k or top-p rule, and if not, raises the pivot and tries again. Its "dual pivot" version provably finishes in O(log(1/ε)) rounds, and in practice in a few, all inside one fused kernel.
A floating-point trap

FlashInfer's authors note that a parallel prefix sum of non-negative floats is not guaranteed to be monotone, because the parallel adds happen in a different order than a sequential scan. A "CDF" that dips slightly can return an invalid token. Floating-point addition order will come back as the main character in the determinism section.

Greedy decoding and the repetition trap

The simplest decoder uses no randomness: always take the most likely token, token = argmaxi zi. This is greedy decoding. It needs no softmax (the largest logit has the largest probability) and, in exact math, the same prompt always gives the same output. Greedy is a good choice for short, closed answers: classification labels, extracting a field, a yes/no. It is a poor choice for anything long.

Why greedy loops. Language models learn that text often repeats itself: names recur, code repeats patterns, lists have parallel structure. Attention heads that find an earlier occurrence of the current token and copy what followed it (induction heads, Chapter 5) make copying a strong signal. Once a sentence has appeared twice, the evidence that it will appear a third time is stronger. Holtzman et al. measured this: the probability of repeating a phrase rises with each repetition. Greedy decoding always takes the top choice, so once the loop becomes the top choice it can never escape. It is a positive-feedback loop, like a microphone near its own speaker.

Sampling breaks loops because a random draw sometimes takes a lower-probability exit. Penalties and DRY (later in this chapter) attack loops directly. Long reasoning traces are especially prone to loops, which is why Qwen3's model card says, in bold, not to use greedy decoding in thinking mode: it "can lead to performance degradation and endless repetitions".

There is a second, quieter problem. The single most likely continuation is not what human text looks like. People do not always pick the most predictable next word; real text has frequent small surprises. Text built only from argmax choices reads as bland. That observation is the starting point for nucleus and typical sampling below.

Temperature

The problem. Pure sampling uses the model's distribution as is. Sometimes we want it more decisive (fewer odd choices, more consistent answers) and sometimes more varied (brainstorming, fiction). We need one knob that sharpens or flattens the whole distribution while keeping the ranking.

The idea. Divide every logit by a positive number T before softmax. Dividing by a small T stretches the gaps between logits, so the winner takes more. Dividing by a large T shrinks the gaps, so everything moves toward equal.

pi(T) = ezi/TΣj ezj/T     and so    pipj = e(zi − zj)/T T = temperature. T = 1 is the model's own distribution. The ratio form is the useful one: a logit gap of Δ becomes a probability ratio of eΔ/T. Ranking never changes, only how lopsided it is.

Worked example. The gap between ␣mat (4.0) and ␣floor (3.2) is 0.8. At T = 1 the ratio is e0.8 = 2.23 (0.467 vs 0.210). At T = 0.5 it is e1.6 = 4.95, and ␣mat rises to 0.775. At T = 2 it is e0.4 = 1.49, nearly a coin flip between the two.

  • T → 0: the largest logit's share goes to 1. The limit is greedy decoding. Dividing by zero is undefined, so engines special-case it: vLLM treats T < 10−5 as greedy, llama.cpp treats T ≤ 0 as greedy.
  • T = 1: sample from what the model learned. This is the distribution training optimized (Chapter 8).
  • T → ∞: every token gets 1/V, including all 128,244 junk tokens. Output becomes random bytes.
Why it is called temperature

The formula is the Boltzmann distribution from statistical physics: a system is in state i with probability proportional to e−Ei/kT. Read a logit as negative energy. At low temperature a physical system sits in its lowest-energy state (the argmax); at high temperature it visits every state almost equally. Same math, same behavior.

Entropy: one number for "how spread out"

We need a measure of how uncertain a distribution is. The standard one is entropy, the average surprise of a draw:

H(p) = − Σi pi log2 pi   bits −log2 pi is the surprisal of token i in bits: 1 bit for a token with p = 0.5, 10 bits for p = 1/1024. Entropy averages it. H = 0 means one certain token; H = log2 128,256 = 16.97 bits is the uniform maximum. 2H is the "effective number of choices" (the perplexity of this one step).

For our example: at T = 1, H = 2.54 bits, about 5.8 effective choices. At T = 0.5, H = 1.10 bits (2.1 choices). At T = 1.5 it jumps to 10.8 bits, and at T = 2 to 16.2 bits, close to the uniform maximum. Why the jump? Look at the tail.

The tail explosion. Each junk token has a logit 16 below ␣mat. At T = 1 its weight relative to ␣mat is e−16 ≈ 1.1 × 10−7; times 128,244 tokens that is 0.014, under 1% of the total. At T = 2 the gap halves to 8, so each junk token's weight is e−8 = 3.4 × 10−4, and 128,244 of them add up to 43 times the weight of ␣mat. The junk now holds 91.5% of the probability. A large vocabulary means a huge number of individually negligible tokens, and temperature raises all of them at once. This is why raw high-temperature sampling produces gibberish, and why every serious sampler combines temperature with truncation.

Key takeaway

Temperature multiplies every logit gap by 1/T. It keeps the ranking and changes how lopsided the distribution is. Below 1 it trims variety smoothly; above 1 it hands probability to the vast tail of junk tokens, so it must be paired with truncation.

Truncation: top-k, top-p, min-p, typical

The problem. Most of the vocabulary is nonsense in any given context, but each nonsense token gets a small non-zero probability. One at a time they do not matter; together they do, and temperature makes them matter more. Holtzman et al. called this the "unreliable tail". Truncation removes tokens judged unreliable, renormalizes the survivors so they sum to 1, and samples only among them. The methods differ in how they decide where the tail starts.

Top-k

Keep the k most likely tokens. Simple and cheap. Its weakness is that k is fixed, while the shape of the distribution changes from step to step. After "The cat sat on the", 5 tokens is generous. After "My favorite fruit is", there may be a dozen equally good answers, and k = 5 throws away half of the probability mass for no reason.

Top-p (nucleus sampling)

Keep the smallest set of top tokens whose probabilities add up to at least p. This set is the nucleus. It adapts: a peaked distribution gives a small nucleus, a flat one gives a large nucleus. Holtzman et al. (2019) introduced it, and it became the default filter in most APIs (top_p).

keep the top m tokens, where m = min { m : p(1) + … + p(m) ≥ p } p(1) ≥ p(2) ≥ … are the probabilities sorted in descending order. For our example with p = 0.9: 0.467, 0.676, 0.780, 0.850, 0.892, 0.921 → m = 6 tokens.

Its weakness: the nucleus is defined by total mass. If many junk tokens together hold a lot of mass, which is exactly what high temperature causes, the nucleus has to swallow thousands of them to reach p.

Min-p

Keep every token whose probability is at least a fraction of the top token's probability. Nguyen et al. (ICLR 2025) proposed it; it is now in llama.cpp (default 0.05), Hugging Face and vLLM.

keep token i if  pi ≥ pbase · pmax pmax = probability of the most likely token. pbase = the min-p setting, typically 0.05–0.1. Peaked example: 0.1 × 0.467 = 0.047, so 4 tokens survive (␣edge at 0.042 just misses). Flat example: 0.1 × 0.119 = 0.012, so all 12 fruits survive.

The threshold moves with the model's confidence. When the model is sure, the bar is high. When it is unsure, the bar drops and many options survive. And a single junk token's probability stays tiny relative to the top token even at high temperature, so min-p removes the tail no matter how hot the sampling is. That is why it pairs well with T > 1.

Typical sampling

Meister et al. (2022) asked a different question: not "is this token likely?" but "is this token about as surprising as a token here should be?" Human text tends to carry a steady amount of information per word. Locally typical sampling keeps tokens whose surprisal −log pi is close to the entropy H, adding tokens in order of closeness until their mass reaches τ (the typical_p setting).

Worked example: H = 2.54 bits. Surprisals: ␣mat 1.10, ␣floor 2.25, ␣bed 3.26, ␣couch 3.84 bits. Distances from H: 1.44, 0.29, 0.72, 1.30. With τ = 0.3 the method keeps ␣floor then ␣bed (0.21 + 0.10 = 0.31 ≥ 0.3) and drops ␣mat, the most likely token, as "too predictable". No other filter here can do that. With τ = 0.9 it keeps the same 6 tokens as top-p.

A few more filters exist, mostly in local engines. Top-nσ keeps tokens whose logit is within n standard deviations of the maximum logit; because it works on logits, the kept set does not change with temperature. XTC ("exclude top choices", llama.cpp) does the opposite of truncation for creative writing: with some probability it removes the most likely tokens above a threshold, keeping only the least likely of them. Mirostat is a feedback controller that adjusts truncation each step to hold the surprise of the generated text near a target. Hugging Face also has epsilon and eta sampling (fixed and entropy-dependent probability floors).

Key takeaway

Truncation decides which tokens are allowed; temperature decides how to weight the allowed ones. Top-k uses a count, top-p uses total mass, min-p uses a ratio to the best token, typical uses closeness to the expected surprise. Min-p is the most robust when temperature is above 1.

The sampler chain: order matters

Real samplers apply several of these stages in sequence. The stages do not commute. Two examples:

  • Temperature before or after top-p. If temperature comes first, top-p sees the flattened distribution, and a hot temperature makes the nucleus enormous. If temperature comes last, top-p chooses the survivors from the T = 1 distribution and temperature only reshapes the survivors. Junk cannot get back in.
  • Top-k then top-p. After top-k removes tokens, the survivors are renormalized, so each one's share grows and top-p's threshold is reached with fewer tokens than it would be on the full distribution.

The three most common engines use different orders. These come from their current source code (llama.cpp common/common.h, Hugging Face generation/utils.py, vLLM v1/sample/sampler.py):

A worked example of order changing the answer. Set T = 1.5, top-p = 0.95, nothing else. In llama.cpp order, top-p runs on the T = 1 distribution and keeps 8 tokens (cumulative 0.959); temperature 1.5 then spreads probability among those 8, so ␣mat drops to 0.353 and no junk can appear. In vLLM or Hugging Face order, temperature runs first, the tail grows to 49% of the mass, and to reach 0.95 the nucleus must include the 12 named tokens plus about 115,000 junk tokens. About 46% of all draws become junk. Same settings, different engine, very different text. Adding min-p = 0.05 repairs the second chain, because no single junk token comes close to 5% of ␣mat's probability.

Penalties, DRY and logit bias

The problem. Sampling escapes loops sometimes, not always. Models also overuse favorite words. We want to make reuse less attractive without banning it. Every engine offers a few penalty knobs. They all edit logits before temperature, and all of them need the history of generated tokens, kept as a per-sequence count array of size V on the GPU.

Repetition penalty (multiplicative)

Introduced with the CTRL model (Keskar et al., 2019). For every token that has already appeared, shrink its logit by a factor θ:

zj ← zj / θ   if zj > 0,     zj ← zj · θ   if zj ≤ 0     (only for tokens already seen) θ ≥ 1 is the penalty; the CTRL paper suggests about 1.2. The sign split exists because dividing a negative logit by 1.2 would raise it. It is a yes/no test: seeing a token once or ten times gives the same penalty. Example: ␣mat 4.0 → 3.33, and its probability falls from 0.467 to 0.310.

What counts as "already seen" differs: Hugging Face and vLLM include the prompt, llama.cpp looks at the last 64 tokens by default (penalty_last_n). Including the prompt is a real problem for code and JSON, where you must reuse the prompt's variable names, quotes and brackets.

Frequency and presence penalties (additive)

OpenAI's API documents the exact formula:

zj ← zj − cj · αfrequency − [cj > 0] · αpresence cj = how many times token j has been sampled so far. [cj > 0] is 1 if it appeared at all. Both coefficients range from −2 to 2 (negative values encourage repetition); OpenAI calls 0.1–1 reasonable. vLLM counts only generated tokens for these two.

Worked example: ␣mat has been generated twice, αfrequency = 0.5, αpresence = 0.6. New logit 4.0 − 2 × 0.5 − 0.6 = 2.4. ␣floor was seen once: 3.2 − 0.5 − 0.6 = 2.1. Now ␣mat has probability 0.19 instead of 0.467, ␣floor still trails it, and ␣bed (never seen, logit still 2.5, probability 0.21) is the new favorite. Because the change is additive in logit space, its effect is the same for every token regardless of the logit's scale. That makes it more predictable than the multiplicative penalty.

DRY: penalize repeated sequences, not tokens

The penalties above punish individual tokens, so they also punish "the", commas and every legitimately repeated name. DRY ("Don't Repeat Yourself", proposed by p-e-w for text-generation-webui and now in llama.cpp) targets the actual failure: verbatim loops. At each step it finds the longest suffix of the context that also occurred earlier. The token that followed that earlier occurrence is the token that would continue the loop, and only it gets penalized:

penalty = multiplier · basen − allowed_length    for n ≥ allowed_length n = length of the repeated suffix. The standard settings are multiplier 0.8, base 1.75, allowed length 2 (llama.cpp ships with the multiplier at 0, i.e. disabled). Matching stops at "sequence breakers" (llama.cpp default: newline, :, ", *), so chat-format prefixes such as "User:" are not penalized. The penalty grows exponentially, so a long verbatim loop becomes impossible.

Logit bias, bans and allow-lists

The bluntest tool: add a fixed number to chosen token IDs, zj ← zj + bj. OpenAI accepts biases from −100 to 100; −100 effectively bans a token and +100 effectively forces it. vLLM also has bad_words and allowed_token_ids, and Hugging Face has no_repeat_ngram_size, which hard-bans any repeated n-gram. The catch is that biases act on token IDs, not words. To ban "cat" you must ban cat, ␣cat, ␣Cat, CAT and every multi-token spelling (Chapter 3). For anything bigger than a handful of tokens, use constrained decoding instead (later in this chapter).

Beam search, and why chat does not use it

The problem greedy cannot solve. Greedy commits to the best token now, even if a slightly worse token now leads to a much better sentence. Beam search keeps several partial sequences ("beams") alive and picks the best complete one at the end. Think of it as a breadth-limited search: at every step expand each of the B beams by its top tokens, score every candidate by its total log-probability, and keep the best B.

score(y1..t) = Σs=1..t log p(ys | context, y<s)    (optionally divided by tα) The total log-probability of the sequence. Summing logs equals multiplying probabilities. Longer sequences always have lower totals, so engines divide by length to the power α (the "length penalty") to avoid favoring short outputs.

Why chat does not use it. Beam search is excellent when there is one right answer and the model's most probable sequence is that answer: machine translation and speech recognition used it for years. For open-ended text it is the wrong objective. Holtzman et al. showed that maximizing sequence probability produces bland, generic and repetitive text, the same degeneration greedy has, only more so. It also costs B× the decode work and KV cache (prefixes can be shared copy-on-write, Chapter 12), and it cannot stream, because the best beam can change until the very end. Modern ways to spend extra compute on quality, like best-of-N with a verifier or self-consistency voting, are built on sampling instead (Chapter 10).

Stopping: EOS, stop sequences, max_tokens

The loop has to end. There are four ways, and the API reports which one happened in finish_reason (OpenAI Chat Completions), the response status (OpenAI Responses) or stop_reason (Anthropic).

  1. A stop token. The model samples a special end token such as Llama 3's <|eot_id|> (special tokens are covered in Chapter 3). The engine checks every sampled ID against a small set of stop IDs. This is a token-level check and costs nothing.
  2. A stop sequence. The user supplies strings, for example "</answer>". This check is on text, not on token IDs, because the same string can be tokenized many ways, and a match can begin in the middle of a token. OpenAI accepts up to 4 stop sequences (and not on its latest reasoning models); the returned text excludes the stop sequence (vLLM has include_stop_str_in_output to keep it).
  3. A length limit. max_tokens (OpenAI now max_completion_tokens in Chat and max_output_tokens in Responses; both also count hidden reasoning tokens) or the context window runs out. The output is cut mid-thought, often mid-sentence or mid-JSON.
  4. Other. A tool call (tool_calls / tool_use, Chapter 9), a content filter, or a refusal.

Streaming makes stop sequences tricky. If the model has produced "</", the server cannot send it yet: it might be the start of "</answer>", which must not reach the client. So the server keeps a holdback buffer of text that is a prefix of some stop string, and releases it only when the match fails.

Seeds and random number generators

Computers do not produce true randomness on demand. A pseudo-random number generator (PRNG) is a deterministic function that turns a seed into a long stream of numbers that look random. Same seed and same sequence of calls give the same stream, bit for bit. The widgets in this chapter use mulberry32, a 32-bit generator small enough to show in full:

function mulberry32(seed) {            // state = one 32-bit integer
  return function () {
    seed = (seed + 0x6D2B79F5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;   // u in [0, 1)
  };
}
const rand = mulberry32(42);   // seed 42: the same 1,000 draws in every browser

Seed 42 gives the same 1,000-draw histogram in your browser, in mine, and in the screenshot tool used to check this page. That works because everything else is fixed too: the logits are constants, the arithmetic is a short sequence of IEEE doubles done in one fixed order, and nothing else shares the computation. Keep those three conditions in mind; a GPU server breaks all of them.

On GPUs, PyTorch's CUDA generator uses Philox, a counter-based generator: the random number at position i is a hash-like function of (seed, offset + i). There is no sequential state to pass between threads, so 128,256 threads can each compute their own number independently, like indexing into an infinite random array. This is why the exponential race in Figure 14.3 is cheap.

Seeds in serving. Without a per-request seed, vLLM fills the noise for the whole batch from one shared generator, so which random numbers your request gets depends on who else is in the batch. With seed set, vLLM gives the request its own generator (its source notes this per-request path is slower). OpenAI's seed parameter is now marked deprecated and was always "best effort", with system_fingerprint to detect backend changes. A seed fixes the random bits. It does not fix the logits, and the logits are where the next problem lives.

Why temperature 0 is still not deterministic

Greedy decoding uses no randomness, so the same prompt should always give the same output. On real servers it does not. Thinking Machines Lab measured this in 2025: 1,000 completions of "Tell me about Richard Feynman" at temperature 0 from Qwen3-235B-A22B-Instruct-2507 on vLLM, 1,000 tokens each, produced 80 different outputs. All 1,000 agreed for the first 102 tokens. At token 103, 992 continued "Queens, New York" and 8 wrote "New York City". From there the texts went their own ways.

The root cause is floating-point addition order. Floating-point addition is not associative: (0.1 + 1020) − 1020 = 0, but 0.1 + (1020 − 1020) = 0.1, because the first sum rounds 0.1 away. Every logit is the end of millions of additions: dot products over d = 4,096 in every layer, attention sums, normalization sums. Change the order of any of them and the last bits of the result change.

But the order is fixed for a given kernel, so why would it change? The popular answer is "GPU threads finish in random order and atomics add in random order". Thinking Machines showed that this is mostly not the issue: the kernels in an LLM forward pass generally do not use atomics and give identical bits when run twice on identical inputs. The real issue is that kernels are not batch-invariant. To keep all 132 SMs of an H100 busy, a matmul library picks its strategy from the problem shape. With few rows it may split the long reduction dimension across several cores and combine the partial sums at the end (split-K); with many rows it does not need to. Attention kernels similarly choose how many pieces to split the KV cache into. The batch size changes the shape, the shape changes the strategy, the strategy changes the addition order for your row. And with continuous batching (Chapter 15) the batch size at each decode step depends on how many other users happen to be active.

Other sources add to the same effect:

  • MoE routing. The router picks the top-k experts per token (Chapter 7). A last-bit change can flip which expert wins a near-tie, which changes the whole layer's output for that token. Engines with expert capacity limits can also drop or reroute tokens depending on what else is in the batch.
  • How the prompt is chunked. Chunked prefill and prefix caching change how much of the attention sum is computed in one piece versus read from the cache, so the same token's attention can be reduced in a different order.
  • Different hardware or software. A different GPU model, driver, kernel library version, tensor-parallel degree (which changes all-reduce order), quantization, or engine version changes the numerics. Behind one API model name there may be many such deployments.
  • Sampling itself. With T > 0, a draw u near a segment boundary flips when the boundaries move by a few ulps, even with a fixed seed.

How to get determinism. Make every kernel batch-invariant: use one reduction strategy for all batch sizes (one tile configuration, no split-K), split attention's KV into chunks of a fixed size rather than a fixed number of chunks, and lay out the KV cache the same way whether a token comes from prefill or decode. Thinking Machines did this on vLLM: all 1,000 Feynman completions became identical. The cost on Qwen3-8B, 1,000 requests: 26 s with default vLLM, 55 s with unoptimized deterministic kernels, 42 s after improving the attention kernel. vLLM now ships this as VLLM_BATCH_INVARIANT=1 (Hopper-class GPUs or newer), and its docs add that reproducibility holds only on the same hardware and the same vLLM version. On a local single-user engine, a fixed seed with nothing else in the batch usually reproduces exactly.

Common misconception

"Temperature 0 means deterministic." It means no randomness in the sampler. The logits themselves depend on batch composition, hardware and software versions. Deterministic output needs batch-invariant kernels and a pinned deployment. Why it matters beyond debugging: evaluations become repeatable, and in reinforcement learning (Chapter 10) the inference engine that generates the training samples and the trainer that scores them can compute bit-identical probabilities, so the model is trained on exactly the distribution it sampled from.

Structured output: constrained decoding

The problem. Programs need output they can parse: JSON matching a schema, a function call, a date in one format, one label from a fixed list. Asking nicely works most of the time. OpenAI reported that training alone got its August 2024 model to 93% on a hard schema-following benchmark; 7% failures is a lot of crashed parsers. Older models scored under 40%.

The idea. Do not ask; make invalid output impossible. Compile the format into an automaton. At every decoding step, ask the automaton which vocabulary tokens could extend the current output and still lead to a valid document. Set every other token's logit to −∞ before softmax. Their probability becomes exactly 0, the rest are renormalized, and sampling proceeds as usual. Then advance the automaton by the characters of the token that was actually chosen. This is constrained decoding. With it, OpenAI's Structured Outputs reached 100% schema compliance on that benchmark.

  • JSON mode guarantees syntactically valid JSON, any shape.
  • JSON Schema / Structured Outputs guarantees the shape: required keys, types, enums. (OpenAI response_format with strict: true; Anthropic output_config.format; vLLM structured_outputs.)
  • Regex and grammars (llama.cpp's GBNF, Lark/EBNF elsewhere) express arbitrary formats: SQL subsets, a DSL, a tool-call syntax.

How grammar engines make the mask fast

The hard part is speed. A naive engine would test all 128,256 tokens against the grammar at every step, each token being a multi-character string. Three designs dominate:

  • Outlines (Willard & Louf, 2023) turns a regex or simple schema into a finite-state machine and precomputes, for every FSM state, the list of tokens that are legal from it. At run time the mask is a table lookup. The cost moves to compile time and memory.
  • XGrammar (Dong et al., MLSys 2025) handles full context-free grammars with a pushdown automaton. It splits the vocabulary into context-independent tokens, whose legality depends only on the current grammar position and can be precomputed, and context-dependent tokens, which need the stack and are checked at run time with a persistent stack. It reports up to 100× speedups over earlier engines and overlaps mask computation with GPU work.
  • llguidance (Microsoft) runs an Earley parser over a regex-derivative lexer and walks a trie of all tokens, pruning whole subtrees at once. It quotes about 50 μs of CPU time per token for a 128K vocabulary with negligible startup, and has powered OpenAI's Structured Outputs since May 2025. It is also integrated into vLLM, SGLang and llama.cpp.

The budget is tight but clear: a decode step of an 8B model on an H100 takes a few milliseconds (Chapter 11), and the CPU computes the next mask while the GPU runs the forward pass. If the mask takes longer than the step, decoding stalls.

Constraints change what the model says

The mask guarantees form, not content. When the model's preferred tokens are illegal (Step 5), its remaining probability is renormalized among tokens it found less likely, which can lower quality. Practical rules: describe the format in the prompt as well, so the model already wants to produce it; put free-text "reasoning" fields before "answer" fields so the model thinks before it commits; check for length stops, which leave the JSON unfinished; and handle refusals, which OpenAI reports in a separate refusal field.

Logprobs: reading the distribution

The sampler throws away almost everything the model computed: 128,255 of 128,256 probabilities per step. Many APIs let you keep a little of it. With logprobs on, each generated token comes back with its log-probability (natural log, so always ≤ 0), and with top_logprobs = k (OpenAI allows 0–20) you also get the k most likely alternatives at that position. Convert back with p = elogprob: −0.34 means 0.71, −2.3 means 0.10. OpenAI also returns each token's raw UTF-8 bytes, because a single character can be split across tokens (Chapter 3).

Uses. Flag low-confidence spans (a number or a name with p = 0.4 deserves a second look). Classify with scores instead of text: ask for a one-token label and read the logprobs of each label. Score fixed candidate answers by summing their token logprobs. Compute perplexity for evaluation (Chapter 8). Debug sampler settings by seeing what was cut.

Caveats. Which distribution is reported varies: vLLM by default returns logprobs computed from the raw logits, before penalties and temperature; other servers report the processed distribution. Post-training tends to make probabilities less calibrated than a base model's, so a 0.9 does not mean "right 90% of the time". And reasoning models often do not expose logprobs at all: OpenAI's GPT-5.2 accepts logprobs only with reasoning effort none.

Recommended settings

Two principles cover most cases. If the task has one right answer, sample less: low temperature or greedy, plus structured output when a program reads the result. If you want variety, sample more, but cut the tail with min-p or top-p so that variety does not mean junk. Change one knob at a time; OpenAI's own docs advise altering temperature or top-p, not both.

Reasoning models want their own temperature

Reasoning models (Chapter 10) are trained with reinforcement learning on samples drawn at a specific temperature, and their useful behaviors, such as exploring an alternative or noticing a mistake, were learned under that sampling. Low temperatures and greedy decoding push long chains of thought into loops. As a result, vendors now publish fixed recommendations or simply refuse other values:

Key takeaway

For hosted frontier models the trend is clear: the sampler is becoming part of the model, tuned by the vendor and locked. The knobs in this chapter still matter for open-weight models you run yourself, for non-reasoning modes, and for understanding why outputs vary. When you do set them: temperature for spread, min-p or top-p for the tail, structured outputs for format, and batch-invariant kernels if you need exact repeatability.
