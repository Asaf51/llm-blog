Part III · Chapter 10

Reasoning, Thinking & Effort

A "reasoning model" is an ordinary transformer that has been trained to write a long scratchpad before it answers. This chapter explains why those extra tokens make it smarter, how reinforcement learning teaches the habit, what the thinking looks like at the token level, and what the effort knob in today's APIs actually changes: tokens, latency, memory and money.

In this chapter
  • Why thinking helps: every token gets the same fixed compute (≈ 2N FLOPs) and the same fixed depth (L layers). Writing intermediate tokens adds serial steps and scratch memory.
  • Test-time compute: thinking longer (one long chain) versus thinking wider (many samples + majority vote or a verifier), with real numbers.
  • How reasoning is trained: reinforcement learning with verifiable rewards, the GRPO math worked step by step, the DeepSeek-R1 recipe, distillation into small models, outcome vs process rewards.
  • What a reasoning response is, token by token: <think> blocks and harmony channels, which tokens are billed, shown, and kept for the next turn; hidden, summarized and encrypted reasoning in commercial APIs; thinking between tool calls.
  • Effort and thinking budgets in the OpenAI, Anthropic, Gemini, Qwen3 and gpt-oss interfaces, and the four ways effort is implemented: prompt conditioning, budget forcing, hard caps and adaptive thinking.
  • What thinking costs (worked example on Llama 3.1 8B), how it fails, and how to pick an effort level. An interactive effort simulator.
  • Build it: a one-GPU reasoning lab: measure thinking longer vs thinking wider on real models, write a budget forcer and the GRPO loss from the equations, run a mini R1-Zero on a 0.5B base model, and pit it against distillation.

Why thinking helps

The problem. A transformer produces one token per forward pass (Chapter 1). Each pass does a fixed amount of work: about 2N FLOPs for N parameters, pushed through exactly L layers (Chapter 6). For Llama 3.1 8B that is about 16 GFLOP and 32 layers per token, no matter whether the question is "What is 2 + 2?" or "Prove this theorem." The model cannot decide to spend more on a hard token. If the answer needs more computation than one pass can hold, the first answer token is a guess.

The idea. Let the model write intermediate tokens before the answer. Each written token buys one more full forward pass, and its result is stored in the context where every later token can read it. This is the same trick you use when you multiply 47 × 38 on paper instead of in your head: you do not get smarter, you get more steps and a place to write partial results.

Intuition: a fixed-depth circuit with a tape

One forward pass is like a combinational circuit with a fixed depth of 32 stages: it can do a lot in parallel, but only 32 stages in sequence. Generating a token and feeding it back turns the circuit into a loop with an external tape. The tape is the context (physically, the KV cache, Chapter 12). A loop with a tape can run algorithms whose number of sequential steps grows with the problem. That is the whole reason chain-of-thought works.

Two resources a token gets: compute and depth

It helps to separate two things a written token provides.

  • Serial depth. Inside one forward pass, information climbs at most L = 32 layers. Attention lets a position read other positions, but only at the same layer (sideways, never upward). So a single pass is a computation of depth 32, however wide. When a token is emitted and fed back, the result of layer 32 re-enters at layer 1 of the next position. Depth adds up: 32 per token.
  • Scratch memory. Each written token leaves keys and values in all 32 layers (128 KiB per token for Llama 3.1 8B in BF16). Later tokens read that memory through attention. Thinking tokens are literally the model's working storage.

Theory backs this up. Li et al. (2024) show that a constant-depth transformer without chain-of-thought can only solve problems in a small parallel complexity class, while the same transformer allowed T intermediate tokens can simulate any boolean circuit of size T. In plain words: without thinking tokens the model is a shallow parallel circuit; with them it is a sequential computer whose running time you pay for in tokens. Problems such as multi-digit arithmetic, tracking state through a long program, or checking a proof are inherently serial, so they benefit most.

Low-level: a thinking token is an ordinary decode step

There is no special "thinking hardware" or mode. A thinking token is generated by exactly the same decode step as any other token (Chapter 11): read all 16.06 GB of weights, do ≈ 16 GFLOP of matmuls plus 4·L·d·t = 524,288·t FLOPs of attention at position t, append 128 KiB to the KV cache, sample. At batch 1 on an H100 the bandwidth ceiling is roughly 209 tok/s (an approximate upper bound; Chapter 11 refines it to ≈ 223), so 500 thinking tokens take at least about 2.3 s. The only things that make a token "thinking" are its position (between <think> and </think>, or in an analysis channel) and what the serving layer does with it afterwards.

Key takeaway

Compute per token is fixed by the architecture. Compute per answer is not: it is proportional to the number of tokens generated. Reasoning models turn that observation into a product feature, and "effort" is the knob that sets how many tokens they spend.

From prompt trick to trained skill

Reasoning started as a prompting trick and became a training target. The short version of the history:

  • Scratchpads (2021). Nye et al. trained small transformers to emit intermediate steps of addition and program execution into a "scratchpad" before the result. Multi-step tasks that failed "in one pass" started to work.
  • Chain-of-thought prompting (Jan 2022). Wei et al. put eight worked examples with step-by-step solutions in the prompt. A 540B model then wrote its own steps and reached state-of-the-art accuracy on GSM8K grade-school math.
  • Self-consistency (Mar 2022). Wang et al. sampled many chains and took a majority vote over the final answers: +17.9 points on GSM8K. This is the first big "spend more inference compute" result.
  • Zero-shot CoT (May 2022). Kojima et al. found that appending "Let's think step by step" was enough: GSM8K accuracy of text-davinci-002 went from 10.4% to 40.7%.
  • RL-trained reasoning (Sep 2024). OpenAI's o1 was trained with large-scale reinforcement learning to produce a long hidden chain of thought. Accuracy improved smoothly with both more RL training and more thinking at test time.
  • Open recipes and effort knobs (2025 →). DeepSeek-R1 published a full RL recipe; s1 showed test-time scaling from 1,000 examples plus "budget forcing"; Qwen3 and gpt-oss made thinking switchable and leveled. APIs then moved from token budgets to effort levels with adaptive thinking.

The important shift is from asking a model to show steps to training it so that writing steps pays off. A prompted model imitates the look of reasoning from its pretraining data. An RL-trained model has been rewarded only when its chains led to correct answers, so it keeps the habits that work (checking, backtracking, trying another approach) and drops the ones that do not.

Test-time compute: think longer or think wider

The problem. You have a fixed model and want a better answer. You cannot change the weights at request time, so the only thing you can spend is inference compute, usually called test-time compute. There are two ways to spend it, and they have very different latency profiles.

  • Sequential: think longer. One chain of thought with more tokens. The model can notice a mistake in step 3 and fix it in step 7. Cost and latency both grow with length, because decode is strictly serial.
  • Parallel: think wider. Sample N independent answers and combine them. Cost grows with N, but latency barely grows if the N samples run as one batch (decode is memory-bound, so a batch of 8 costs little more wall-clock than a batch of 1; see Chapter 11).

Combining parallel samples

Three combiners are common, from cheapest to most powerful.

  • Majority vote (self-consistency). Extract each sample's final answer and return the most frequent one. It needs no extra model. It returns the mode of the model's answer distribution, so it helps exactly when the correct answer is the single most likely answer but has less than 100% probability. It does nothing for free-form outputs like essays, where no two samples are equal.
  • Best-of-N with a verifier. Score each sample with something that can judge it: unit tests for code, a checker for math, or a learned reward model. With a perfect verifier, accuracy becomes pass@N, the probability that at least one sample is right (formula below; the counting behind the unbiased pass@k estimator is in Primer 4).
  • Search guided by a process verifier. Score partial solutions step by step and expand only promising ones (beam search over reasoning steps). Snell et al. (2024) found that choosing the strategy per prompt difficulty ("compute-optimal" scaling) beat plain best-of-N by more than 4× in compute efficiency.
pass@N = 1 − (1 − p)N where p is the probability that a single sample is correct and samples are independent. With p = 0.30: one sample gives 30%, eight samples give 1 − 0.78 = 94.2%. Even p = 0.05 reaches 96.2% at N = 64, if (a big if) the verifier never picks a wrong answer.

Real numbers make the trade-off concrete. On the 2024 AIME math exam, OpenAI reported that GPT-4o solved 12% of problems. o1, which thinks sequentially, solved 74% with one sample, 83% with a majority vote over 64 samples, and 93% when re-ranking 1,000 samples with a learned scoring function. Sequential thinking gave the big jump; parallel sampling added the last points at 64× to 1,000× the cost.

Common misconception

"More thinking always helps." The curve is logarithmic at best: going from 1,000 to 10,000 tokens costs 10× and might add ten points; going from 10,000 to 100,000 costs another 10× and might add two. On easy questions the curve is flat from the start, and the extra tokens are pure cost (see "How reasoning fails" below).

Training reasoning with reinforcement learning

The problem. Supervised fine-tuning (Chapter 9) teaches a model to copy example outputs token by token. For reasoning that is a poor fit: we rarely have good long chains of thought to copy, and copying a human's chain does not teach the model which of its own habits lead to right answers. What we do have, for math and code, is a cheap way to check the final answer.

The idea: reinforcement learning with verifiable rewards (RLVR). Let the model try. Check the result with a program. Make the tokens of successful attempts more likely and the tokens of failed attempts less likely. Repeat millions of times. Nobody writes the chains; the model discovers which ones work. This is trial-and-error learning, like tuning a heuristic by running it against a test suite, except the "heuristic" is billions of weights and the gradient tells you which way to nudge each one.

Three pieces of vocabulary, used precisely below:

  • Policy πθ: the model being trained, viewed as a function that gives a probability to every next token. θ are its weights.
  • Rollout: one complete sampled response (thinking plus answer) to a prompt.
  • Reward r: a number scoring a rollout. In RLVR it comes from a rule, not a neural network: 1 if the boxed answer equals the reference (checked with a math parser such as sympy), or if the code passes the unit tests; 0 otherwise. DeepSeek-R1-Zero also used a format reward for putting the reasoning between <think> and </think>.

Why does this work at all? Because the starting model already produces a correct, well-reasoned answer sometimes. A strong base model sampled at temperature 1 explores many different chains. RL does not have to invent reasoning from nothing; it shifts probability mass toward chains that happen to succeed. Over thousands of steps, behaviors that raise the success rate (re-checking, decomposing, trying a second method) become common. If the model never gets a problem right, every sample earns 0 and there is nothing to learn from that problem. That is why the prompt pool is filtered to problems that are hard but not hopeless.

GRPO step by step

The problem GRPO solves. Policy-gradient methods need to know whether a rollout was better or worse than expected, not just its raw reward. A reward of 1 on a trivial problem says little; a reward of 1 on a problem the model usually fails says a lot. Classic PPO (used for RLHF, Chapter 9) learns a separate value model, a second network about as large as the policy, to predict the expected reward at each token. That doubles the trainable memory, and predicting the value in the middle of a 30,000-token chain from a single final 0/1 reward is hard.

The idea. Group Relative Policy Optimization (GRPO, from DeepSeekMath, 2024) drops the value model. For each prompt it samples a group of G rollouts and uses the group itself as the baseline: a rollout's advantage is how much better its reward is than the group average, measured in group standard deviations. Like grading on a curve.

The objective, symbol by symbol

J(θ) = 𝔼 [ 1G Σi=1..G 1|oi| Σt ( min( ρi,t Âi, clip(ρi,t, 1−ε, 1+ε) Âi ) − β · DKL ) ] ρi,t = πθ(oi,t | q, oi,<t) / πold(oi,t | q, oi,<t) — how much the new weights changed the probability of the token that was actually sampled.
Âi = (ri − mean(r1..G)) / std(r1..G) — the group-relative advantage, shared by all tokens of rollout i.
|oi| — rollout length in tokens (averaging per rollout). ε — clip range, 0.2 is typical. β — KL weight (0.04 in DeepSeekMath, 0.001 in DeepSeek-R1).
DKL per token ≈ πref/πθ − ln(πref/πθ) − 1, an estimator that is always ≥ 0.

Work one token through it (the 𝔼 is an average over samples and DKL a distance between two distributions; refresher: Primer 4). A token in a correct rollout had πold = 0.20 and after some updates πθ = 0.23, so ρ = 1.15. With Â = +1.29: ρ·Â = 1.48 and clip(1.15)·Â = 1.48, the minimum is 1.48, and the gradient flows. If ρ had reached 1.30, the clipped term 1.2 × 1.29 = 1.55 would be the minimum, and it does not depend on θ, so that token contributes no more push. The KL term for this token with πref = 0.20: 0.870 − ln 0.870 − 1 = 0.0093, times β = 0.001: negligible early on, but it accumulates over thousands of tokens and steps. DeepSeek also notes that a KL penalty summed over very long outputs implicitly penalizes length, and they periodically reset the reference model to the current policy (every 400 steps in R1) so the policy can travel further.

Why does raising "log-probability of the sampled tokens" improve the model? The gradient of the unclipped term is Âi · ρ · ∇θ ln πθ(oi,t). The ∇ ln π part is the same gradient as in pretraining's cross-entropy loss for that token (Chapter 8; why the gradient of a probability becomes ∇ ln π is in Primer 3). So GRPO is "supervised training on your own samples", weighted by +1.29 for winners and −0.77 for losers. Credit assignment is coarse: every token in a winning chain is reinforced, including a useless detour. It works because, averaged over many rollouts, tokens that actually help appear more often in winners than in losers.

Low-level: what one RL step costs (8B model)

Memory. PPO-style RLHF keeps four 8B networks, ≈ 288 GB before activations (Chapter 9, Figure 9.4). GRPO with a rule-based verifier keeps two: the trainable policy (128 GB) and the frozen reference (16 GB): ≈ 144 GB. The verifier is a Python function.

Compute. Take an R1-sized step: 512 rollouts, and suppose they average 8,000 tokens (illustrative): 4.1 M tokens. Generating them costs 2N per token ≈ 6.6 × 1016 FLOPs; reference log-probs another 2N (6.6 × 1016, a prefill-like pass); the training forward + backward 6N (2.0 × 1017). About 3.3 × 1017 FLOPs per step.

Why generation dominates anyway. The generation FLOPs are the smallest item, but they run as memory-bound decode, one token at a time per sequence. Holding all 512 sequences at 8,000 tokens needs 512 × 8,000 × 128 KiB ≈ 500 GiB of KV cache (Chapter 12), and the longest rollout in the batch decides when the step can finish. RL frameworks therefore pair an inference engine for rollouts with a training engine for updates and copy weights between them every step (16 GB for 8B in BF16).

Optional deep dive: known biases in GRPO and later fixes

Zero-variance groups. If all G rollouts get the same reward (all right or all wrong), the standard deviation is 0 and every advantage is 0: the prompt contributes no gradient but still costs a full group of rollouts. DAPO (2025) adds dynamic sampling, which drops such groups and refills the batch, and a decoupled clip with a larger upper bound so low-probability tokens can rise faster.

Length bias. The 1/|oi| factor averages the loss within each rollout. For a wrong rollout (negative advantage), a longer chain spreads the same penalty over more tokens, so each token is punished less. Dr. GRPO (2025) shows this artificially inflates response length, especially of incorrect outputs, and removes the per-rollout length normalization and the std division.

Difficulty weighting. Dividing by the group std up-weights prompts where nearly all rollouts agree (very easy or very hard), because a small std makes advantages large. Whether that is desirable is debated.

The DeepSeek-R1 recipe, and distillation

DeepSeek-R1 (paper January 2025, extended version January 2026) is the best-documented recipe for a frontier reasoning model, so it is worth following end to end. It has two parts: an experiment that shows RL alone can create reasoning, and a practical pipeline that makes the result usable.

R1-Zero: RL straight on a base model

The DeepSeek team took DeepSeek-V3-Base (671B-parameter MoE, 37B active, Chapter 7), skipped supervised fine-tuning entirely, and ran GRPO with only two rule-based rewards: accuracy (is the final answer right?) and format (is the reasoning inside <think>…</think> and the answer inside <answer>…</answer>?). The prompt template simply said the assistant "first thinks about the reasoning process in the mind and then provides the user with the answer."

What happened is the most cited result in this area:

  • AIME 2024 accuracy (pass@1) rose from 15.6% to 77.9% over training, and to 86.7% with self-consistency voting.
  • The average response length grew steadily on its own, from hundreds to thousands of tokens. Nobody asked for longer answers; longer answers earned more reward.
  • Reflective behavior emerged: the frequency of words like "wait", "verify", "mistake" and "check" rose 5–7× during training. The paper shows an "aha moment" where the model writes "Wait, wait. Wait. That's an aha moment I can flag here" and re-derives a step.
  • The downsides: poor readability and language mixing (English and Chinese inside one chain), and weak general skills such as writing. Instruction-following (IF-Eval) was only 46.6%.

R1: four stages to make it usable

  1. Cold start. Fine-tune the base model on a few thousand long chains of thought written in a clean, conversational style. This gives RL a readable starting point.
  2. Reasoning RL. GRPO on math, code and logic with rule-based rewards, plus a language-consistency reward (the fraction of words in the target language). The paper's ablation shows this costs a little accuracy but makes the chains readable.
  3. Rejection sampling and SFT. Sample many answers from the RL checkpoint, keep only correct and readable ones (about 600k reasoning samples), add about 200k non-reasoning samples (writing, factual QA, translation) and fine-tune on all 800k. For a simple query like "hello", the training target has no chain of thought at all.
  4. RL for all scenarios. A final GRPO round mixing rule-based rewards for reasoning with neural reward models for helpfulness and harmlessness (Chapter 9).

The whole RL effort was cheap relative to pretraining. The paper reports 512 H800 GPUs for about 198 hours for R1-Zero (101K GPU-hours), 41K GPU-hours for R1 and 5K for building the SFT data: 147K H800 GPU-hours, about $294K at $2/hour. DeepSeek-V3's full training run took about 2.79M H800 GPU-hours, so the reasoning stage added roughly 5% (Chapter 8 has the pretraining numbers).

Distillation: the cheap way to a small reasoning model

Distillation here means plain supervised fine-tuning of a smaller model on the big model's outputs (full chain of thought plus answer); see Chapter 9 for the general technique. DeepSeek fine-tuned Qwen2.5 and Llama models on the same 800k samples for 2–3 epochs. One of the bases was Llama 3.1 8B, this blog's running model. A big model discovers them; distillation hands them down. Qwen3 used the same idea ("strong-to-weak distillation", from the teacher's logits rather than sampled text) for its small models and reported needing about 1/10 of the GPU-hours of running its full four-stage pipeline on each one.

Key takeaway

Reasoning ability is mostly created by RL on large models with verifiable rewards, then copied into smaller models by supervised fine-tuning on their chains of thought. The chains themselves are the valuable artifact, which is one reason commercial vendors hide them (next section but one).

Outcome rewards vs process rewards

The problem. A 0/1 reward on the final answer is sparse. A 5,000-token chain that makes one arithmetic slip at token 4,900 gets the same 0 as total nonsense, and a chain that reaches the right answer by luck gets full credit for its wrong steps.

  • An outcome reward model (ORM) scores only the final result. Rule-based verifiers are perfect ORMs for checkable tasks.
  • A process reward model (PRM) is a neural network that scores each intermediate step. OpenAI's "Let's Verify Step by Step" (2023) collected PRM800K, 800,000 human labels of individual steps of MATH solutions, and found that a process-supervised reward model, used to pick the best of many sampled solutions, solved 78% of a representative subset of the MATH test set, clearly beating outcome supervision.

PRMs look strictly better, so why did DeepSeek-R1 not use them? The paper lists them as an unsuccessful attempt, for three reasons: it is hard to define what a "step" is in free-form reasoning; it is hard to label step correctness at scale (humans are expensive, models are unreliable); and any neural reward model can be reward-hacked (the policy learns to produce text the reward model likes rather than text that is correct), which forces retraining the reward model. Rule-based outcome rewards cannot be flattered. The current consensus is: outcome rewards for RL training on checkable tasks, and PRMs (or other learned verifiers) for test-time search and re-ranking, where they guide which partial solutions to expand.

What a reasoning response looks like, token by token

A reasoning response is one flat token stream (Chapter 3 covers chat templates and special tokens). The model writes a delimited thinking region, then a closing delimiter, then the answer. The same thing in other formats

gpt-oss uses OpenAI's harmony format. Instead of think tags it has channels: the chain of thought goes to the analysis channel, tool calls usually to commentary, and the user-facing answer to final. The reasoning level is a line in the system message:

<|start|>system<|message|>You are ChatGPT, a large language model trained by OpenAI.
Knowledge cutoff: 2024-06
Current date: 2026-10-31

Reasoning: high

# Valid channels: analysis, commentary, final. Channel must be included for every message.<|end|>
<|start|>user<|message|>What is 47 × 38?<|end|>
<|start|>assistant  ← generation starts here
<|channel|>analysis<|message|>47×38 = 47×40 − 47×2 = 1880 − 94 = 1786.<|end|>
<|start|>assistant<|channel|>final<|message|>1786<|return|>

Each <|…|> marker is a single special token in the o200k_harmony encoding (<|start|> = 200006, <|end|> = 200007, <|message|> = 200008, <|channel|> = 200005, <|return|> = 200002). The harmony spec gives the same history rule as Qwen3: drop previous chain-of-thought once a turn has ended with a final message, but keep it while the model is in the middle of tool calls. It also warns that the analysis channel is not trained to the same safety standard as final and should not be shown to end users.

Qwen3's "no thinking" mode is a neat trick: with enable_thinking=False the chat template simply pre-fills an empty block, <think>\n\n</think>\n\n, right after assistant\n. The model sees that thinking is already over and starts answering. The soft switches /think and /no_think in a user message do the same thing from inside the conversation, because the model was trained on data where those flags decide whether the think block is filled.

Commercial APIs: hidden, summarized, encrypted

Closed models generate the same kind of stream, but the API changes what you receive. Three mechanisms recur across vendors:

  • Hidden raw thinking. OpenAI does not expose raw reasoning tokens at all. Anthropic's docs state that no setting returns the raw chain of thought. You pay for the thinking tokens either way.
  • Summaries. You can ask for a readable summary instead: OpenAI reasoning.summary (auto, concise, detailed), Anthropic thinking.display: "summarized" (the default on newer Claude models is "omitted", an empty block), Gemini thinking_summaries: "auto". Anthropic notes the summary is written by a different model, and you are billed for the full thinking, not the summary. So the billed output can be much larger than what you see.
  • Encrypted reasoning for round trips. In a tool-use loop the model must see its own earlier thinking when it resumes. The provider does not want to give you the plaintext, so it gives you an opaque ciphertext to send back: OpenAI's reasoning items carry encrypted_content (returned by default when store is false), Anthropic's thinking blocks carry a signature containing the encrypted full thinking, and Gemini returns thought signatures. The server decrypts it and splices the original thinking back into the prompt. You must pass these blocks back unchanged; Anthropic rejects modified thinking blocks with a 400 error.

Thinking between tool calls

Agents call tools in a loop (Chapter 9). Interleaved thinking means the model can think again after each tool result, inside the same assistant turn, instead of planning everything up front. OpenAI's current reasoning models and Anthropic's adaptive-thinking models do this by default; older Claude models needed the interleaved-thinking-2025-05-14 beta header.

Common misconception

"Thinking is free because I never see it." It is billed as output at the full output price, it occupies the context window (a request can hit max_output_tokens during thinking and return an empty answer that you still pay for), and on models that keep past thinking it is re-billed as input on every later turn.

Effort controls in today's APIs

The problem. One model serves both "classify this email" and "find the race condition in this kernel". Thinking 20,000 tokens on the first is waste; thinking 200 on the second is failure. Every major interface now exposes a knob for how much the model should think. The names differ, and so do the semantics: some are soft (a request the model was trained to honor approximately), some are hard (a limit enforced by the serving code).

Three details matter in practice. First, the levels are not portable: Anthropic's docs warn that a level on one model does not produce the same amount of thinking as the same level on another, and OpenAI's supported values and defaults change per model. Second, modern effort settings are adaptive: OpenAI says models "reason adaptively across reasoning efforts, using fewer tokens for simpler tasks", and Anthropic's adaptive thinking may skip thinking entirely on easy inputs at lower effort. Effort sets a posture, not a token count. Third, effort can affect more than thinking: Anthropic applies it to all output, so lower effort also means fewer and terser tool calls.

The gpt-oss numbers show what a level buys on hard math: about 30 points from low to medium and 12 more from medium to high on AIME 2025. On GPQA (graduate science questions, more knowledge than search) the steps are 6 and 7 points. The model card summarizes it as "log-linear returns on most tasks, where longer CoTs provide higher accuracy at a relatively large increase in final response latency and cost."

How effort is implemented

An effort setting has to turn into a different number of generated tokens. There are four mechanisms, and real systems combine them.

1. Conditioning: effort is text in the prompt

The simplest and most common mechanism: the effort level is rendered into the context as tokens, and the model was trained to behave differently depending on those tokens. gpt-oss is explicit about it: the model card says the three levels "are configured in the system prompt by inserting keywords such as Reasoning: low" and that the models were trained to support them. Anthropic's docs say the resolved effort value (and the legacy budget_tokens) "is rendered into the prompt", which is exactly why changing it between requests breaks the prompt cache: the prefix tokens changed (Chapter 12). Qwen3's /think and /no_think flags work the same way.

How is a model trained to respect such a tag? The vendors do not publish details, but the general approach is straightforward: during RL, sample the effort tag along with the prompt, and make the reward depend on both correctness and length relative to what that tag allows (for example, a penalty for exceeding a target length at low effort). The model learns a conditional policy: a different length distribution per tag. Because this is learned behavior, it is approximate. That is why every vendor calls effort "soft".

2. Budget forcing: the serving loop edits the stream

The second mechanism needs no training at all. The decode loop counts thinking tokens and intervenes at the token level. The s1 paper (2025) named it budget forcing:

  • To cap thinking: when the count reaches the budget, append the end-of-thinking delimiter yourself (and optionally a phrase like "Final Answer:"). The model, seeing its thinking is over, writes the answer. Qwen3 documents its own version: insert "Considering the limited time by the user, I have to give the solution based on the thinking directly now.\n</think>.\n\n".
  • To extend thinking: when the model tries to emit the end-of-thinking delimiter too early, suppress it and append "Wait" instead. The model, reading "Wait", re-examines its work. s1-32B went from 50% to 57% on AIME 2024 this way.

In code, the whole mechanism is a wrapper around the ordinary decode loop:

def generate_with_budget(model, prompt_ids, min_think, max_think, max_tokens):
    out, n_think, thinking = [], 0, True      # prompt already ends in "<think>\n"
    kv = model.prefill(prompt_ids)                  # Chapter 11
    while len(out) < max_tokens:
        logits = model.decode_step(kv)               # one forward pass
        if thinking and n_think >= max_think:
            forced = tok("\n</think>\n\n")                # too long: hard stop
        elif thinking and n_think < min_think and argmax(logits) == END_THINK:
            forced = tok(" Wait")                         # too early: extend
        else:
            if thinking and n_think < min_think:
                logits[END_THINK] = -float("inf")      # never sample a stop yet
            forced = [sample(logits)]                    # normal path (Chapter 14)
        for t in forced:                                 # append + extend KV cache
            out.append(t); model.feed(kv, t)
            if t == END_THINK: thinking = False
            elif thinking: n_think += 1
            if t == END_OF_TURN: return out
    return out                                          # truncated: "incomplete"

Note what the forced tokens cost: each one still goes through a forward pass to extend the KV cache (it is just not sampled). Forcing a 30-token sentence like Qwen3's costs 30 decode steps, or one small prefill if the engine batches them.

3. Hard caps: max_tokens

max_tokens (Anthropic), max_output_tokens (OpenAI, Gemini) is the crudest control: generation simply stops. It is the only limit every provider guarantees, and it counts thinking and answer together. OpenAI's guide warns that a response can end with status incomplete before any visible text and recommends reserving at least 25,000 tokens for reasoning and output when you start. Use it as a safety net for cost, not as an effort control.

4. Adaptive thinking: the model decides

The newest mechanism moves the decision into the model. Qwen3's "thinking mode fusion" stage trained one model on a mix of samples with full think blocks and samples with empty ones, so the same weights can do both; the Qwen3 report notes that the ability to answer from incomplete thinking, which their budget mechanism relies on, emerged from this mix without being trained directly. Commercial adaptive modes (Anthropic's type: "adaptive", Gemini's dynamic thinking, OpenAI's adaptive reasoning within an effort level) go further: the model judges each request's difficulty and may emit no thinking block at all. Effort then sets the threshold: at low it skips thinking on most easy prompts, at max it thinks readily and deeply. Anthropic also notes that in a tool loop the first request after new user input usually carries most of the reasoning, and later requests that only process tool results may skip it.

Intuition: four layers of control

Think of a process scheduler. Prompt conditioning is the nice value: a hint the process was written to respect. Adaptive thinking is the process deciding how long to run based on its workload. Budget forcing is a supervisor that sends signals at fixed points ("not yet", "stop now"). max_tokens is SIGKILL.

One more knob is orthogonal to all of this: parallel effort. OpenAI's reasoning.mode: "pro" (on GPT-5.6 and GPT-6 models) "performs more model work" for the same effort level and bills all of those tokens. The documentation does not describe the method; sampling several candidates and combining them is the classic way to spend extra compute without adding latency (the parallel axis of Figure 10.4).

Thinking tokens are output tokens in every sense that matters to the machine: one decode step each, 128 KiB of KV cache each (for our 8B model), and output-token pricing. Work through one request on the running model to see the size of each effect.

How reasoning fails

Reasoning models fail in ways that ordinary chat models do not. Knowing the patterns tells you what to watch in logs and evals.

  • Overthinking. Spending thousands of tokens on "what is 2 + 3?", re-verifying an answer that was right the first time. A 2024 study of o1-like models named the problem and measured large token waste on easy questions. It hurts cost and latency, rarely accuracy. Fix: lower effort, adaptive thinking.
  • Truncation. Hitting max_tokens during thinking. The visible answer is empty or cut off and the tokens are still billed. Fix: a generous max_tokens, lower effort, or a server-side budget that forces an answer.
  • Repetition loops. Long chains under greedy decoding can fall into cycles ("Wait, let me re-check… Wait, let me re-check…"). Qwen3's model card says explicitly not to use greedy decoding in thinking mode; use the vendor's recommended sampling settings (Chapter 14).
  • Unfaithful chains of thought. The visible reasoning is not guaranteed to be the reasoning that produced the answer. Anthropic researchers planted hints in prompts (for example, a note that a professor thinks the answer is C) and checked whether models that used the hint said so. Claude 3.7 Sonnet mentioned the hint 25% of the time and DeepSeek-R1 39% of the time; unfaithful chains were on average longer than faithful ones. With commercial APIs there is a second layer: the text you see is a summary written by another model.
  • Reward hacking. RL optimizes the reward, not your intent. With unit-test rewards a model can learn to special-case the tests; with a neural reward model it can learn to please the grader. This is why R1 avoided neural rewards for reasoning, and why chain-of-thought monitoring (reading the thinking during training to spot hacking) is an active safety topic; a 2025 position paper argues that this monitorability is valuable and fragile.
  • Narrow skills. RL on math and code does not automatically help writing or instruction-following. R1-Zero scored 46.6% on IF-Eval; the full R1 pipeline with SFT and general RL raised it to 83.3%. R1-Zero also mixed English and Chinese mid-chain.
Common misconception

"The chain of thought is the model's explanation." It is generated text that helped the model reach an answer, shaped by a reward that looked only at the answer. It is often informative and sometimes misleading. Treat it as a debugging aid, not as a proof or an audit log.

Choosing an effort level

Start from the workload, then measure. A sensible default table:

WorkloadStart atReason
Classification, extraction, routing, autocomplete, voicenone / minimal / lowlatency-bound; the answer is one short step
Chat, drafting, summarization, simple Q&Alow / mediumsome planning helps; long chains mostly add delay
Agentic coding, multi-step tool use, data analysismedium / highplanning and recovering from tool errors pay off
Hard math, proofs, deep debugging, research, long agent runshigh / xhigh / maxaccuracy still rising with tokens; run asynchronously if you can
  1. Sweep, do not guess. Run your eval set at two or three levels and plot accuracy against cost and latency. Levels are recalibrated between model versions, so redo it when you switch models.
  2. Lower effort before prompt tricks. Effort is a trained, calibrated control; "answer briefly, do not deliberate" in the prompt is wording-sensitive.
  3. Size max_tokens for thinking plus answer. It is the only hard cap. Too small and you pay for truncated thoughts with no answer.
  4. Keep effort stable inside a cached conversation. The request-level setting is part of the prompt prefix; changing it restarts the cache. Some newer models accept a per-message effort change (Anthropic, beta) that keeps the cached prefix.
  5. Prefer parallel compute when you have a verifier. If you can check answers (tests, a solver), several medium-effort samples plus a check often beat one max-effort chain, at lower latency.
  6. Watch the usage fields. reasoning_tokens / thinking_tokens / total_thought_tokens tell you what you actually paid for.
Key takeaway

A reasoning model buys accuracy with tokens. Every effort level is a point on a curve where each extra 10× of thinking costs 10× in output tokens, latency and KV-cache time, and returns a shrinking gain. Pick the point per workload, verify it with evals, and remember that the thinking you do not see is still on the bill.

Hints (open only when stuck)
  • Advantages come out as +1.21 / −0.72: torch.std defaults to the Bessel-corrected sample std. Figure 10.7 uses the population std (correction=0). Implementations differ; pick one and say which in the report.
  • Out of memory computing log-probs: 128 rollouts × 700 tokens × 151,936 vocabulary entries × 4 B ≈ 54 GB of FP32 logits. Run the forward pass 4–8 sequences at a time and gather the sampled token's log-prob immediately (logit minus logsumexp).
  • Clip fraction is nonzero on the very first update: πold must come from a forward pass of the same model in the same dtype, not from generate's scores. If you sample at temperature T, divide the logits by T in every log-prob computation.
  • Clip fraction is always exactly 0: with one optimizer step per rollout batch, ρ ≡ 1 by construction. Split each batch into 2–4 mini-batches; later ones see ρ ≠ 1.
  • Garbage rollouts in batched generation: decoder-only models need left padding (tokenizer.padding_side = "left"). The loss mask starts after the prompt and ends at the first EOS, inclusive. A rollout that hits max_new without an answer earns 0, and the policy learns to stop.
  • The 0.5B base will not follow the template: SimpleRL-Zoo found that complex prompts destabilize zero-RL on weak instruction followers, and used simpler ones for its small Qwen models. Start with "…put your final answer in \boxed{}"; add the <think> format reward only after that trains.
  • maj@k looks too good: normalize answers before voting (1,786 and 1786.0 are one vote), let None abstain, and break ties uniformly at random. Breaking ties toward the first answer seen quietly inflates the score.
  • Budget counts drift in the vLLM version: decoding and re-tokenizing between phases can merge tokens across the boundary (Chapter 3). Keep token IDs end to end, and count thinking tokens from IDs, never from text.
  • vLLM and training on one card: vLLM reserves most of the GPU by default. Lower gpu_memory_utilization, or run the sampling-heavy milestones in a separate process from training.
