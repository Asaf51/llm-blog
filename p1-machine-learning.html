What Machine Learning Is: programs found by search

Some programs cannot be written by hand, but they can be found. Pick a family of functions, measure how wrong each member is on examples, and keep nudging the numbers that select the function until the error is small. This chapter builds that idea from a two-parameter line up to the vocabulary that every later chapter assumes.

In this chapter
  • Machine learning replaces hand-written rules with examples. You choose a family of functions, and an optimizer picks the member that fits the data. An LLM is the extreme case: no rulebook can predict the next word, but ~15 trillion tokens of examples exist.
  • Every training setup has four ingredients: data, a model with parameters, a loss and an optimizer. Parameters are learned (2 for a line, 8,030,261,248 for Llama 3.1 8B). Hyperparameters, such as the learning rate, are chosen by you.
  • On 8 requests, the best line through time to first token versus prompt length is 36.14 ms per thousand tokens plus 20.68 ms, with a mean squared error of 23.47 ms². A guess of 40 ms per thousand tokens scores an MSE of 187.
  • Gradient descent walks downhill on the loss landscape: measure the slope, then step against it by η × slope. Starting from (0, 0) with η = 0.1, it matches the exact least-squares answer to within 10−6 in 423 steps. Any η above 0.139 (2 divided by the steepest curvature of the landscape) diverges.
  • Minibatches give a noisy but cheap slope. After one pass over 1,000 requests, full-batch descent has taken 1 step (MSE 10,157), while batches of 32 have taken 32 steps (MSE ≈ 134, best possible 105).
  • Logistic regression turns a score into a probability with the sigmoid and trains on log loss. A predictor of missed latency targets reaches 92.6% validation accuracy and a log loss of 0.220, against 72.0% and 0.597 for a dumb baseline.
  • What counts is error on data the model has not seen. A degree-11 polynomial fits 12 points exactly but has a validation RMSE of 1,622 requests/s, while degree 5 scores 46.5. Train/validation/test splits, more data, weight decay, early stopping and dropout fight overfitting. Leakage silently breaks all of them.
  • Supervised, self-supervised and reinforcement learning differ only in where the right answers come from. Next-token prediction gets its labels for free.
  • Build it: fitlab, a NumPy-only lab that fits the chapter's line by gradient descent and checks it against least squares to 10−6, finds the learning rate where descent diverges, races minibatches against full batches, and then overfits, regularizes and honestly evaluates polynomials and a logistic classifier, reproducing every number above.

Programs you cannot write by hand

Part 0 of this book, the Primer, is six short chapters on the machine-learning ideas, math and tools that Chapters 1–16 assume. If you already know gradient descent, train/validation splits, derivatives, probability and PyTorch, skip straight to Chapter 1. Later chapters link back here whenever they lean on a Primer idea.

Suppose you run an LLM service and want an alert when a request is about to miss its latency target: say 500 ms to the first token. You could write a rule: if prompt > 6000 and queue > 10: alert(). Where do 6,000 and 10 come from? You would look at past requests and pick thresholds that separate the misses from the rest. In other words, you would be fitting the rule to data by eye. With two inputs that works. With fifty (model, GPU type, batch size, cache hit rate, time of day…) nobody can tune the thresholds by hand, and nobody knows which combinations matter.

Machine learning automates the tuning. Instead of writing the rule, you write a rule template with blanks: "score = w1 × prompt length + w2 × queue depth + b; alert when the score is high". The blanks are numbers. A program then searches for the values that make the template agree with many past examples. Later in this chapter that search turns 100 past requests into three numbers, w1 = 1.15, w2 = 0.78 and b = −16.1. The result predicts 500 requests it never saw correctly 92.6% of the time.

Next-word prediction is the extreme case. What rule says that after "The cat sat on the" the next word is probably "mat"? Such a rule would need grammar, idioms, facts about cats and the conventions of children's books, and the same again for every other context. Nobody can write that rulebook. Examples, however, are free: every sentence ever written is a list of (context, next word) pairs. Llama 3.1 8B is a template with 8,030,261,248 blanks, filled in by searching against about 15 trillion tokens of text. Given "The cat sat on the", it puts probability 0.755 on ␣mat. Chapter 1 explains why this one task forces so much capability into the blanks.

This chapter teaches the search: what is being searched, how "wrong" is measured, how the search moves, and how you can tell whether the result will work on data it has never seen. Every example is small enough to check by hand or in a few lines of NumPy. The same loop, scaled up by about nineteen orders of magnitude, trains an LLM.

Systems analogy: an autotuner with a compass

If you have used an autotuner (ATLAS tuning BLAS block sizes, or a GPU kernel tuner trying tile shapes and keeping the fastest), you already know the shape of machine learning: a program with knobs, a measurement, and a search over the knobs. Machine learning differs in three ways. The knobs are continuous numbers, and there can be billions of them. The measurement is "how wrong are the outputs on examples" rather than speed. And the search has a compass that autotuners lack: the slope of the error tells it which way to turn every knob at once. Without that compass, billions of knobs would be hopeless.

The four ingredients: data, model, loss, optimizer

Every training setup in this book, from the line below to Llama, is built from the same four parts.

  1. Data. A set of examples. Each example is an input x and the desired output y. The parts of the input are called features (prompt length, queue depth). The desired output is the label (the measured latency, or "missed the target: yes or no").
  2. Model. A family of functions with a fixed shape and some adjustable numbers. The numbers are the parameters, written θ (theta) when we mean all of them at once, and also called weights. Choosing θ picks one function from the family. The model's output for an input is its prediction, written ŷ ("y-hat"): ŷ = f(x; θ). The semicolon separates the input from the parameters.
  3. Loss. One number that says how wrong the predictions are across the data. Lower is better, and 0 usually means perfect. The loss is the only thing the search can see, so whatever it fails to measure, the model will not learn.
  4. Optimizer. The algorithm that changes θ to make the loss smaller. Running the optimizer over the data is training. Afterwards the parameters are frozen and the model is only used. That is inference, the subject of Chapters 11–15.

Parameters versus hyperparameters

The optimizer learns the parameters, but some choices it cannot make. Which family of functions to use, how big each step is, how many steps to take, how many examples to look at per step: you choose all of these before training starts. Any such setting is a hyperparameter. The difference matters because the two are tuned in different ways. Parameters are fitted to the training data by the optimizer. Hyperparameters are chosen by trying a few values and comparing the results on separate data (see Generalization below).

A first model: fitting a line

Here is a small data set: eight requests to an LLM server, each with its prompt length and its measured time to first token (TTFT, the delay before the first output token appears; Chapter 11). The numbers are illustrative, but they have the shape of a real single-GPU server. Processing the prompt costs work in proportion to its length, plus a fixed overhead for tokenizing, scheduling and launching the work.

The input x is the prompt length in thousands of tokens, and the label y is TTFT in milliseconds. The model is a straight line:

ŷ = w · x + b where w is the slope (extra milliseconds per thousand prompt tokens) and b is the intercept (the fixed overhead in milliseconds). These two numbers are the parameters, θ = (w, b). Every pair (w, b) is one line, and the model family is the set of all lines.

To compare lines we need the loss. The standard choice for predicting a number is the mean squared error (MSE). Take each prediction's error, square it, and average the squares:

MSE(w, b) = 1N Σi=1N (ŷi − yi)2 N = the number of examples (8 here). i numbers the examples. Σ ("sigma") means "add up the expression for i = 1, 2, …, N". ŷi = wxi + b is the prediction for example i, and yi is its label. The error ei = ŷi − yi is in ms, so MSE is in ms².

Squaring does three jobs. Positive and negative errors cannot cancel. Big errors cost more than small ones: being 20 ms off costs 400, four times the cost of being 10 ms off. And, as the next section shows, the result is a smooth bowl that is easy to search. To get back to milliseconds, take the square root: the root mean squared error (RMSE) is a typical error size.

The fitted model is just these two numbers, and it answers for prompts it never saw: a 2,700-token prompt gets 36.14 × 2.7 + 20.68 ≈ 118.3 ms.

Optional deep dive: the closed-form answer, and why we search anyway

For this one combination, a linear model with squared error, the best parameters have a formula. Let x̄ and ȳ be the averages (2.25 and 102). Then w = Σ(xi − x̄)(yi − ȳ) / Σ(xi − x̄)2 = 379.5 / 10.5 = 36.142857, and b = ȳ − wx̄ = 102 − 36.142857 × 2.25 = 20.678571. This is the method of least squares, published by Legendre in 1805. NumPy's np.linalg.lstsq computes it for any number of features.

So why does the rest of the chapter search? Because the formula exists only for this special case. Change the loss to the log loss of the classification section, or the model to a neural network, and no formula exists. A search guided by slopes works for all of them. Here, the formula gives us a reference answer to check the search against.

The loss landscape

Fix the data, and the loss becomes a function of the parameters alone: each (w, b) pair gives one MSE. Picture it as terrain. The two parameters are map coordinates and the loss is the altitude. This surface is the loss landscape, and training means finding its lowest point.

Start with a slice. Hold b at its best value, 20.68, and vary w alone. The loss traces a parabola with its bottom at w = 36.14 (left of Figure P1.4). At every point the curve has a slope: how much the loss rises per unit increase of w. Left of the bottom the slope is negative (at w = 10 it is −333), and right of it the slope is positive (+304 at w = 60). At the bottom it is exactly zero. So the sign of the slope tells you which way the bottom is, and its size tells you roughly how far away it is.

Now both parameters at once. The right panel draws the landscape as a contour map: each ring joins points of equal loss, like the height lines on a hiking map. For a linear model with squared error, the landscape is always a perfect bowl with a single bottom and no false valleys. (The technical word is convex.) The rings are long, thin and tilted, though. The tilt says that w and b can trade off: a steeper line with a lower intercept fits almost as well. Every prompt in the data has a positive length (2.25 thousand tokens on average), so raising w by 1 can be mostly undone by lowering b by about 2.25. In the direction across the valley the bowl is steep. Along the valley it is almost flat. That shape will decide how fast the search can go.

An LLM's landscape has 8,030,261,248 coordinates, so it cannot be drawn. Nor is it a bowl. It has many valleys, ridges, saddle points and long flat stretches. Locally, though, the picture is the same: at any point there is an altitude (the loss) and a slope in each direction. That is all the search below needs.

Worked numbers: why not just try every value?

You could search a grid: 1,000 values of w × 1,000 values of b is 106 loss evaluations, cheap for 8 points. But the cost multiplies with every parameter. Three parameters need 109 evaluations and ten need 1030. Llama would need 1,0008,030,261,248. Exhaustive search dies at a handful of parameters. Following the slope costs one slope per parameter per step, whatever the number of parameters.

Gradient descent: walking downhill

The idea is simple: from wherever you are, find which way is downhill, take a small step that way, and repeat. Finding the downhill direction only needs one slope per parameter, and you can measure a slope like a programmer: nudge the parameter a tiny amount and see how the loss changes.

Start from the guess (w, b) = (40, 0), where MSE = 187.0. Nudge w to 40.001 and recompute: the MSE becomes 186.95613, a change of −0.04387. Dividing by the nudge gives a slope of about −0.04387 / 0.001 ≈ −43.87. The slope is negative, so increasing w lowers the loss. Nudging b the same way gives a slope of −24.0, so increasing b helps too. For a line with MSE the slopes also have an exact formula, (2/N) Σ eixi for w and (2/N) Σ ei for b. They give −43.875 and −24 exactly. Primer 3 derives such formulas and shows how a computer gets them automatically for any program. Here you only need the idea that a slope says "this way is up, this steeply".

The list of slopes, one per parameter, is the gradient. It points uphill, so the step goes the other way:

w ← w − η · slopew      b ← b − η · slopeb ← means "replace with", like w -= eta * slope_w in code. η (the Greek letter eta) is the learning rate, a small positive number that scales the step. It is a hyperparameter. Repeating this update is gradient descent, published by Cauchy in 1847 and still the core of every optimizer used for LLMs.

Figure P1.5 runs one step with η = 0.05 in numbers.

The learning rate: too small, about right, too big

How big should η be? Look at the one-dimensional slice again, with b fixed at its best value. There the loss is exactly 23.47 + 6.375 (w − 36.14)2 and its slope is 12.75 (w − 36.14). Put that slope into the update rule and one step does this:

(w − 36.14) ← (1 − 12.75 η) · (w − 36.14) Each step multiplies the distance to the bottom by the same factor, 1 − 12.75η. The number 12.75 is how quickly the slope itself changes as w moves: the curvature of the bowl. It equals twice the average of x2. Primer 3 covers curvature properly.

Everything about the learning rate follows from that factor. Starting at w = 10 (Figure P1.6):

  • η = 0.01: factor 0.8725. Each step removes only 13% of the remaining distance. After 8 steps w is 27.4 and the loss is still 514.9. The search is correct but slow.
  • η = 0.07: factor 0.1075. Each step removes about 90% of the distance, so the search is essentially at the bottom after two steps.
  • η = 0.15: factor −0.9125. A negative factor means overshooting: each step jumps past the bottom to the other side, landing a little closer. The search zigzags and settles slowly.
  • η = 0.17: factor −1.1675. Each jump lands farther away than where it started. The distance grows by 17% per step, and after 8 steps the loss is 51,939. This is divergence: the search runs away and soon overflows to infinity.

The edge is where the factor reaches −1: η = 2 / 12.75 = 0.157. A steeper bowl (bigger curvature) has a smaller safe learning rate.

With both parameters, the steepest direction sets the limit. Across the tilted valley the curvature is 14.39 (technically, the largest eigenvalue of the Hessian, the table of second slopes that Primer 3 introduces), so any η above 2 / 14.39 = 0.139 diverges. Running it confirms this: η = 0.138 still converges, bouncing for 1,167 steps, and η = 0.140 blows up. The flattest direction, along the valley, has curvature 0.365 and sets the speed. Even at the best rate (about 0.135), each step shrinks the along-valley distance by only about 5%. From (0, 0), getting both parameters within 10−6 of the least-squares answer takes 4,298 steps at η = 0.01, 854 at 0.05, 423 at 0.1 and 309 at 0.135 (from Figure P1.5's start (40, 0), η = 0.05 takes 912). The ratio of the two curvatures, 39 here, is called the condition number. The bigger it is, the slower plain gradient descent becomes. Fixing that is the job of the optimizers in Chapter 8 (momentum and Adam), whose Figure 8.7 races them on a valley like this one.

Gotcha: units change the safe learning rate

Measure prompt length in tokens instead of thousands of tokens and nothing about the problem changes, except that x is 1,000 times bigger. The curvature in the w direction grows a million-fold to 12,750,000, so the largest safe learning rate becomes 1.57×10−7. At that rate, b (curvature 0.41) would need hundreds of millions of steps to converge. This is why inputs are usually rescaled to a similar size before training (fitlab does it in milestone 5). Inside networks, normalization layers keep values at a standard scale (Chapter 4), and Adam gives every parameter its own step size (Chapter 8).

Key takeaway

Gradient descent repeats one move: measure the slope of the loss for every parameter and step each one against its slope, scaled by the learning rate η. Too small an η wastes steps. Too large an η overshoots, and past a hard edge (here 0.139) every step makes things worse. The edge is set by the steepest direction of the landscape and the speed by the flattest.

Batches, steps and epochs

The loss is an average over all N training examples, so its exact slope is an average over all of them too. Computing it means one full pass over the data for every single step. For 8 points that is nothing. For an LLM, one pass over 15 trillion tokens is the entire training budget (about 7.2×1023 FLOPs; Chapter 1), so exact slopes would allow exactly one step.

The idea is to estimate the slope from a random sample. Pick B examples at random, a minibatch, and average their slopes. The average over a random batch is right on average (it is unbiased), with noise that shrinks as the batch grows. Here is that noise measured on a larger synthetic data set of 1,000 requests (simulated with the same 36 ms per thousand tokens plus 20 ms, and random noise), at the point (w, b) = (30, 0), where the exact slope for w is −442:

Gradient descent with batch slopes is stochastic gradient descent (SGD). "Stochastic" means random. Strictly, SGD meant one example per step, but today the term covers minibatches of any size. Three counters describe a run:

  • The batch size B is the number of examples per slope estimate.
  • A step (or iteration) is one parameter update, using one batch.
  • An epoch is one full pass over the training set: N / B steps, rounded up. The examples are usually reshuffled before each epoch so the batches differ.

Why accept a noisy slope? Because it buys many more steps for the same work. Run each choice for exactly one epoch over the 1,000 requests at η = 0.01, so every run touches each example once and does the same arithmetic:

Full-batch descent has spent all that work on one careful step and is still far from the answer. Batches of 32 took 32 rough steps and are within 30% of the best possible loss. Very small batches have their own problems. At B = 1 the noise is 74% of the signal, and the hardware sits mostly idle: a GPU processes 32 examples in about the time it takes for one, because it reads the weights once for the whole batch (Chapter 4, Chapter 11). In practice, you pick the largest batch that keeps the hardware busy and still leaves enough steps. LLM batches are counted in tokens: Llama 3 405B grew its batch from 4 million to 16 million tokens per step (Chapter 8).

One side effect: with a constant learning rate, minibatch descent never settles exactly. Near the bottom the batch noise keeps kicking the parameters around. Set the widget above to batch size 2 and watch the dot jitter around the minimum. The fix is to shrink η over the course of training. That is the learning-rate schedule, covered with warmup and decay in Chapter 8.

Classification: logistic regression

Back to the alert from the opening. The label is now yes or no: did the request miss its 500 ms target? Predicting one of a fixed set of answers is classification, and with two answers it is binary classification. By convention the two classes are 1 ("missed") and 0 ("met"). A line is the wrong tool for this, because its output can be any number, including −7 or 3.2. What we want is a probability, a number between 0 and 1 that says how likely a miss is.

The idea is to keep the linear part and squash its output. First compute a score from the features, exactly as before. Then pass it through the sigmoid function σ ("sigma"), which maps any number into the range from 0 to 1:

z = w1x1 + w2x2 + b,     p = σ(z) = 11 + e−z x1 = prompt length (thousands of tokens), x2 = queue depth (requests already waiting), z = the score, also called the logit. e ≈ 2.718 is the base of natural exponents. e−z is huge when z is very negative and nearly 0 when z is large (Primer 4 reviews exp and log). So σ(z) runs from almost 0 to almost 1: σ(−2) = 0.119, σ(0) = 0.5, σ(2) = 0.881, σ(4) = 0.982.

A linear score followed by a sigmoid is logistic regression. ("Regression" because it predicts a number, the probability. It is used for classification.) The parameters are w1, w2 and b. Training on 100 past requests (24 of them missed) gives w1 = 1.153, w2 = 0.779 and b = −16.12. Take a request with a 5,000-token prompt arriving behind 15 queued requests:

z = 1.1531 × 5 + 0.7787 × 15 − 16.123 = 5.7655 + 11.6805 − 16.123 = 1.323
p = σ(1.323) = 0.79 The weights are written to four digits here so that the arithmetic checks. The model says this request has a 79% chance of missing its target. Each extra thousand prompt tokens adds 1.153 to the score and each queued request adds 0.779, so one queued request "costs" about as much as 675 prompt tokens (0.779 / 1.153 thousand). The data were simulated with 22 ms per queued request and 36 ms per thousand tokens, a ratio of 610 tokens; the model recovered it from 100 examples.

To make a yes/no decision, threshold the probability: predict "miss" when p > 0.5. Since σ(0) = 0.5, that is the same as z > 0, that is, 1.153x1 + 0.779x2 > 16.12. In the plane of the two features, this condition is one side of a straight line, x2 = 20.7 − 1.48x1. That line is the decision boundary. Logistic regression always draws a straight boundary (a flat one in more dimensions). Curved boundaries need curved features or a neural network.

Log loss

Classification needs a different loss. For each example, look at the probability the model gave to what actually happened, and charge −ln of it. The log loss (also called binary cross-entropy) of one example is −ln p if the request missed (y = 1) and −ln(1 − p) if it met its target (y = 0). Written as one formula and averaged over the data:

log loss = − 1N Σi [ yi ln pi + (1 − yi) ln(1 − pi) ] ln is the natural logarithm. For each example, exactly one of the two terms is switched on by its label, so this is just "−ln of the probability given to the right answer", averaged. Because it uses the natural log, the unit is called the nat (Primer 4 converts nats to bits).

Read it as surprise. Confident and right costs almost nothing: p = 0.99 for a request that missed costs 0.01. Confident and wrong costs a lot, without limit: p = 0.01 for a request that missed costs 4.6. The worked request with p = 0.79 costs 0.236 if it really missed and 1.561 if it did not. A model that always says 0.5 pays ln 2 = 0.693 per example, whatever happens. That number reappears often in this book.

Why not keep MSE? With a sigmoid on top, MSE gives a landscape with flat plateaus. A confidently wrong prediction sits where the sigmoid is nearly flat, so it gets almost no slope and learns slowly. Log loss gives logistic regression a bowl again (convex, with no false valleys), and its slope grows with the size of the mistake. There is a deeper reason too: minimizing log loss is maximizing the probability the model assigns to the observed data (Primer 4).

Trained by gradient descent on the 100 requests, the model reaches a training log loss of 0.208 and 92% accuracy. On 500 requests it never saw, it scores 0.220 and 92.6%. The two are close, which is a good sign (see the next section).

From two classes to 128,256

An LLM is a classifier too. Its "classes" are the 128,256 tokens of its vocabulary, and its question is "which token comes next?". With many classes, the sigmoid is replaced by softmax, which turns one score per class into probabilities that sum to 1 (Chapter 4). The loss is the same idea, −ln of the probability given to the right answer: Chapter 4's cross-entropy. With two classes, softmax reduces exactly to the sigmoid of the score difference. The same −ln σ(score) also trains reward models and DPO in Chapter 9, whose loss starts at exactly 0.693.

Generalization: train, validation, test

So far, every model was judged on the data it was trained on. That number measures fit, but you care about something else: how well the model does on the next request, the one that is not in your data. Doing well on unseen data is generalization, and the training loss alone can be badly misleading about it.

Here is a case where it misleads. Benchmark a service at different numbers of concurrent clients and record its throughput. Throughput rises with concurrency, peaks (here at about 31 clients) and then falls, as lock contention and coordination overhead grow faster than the useful work. This is the shape of Gunther's Universal Scalability Law, familiar from any shared-resource system. Each measurement carries benchmark noise of about ±40 requests/s. We fit polynomials to 12 measurements:

ŷ = w0 + w1t + w2t2 + … + wdtd t = the concurrency rescaled to the range −1 to 1 (that is, (clients − 32.5) / 31.5), d = the degree, a hyperparameter. A degree-d polynomial has d + 1 parameters. Because the prediction is linear in the parameters, least squares fits it exactly, just like the line.

The degree controls the model's capacity: how many different shapes the family can take. Degree 1 can only draw straight lines. Degree 11, with 12 parameters, can pass exactly through any 12 points. To judge each fit fairly, score it on 30 other measurements that were not used for fitting. The error is RMSE in requests/s:

Training error falls with every extra degree, reaching exactly 0 at degree 11. Validation error falls only up to degree 5 and then explodes. The two failure modes have names. Underfitting means the family is too simple to follow the pattern, so both errors are high (degree 1). Overfitting means the family is flexible enough to follow the noise as well as the pattern. Training error keeps improving while validation error gets worse (degree 8 and up).

Systems analogy: memorization is a cache that only hits on seen keys

The most extreme overfit model is a lookup table: store every training input with its label. Its training error is zero, and on any new input it misses with no fallback. Degree 11 is nearly that: exact at its 12 keys and garbage between them. A model that generalizes is more like a compression scheme. It cannot store every example, so it has to keep the pattern that produced them. Llama 3.1 8B is 16 GB of weights trained on about 60 TB of token IDs (Chapter 8), so it cannot be a lookup table for most of its data. It does still memorize text that appears many times, such as famous passages. Chapter 1 connects prediction and compression, and its Build it measures that memorization.

Three sets, three jobs

The fair score above came from data held out of training. Done properly, the data is split three ways, once, at random, before you look at anything:

  • The training set is used by the optimizer to fit the parameters.
  • The validation set (also "dev set" or "held-out set") is used by you to compare models and choose hyperparameters: the degree, λ, the learning rate, when to stop.
  • The test set is used once, at the very end, to produce the number you report.

Why not two sets? Because choosing among twelve degrees by validation score is itself a kind of fitting. The winner was picked because it scored best on those 30 points, so its validation score is slightly optimistic. The test set has influenced no decision at all, so its score is an honest estimate. Typical splits are 80/10/10. With LLMs, held-out text runs to millions of tokens, and benchmarks act as test sets (Chapter 9).

Key takeaway

Training error measures fit; held-out error measures what you care about. Capacity too low underfits, and capacity too high fits the noise. Fit parameters on the training set, choose hyperparameters on the validation set, and touch the test set once.

Fighting overfitting

Overfitting happens when the model has more freedom than the data can pin down. There are two ways out: more data to pin the freedom down, or less freedom, by restricting the model directly or by stopping before it uses all of its freedom. Four standard tools, each measured on this chapter's data:

1. More data

Keep degree 11, but fit it on 48 measurements instead of 12. The validation RMSE drops from 1,622 to 52.1. A wiggle needs a gap between data points to hide in. With four times as many points, the noise pulls in more directions at once and largely averages out. Collecting more data is the most reliable cure when it is possible. It is also the main reason LLM pretraining overfits so little: each token is seen about once.

2. Weight decay (L2 regularization)

Look at the coefficients. The degree-5 fit's coefficients are all below 1,000. The degree-11 fit, which passes exactly through all 12 points, needs coefficients as large as 158,474, huge positive and negative terms that cancel almost exactly at the 12 training points and nowhere else. Overfit solutions tend to need large weights. So add a penalty on weight size to the loss:

loss = MSE + λ Σk=1d wk2 λ (lambda) ≥ 0 is the strength, a hyperparameter. The intercept w0 is usually not penalized. Penalizing the sum of squares is called L2 regularization; in general, a regularizer is any change that trades a little training fit for better generalization.

With λ = 0.001, degree 11 on 12 points scores 46.1 on validation instead of 1,622. In gradient descent, the penalty adds 2λw to each weight's slope. The update then shrinks every weight by a factor of (1 − 2ηλ) at every step, before the data pulls it back. Weights the data does not keep supporting decay toward zero, hence the name weight decay. LLM training uses it through AdamW, which applies the shrink directly and separately from the gradient (Chapter 8, where λ = 0.1 is typical). Set λ too large and the model underfits: at λ = 0.1 the degree-3 fit's training RMSE rises from 38.6 to 103.2, and its validation RMSE from 55.0 to 59.8.

3. Early stopping

Gradient descent fits the strong, consistent patterns first and the noise later, so overfitting builds up over the course of training. To see it, give the SLO classifier a harder job: only 40 training requests, and 30 extra features that are pure noise (think hashed request IDs or random log fields). The model now has 33 parameters and 40 examples, enough freedom to memorize.

Training loss falls steadily toward zero (0.005 after 5,000 steps). Validation loss falls to 0.465 at step 66 and then rises to 1.18, twice as bad as the constant baseline of 0.595, which ignores the features entirely. Early stopping evaluates the validation loss as training goes, keeps a copy (a checkpoint) of the parameters whenever it improves, and stops once it has stopped improving for a while. The figure also shows two alternatives. Weight decay with λ = 0.1, trained to the end, reaches 0.473. Simply removing the 30 junk features, also trained to the end, reaches 0.317, better than either. The best regularizer is knowing what not to feed the model.

4. Dropout

Neural networks (Chapter 4) have one more standard tool. At each training step, dropout sets each hidden value (an intermediate number computed inside the network) to zero with probability p (often 0.1) and scales the survivors by 1/(1 − p), so their average is unchanged. At inference nothing is dropped. Because no unit can count on any other unit being present, the network has to spread what it knows over many units instead of building fragile, memorized combinations. Large LLM pretraining runs often do without it, because they see most data only once: the Llama 3 paper never mentions dropout, and the Hugging Face config.json of Llama 3.1 8B sets attention_dropout to 0.0. Dropout shows up mostly in fine-tuning on small data sets, for example as the dropout option of LoRA adapters (Chapter 9).

Tuning hyperparameters

Every knob above (degree, λ, when to stop, dropout rate, and the learning rate and batch size from earlier) is a hyperparameter, and all are chosen the same way. Train with several values, compare them on the validation set, keep the best. That can be a grid ("λ in 0.0001, 0.001, 0.01, 0.1") or random draws. Either way the test set stays locked. LLM labs do this on small models and extrapolate to big ones, because each big run is too expensive to repeat (Chapter 8).

Leakage: when the held-out data is not held out

All of this assumes that the validation and test sets are truly unseen. Data leakage is any path by which information from evaluation data reaches training or model selection. It makes scores look better than reality, and nothing crashes to warn you. Common forms:

  • Duplicates across splits. The same request logged twice, once in training and once in test. The web is full of copies, which is why LLM data is deduplicated (Chapter 8).
  • Preprocessing fitted on all the data. Rescaling features using a mean and standard deviation computed over every row lets test statistics into training. Compute them on the training set only, as fitlab does.
  • Time travel. A random split of time-ordered data trains on Tuesday's requests to "predict" Monday's. For anything you will deploy forward in time, split by time.
  • Target leakage. A feature that is a consequence of the label, such as "the client retried" when predicting SLO misses: retries happen because the request was slow. The model looks brilliant offline and is useless at prediction time.
  • Contamination. For LLMs: benchmark questions that leaked into the training crawl. The score then measures memory, not skill. Defenses are n-gram decontamination, which drops training documents that share long word sequences with a benchmark (Chapter 8), and fresh or private test sets (Chapter 9).
Systems analogy: benchmarking with a warm cache

Evaluating on training data is like benchmarking a storage system with the whole data set already in the page cache: the numbers are real, but they measure the cache, not the disk. Leakage is the subtle version. You dropped the caches, but the benchmark's working set overlaps the warm-up run, so part of the "cold" measurement is still warm.

Optional deep dive: when bigger does not overfit (double descent)

The U-shaped validation curve above is the classical picture, and it holds for this polynomial. Very large neural networks complicate it. Belkin et al. (2019) and Nakkiran et al. (2019) showed that as capacity grows past the point where the model can fit the training data exactly, validation error can peak and then fall again: double descent. Very wide models trained by gradient descent tend to find smooth solutions among the many that fit, so "number of parameters" is not the whole story of capacity; the optimizer's implicit preferences and the amount of data matter too. In practice LLMs live in a regime where bigger models trained on more data keep getting better (Chapter 8's scaling laws). The tools in this section still matter: fine-tuning on small data sets overfits readily, and it is the reason Chapter 9 runs supervised fine-tuning for only one to a few epochs.

Metrics and baselines

The loss is what the optimizer minimizes. A metric is what you report and care about. Sometimes they coincide (MSE can be both), and often they do not. Accuracy, the fraction of correct yes/no decisions, is the obvious metric for the SLO classifier, but it is useless as a loss. Nudge a weight slightly and almost no prediction crosses the 0.5 threshold, so accuracy does not change at all: its slope is zero nearly everywhere, and gradient descent gets no direction. So you train on a smooth loss (log loss) and report the metric (accuracy), usually alongside the loss.

For numbers, predict the training mean. For classes, predict the most common class (or always give its frequency as the probability). For language, give every token the same probability. The coin-flip baseline p = 0.5 would score 0.693. The uniform guess over the vocabulary is ln 128,256 ≈ 11.76 nats, which is where an untrained Llama 3 starts (Chapter 4). For the line, 1 − 23.47 / 1,738 = 0.986: the line explains 98.6% of the variation in TTFT, a statistic known as R2.

Two habits complete the picture. First, look at the classes. If only 1% of requests miss, "never alert" is 99% accurate and catches nothing. For rare events, report how many of the real misses the model caught (recall) and how many of its alarms were real (precision). Second, remember that a metric measured on a finite sample is itself noisy. The 92.6% above, measured on 500 requests, is only good to about ±1.2 points. A rival model scoring 93.1% on the same set is not clearly better. Primer 4 computes that noise, and Chapter 9 applies it to LLM benchmarks.

Common misconception

"The loss went down, so the model got better." The training loss is supposed to go down; that is what the optimizer is for. Better means a lower held-out metric than both the previous model and a dumb baseline, by more than the measurement noise. Figure P1.12's model had a training loss of 0.005 and was worse than predicting the base rate.

Supervised, self-supervised, reinforcement

The four ingredients do not change from one kind of learning to another. What changes is where the right answers come from.

Supervised learning. Each input comes with a label that a person or a logging system attached. Every example in this chapter so far is supervised: measured latencies, recorded SLO outcomes. Labels are the bottleneck. Someone has to produce them, which caps data sets at thousands to millions of examples. Chapter 9's supervised fine-tuning is exactly this: (prompt, ideal answer) pairs, written or checked by people, teach a pretrained model to act as an assistant.

Self-supervised learning. The data labels itself: hide part of it and predict the hidden part. For text, the hidden part is the next token. The sentence The ␣cat ␣sat ␣on ␣the ␣mat yields five supervised examples for free: The → ␣cat, The ␣cat → ␣sat, and so on up to "The cat sat on the" → ␣mat. Fifteen trillion tokens of text become about fifteen trillion labeled examples with no annotator. The training is ordinary classification, over 128,256 classes, with log loss. This is pretraining (Chapter 8), and it is why LLMs could be trained at a scale no labeled data set allows.

Reinforcement learning. There is no right answer for each step, only a score for a finished attempt. The model produces an output, a reward function rates it (1 if the final math answer is correct, or a learned judge of helpfulness), and the parameters are nudged to make high-reward outputs more likely and low-reward ones less likely. The model learns from its own attempts, so it can discover strategies that no labeler wrote down. Rewards are sparse and noisy, though, and an optimizer will exploit any flaw in the reward. RLHF (Chapter 9) and reasoning training with GRPO (Chapter 10) are both reinforcement learning.

Low-level view: what one step costs

For the line, one full-batch step is about 56 floating-point operations: 16 for the predictions, 8 for the errors, about 24 for the two slopes and a few for the update. The whole 423-step fit is about 24,000 FLOPs: microseconds of compiled code on one CPU core (Python's interpreter overhead stretches it to milliseconds). For an LLM, one step costs about 6 FLOPs per parameter per token in the batch: 2 for the forward pass and 4 for the backward pass (Chapter 8). For Llama 3.1 8B that is 6 × 8.03×109 ≈ 4.8×1010 FLOPs per token, times millions of tokens per step. The arithmetic is the same kind (multiply, add, compare), organized as matrix multiplications so that GPUs can run it (Chapter 2).

The mental model to carry forward

A model is a function family plus learned numbers. Training is gradient descent on a loss, one minibatch at a time, with a learning rate that must stay below the landscape's edge. Success is judged on held-out data, against a baseline, without leaks. An LLM is this recipe with 8 billion numbers, 15 trillion tokens and a 128,256-way classification at every position.

# 3. Throughput vs concurrency: Universal Scalability Law + benchmark noise
def usl(n, lam=100.0, sigma=0.05, kappa=0.001):
    return lam * n / (1 + sigma * (n - 1) + kappa * n * (n - 1))

def throughput(seed=0):
    rng = np.random.default_rng(seed)
    n = rng.integers(1, 65, size=108)  # concurrency 1..64
    y = np.round(usl(n) + rng.normal(0, 40, size=n.size), 0)  # req/s
    # training pool, validation, test
    return (n[:48], y[:48]), (n[48:78], y[48:78]), (n[78:], y[78:])

# 4. Will a request miss its 500 ms SLO? (prompt length, queue depth) -> 0/1
def slo(n=1000, seed=1):
    rng = np.random.default_rng(seed)
    x1 = np.round(rng.uniform(0.2, 8.0, n), 2)  # prompt, k tokens
    x2 = rng.integers(0, 21, n).astype(float)  # queue depth
    ttft = 20 + 36 * x1 + 22 * x2 + rng.normal(0, 60, n)
    return np.c_[x1, x2], (ttft > 500).astype(float)

Hints (open only when stuck)
  • Descent never reaches 10−6: check that you work in float64 and compare each parameter separately with the closed form. Too large an η close to the edge (0.139) converges, but slowly: 0.1390 takes over 36,000 steps.
  • Overflow warnings in the sweep: expected. Stop a run as soon as |w| > 109 or the loss is not finite, mark it diverged, and wrap the loop in np.errstate(over="ignore").
  • Minibatch runs explode at large B: you summed the slopes over the batch instead of averaging, so the effective learning rate grows with B.
  • High-degree polynomials look like nonsense: raw concurrency raised to the 11th power reaches 6411 ≈ 7×1019. Rescale to t in [−1, 1] first, and solve with lstsq, not by inverting ATA.
  • Your ridge numbers differ slightly: the chapter's λ multiplies the mean squared error. With lstsq, append d rows √(λ·m)·ek for k = 1…d (m = number of training points) and zeros to y. Do not penalize w0.
  • Log loss is nan or inf: a probability hit exactly 0 or 1. Clip p to [10−12, 1 − 10−12].
  • The early-stopping curve does not turn up: the junk features must be standardized-normal noise added to all rows, the real features standardized with the 40 training rows' statistics, and no weight decay in that run.

  • Decay the learning rate. Run B = 1 for 30 epochs, once with a constant η = 0.01 and once with ηk = 0.01 / (1 + k/1,000) at step k, and plot how far each strays above the optimum 105.16. The constant-rate run keeps jumping by tens of ms²; the decayed run stays close. Chapter 8's schedules do this more carefully.
