Part I · Chapter 1

The Big Picture: what an LLM actually is

A large language model is one function, called in a loop, whose behavior lives in 16 GB of learned numbers. This chapter gives you a precise mental model of that function, the loop, those numbers, and the map of everything that the rest of the blog fills in.

In this chapter
  • An LLM maps a sequence of tokens to a probability for every possible next token. Nothing more.
  • Text comes out of a loop: predict, sample, append, repeat, stop. You will watch Llama 3.1 8B do it with its real probabilities.
  • A model is a few hundred lines of code plus billions of learned numbers. You will see the actual files, tensor names and sizes.
  • Training finds the numbers once, at enormous cost. Inference uses them, read-only, for every request.
  • The pipeline map: every stage from text to text, each linked to the chapter that explains it.
  • Why "just predicting the next token" produces real capability, and where that argument stops.
  • Build it: read Llama 3.1 8B's safetensors files by hand, wrap them as the function f, write the generation loop yourself, then turn that loop into llmzip, a lossless compressor that stores each token in about −log2 p bits.

One function: tokens in, probabilities out

Remove the chat window, the API and the GPU cluster, and an LLM is one mathematical function. You give it a sequence of tokens. It gives back a probability for every token that could come next. Everything else in this blog is about how that function is computed, how its numbers were found, or how to call it quickly and cheaply.

A token is a short piece of text, usually a word or part of a word, identified by an integer ID (Chapter 3 shows how text is split). The set of all tokens a model knows is its vocabulary. Llama 3 has 128,256 of them. Our running sentence, "The cat sat on the", is five tokens: The ␣cat ␣sat ␣on ␣the, with IDs 791, 8415, 7731, 389 and 279. (The ␣ marks a leading space, which belongs to the token.)

f(x1, …, xn) = p ∈ ℝV,   pi = P(xn+1 = i ∣ x1, …, xn),   ∑i pi = 1 where x1…xn are the token IDs of the input (the context), n is how many there are, V is the vocabulary size (128,256), and pi is the probability that the next token is token i. Every pi is between 0 and 1 and together they sum to 1.

Here is that function evaluated for real. I ran the published Llama 3.1 8B base weights on the five tokens above, using my own NumPy code (numbers rounded). One evaluation of f like this is called a forward pass.

Three properties of this function shape everything that follows.

  • It outputs a distribution, not text. Turning probabilities into words is a separate, tiny piece of code (next section).
  • It is deterministic. Same tokens and same weights give the same probabilities (up to floating-point rounding effects that Chapter 14 explains). Randomness enters only when a token is chosen.
  • It is stateless. The function sees only the tokens you pass in. It has no memory of earlier calls. A chat "remembers" because the client sends the whole conversation every time. The maximum number of tokens it can accept is the context window: 131,072 for Llama 3.1.
Low-level view

The raw output is a vector of 128,256 scores called logits, one per token, which a function called softmax turns into probabilities (Chapter 4). In FP32 that vector is 128,256 × 4 B = 513,024 bytes per position. Computing it for one token costs about 2 × 8.03 billion ≈ 16 GFLOP, two floating-point operations (a multiply and an add) per parameter (Chapter 6 derives this).

The generation loop

A function that predicts one token cannot write a paragraph. A loop can. Every LLM product, from autocomplete to a coding agent, runs this loop:

  1. Predict. Run f on the current context to get the distribution over the next token.
  2. Sample. Choose one token from that distribution. Always taking the most likely token is greedy decoding. Drawing at random in proportion to the probabilities is sampling. Settings such as temperature reshape the distribution before the draw (Chapter 14).
  3. Append. Add the chosen token to the end of the context.
  4. Repeat from step 1 with the longer context.
  5. Stop when the model emits a special end-of-text token, when a length limit (max_tokens) is reached, or when a chosen stop string appears.

This is autoregressive generation: each output becomes part of the next input. The model never plans a sentence and then writes it. It only ever chooses the next token, and the loop strings those choices together.

In code, the whole loop is a few lines. Real engines avoid recomputing the old tokens on every iteration (the KV cache, Chapter 12), but the logic is exactly this:

def generate(model, ids, max_tokens):
    for _ in range(max_tokens):
        probs = model(ids)              # f: 128,256 probabilities for the next token
        next_id = sample(probs)         # greedy, or a weighted random draw (Ch. 14)
        if next_id in END_TOKENS:        # e.g. <|eot_id|> = 128009 for chat-tuned Llama 3.1
            break
        ids.append(next_id)            # the output becomes input
        yield next_id                   # stream it to the user

Here is the loop running on Llama 3.1 8B for eight steps, with the model's real probabilities at each step. At step 2 the sampler picks . even though it had only 12%. A random draw does that, and it is why the same prompt can give different answers even though f itself is deterministic.

Two things to notice. The model's confidence swings from near-certain (99.2% for ␣the) to wide open (39% for the top choice after a period). And from step 4 on, it copies the pattern of its own context. Using the context like this, with no change to the weights, is called in-context learning.

Low-level view: the loop is serial

Token t+1 cannot be computed before token t exists, so generation cannot be parallelized across the output. Each step is a pass through all 8 billion weights. On one H100 GPU, with 3.35 TB/s of memory bandwidth, just reading 16.06 GB of BF16 weights takes about 4.8 ms. So a single sequence can get at most about 3.35×1012 ÷ 16.06×109 ≈ 209 tokens per second, no matter how fast the arithmetic is. (This is an approximate upper bound; Chapter 11 refines it and compares it with measured speeds.) Most of inference engineering is about this bound: process the prompt in one parallel pass, cache what can be cached, batch many users so each weight read serves many tokens, and shrink the weights (Ch. 11, 12, 13, 15).

Parameters: the numbers that were learned

What is inside f? Two things. First, a fixed recipe of operations, mostly matrix multiplications, written by people in a few hundred lines of code. Second, a very large set of numbers that the recipe multiplies by. These are the parameters, also called weights. Nobody chose them by hand. Training found them, as described two sections below.

Intuition

Think of the architecture code as an interpreter and the weights as the program it runs. It is a 16 GB program, written by an optimizer instead of a programmer, and nobody can read it line by line. Change the weights and the same code becomes a different model.

The basic unit is a weighted sum: y = w1x1 + w2x2 + …, where the x values come from the input and the w values are parameters. Compute 4,096 such sums over the same 4,096 inputs and you have a matrix–vector product y = Wx, where W holds 4,096 × 4,096 = 16,777,216 parameters. (Chapter 4 builds layers from this; Chapter 2 covers what a matrix multiply costs.) Llama 3.1 8B is 291 such tensors, matrices and vectors, holding 8,030,261,248 numbers in total.

A model on disk

Download Llama 3.1 8B from Hugging Face and this is what you get. The weights are almost all of it. Meta's reference implementation of the whole architecture (model.py in the llama3 repository) is 302 lines of Python, 10,404 bytes. The weights are about 1.5 million times bigger.

The .safetensors files are simple containers: a small JSON header lists each tensor's name, number type, shape and byte range, and the raw numbers follow, packed back to back. Llama 3.1 8B has 291 named tensors, for example model.embed_tokens.weight with shape [128256, 4096] and model.layers.0.self_attn.q_proj.weight with shape [4096, 4096]. Each of the 32 blocks has the same nine tensors, filled with its own values. You do not need to know what q_proj or gate_proj do yet (Chapter 5 and Chapter 6). Notice two numbers that appear in almost every shape: 4,096, the width of the vector that represents each token (d), and 128,256, the vocabulary size (V). Chapter 6 lists every tensor, adds them up to 8,030,261,248, and takes the file format apart byte by byte.

Key takeaway

A model is a small amount of code plus a huge array of learned numbers. Its size is parameters × bytes per parameter: 8.03 B × 2 B ≈ 16.06 GB (14.96 GiB) for Llama 3.1 8B in BF16. Fitting in GPU memory, how fast tokens come out, and what a request costs all start from this one number (Chapter 11; Chapter 13 shrinks it).

The map: from text to text

Now open the box. Figure 1.6 is the whole pipeline for one step of generation, drawn for Llama 3.1 8B and our running sentence. Every box is a link to the chapter that explains it. Come back to this map whenever you lose your place in the blog.

Reading the map from the top left:

  1. Tokenize. Text becomes 5 integer IDs (Ch. 3).
  2. Embed. Each ID selects one row of a 128,256 × 4,096 table, giving a 5 × 4,096 matrix: one vector of d = 4,096 numbers per token (Ch. 3, Ch. 4 for what such vectors mean).
  3. Transform, 32 times. Each block reads the vectors and adds an update to them. In attention, each token pulls information from earlier tokens (Ch. 5). In the MLP, each token's vector is processed on its own (Ch. 6). Mixture-of-experts models replace the MLP with many expert MLPs and use only a few per token (Ch. 7). The shape stays 5 × 4,096 the whole way.
  4. Project to the vocabulary. The last token's vector is normalized and multiplied by a 4,096 × 128,256 matrix, the LM head, giving 128,256 scores called logits (Ch. 6). Softmax turns them into probabilities (Ch. 4).
  5. Choose and emit. The sampler picks ID 5634 (Ch. 14), which is decoded to ␣mat and streamed to you (Ch. 3). Then the ID is appended and the loop runs again.
Low-level view

The first pass processes all 5 prompt tokens at once, as a 5-row matrix pushed through every weight matrix. This is prefill. Each later step pushes only the one new token through, which is decode (Ch. 11). Decode can skip the old tokens because attention's per-token intermediate results (keys and values) are saved in the KV cache: 128 KiB per token for this model (Ch. 12). The same weights are applied at every position. Word order enters mainly inside attention, which rotates query and key vectors by angles that depend on position, a scheme called RoPE (Ch. 5).

Training vs inference, from 10,000 feet

Where do 8 billion good numbers come from? From training. Using them to answer a prompt is inference. These are two very different workloads. Mixing them up is the most common source of wrong intuitions about LLMs, so here is the difference before any details.

Training starts from random weights, so the model first outputs noise. You show it real text. At every position you ask for the probability of the token that actually came next, and you measure how wrong it was with one number, the loss (Ch. 4 defines it). Then, for each of the 8 billion weights, you compute which direction would have made the loss slightly smaller. This is the gradient, found by an algorithm called backpropagation (Ch. 8). You move every weight a tiny step in that direction and repeat, for trillions of tokens. Nobody teaches the model grammar or facts. The weights drift toward whatever values predict text well.

Inference is what happens when you send a prompt. The function runs with the weights frozen. Nothing is learned and the weights are only read. Talking to a model does not change it.

Analogy

Training is compiling and inference is running the binary. You compile once, at great cost, and then run the result billions of times. Because the "binary" is read-only, it can be shared by many users at once, cached, memory-mapped and compressed.

Worked numbers

N is the parameter count (8.03×109) and D the number of training tokens (~15×1012). Training costs about 6 FLOPs per parameter per token: 2 for the forward pass and 4 for the backward pass (Ch. 8). So 6 × 8.03×109 × 15×1012 ≈ 7.2×1023 FLOPs. A 1,000-token answer costs about 2N × 1,000 ≈ 1.6×1013 FLOPs. The training run therefore equals roughly 45 billion such answers. At the H100's peak of 989 TFLOPS (BF16), 7.2×1023 FLOPs would take about 200,000 GPU-hours. Meta reports 1.46 million: real runs reach only a fraction of peak, and the reported figure covers the whole training process, not one ideal pass.

The life of a model

"Training" is really several stages, each with its own data, goal and cost, followed by the steps that turn weights into a product. The model that answers you in a chat app has usually passed through all five of the stages below. Not every model goes through every stage: many open-weight releases publish both the base model and the assistant, and non-reasoning models skip stage 3.

Why predicting the next token is so powerful

"It just predicts the next word" is true, and it sounds like it should produce autocomplete, not a model that can explain code or solve math problems. Two ideas explain the gap. Neither needs hype.

Prediction is compression

A model that predicts well can compress well, and the reverse is also true. This is an old result from information theory. If the model gives the actual next token probability p, an arithmetic coder can store that token in about −log2 p bits. A token predicted with 50% costs 1 bit. A token predicted with 1% costs 6.6 bits. Training with the standard loss (Ch. 4, Ch. 8) minimizes exactly this number, averaged over trillions of tokens. In other words, pretraining is a search for the shortest description of its training text.

Delétang et al. (2023) measured this directly. Used as a compressor, Chinchilla 70B, trained mostly on text, compressed ImageNet image patches to 43.4% of their size and LibriSpeech audio to 16.4%, beating PNG (58.5%) and FLAC (30.3%), again not counting the model's own size. Here is the point. The cheapest way to compress the internet is to capture what generates it: grammar, facts, arithmetic, the meaning of code, what people in a story want. A model that has not captured these pays bits for every token that depends on them.

Prediction forces a model of the world

To predict the next token of many texts, a model has to represent whatever those texts are about. The cleanest evidence comes from a toy experiment. Li et al. (2023) trained a GPT-style model only on lists of moves from the board game Othello. It never saw a board. Yet probes found an internal representation of the board state, and editing that representation changed the model's predicted moves as if the board had changed. Figure 1.10 shows the same pressure on the real model: each prompt can only be completed well by something beyond word statistics.

Where the argument stops

The training objective rewards plausible continuations of the training data, not true ones. A fluent wrong answer and a fluent right answer are produced by the same machinery; a "hallucination" is the model doing exactly what it was trained to do on a question its weights do not answer well. A base model imitates its data, including its errors. Post-training shapes behavior on top of this (Ch. 9). And every token gets the same fixed budget of about 2N FLOPs through a fixed number of layers, which limits how much reasoning fits into one step. Letting the model write intermediate "thinking" tokens buys more computation per answer (Ch. 10).

The mental model to carry forward

An LLM is a deterministic function from tokens to a next-token distribution, defined by a few hundred lines of code and billions of learned numbers. Text comes from calling it in a serial loop. Training searches for the numbers once; inference reads them for every token. Every later chapter refines one box of the map in Figure 1.6.

Build itllmzip: read the weights, call f in a loop, compress text with it

Time14–20 hours LevelIntermediate StackPython, PyTorch, Hugging Face transformers Hardware1 GPU, 24 GB+ (any GPU for the 0.5B dev model) UsesSections: One function: tokens in, probabilities out · The generation loop · Parameters: the numbers that were learned · Training vs inference, from 10,000 feet · Why predicting the next token is so powerful

This chapter makes three claims you can check with your own hands. A model is code plus a pile of learned numbers. The code computes one function f from tokens to 128,256 probabilities. Text comes from calling f in a loop. In this project you build each piece yourself around the real Llama 3.1 8B files. Then you put them to a use that tolerates no hand-waving: llmzip, a lossless compressor that stores each token of a text in about −log2 p bits, exactly as Prediction is compression describes.

The compressor is the strictest exam this chapter can get. Its decompressor is your generation loop with the sampler swapped for an arithmetic decoder: the compressed file is nothing but the record of which token was chosen at each step. It only works if the decoder sees the very same probabilities, bit for bit, that the encoder saw. So you will learn exactly how deterministic f is, and where floating-point rounding breaks that. And the output size is a direct measurement of how well 16 GB of learned numbers predict text.

You use Hugging Face transformers for the inside of f; writing the forward pass yourself is the Chapter 6 project (if you build it later, swap it in: llmzip is a ruthless bit-exactness test). Everything around it, from the bytes on disk to the bits in the output file, is yours.

The deliverable

  • st_reader.py and census.py: a safetensors parser that never imports safetensors, and a census that rebuilds Figure 1.5 from the raw bytes.
  • fn.py: load_model(), which builds the architecture from config.json and fills it with your tensors, and next_token_probs(), which is f.
  • loop.py: a hand-written generate() with greedy and seeded random choice, all three stop conditions, and a step-time benchmark.
  • bits.py: a meter that prices every token of a text in bits, per token and per byte.
  • llmzip.py: an arithmetic coder plus compress / decompress commands that restore files byte for byte.
  • A one-page report: your measurements next to the chapter's numbers, four plots, and the answer to "when does a 16 GB compressor pay for itself?"

Milestones

  1. Read the weights with your bare hands

    Write a parser for the format in A model on disk: an 8-byte little-endian header length, a JSON header mapping each tensor name to its dtype, shape and data_offsets, then the raw numbers packed back to back. Follow model.safetensors.index.json to find which of the four shards holds each tensor. Map files with mmap and build tensors with torch.frombuffer, so opening 16 GB costs nothing until you touch a tensor. Then write the census: group the 291 names into embedding, attention, MLP, norms and LM head by their name patterns, and print counts, bytes and percentages.     Teacher-force the path of Figure 1.3 (␣mat . ␣The ␣dog ␣sat ␣on ␣the ␣log) and print each chosen token's probability: 75.5, 12.0, 38.9, 37.4, 50.8, 93.7, 99.2, 30.3%, each within about 1 point. Greedy output for 64 tokens matches model.generate(do_sample=False) token for token on at least 9 of 10 prompts; at any divergence the top two probabilities are nearly tied (rounding, not a bug; say why in your report). 10,000 seeded draws from the step-1 distribution pick ␣mat 75.5% ± 1 point of the time. Your step time never beats the bandwidth ceiling. The curve is flat for short contexts, then climbs roughly linearly: that is the cost of recomputing the whole context every step, which the KV cache of Chapter 12 removes.

  4. A bit meter: what every token costs

    One forward pass over a whole text gives the distribution at every position at once. This is how training scores text too (Training vs inference, from 10,000 feet). Use it to price each actual token at −log2 p, and report bits per token and bits per byte of UTF-8. Bits per byte is the fair unit because it does not depend on the tokenizer. Build a corpus of 10–50 KB files: fresh English prose written after December 2023, Llama 3.1's knowledge cutoff (your own writing is ideal); a famous text the model has surely seen many times; some of your own source code; a non-English text; and 10,000 random hex digits from secrets.token_hex. Score long files in windows of at most 2,048 tokens, each starting with the begin-of-text token, and plot the average cost by position within the window.

    def token_bits(model, ids: list[int]) -> np.ndarray:
    """bits[t-1] = -log2 p(ids[t] | ids[:t]) for t = 1..n-1, from ONE forward pass."""

    "The cat sat on the mat." costs 5.3, 13.7, 8.7, 0.5, 0.2, 0.4, 3.1 bits token by token, as in Figure 1.9 (each within about 0.3), and 31.9 ± 1 bits in total against 184 bits of UTF-8. Random hex costs at least 4.0 bits per digit, its true entropy; anything lower means you are scoring the wrong token. The famous text is far cheaper than the fresh prose: that gap is memorization. Average cost falls with position in the window: context makes prediction cheaper. For a few prefixes, compare this meter with milestone 2's f called on the prefix alone. They agree to a few hundredths of a bit but are not bit-identical. Remember that for the next milestone.

  5. llmzip: turn the loop into a compressor

    An arithmetic coder turns a sequence of choices, each a sub-interval of a known distribution, into one binary fraction, spending about −log2 p bits per choice. Write one with integer arithmetic (Python's unbounded ints make this pleasant) and test it alone first, on symbols from a fixed toy distribution. Then connect it to f. The encoder walks the text's tokens and encodes each one with f's distribution at that step. The decoder is your milestone 3 loop with the sampler replaced by Decoder.target: ask f for the distribution, read which token the bits point at, append it, repeat, and stop after the token count stored in the header. Both sides must turn probabilities into integer counts in exactly the same way. Use fixed-size windows (512 tokens is a good start) so each step's context stays bounded, and define a small file format: magic bytes, model name, window size, token count, payload.

    def quantize(probs: torch.Tensor, total_bits: int = 30) -> torch.Tensor:
    """float32 [V] -> int64 CDF [V+1]; every token gets >= 1 count. Reproducible."""

class Encoder:
    def encode(self, lo: int, hi: int, total: int) -> None: ...
    def finish(self) -> bytes: ...

class Decoder:
    def __init__(self, data: bytes): ...
    def target(self, total: int) -> int: ...         # the count the code points at
    def consume(self, lo: int, hi: int, total: int) -> None: ...

    Alone, the coder packs 100,000 symbols drawn with probabilities (1/2, 1/4, 1/8, 1/8) into the sample's own ∑−log2 p plus a few bytes: about 21,875 bytes, 1.75 bits per symbol. With f, every corpus file survives compress then decompress byte for byte (cmp is silent), and the payload is at most 1% plus a few bytes above the ideal ∑−log2 p along the same path. The running sentence, 23 bytes, becomes about 4–5 bytes of payload. In your table against zlib (level 9), bz2 (level 9) and lzma (preset 9 | PRESET_EXTREME), llmzip is at least 2× smaller than the best of them on fresh prose, and far better still on the famous text. On random hex nothing beats 4 bits per digit (50%), and llmzip ties or loses to lzma: there is nothing to predict.

  6. Same code, different numbers

    The chapter claims that changing the weights turns the same code into a different model, and that training is what moves the numbers from noise to knowledge. Test both. First, skip loading: from_config alone gives you the architecture filled with random numbers. Generate from it and score your fresh prose. Second, download meta-llama/Llama-3.1-8B-Instruct, open it with your reader and diff its header against the base model's. Compute the relative change ‖Winstruct − Wbase‖ / ‖Wbase‖ for every tensor and plot it by layer for each tensor kind: this is how far post-training moved the numbers (The life of a model). Load the Instruct numbers into the same code, format one question with tokenizer.apply_chat_template, and run base and Instruct on the identical token sequence with your loop. Third, settle the caveat under Figure 1.9: the comparison ignores the size of the model. Count the 16.06 GB of weights as part of llmzip's output (Delétang et al. call this the adjusted compression rate) and compute how much fresh text you would need before llmzip beats lzma overall.

    The random model writes gibberish and costs about 17 bits per token or more: log2 128,256 ≈ 16.97, no better than a uniform guess. The trained base model costs a small fraction of that on the same text; the difference is what 1.46 million GPU-hours bought. The Instruct header has the same 291 names, shapes and dtypes as the base header: only the numbers differ. Instruct answers and stops at <|eot_id|> (128009); base behaves like a document completer. Your break-even size comes out far beyond any file you own: tens of gigabytes of text or more.

Hints (open only when stuck)
  • data_offsets count from the start of the data section (byte 8 + header length), not from the start of the file. The JSON may be padded with trailing spaces. Skip the __metadata__ key: it is not a tensor.
  • NumPy has no bfloat16, but torch.frombuffer(buf, dtype=torch.bfloat16, count=..., offset=...) reads BF16 directly (how BF16 is laid out is Chapter 2's business). A read-only mmap triggers a non-writable-buffer warning; it is harmless here, or map with mmap.ACCESS_COPY.
  • A skeleton built on the meta device leaves non-persistent buffers, such as the rotary inv_freq, unmaterialized, because they are not in the file. The simplest route is to build the skeleton directly on the GPU in BF16, then copy your tensors in. As a bonus, the untouched skeleton is milestone 6's random model.
  • Small models such as Qwen2.5-0.5B tie the LM head to the embedding (tie_word_embeddings in config.json), so the file has no lm_head.weight. Accept exactly that one missing key and tie the weights. Qwen's tokenizer also adds no begin-of-text token: prepend <|endoftext|> yourself so the first real token has a context.
  • Llama 3's tokenizer prepends <|begin_of_text|> (128000) by default, and the chapter's numbers include it. If ␣mat comes out far from 75.5%, check ids[0].
  • The logits at position t predict token t+1: score log_softmax(logits[:-1]) against ids[1:].
  • Time GPU work inside torch.inference_mode(), after a few warm-up steps, with torch.cuda.synchronize() before every clock read. For long contexts, ask for last-position logits only (recent transformers versions accept logits_to_keep=1): full float32 logits at n = 4,096 are 2.1 GB.
  • A stop string can be split across two tokens. Check the tail of the decoded text after every step, not individual tokens.
  • If decompressed text turns to garbage after some token, encoder and decoder computed different probabilities at that step. Make the encoder call f on exactly the prefixes the decoder will, with the same shapes, dtype and device. Never encode with milestone 4's one-pass probabilities. Set torch.use_deterministic_algorithms(True) (with CUBLAS_WORKSPACE_CONFIG=:4096:8), log the first mismatching position, and compare the two CDFs there.
  • Quantize in float64 then int64: counts = floor(p · (T − V)) + 1, cumulative sum, and use the actual final sum as the total. Keep the coder's state at about 62 bits and the total at or below 230, so every token's interval stays non-empty after renormalizing.
  • Before blaming the coder, check that tokenizer.decode(ids, clean_up_tokenization_spaces=False) returns each corpus file exactly (minus the begin-of-text token). A lossy tokenizer round trip makes the whole compressor lossy.
  • Compression with the 8B model is slow: a window of W tokens costs W forward passes on both sides. Keep 8B test files near 10 KB. If you want speed, the library's built-in cache (use_cache=True, past_key_values) is allowed as long as encoder and decoder make identical calls. Building a cache yourself is the Chapter 12 project.
