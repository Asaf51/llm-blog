Attention

Attention is the one place in a transformer where tokens exchange information. This chapter builds it from a soft hash-table lookup up to the exact tensor math, the way position is encoded with rotations, the variants that real models ship (GQA, MLA, sliding windows), and what it costs in FLOPs and bytes.

Why tokens need to talk

After tokenization and the embedding lookup (Chapter 3), our sentence is a matrix X with one row per token: 5 rows of d = 4,096 numbers for Llama 3.1 8B. Each row was looked up from a table using only its own token ID. The row for ␣the at position 4 is the exact same vector as ␣the anywhere else in any text.

Now look at the other layers you met in Chapter 4. RMSNorm normalizes each row by itself. The MLP applies the same function to each row by itself. A residual add combines a row with an update to that same row. In every one of these, output row i depends only on input row i. Stack a hundred of them and the final vector for ␣the still knows nothing about ␣cat, ␣sat or ␣on. Such a model could only learn statistics of the form “after ␣the, what usually comes next?”. That is a bigram model. It might guess ␣first or ␣same; it has no reason to prefer ␣mat.

To predict ␣mat, the vector at the last position must pull in information from earlier positions: there is a cat, it sat, it sat on something. Attention is the only layer in a transformer that moves information between positions. Everything else is a per-token map.

Systems analogy

Think of a transformer as a parallel program over n workers, one per token. The MLP and norms are embarrassingly parallel map steps: each worker transforms its own state. Attention is the communication step, where each worker reads from the others. A transformer block alternates the two: communicate, then compute, then communicate again. Chapter 6 shows the full block.

Key takeaway

Per-token layers transform information. Attention moves it between positions. Without attention, context cannot influence a prediction at all.

The core idea: a soft hash-table lookup

How should the last token decide which earlier tokens to read from? The answer is a dictionary lookup, made soft.

In a normal hash table you call get(key). The table finds the one stored key that exactly matches and returns its value. Attention does something similar, with three changes:

  1. Every token is both a stored entry and a reader. Each token publishes a key (a vector that says “this is what I contain”) and a value (a vector that says “this is what I hand over if you pick me”). Each token also issues a query (a vector that says “this is what I am looking for”).
  2. Matching is by similarity, not equality. The match score between a query q and a key k is their dot product q·k: large when they point the same way (Chapter 4 covers dot products).
  3. No single winner. Instead of returning the best value, attention turns all scores into weights with softmax (positive, summing to 1) and returns the weighted average of all values.

Why soft? Because the model must be trained. A hard “pick the best key” is a step function: nudging a weight slightly does not change which key wins, so the gradient is zero almost everywhere and the model cannot learn which keys to prefer. A softmax-weighted average changes smoothly with every number, so gradients flow back into the queries, the keys and the values (Chapter 8 covers gradients). A soft lookup can also gather from several tokens at once, which is often what is needed.

In a transformer, queries, keys and values all come from the same token vectors, through three learned matrices. That is why it is called self-attention: the sequence attends to itself. (The original 2017 translation model also had cross-attention, where queries come from one sequence and keys/values from another; decoder-only LLMs do not use it. History is in Chapter 6.)

Common misconception

“The key stores the word’s meaning and the query asks a question” is an analogy, not a spec. Nobody designs what keys and queries mean. The three matrices start random and training shapes them into whatever projections reduce prediction error. Some heads end up with crisp, human-readable jobs; many do not.

One attention head, exactly

Here is the full computation for one head (one independent copy of the attention mechanism; real layers run many in parallel, covered below). The input is the matrix X of n token vectors.

Q = X WQ,   K = X WK,   V = X WV
S = Q KT√dh + M,    A = softmaxrow(S),    O = A V X ∈ ℝn×d: token vectors (one row per token). WQ, WK, WV ∈ ℝd×dh: learned projection matrices; dh is the head dimension. Q, K, V ∈ ℝn×dh: one query, key and value row per token. S ∈ ℝn×n: scores; Sij = qi·kj/√dh says how much token i wants token j. M: the causal mask (0 where j ≤ i, −∞ where j > i). A: attention weights, each row sums to 1. O ∈ ℝn×dh: output, row i = Σj Aij vj.

For Llama 3.1 8B, d = 4,096 and dh = 128, so each head’s WQ is a 4,096 × 128 slice of a larger matrix. For our 5-token sentence, Q, K, V are 5 × 128 and the score matrix is 5 × 5. The stepper below runs the same computation with tiny, made-up numbers (dh = 4) so you can check every value by hand.

Why divide by √dh?

A dot product of two dh-dimensional vectors is a sum of dh products. If the components are roughly independent with mean 0 and variance 1, the sum has variance dh, so its typical size (standard deviation) is √dh. For dh = 128 that is about 11.3. Raw scores of ±11 to ±23 are common.

Softmax on numbers that far apart is nearly one-hot. Scores [22.6, 11.3, 0] give weights [0.99999, 0.00001, 0.0000]. Divide by √128 ≈ 11.3 first and the scores become [2, 1, 0], which softmax maps to [0.665, 0.245, 0.090]. The second version can still learn: when softmax is saturated, its gradient ∂wi/∂sj = wi(δij − wj) is almost zero everywhere, and training stalls. Dividing by √dh keeps the score variance near 1 regardless of head size. It is a fixed scale, not a learned one; the model can still learn sharp attention by making q and k longer.

Some recent models add more guard rails on top. Gemma 2 “soft-capped” the attention scores (squashed very large ones with a tanh); Gemma 3 and Qwen3 replace that with QK-norm, an RMSNorm applied to each query and key vector before the dot product, which bounds the scores and stabilizes training.

The low-level view of one head

Three kinds of work happen, with very different hardware profiles:

  • Projections (XWQ etc.) are ordinary matrix multiplies: 2·n·d·dh FLOPs each (Chapter 2 covers matmul cost). In practice all heads are projected together in one big GEMM.
  • QKT and AV are batched matmuls of shape (n × dh)·(dh × n) and (n × n)·(n × dh): 2·n²·dh FLOPs each. Their cost grows with n², not n.
  • Mask + softmax is a row-wise reduction: find the row max, exponentiate, sum, divide (the max-subtraction trick is in Chapter 4). Only a few FLOPs per element, so it is limited by memory bandwidth, not compute.

A naive implementation writes the n × n score matrix to GPU memory (HBM), reads it back for softmax, writes the weights, and reads them again for AV. That is four passes over an n² array per head. FlashAttention fuses all three stages into one kernel that works on tiles in on-chip SRAM and never stores S. That is the subject of Chapter 15; here it is enough to know the score matrix is a conceptual object, not necessarily a buffer.

# One causal attention head in numpy (reference semantics, not fast)
def attention_head(X, Wq, Wk, Wv):          # X: (n, d); W*: (d, d_h)
    Q, K, V = X @ Wq, X @ Wk, X @ Wv            # each (n, d_h)
    n, d_h = Q.shape
    S = (Q @ K.T) / np.sqrt(d_h)               # (n, n) scores
    S = np.where(np.tril(np.ones((n, n))) == 1, S, -np.inf)  # causal mask
    S = S - S.max(axis=1, keepdims=True)        # numerical stability
    A = np.exp(S); A /= A.sum(axis=1, keepdims=True)  # row softmax
    return A @ V                                # (n, d_h)

Causal masking

Step 4 of the stepper deleted the upper triangle. There are two reasons for this, one from training and one from inference, and they fit together.

Training. A training sequence of n tokens contains n prediction problems: after The predict ␣cat, after The cat predict ␣sat, and so on. A transformer solves all n in a single forward pass, one per row (the objective itself is Chapter 8’s topic). That only works if row i cannot see token i+1, its own answer. Without the mask, row ␣cat would attend to ␣sat and copy it. The loss would drop to near zero and the model would learn nothing useful. With the mask, the computation at row i is exactly what it would be if the text ended at token i.

Inference. Generation runs left to right; when predicting the next token, future tokens do not exist yet. Because training already used the same mask, the model never learned to rely on information it will not have.

A useful side effect: row i depends only on tokens 0…i, so appending new tokens never changes the keys and values computed for earlier positions. They can be computed once and kept. That memoization is the KV cache, and it is the whole subject of Chapter 12.

Low-level: how the mask is applied

Conceptually the mask is a matrix M added to the scores before softmax. Real kernels never build it. A fused attention kernel processes the score matrix in tiles; tiles fully above the diagonal are skipped (about half of all work for long sequences), tiles on the diagonal apply the mask per element, and tiles below run unmasked. Implementations often use a large finite negative number instead of −∞, because a row that is entirely −∞ (for example a padding row) would make softmax compute 0/0 = NaN.

When training on several documents packed into one long sequence, the mask can also block attention across document boundaries, giving a block-diagonal causal pattern. Llama 3 used this and found it mattered most during long-context training.

Encoder models like BERT use no mask; every token sees the whole input. That works for classification and search embeddings, but such a model cannot generate text left to right. Every model in this blog is a decoder with a causal mask.

Many heads in parallel

One head computes one weighted average per token. But a token typically needs several different things at once. ␣the might want to know the previous word, the verb of the clause and the subject being discussed. A single softmax has to spread one unit of attention across all of them, and the values it gets back are blended into one vector. Asking one lookup to serve several purposes muddles all of them.

The fix is to run h heads side by side, each with its own WQ, WK, WV, so each can learn its own notion of “relevant”. To keep the cost the same as one wide head, each head is made narrow: dh = d/h. Llama 3.1 8B uses h = 32 heads of dh = 128 (32 × 128 = 4,096 = d). The head outputs are concatenated back to width d and passed through one more learned matrix, WO.

headk = Attention(X WQ(k), X WK(k), X WV(k))
MHA(X) = Concat(head1, …, headh) · WO = Σk headk · WO(k) headk ∈ ℝn×dh: output of head k. WO ∈ ℝh·dh×d: output projection; WO(k) is its block of dh rows that belongs to head k. The second form shows that “concatenate, then multiply” equals “each head projects its own output, then sum”: heads write into the token’s vector independently and additively.

Shapes and memory layout

Nothing is actually split into separate matrices. With a batch of B sequences:

  1. X is (B, n, 4096). One GEMM with WQ (4096 × 4096) gives Q as (B, n, 4096).
  2. Reshape to (B, n, 32, 128). In row-major memory this is free: each token’s 4,096 numbers are already 32 consecutive runs of 128.
  3. Transpose to (B, 32, n, 128) so each head’s rows are contiguous. This is either a real copy or a strided view that the attention kernel reads directly.
  4. Run batched matmuls over the (B, 32) batch dimensions; then transpose back to (B, n, 32, 128), reshape to (B, n, 4096) and multiply by WO.

Per layer, Llama 3.1 8B’s attention weights are WQ 16,777,216 + WK 4,194,304 + WV 4,194,304 + WO 16,777,216 = 41,943,040 parameters. (WK and WV are only 4,096 × 1,024 because of grouped-query attention, explained later.) Over 32 layers that is 1.34 B parameters, about 17% of the model; the MLPs hold most of the rest (Chapter 6 does the full count). Each token passing through the four projections costs 2 × 41.9 M ≈ 84 MFLOP per layer, or 2.7 GFLOP for all 32 layers, part of the ≈ 16 GFLOP per token the whole model needs.

What heads learn

Because each head has its own projections, heads specialize during training. Interpretability research has found several recurring types. These are measured in real models, but any particular head is usually messier than the clean description.

  • Previous-token heads attend almost entirely to position i−1. They copy “what came just before me” into each token’s vector. Many later mechanisms build on this.
  • First-token (sink) heads put most of their weight on the first token. This is usually a way of doing nothing, explained in the section on attention sinks below.
  • Content heads attend by meaning: a verb to its subject, a pronoun to the name it refers to, a closing bracket to its opening bracket.
  • Induction heads implement copying: if the text earlier contained “… A B …” and the current token is A again, attend to the B that followed last time and predict B.
  • Positional heads attend at a fixed offset or to recent tokens with a smooth decay.

Induction heads deserve a closer look because they show how heads in different layers compose. Anthropic’s 2022 study found that they appear suddenly during training, at the same moment the model gets much better at using earlier context (“in-context learning”), and argued they are a major mechanism for it. An induction head cannot exist in a one-layer model; it needs a previous-token head in an earlier layer.

Two cautions. First, attention weights show where a head reads, not what it moves: the value vectors and WO decide that, and a head can attend strongly to a token whose value is almost zero. Second, heads are redundant; removing many individual heads barely changes model quality. Chapter 6 touches on the wider interpretability toolkit.

Position: attention is blind to order

Look back at the formulas. Nothing in them refers to where a token sits. If you shuffle the rows of X, the rows of Q, K and V shuffle the same way, the score matrix gets its rows and columns permuted, and the output rows come out shuffled in the same way. Attention treats its input as a set of (key, value) pairs: a weighted sum does not care about the order of its terms. Mathematicians call this permutation equivariance.

That is a problem for language. “The dog bites the man.” and “The man bites the dog.” contain exactly the same tokens. For the final ., which sees every token in both sentences, attention without position information would produce bit-identical outputs, and so identical predictions for what comes next.

(A causal mask leaks a little position information: a token can “count” how many tokens it sees. Models trained with no positional encoding at all, called NoPE, do learn some position from this. But explicit position signals work much better, and every major model uses them.)

A short history of position signals

  • Sinusoidal, added (2017). The original transformer added a fixed vector to each embedding: dimension pair i of position t held sin(t·ωi) and cos(t·ωi) with frequencies ωi = 10,000−2i/d, a geometric ladder from fast to slow. Keep this idea in mind; RoPE reuses it.
  • Learned, added. GPT-2 and BERT learned a separate table of position vectors (1,024 and 512 rows). Simple, but the model has nothing to use beyond the last row of the table.
  • Relative biases. Instead of changing the input, add a learned or fixed bias to each score based on the distance i−j. T5 used learned biases per distance bucket. ALiBi (2021) adds a fixed penalty −m·(i−j) with a different slope m per head (a geometric series such as 1/2, 1/4, …, 1/256). Distant tokens are simply discouraged. ALiBi extrapolates gracefully to longer inputs; BLOOM and MPT used it.
  • Rotary (RoPE, 2021). Rotate queries and keys by a position-dependent angle. Used by Llama, Mistral, Qwen, Gemma, DeepSeek, gpt-oss and nearly every open model since 2023. The next section explains it in detail.

RoPE: position as rotation

What we want is for the score between a query at position m and a key at position n to depend on how far apart they are, m − n, not on where they sit in absolute terms. “The word right before me” should mean the same thing at position 10 and at position 10,000.

RoPE gets this with a geometric trick. Split the dh numbers of a query or key into dh/2 pairs, and treat each pair as a point in a 2D plane. At position t, rotate pair i by the angle t·θi. Rotation does not change a vector’s length, and the dot product of two vectors depends only on their lengths and the angle between them. If the query was rotated by mθ and the key by nθ, the angle between them changed by exactly (m − n)θ. The absolute positions cancel out; only the offset remains.

Each pair rotates at a different speed, using the same geometric ladder as the 2017 sinusoids. Picture a clock with 64 hands. The fastest hand turns about one radian per token, so it distinguishes “1 token back” from “2 tokens back” clearly, but it wraps around every ~6 tokens. The slowest hands barely move from one token to the next, but they keep turning steadily across hundreds of thousands of tokens, so they tell “near” from “far”. Together they work like the digits of an odometer: fast digits for fine position, slow digits for coarse position.

θi = b−2i/dh,   [x′2i, x′2i+1] = [x2i cos tθi − x2i+1 sin tθi,  x2i sin tθi + x2i+1 cos tθi]
⟨Rmq, Rnk⟩ = qTRmTRnk = qTRn−mk i = 0 … dh/2 − 1: index of a dimension pair. θi: rotation speed of pair i in radians per token. b: the base (10,000 in the paper and Llama 2; 500,000 in Llama 3). t: the token’s position. Rt: the block-diagonal matrix that rotates every pair by its angle tθi. Because rotations compose (RmT = R−m), the score depends only on n − m. In complex-number form: pair i is z = x2i + i·x2i+1, and RoPE multiplies it by eitθi.

Worked example. Take one pair with θ = 0.5 rad/token, and let q = k = (1, 0) before rotation. Query at m = 5, key at n = 2: q is rotated by 2.5 rad, k by 1.0 rad, the angle between them is 1.5 rad and q·k = cos 1.5 ≈ 0.071. Move both 8 tokens later (m = 13, n = 10): rotations of 6.5 and 5.0 rad, still 1.5 rad apart, still 0.071. Same offset, same score.

Llama 3.1 8B numbers. dh = 128 gives 64 pairs; b = 500,000. Pair 0 turns θ0 = 1 rad per token (one revolution every 2π ≈ 6.3 tokens). Pair 16 turns 0.0376 rad/token (a revolution every 167 tokens), pair 32 every 4,443 tokens, and pair 63 at 2.46 × 10−6 rad/token, one revolution every 2.56 million tokens. A larger base slows the slow hands down further, so distant positions stay distinguishable. Meta raised the base from 10,000 to 500,000 for Llama 3 to support longer contexts.

What RoPE does and does not touch

  • RoPE is applied to q and k after the projections and before the dot product. Values are not rotated: position influences where a head looks, not what it carries.
  • Keys are stored in the KV cache already rotated. A cached key permanently encodes its position, which is why tricks that move or evict cached tokens have to think about positions (Chapter 12).
  • It adds no parameters. The cost is one 2×2 rotation per pair: about 6 FLOPs per pair, roughly 400 FLOPs per 128-dim vector, negligible next to the projections. The cos/sin values form an n × dh/2 table that is precomputed or generated inside a fused kernel.
  • Because the score involves cos((m − n)θi) terms at many frequencies, contributions from different pairs fall out of phase as distance grows, which gives a soft bias toward nearby tokens. The RoFormer paper calls this long-term decay. Try it in the playground below.
  • Some models rotate only part of each head (“partial RoPE”) and leave the rest position-free. MLA, later in this chapter, does a version of this.
Optional deep dive: the two pair layouts (a real-world bug source)

“Pair i” can mean two different things. Meta’s original Llama code views the head as complex numbers, so pairs are adjacent dimensions (0,1), (2,3), …. Hugging Face’s implementation uses a rotate_half function that pairs dimension i with dimension i + dh/2, that is (0,64), (1,65), …, and its conversion script permutes the rows of WQ and WK to match. Both are correct as long as weights and code agree; llama.cpp calls them the “normal” and “NeoX” RoPE types. Load weights with the wrong convention and nothing crashes: the model just produces fluent-looking nonsense.

Stretching the context window

Llama 3 was pretrained mostly on 8,192-token sequences. Llama 3.1 supports 131,072. What goes wrong if you simply feed a RoPE model positions it never saw?

Look at the hands again. Fast pairs complete thousands of revolutions within 8K tokens, so during training they saw every possible angle; position 50,000 gives them nothing new. Slow pairs are different. Llama’s pair 63 turns only about 0.02 rad over 8,192 tokens. At position 50,000 it sits at an angle it never saw during training, and the attention scores it produces are unlike anything the model was trained on. Quality collapses: perplexity, the standard measure of how surprised the model is by real text (Chapter 8), explodes. Context extension is the craft of fixing this, mostly by changing θi.

  • Position interpolation (PI, 2023). Divide every position by the stretch factor s = Lnew/Ltrain. Position 50,000 at s = 8 behaves like 6,250: never out of range. The cost: fast pairs get squeezed too. Neighbouring tokens now differ by 1/8 of the usual angle, so fine-grained order becomes harder to read. Works after a short fine-tune, a little extra training on long text (around 1,000 steps in the paper).
  • “NTK-aware” scaling (2023). Raise the base instead: b′ = b · sdh/(dh−2). The fastest pair is unchanged, the slowest is slowed by almost exactly s, and pairs in between are stretched by intermediate amounts. Example: b = 10,000, s = 4, dh = 128 gives b′ ≈ 40,890.
  • “NTK-by-parts”. Decide per pair by comparing its wavelength λi = 2π/θi with the training length. Pairs with λ much shorter than Ltrain are left alone (they never had a problem). Pairs with λ longer than Ltrain are interpolated by s. Pairs in between are blended.
  • YaRN (2023) = NTK-by-parts plus a temperature: attention scores are multiplied by a factor slightly above 1, implemented by scaling q and k each by 0.1·ln s + 1 (1.208 for s = 8). With many more keys, softmax spreads its weight thinner; the sharper scores compensate. YaRN needed about 10× fewer fine-tuning tokens than earlier methods. DeepSeek-V3’s config uses YaRN with factor 40 to go from 4,096 to 163,840 positions; gpt-oss uses YaRN to reach 131,072.

Llama 3.1’s rule is an NTK-by-parts variant. Its config.json says "rope_scaling": {"factor": 8.0, "low_freq_factor": 1.0, "high_freq_factor": 4.0, "original_max_position_embeddings": 8192, "rope_type": "llama3"}. The reference implementation:

# From Meta's Llama 3.1 reference code (comments added)
def apply_scaling(freqs):                       # freqs[i] = theta_i = 500000**(-2i/128)
    scale_factor, low_freq_factor, high_freq_factor = 8, 1, 4
    old_context_len = 8192
    low_freq_wavelen  = old_context_len / low_freq_factor     # 8192
    high_freq_wavelen = old_context_len / high_freq_factor    # 2048
    new_freqs = []
    for freq in freqs:
        wavelen = 2 * math.pi / freq
        if wavelen < high_freq_wavelen:   new_freqs.append(freq)                 # fast: keep
        elif wavelen > low_freq_wavelen:  new_freqs.append(freq / scale_factor)  # slow: interpolate 8x
        else:                                                                     # between: blend
            smooth = (old_context_len / wavelen - low_freq_factor) / (high_freq_factor - low_freq_factor)
            new_freqs.append((1 - smooth) * freq / scale_factor + smooth * freq)
    return new_freqs

Plugging in b = 500,000 and dh = 128: pairs 0–28 have wavelengths under 2,048 tokens and are untouched; pairs 35–63 have wavelengths over 8,192 and are slowed 8×; the six pairs 29–34 are blended. The slowest pair’s wavelength goes from 2.56 M to 20.5 M tokens.

Changing the frequencies is only half the job. The model still has to learn to use long-range information, which requires training on long documents. Llama 3 extended its context in six stages from 8K to 128K using about 800 B tokens of long-context pretraining (Chapter 8). Methods like dynamic NTK can stretch a model somewhat without any training, but quality is lower.

Key takeaway

RoPE encodes position by rotating dimension pairs at geometrically spaced speeds, so scores depend on relative distance. Context extension mostly means slowing the slow pairs (the only ones that would see new angles) while leaving the fast ones alone, then training briefly on long text.

The n² problem: cost at prefill and decode

A model handles a request in two phases (Chapter 11). Prefill runs the whole prompt through the model in one pass. Decode then generates the answer one token per step. Attention costs very different amounts in the two.

In prefill, every query meets every earlier key. Double the context and each token has twice as many keys to score, and there are twice as many tokens doing it: four times the work. This quadratic term is the defining cost of attention.

Counting FLOPs

Per layer, for n tokens: QKT costs 2·n²·dh per head, and AV the same. Over h heads with h·dh = d, that is 4·n²·d for the full square (O(n²·d) in big-O terms), or about 2·n²·d if the kernel skips the masked half. Seen per token, a token at position t scores t keys, so it costs about 4·L·d·t FLOPs across all layers, on top of the ≈ 2N FLOPs of the weight matmuls.

For Llama 3.1 8B (L = 32, d = 4,096): a token at position 8,192 needs 4 × 32 × 4,096 × 8,192 ≈ 4.3 GFLOP of attention, about a quarter of the 16 GFLOP for weights. At position 131,072 it needs 68.7 GFLOP, more than four times the weights. The two are equal at t = N/(2·L·d) ≈ 30,600 (Chapter 6 refines this to ≈ 28,600 by not counting the embedding lookup, which does no math). Below that, the weights dominate; above it, attention does.

Memory: the score matrix that must not exist

Materializing S takes n² numbers per head per layer. At n = 8,192 in BF16 that is 134 MB per head, or 4.3 GB per layer for 32 heads. At 131,072 tokens it is 34 GB for a single head. A naive implementation runs out of memory long before it runs out of compute. This is why real kernels never store S: FlashAttention, mentioned above, needs only O(n) extra memory (Chapter 15). The FLOPs stay quadratic; only the memory problem is solved. Long-context training additionally splits the sequence across GPUs (ring/context parallelism, Chapter 8).

Decode: one query row

Generation is different. After the prompt has been processed, each step adds one token. Its query is a single row, 1 × dh per head. The keys and values of all earlier tokens were already computed and kept in the KV cache (Chapter 12). So a decode step computes one row of the score matrix, not a whole matrix: 2·dh·t FLOPs for the scores and 2·dh·t for the weighted sum, per head. The per-step cost grows linearly with the context length t, and generating many tokens is quadratic overall.

Low-level: decode attention is memory-bound

In a decode step, each cached key (a dh-vector, 2·dh bytes in BF16) is loaded once and used by the g query heads that share it (the group size, next section), one multiply-add per element each. That is an arithmetic intensity of about g FLOPs/byte; values work out the same. For Llama 3.1 8B, g = 4, against an H100 ridge point of about 295 FLOPs/byte (Chapter 2), so the speed is set by how fast the cache streams out of HBM. Batching does not help, because every sequence reads its own cache (Chapter 11 works this out on the roofline). The only levers are fewer bytes per cached token (GQA, MLA, KV quantization) and fewer cached tokens read (sliding windows, sparse attention). Most of the variants in the rest of this chapter pull one of these two levers.

Sharing keys and values: MHA, MQA, GQA, MLA

Queries are used once and thrown away. Keys and values are stored for every past token and re-read at every decode step. So the number and size of key/value heads, not query heads, decides how much memory the cache takes and how many bytes each step must stream. The variants below keep all the query heads and change only the key/value side.

  • MHA (multi-head attention). The original: every query head has its own key and value head, hkv = h. Llama 2 7B used it with 32 of each.
  • MQA (multi-query attention, Shazeer 2019). All query heads share a single key head and a single value head, hkv = 1. The cache shrinks by a factor of h. Fast, but with some quality loss. PaLM used it.
  • GQA (grouped-query attention, Ainslie et al. 2023). The middle ground: query heads are split into hkv groups, and each group shares one key/value head. Query head j reads KV head ⌊j/g⌋, where g = h/hkv. Llama 3.1 8B: 32 query heads, 8 KV heads, g = 4. The GQA paper showed quality close to MHA at speed close to MQA, and that an existing MHA checkpoint can be converted with about 5% of the original pretraining compute.
  • MLA (multi-head latent attention, DeepSeek-V2, 2024). Instead of sharing heads, compress: store one small latent vector per token and reconstruct every head’s keys and values from it with learned up-projections. Detailed below.

GQA in practice

GQA shrinks the key/value projections. In Llama 3.1 8B, WK and WV are 4,096 × 1,024 (8 heads × 128) instead of 4,096 × 4,096, which is why they have 4.2 M parameters each while WQ has 16.8 M. Tensors are Q: (B, 32, n, 128) and K, V: (B, 8, n, 128).

The simple implementation (Hugging Face’s repeat_kv) expands K and V to 32 heads before attention. That works but copies data, and it throws away the bandwidth saving. Good kernels never copy. They compute the KV head index as q_head // 4, or better, stack the 4 query heads that share a KV head into the rows of one small matrix. At decode that turns four 1 × 128 vector-times-matrix products into one 4 × 128 matrix-times-matrix product that loads each key once. This is where the g FLOPs/byte from the previous section comes from.

MLA: compress instead of share

DeepSeek’s MLA keeps 128 full query heads but caches far less than even GQA would. For each token, the hidden vector ht (d = 7,168 in DeepSeek-V3) is projected down to a latent ct of only 512 numbers. Per-head keys and values are produced from that latent by learned up-projections, so heads still get different keys and values, but all of them are derived from 512 shared numbers. Only the latent is cached.

ct = WDKVht,   kCt,i = WUKict,   vt,i = WUVict,   kRt = RoPE(WKRht)
scorei(m, n) = (qCm,i·kCn,i + qRm,i·kRn) / √(128 + 64) ct ∈ ℝ512: the cached latent (DeepSeek’s “KV compression dimension” dc). WUKi, WUVi: head i’s up-projections, 128 × 512 each. kRt ∈ ℝ64: a small extra key that carries RoPE, shared by all heads and also cached. Queries are built the same way from a separate 1,536-dim latent, with a 128-dim content part qC and a 64-dim RoPE part qR per head. Values from DeepSeek-V3’s config.json: kv_lora_rank 512, q_lora_rank 1536, qk_nope_head_dim 128, qk_rope_head_dim 64, v_head_dim 128, 128 heads.

The absorption trick. Reconstructing 128 heads of keys from every cached latent at every step would be expensive. But matrix products can be regrouped: qC·kC = qC T(WUKic) = (WUK TiqC)Tc. Multiply the query by WUK T once, and it can be dotted directly with the 512-dim cached latents. Likewise WUV folds into WO. After absorption, decode-time MLA looks like MQA with one 576-dim key (latent plus RoPE key) and one 512-dim value shared by all 128 heads, with each head seeing it through its own learned projection.

Why the RoPE part has to be separate. RoPE inserts a position-dependent rotation between query and key: qTRn−mWUKc. The rotation depends on which key is being scored, so WUK can no longer be folded into the query once for all keys. DeepSeek’s fix is to keep the compressed part position-free and carry position in a separate 64-dim query/key pair that is rotated normally and not compressed.

The hardware consequence. With absorption, each decode step reads 576 cached numbers per token per layer and uses them for all 128 heads: about 2 × 128 × (576 + 512) FLOPs per 1,152 bytes, roughly 240 FLOPs/byte, close to the H100’s ridge point. Decode attention goes from deeply memory-bound (GQA: g = 4) to nearly balanced. This is a big part of why DeepSeek-style models serve long contexts cheaply. The cache-size comparison is in Chapter 12.

Local, sparse and sink attention

The variants above make each cached token cheaper. The next family reads fewer cached tokens.

Sliding windows and local/global layers

In sliding-window attention, each token attends only to the previous W tokens. Cost per token is O(W) instead of O(t), and the cache for that layer never holds more than W entries. Information can still travel further than W: each layer moves it up to W positions, so after k layers it can have come from k·W tokens back. Mistral 7B used W = 4,096 in all 32 layers, a theoretical reach of about 131K tokens. In practice, information relayed through many hops gets weaker, so modern models mix local layers with full (“global”) ones:

  • Gemma 2 alternates 1:1, local window 4,096 and global span 8,192.
  • Gemma 3 uses 5 local layers per global layer with a window of only 1,024. The report measures that all-global attention adds about 60% memory overhead from the KV cache at long context, while local-heavy layouts with a 1,024 window bring that under 15%.
  • gpt-oss alternates full layers with banded layers whose window is just 128 tokens.

Sparse, content-selected attention goes further: let each query pick which keys to read. DeepSeek-V3.2’s DeepSeek Sparse Attention adds a small “lightning indexer”, a lightweight scorer that runs in FP8 with a single shared key per token, which scores all previous tokens and selects the top 2,048 for each query. The main MLA attention then runs over only those. The indexer is still quadratic, but it is much lighter than full attention, so long-context cost drops.

Attention sinks

Softmax forces every row of weights to sum to 1. A head has no way to say “nothing here is relevant to me”. In practice, trained models solve this by dumping the unwanted weight on the first token, which every position can see. Its value vector learns to be small or harmless, so attending to it is close to a no-op. Xiao et al. (2023) called these tokens attention sinks. They found that a large share of attention in most layers goes to the first few tokens, regardless of what those tokens are.

This matters for systems. If you run sliding-window attention and evict the first tokens, quality collapses, because the heads lose the place where they park unused weight. StreamingLLM keeps the first 4 tokens plus a recent window and stays stable on streams of millions of tokens without retraining. Newer architectures build in a proper “nothing” option. gpt-oss gives each head a learned bias in the softmax denominator, so the weights may sum to less than 1:

wj = esjeb + Σk esk sj: the scores of the row. b: a learned per-head sink logit. When every sj is much smaller than b, all weights approach 0 and the head outputs almost nothing. With b → −∞ this is ordinary softmax.

Beyond softmax attention: linear attention, state-space models, hybrids

All the variants so far keep exact attention over some set of tokens and pay O(t) per token for it. A different line of work replaces the mechanism.

Linear attention drops the softmax and uses a plain product of feature maps: score(q, k) = φ(q)·φ(k). Then the output for token t regroups by associativity:

ot = Σj≤t (φ(qt)·φ(kj)) vj = φ(qt)T St,    St = St−1 + φ(kt) vtT St: a fixed-size dh × dh state matrix that summarizes all keys and values so far (normalization omitted). Each new token costs O(dh²) regardless of context length, and memory is constant.

This is an RNN: a fixed-size state updated once per token. It is fast and needs no growing cache. The catch is the fixed size. Every past token is written into the same dh × dh matrix by superposition, like a hash table with far more items than buckets and no collision handling. Exact recall (repeat a phone number from 50K tokens ago, copy a long passage) suffers. Modern versions add forgetting and smarter writes. Mamba (2023), a selective state-space model, makes the state’s decay and input/output projections depend on the current token, so the model chooses what to keep. Gated DeltaNet uses a “delta rule” update that first reads what the state currently stores for key k and writes only the correction, plus a decay gate.

Pure recurrent models still trail attention on recall-heavy tasks, so the trend in 2025–2026 is hybrids: mostly linear or state-space layers, with a full attention layer every few layers for exact lookup.

  • Qwen3-Next 80B-A3B: 48 layers in a repeating pattern of 3 Gated DeltaNet layers then 1 gated softmax-attention layer. Qwen3.5 (e.g. 397B-A17B) carries the same 3:1 pattern into Qwen’s main line.
  • Kimi Linear: Kimi Delta Attention layers mixed with MLA layers at about 3:1.
  • NVIDIA Nemotron 3: Mamba-2 layers with a few attention layers.

Only the attention layers keep a KV cache, so a 3:1 hybrid caches roughly a quarter as much, and its per-token cost grows four times more slowly with context. Whether hybrids fully match pure attention at the frontier is still an open question; the industry is clearly testing it at scale.

Long context in practice

A model that accepts 128K tokens does not necessarily use all of them well. Two well-known measurements:

  • Lost in the middle (Liu et al., 2023). In multi-document question answering and key-value retrieval, accuracy was highest when the relevant information was at the beginning or the end of the context and dropped clearly when it was in the middle: a U-shaped curve.
  • RULER (Hsieh et al., 2024). Simple needle-in-a-haystack tests were nearly saturated, but on harder synthetic tasks (multiple needles, multi-hop tracing, aggregation) 17 long-context models all degraded with length. Although all claimed 32K or more, only about half held satisfactory performance at 32K.

Frontier models have improved a lot since these papers, especially on retrieval. Treat advertised context as an upper bound, and test effective context on your own task. Mechanically, the reasons are the ones you have seen in this chapter:

  1. Dilution. A relevant key must outscore every irrelevant one. With 100K competitors, many small accidental matches together can take a lot of the softmax mass. YaRN’s temperature term exists for exactly this reason.
  2. Training distribution. Most text has its useful information nearby, so heads learn recency and sink habits. Truly long-range dependencies are rare even in the long-context training phase. For Llama 3, that phase was about 800 B tokens out of more than 15 T.
  3. Position stretching is approximate. The slowest RoPE pairs were trained on a narrow range of angles and interpolated afterwards.
  4. Architecture shortcuts. Sliding windows, sparse selection and recurrent layers all trade some exact long-range access for cost.

Practical consequences: put the question or instructions after long documents (or at both ends), keep context relevant instead of stuffing it, and remember that every extra token costs prefill compute (quadratic term), cache memory (Chapter 12) and money (Chapter 15).

Key takeaways
  • Attention is a soft, trainable dictionary lookup and the only place tokens exchange information.
  • One head: project to Q, K, V; score QKᵀ/√dh; mask the future; softmax each row; mix V. Many narrow heads run in parallel and are merged by WO.
  • The causal mask makes training parallel and honest and makes the KV cache possible.
  • RoPE rotates pairs of dimensions at geometric speeds so that scores depend on relative position. Context extension slows only the slow pairs.
  • Prefill attention is O(n²) FLOPs. Decode attention is one query row against the cache, O(t) per token and memory-bound.
  • Variants trade along two axes: make each cached token smaller (GQA, MQA, MLA) or read fewer of them (windows, sinks, sparse selection, recurrent hybrids).
