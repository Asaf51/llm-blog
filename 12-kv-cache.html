The KV Cache

Every new token needs the keys and values of every token before it. The KV cache stores them so each one is computed exactly once. This chapter shows what is stored, byte by byte, how much memory it takes, how inference engines manage it the way an operating system manages pages, and how API providers turn it into cheaper, faster prompts.

In this chapter

Generation without memory

Recall the generation loop from Chapter 1: run the model, pick a token, append it, run again. The simplest implementation calls the model on the whole sequence every time. The reference generate in Chapter 6 does exactly that. To produce token t+1 it pushes all t tokens through all 32 layers, and then uses only the last row of the output.

Count the work. Generating a sequence of n tokens this way costs 1 + 2 + … + n = n(n+1)/2 token-passes, where a token-pass means pushing one token through the whole network. The work grows with the square of the length.

Almost all of it is repeated. Here is the key fact. Under causal masking (Chapter 5), the hidden state of token j in every layer depends only on tokens 0…j. Appending tokens later never changes it. So everything computed for old tokens is final the moment it is computed.

What does a new token actually need from old tokens? Attention is the only place where positions exchange information; the MLP works on each token alone. And attention reads only two things from old positions: their keys and their values. So it is enough to keep, for every layer, the key vector and value vector of every past token. Each step then computes one new token, appends its keys and values, and reads the rest. That store is the KV cache.

Intuition: memoization of an append-only log

Think of each layer as keeping an append-only log: one record (a key and a value) per token. Records are written once and never modified, because the past cannot see the future. A new token reads the whole log and appends one record. This is plain memoization. It is safe for the same reason memoizing a pure function is safe: the inputs of an old record never change.

A subtle point makes the saving larger than it first looks. The key of token j in layer 20 is computed from the hidden state of token j at layer 20, which needs layers 0–19 to run for that token, including their attention over earlier tokens. So without a cache you do not just redo a few projections. You redo the entire forward pass for every old token. With the cache, old tokens cost nothing beyond reading their stored keys and values.

Real numbers. Take Llama 3.1 8B with a 1,000-token prompt and 1,000 generated tokens. Without a cache, the generation steps process 1,001 + 1,002 + … + 2,000 = 1,500,500 token-passes. At about 16 GFLOP per token-pass (2N, Chapter 6) that is about 24 PFLOP. With a cache it is 2,000 token-passes, about 32 TFLOP: 750× less compute. Without a cache the old tokens could at least be reprocessed in parallel, so the slowdown in time is smaller than 750×, but the FLOPs are real, and they grow quadratically.

Key takeaway

Causal masking makes the keys and values of past tokens immutable. Caching them is exact, not an approximation, and it changes the cost of generating n tokens from O(n²) token-passes to O(n). What remains is reading the cache, and that read is what the rest of this chapter is about.

What exactly is stored, and why not Q

Look at one attention head when the new token at position t arrives. Its output is a weighted mix of the values of all positions up to t, with weights from its query against their keys (Chapter 5):

ot = Σj ≤ t softmaxj(qt · kj√dh) vj qt: the new token's query (dh numbers). kj, vj: key and value of position j, for every j from 0 to t. dh = 128 in Llama 3.1 8B. The softmax runs over j.

Now ask which of these will be needed again in the future:

  • Keys and values: yes, forever. kj and vj are read by the query of every later token. Compute once, keep.
  • The query: never. qt is used in this step only. No later token ever looks at an old query, because in causal attention queries look backward and keys are looked at.
  • Old outputs and old hidden states: never. The only path from a past token to a future token runs through its keys and values. Once those are stored, the rest of the old token's activations can be thrown away.

So the cache holds, for every layer and every KV head, one key vector and one value vector of dh numbers per position. Two details matter later:

  • Keys are stored after RoPE. RoPE rotates each key by an angle that depends on its position (Chapter 5). The stored key has its position baked in. A cache entry is only valid at the position where it was computed. This is one reason a cached prefix can only be reused as an exact prefix, and why tricks that drop tokens from the middle of a cache must deal with positions.
  • Prefill writes the cache in bulk; decode appends. Prefill (Chapter 11) computes keys and values for all prompt tokens in one parallel pass and writes them all. Each decode step appends exactly one entry per layer per KV head.
Common misconception

The KV cache is not a cache of answers, of text, or of "what the model thought". It is an exact intermediate result, like the partial sums of a computation. Reusing it produces the same output as recomputing it, up to floating-point summation order (Chapter 14 explains why even that can differ).

Low-level: bytes and FLOPs of one step

Per layer, the step writes 2 (K and V) × 8 heads × 128 × 2 B = 4 KiB, and reads the whole cache: 4 KiB × (t+1). Over 32 layers that is a 128 KiB write and a 128 KiB × (t+1) read. At t = 8,191 one step reads exactly 1 GiB of cache.

The attention math on that data is tiny: each cached element serves only the 4 query heads of its group, so the step does about 4 FLOPs per byte read (Chapter 5 derives this), far below the H100's ridge point of about 295. Decode attention is pure memory streaming. A good kernel loads each K and V tile once into shared memory and applies it to all 4 query heads of the group; for long contexts it also splits the positions across many SMs (Flash-Decoding, Chapter 15).

The layout: where every byte lives

The simplest layout, and the default in Hugging Face transformers, keeps two tensors per layer, one for K and one for V, each of shape [B, hkv, n, dh]: batch, KV head, position, head dimension. Row-major, so the last index moves fastest (Chapter 2). For Llama 3.1 8B in BF16 with room for nmax = 8,192 positions, the byte strides are:

Why put heads before positions? The decode kernel handles each (sequence, KV head) pair independently. With this order, all keys of one head form one contiguous run of memory, n × 256 bytes, which streams from HBM at full speed. The price is that appending is strided: one decode step writes eight separate 256-byte rows, 2 MiB apart, in K and the same in V. That is 4 KiB of scattered writes per layer, which is negligible next to the megabytes being read.

Other engines choose differently. A token-major layout, [B, n, hkv, dh], matches how the projection produces k (one row of 1,024 numbers per token), so the append is a single contiguous 2 KiB write and reads become 256-byte chunks with a stride. Paged engines store fixed-size blocks of positions instead of one long run per sequence; a recent vLLM FlashAttention backend, for example, keeps each layer as one tensor of shape [blocks, hkv, block size, 2·dh] with K and V side by side. Layouts change between engines and versions. What every good layout guarantees is contiguous runs of at least dh × bytes per element, so that every memory transaction is full.

Gotcha: growing the tensor

transformers' default DynamicCache appends with torch.cat: every step allocates a new, slightly longer tensor and copies the old one into it. That is O(t) bytes copied per step and O(n²) over a generation, the same quadratic shape we just escaped, now in memory traffic. StaticCache instead preallocates [B, hkv, nmax, dh] once and writes in place; fixed shapes are also what CUDA graphs and torch.compile need (Chapter 15). But preallocating for the maximum length wastes memory on every sequence that ends early. That waste is the problem PagedAttention solves, below.

How big is it?

Every token stores one key and one value, of dh numbers each, for each KV head in each layer:

bytes per token = 2 · L · hkv · dh · b 2: one key and one value. L: layers. hkv: KV heads per layer. dh: head dimension. b: bytes per element (2 for BF16, 1 for FP8). Multiply by context length n for one sequence, and by batch size B for the whole batch.

Llama 3.1 8B: 2 × 32 × 8 × 128 × 2 B = 131,072 B = 128 KiB per token. An 8,192-token conversation holds 1 GiB. A full 131,072-token context holds 16 GiB, more than the model's own weights (16.06 GB ≈ 14.96 GiB). One long conversation can outweigh the model that serves it.

Every attention variant from Chapter 5 exists largely because of this table. Their structure is explained there; here is what each one buys in memory.

Fewer KV heads: GQA and MQA

The cache scales with hkv, not with the number of query heads. Grouped-query attention lets 4 query heads share each KV head in Llama 3.1 8B, which divides the cache by 4: 128 KiB instead of 512 KiB per token. On the same GPU that means 4× more concurrent sequences, or 4× longer contexts. Multi-query attention goes to one KV head (32× smaller than MHA here) but loses quality; GQA with 8 KV heads became the common compromise. Eight is also convenient for tensor parallelism: on 8 GPUs, each GPU holds exactly one KV head.

Compress what is stored: MLA

DeepSeek's multi-head latent attention caches, per layer and token, one compressed latent vector of 512 numbers plus one 64-number RoPE key shared by all heads. There is no factor 2: the same latent serves both keys and values. That gives 61 × (512 + 64) × 2 B = 70,272 B ≈ 68.6 KiB per token, less than Llama 3.1 8B needs, for a 671B-parameter model. Storing full keys and values for its 128 heads (192-number keys, 128-number values) would take 4,880 KiB per token, 71× more. The attention kernel works directly on the latents, with the up-projections folded into the query and output sides (the absorption trick, Chapter 5). That costs extra FLOPs per byte read, which is exactly the right trade for a memory-bound step. One caveat: a single latent cannot be split by head across tensor-parallel GPUs, so it is replicated on each one; large MLA deployments shard by batch instead (Chapter 15).

Cap the cache: sliding windows

A layer that only attends to the last W tokens only needs the last W entries. Mistral 7B used a ring buffer: position t is stored in slot t mod W and overwrites the entry that just left the window. With W = 4,096 its paper reports 8× less cache memory at 32K tokens. Pure windows lose long-range recall, so recent models mix window layers with full ones:

  • Gemma 3 27B: 5 local layers (W = 1,024) per global layer. Of 62 layers, 10 are global: 10 × 8 KiB = 80 KiB per token keeps growing; the 52 local layers stop at 52 × 8 KiB × 1,024 = 416 MiB per sequence. At 128K tokens that is about 10.4 GiB, against 62 GiB if all 62 layers were global.
  • gpt-oss-120b: alternating full and banded layers, with a window of only 128. The 18 full layers store 18 × 2 KiB = 36 KiB per token; the 18 banded layers never hold more than 4.5 MiB per sequence.

Recurrent and state-space layers (Chapter 5) take this to the limit: a fixed-size state per sequence, no matter how long the context.

Key takeaway

KV bytes per token = 2·L·hkv·dh·b. GQA and MQA shrink hkv, MLA replaces 2·hkv·dh with one small latent, sliding windows cap n for most layers, and quantization (later) shrinks b. Modern architectures are designed as much around this formula as around quality.

The cache decides your batch size

Weights are paid once per GPU. The cache is paid per sequence. On a serving GPU, memory is split three ways: weights, a working area for activations and kernels, and everything else for the KV cache. Ignoring the working area (it is a few GB; Chapter 11 covers the full budget), the number of sequences that fit at context n is:

max sequences = GPU memory × utilization − weightsbytes per token × n Utilization is the fraction of GPU memory the engine may use (vLLM's gpu_memory_utilization: 0.92 by default in current releases, 0.9 in older ones; we use 0.9 here). Round down.

Llama 3.1 8B in BF16 on one 80 GB H100 at utilization 0.9: 72 GB − 16.06 GB = 55.94 GB for the cache. That is 55.94 × 109 / 131,072 ≈ 426,788 tokens of KV, shared by everyone. At 8,192 tokens per sequence: 52 sequences. At 131,072: 3. (Chapter 11's fuller budget, with the H100's real 79.65 GiB, vLLM's current 0.92 and the activation and runtime reserves subtracted, gives about 453,000 tokens and 55 sequences: the same picture.) vLLM prints this quantity at startup ("KV cache size: … tokens, maximum concurrency for … tokens per request: …×").

Batch size matters because decode is memory-bound: each step reads all the weights once and shares that read across every sequence in the batch (Chapter 11). More sequences per step means more tokens per second for the same weight traffic. So the KV cache, not the weights, ends up limiting throughput. The bigger model makes it worse: Llama 3.1 70B in BF16 (141 GB) on two H100s leaves almost nothing. By this section's simple count it is 144 − 141 = 3 GB. Even with the cards' true capacity (85.5 GB each) and vLLM's 0.92, only about 30,000 tokens fit in total, three 8K conversations (Chapter 11 works through this budget). That is one reason big models are served with FP8 or 4-bit weights, or on more GPUs: the weights get smaller, the cache gets the rest.

The cache slows every token

Memory capacity is half the story. The other half is bandwidth. Each decode step must read all the weights once, shared by the batch, plus every sequence's entire cache, which is not shared. For a batch of B sequences at context n:

time per step ≥ weight bytes + B · n · KV bytes per tokenmemory bandwidth A lower bound: it assumes reading memory at full bandwidth and nothing else. Each step produces one token for each of the B sequences.

Llama 3.1 8B on an H100 (3.35 TB/s): the weights alone take 16.06 GB / 3.35 TB/s = 4.79 ms. (This is the simple whole-model rule of thumb; Chapter 11's strict count skips the embedding table and gets 4.48 ms. The conclusions are the same.) At 8,192 tokens of context, one sequence adds 1.07 GB of cache: 5.11 ms per step, about 195 tokens/s. At 131,072 tokens the cache is 17.2 GB, larger than the weights: 9.92 ms, about 101 tokens/s. Same model, same GPU, half the speed, purely because of context.

The cache equals the weights at n* = weight bytes / (B × KV bytes per token). For the 8B at batch 1, n* ≈ 122,500 tokens. At batch 16, n* ≈ 7,660 tokens: in a busy server, the cache dominates decode traffic at quite ordinary context lengths.

Key takeaway

Weights are a fixed cost per step; the cache is a cost per sequence per token of context. At long context or large batch the cache dominates both memory and decode bandwidth. Every byte saved per cached token buys either more concurrent users or faster tokens.

Managing cache memory: from slabs to pages

A server does not know how long a sequence will become. The prompt length is known; the output length is not, because the model decides when to stop. Early serving systems gave each request one contiguous slab sized for the maximum possible length, for example 2,048 tokens, and kept it until the request finished. That wastes memory in three ways:

  • Reserved: slots that will be filled later, but sit empty now while other requests wait.
  • Internal fragmentation: slots that will never be filled, because the request stops early.
  • External fragmentation: gaps between slabs that are too small for a new slab.

The PagedAttention paper (Kwon et al., SOSP 2023) measured that in such systems only 20.4%–38.2% of KV cache memory held actual token states.

Readers who know operating systems have seen this problem: contiguous allocation of variable-size, growing objects. The fix is the same as in virtual memory. PagedAttention, the core of vLLM, splits each sequence's cache into fixed-size blocks (16 tokens by default) and stores them anywhere in a pool of physical blocks. Each sequence has a block table that maps its logical blocks, in order, to physical block numbers.

The mechanics, concretely for Llama 3.1 8B on an H100:

  • At startup the engine turns all memory left after the weights and the activation reserve (measured as in Chapter 11) into one big pool per layer. A block holds, per layer, 16 tokens × 8 heads × 128 × 2 B = 32 KiB of K and 32 KiB of V; across 32 layers, 2 MiB. The 55.94 GB from the previous section becomes 26,674 blocks, 426,784 token slots. The same block number is used in every layer: block 7 means slot 7 in each layer's pool, so one block table per sequence serves all layers.
  • Waste is bounded by one partially filled block per sequence: on average about 8 token slots, 1 MiB.
  • The attention kernel receives the block table. For position j it reads block table entry ⌊j/16⌋, then offset j mod 16 inside that block. This indirection made the 2023 kernel 20–26% slower than a contiguous one, yet end-to-end throughput rose 2–4× because many more sequences fit in a batch. Today FlashAttention and FlashInfer kernels accept block tables natively.
  • Block size is a trade-off: small blocks waste less memory, large blocks mean fewer table lookups and longer contiguous reads. The paper found 16 a good balance.

Sharing pays off most where many sequences have a common past: parallel sampling (n > 1) and beam search (Chapter 14), where the paper measured up to 55% memory savings. The next step is to share across different requests.

Prefix caching: never prefill the same tokens twice

A large share of real traffic repeats itself at the start. A chatbot sends the same system prompt and tool definitions with every request. A RAG app (retrieval-augmented generation: the app pastes retrieved documents into the prompt) sends the same document with many questions. Above all, multi-turn chats and agents resend the whole conversation every turn, because the APIs are stateless (Chapter 3). Request k+1 is request k plus a few new messages.

The keys and values of a prefix depend only on the tokens of that prefix and their positions. So if a new request starts with exactly the same tokens as an old one, the old cache entries for that stretch are exactly what prefill would compute. The engine can skip them and prefill only the rest. The conditions are strict but simple: same model weights, same adapter (if LoRA, Chapter 9), same images, and the same tokens from position 0.

Hashing blocks: vLLM's design

vLLM makes full blocks content-addressable. Each full block gets a hash computed from three things: the hash of the previous block, the token IDs in this block, and extra keys such as a LoRA ID, image hashes or a per-tenant salt. Because the parent hash is included, a block's hash identifies the entire prefix up to its end, like a git commit hash identifies its whole history. A global hash table maps block hashes to physical blocks.

When a request arrives, the engine hashes its prompt block by block from the left and looks each hash up until the first miss. Hits are attached to the new request's block table and their reference counts go up; prefill begins at the first missing block. Cached blocks survive the request that made them. When a request finishes, its blocks with reference count 0 go to a free queue in least-recently-used order, but they keep their contents and hash. They are evicted only when the allocator actually needs a block and takes the oldest one. This is the OS page cache again: freed memory still holds useful data until someone needs the frame. A detail worth stealing: a finished request's blocks are queued tail-first, so the end of a long prefix, which is least likely to be shared, is evicted before its beginning.

The savings are large. A 2,000-token system prompt on Llama 3.1 8B costs about 29 TFLOP to prefill, around 60 ms of H100 time at 50% of peak FLOP/s (Chapter 11 works this example), and occupies 2,000 × 128 KiB = 250 MiB of cache. With 100 concurrent conversations sharing it, prefix caching saves 99 prefills and about 24 GiB of HBM, because the shared blocks are stored once. It also cuts time to first token, since the shared part of prefill is simply skipped.

Radix trees: SGLang's RadixAttention

SGLang (Zheng et al., 2023) organizes the same idea as a radix tree, a trie whose edges hold runs of tokens. Each edge points at the KV entries for its tokens; the paper's design uses a page size of one token, so a match can end anywhere, not just at a block boundary. Matching a new request is a walk from the root. Inserting a request that diverges in the middle of an edge splits the edge. Each node has a reference count of running requests; nodes with count 0 are evictable, least-recently-used leaves first, so shared ancestors such as a system prompt outlive the conversations below them.

The tree also helps scheduling. If many waiting requests share prefixes, serving them in order of longest cached prefix, which is roughly a depth-first walk of the tree, keeps the shared parts resident while they are needed. The paper proves that depth-first order maximizes the hit rate for an offline batch and reports up to 6.4× higher throughput on reuse-heavy workloads such as agents, few-shot prompts and multi-turn chat.

Optional deep dive: limits and hazards of prefix caching

Only the right GPU helps. A prefix is cached on the GPU that computed it. With many replicas, a request only hits if it is routed to the replica that holds its prefix. That is why serving clusters use prefix-aware routing (Chapter 15), and why OpenAI's prompt caching documentation talks about routing at all.

Hybrid models are harder. With sliding-window or recurrent layers, the state after token p cannot be cut out of the state after a later token: the window has moved on, or the recurrent state has absorbed newer tokens. Engines therefore save prefix states only at chosen checkpoints. DeepSeek's API, for example, documents that because of sliding-window attention a request hits only if it fully matches a saved "prefix unit", which is persisted at request boundaries and at fixed token intervals.

Timing leaks. A cache hit makes the first token arrive sooner. If two tenants share a cache, one can probe whether the other has sent a given prompt. vLLM supports a per-request cache_salt mixed into the first block's hash; commercial APIs isolate caches per organization (Anthropic per workspace).

Collisions. A hash collision would silently attach someone else's KV to your prompt. vLLM moved to SHA-256 by default for that reason, and also keys the hash table by the exact token tuple.

The exact-prefix rule

Every provider caches only an exact token prefix. If one token differs at position p, everything from p on is a miss. The reason is the dependency structure from the start of this chapter: the keys and values of every later token are computed from hidden states that attended to token p, in every layer. Change one token and every later cache entry is different. A prompt that is "99% the same" but differs in its first line gets no cache hits at all.

Design rules that follow:

  1. Static first, dynamic last. Tools, system prompt, long documents and examples go first. The user's new message goes last.
  2. No volatile values near the top. A timestamp, request ID or user name in the system prompt makes every request unique from that token on. Put such values after the cached part, or leave them out.
  3. Serialize deterministically. Same tool order, same JSON key order, same whitespace. A tokenizer sees {"a":1,"b":2} and {"b":2,"a":1} as different tokens.
  4. Append, do not edit. Rewriting or trimming earlier messages invalidates everything after the edit. The LMCache authors report that context truncation, common in production, can cut the prefix hit rate in half.
  5. Place breakpoints at the end of each stable section (Anthropic), and keep traffic for a shared prefix flowing within the TTL, or pay for a longer one.
  6. Check the usage fields. If cached tokens are zero, the prefix was too short, a byte changed, or the cache expired.
Worked example: what caching saves

A 20,000-token static prefix (instructions and a document) plus a 500-token question, sent 100 times within five minutes to a model at $3 per million input tokens (Claude Sonnet 4.6's listed price).

Without caching: 100 × 20,500 × $3/M = $6.15.

With a 5-minute cache: first request writes 20,000 tokens at $3.75/M = $0.075. The other 99 read them at $0.30/M: 99 × 20,000 × $0.30/M = $0.594. The 100 questions are normal input: 100 × 500 × $3/M = $0.15. Total $0.82, 87% less. Each request also skips a 20,000-token prefill, which is most of its time to first token.

Break-even: a 5-minute write costs 0.25× extra and each read saves 0.9×, so it pays off at the first hit. A 1-hour write costs 1× extra and needs two hits.

Why charge for writes and storage at all? Because the cache is big. The 20,000-token prefix above, on a 70B-class GQA model like Llama 3.1 70B, is 20,000 × 320 KiB ≈ 6.1 GiB of KV that must sit in HBM, or be moved to CPU memory or SSD and brought back. A longer TTL means more of that memory held for you, which is what the next sections are about.

Smaller entries: quantizing the cache

The last factor in the size formula is bytes per element. Storing keys and values in FP8 instead of BF16 halves the cache. That doubles the number of sequences that fit and halves the cache's share of each decode step's memory traffic. For Llama 3.1 8B on one H100: 52 sequences at 8K context become 104, and a batch-1 step at 128K context drops from 9.9 ms to about 7.4 ms.

The mechanics, without the format details (those are Chapter 13's):

  • Quantize on write. After the projection and RoPE, the new k and v are scaled and rounded to FP8 (or INT8, INT4) as they are appended. Each tensor, head, or token-head gets a scale factor stored next to the data.
  • Dequantize on read. The attention kernel loads FP8 tiles, which halves HBM traffic, converts them in registers and computes in higher precision. Some kernels, such as FlashAttention 3 with an FP8 cache, also quantize the query and compute the dot products in FP8.
  • Scales matter. In vLLM, --kv-cache-dtype fp8 (or fp8_e4m3, fp8_e5m2) enables it. Without calibration all scales default to 1.0, which works only when values already sit in FP8's range; the recommended path calibrates per-tensor or per-head scales on sample data. Sensitive layers, sliding-window layers for example, can be left in BF16 with --kv-cache-dtype-skip-layers.

Keys and values are not equally easy. Keys have a few outlier channels with consistently large magnitudes, so they quantize best with a scale per channel. Values do not, so a scale per token works. The KIVI paper builds a 2-bit cache on exactly this split (keys per-channel, values per-token) and reports 2.6× lower peak memory with almost no quality loss. In practice FP8 is the safe default, INT4 is common in memory-starved setups, and 2-bit is still research.

Quantized weights are not a quantized cache

A "4-bit model" usually has 4-bit weights and a BF16 cache. The two settings are independent. At long context it is often the cache, not the weights, that you should quantize first.

Spilling over: CPU memory and SSD

An H100 has 80 GB. A busy prefix cache would like terabytes. So engines build a tiered cache, like a CPU's cache hierarchy: GPU HBM, then CPU DRAM (hundreds of GB to a few TB per server), then local NVMe SSD (tens of TB), then shared storage across servers. Cold prefixes move down; a hit brings them back up.

Is loading a cache from a slower tier worth it? The alternative is recomputing it, so compare. Each byte of KV cache stands for a fixed amount of prefill compute:

FLOPs per KV byte ≈ 2NKV bytes per token    load wins when   link bandwidth > achieved FLOP/sFLOPs per KV byte N: parameters (2N FLOPs per prefilled token, ignoring the attention term, which only helps loading). Achieved FLOP/s: what prefill actually reaches, e.g. 50% of the H100's 989 TFLOP/s.

Llama 3.1 8B: 16.06 × 109 / 131,072 ≈ 122,500 FLOPs per KV byte. At 495 TFLOP/s achieved, loading beats recomputing for any link faster than about 4 GB/s. PCIe 5.0 x16 gives about 64 GB/s per direction (often ~50 GB/s achieved), so an 8,192-token prefix (1.07 GB) comes back from CPU memory in about 20 ms, while recomputing it takes about 0.3 s. Bigger models and MLA models have even more FLOPs per KV byte (DeepSeek-V3: about a million), so for them loading wins by even more.

Tools that implement this: vLLM has native CPU offloading (--kv-offloading-size in GiB, with a native or lmcache backend). LMCache is a KV caching layer for vLLM and SGLang that stores caches in CPU memory, on disk or in remote stores, shares them across engine instances, and moves them in large batched transfers overlapped with compute; its authors report up to 15× higher throughput on multi-round QA and document workloads. The same machinery ships KV caches between GPUs in disaggregated serving, where one GPU pool does prefill and another decode (Chapter 15).

When memory runs out: preemption

Decode makes every running sequence's cache grow by one token per step. A scheduler that admitted a batch when blocks were free can run out a few hundred steps later. Then it must preempt: pick a running sequence (usually the most recently admitted), take its blocks, and resume it later. Since attention needs a sequence's whole cache, eviction is all-or-nothing per sequence. There are two ways to bring it back:

Recomputation is cheaper than it sounds because the generated tokens are already known, so they are reprocessed in parallel like a prompt, not one by one. The PagedAttention paper found the two comparable for block sizes of 16–64 tokens, with swapping losing badly for small blocks. vLLM's current engine (V1) preempts by recompute by default. Frequent preemption is a sign the server is oversubscribed; the fixes are the ones from this chapter: more memory for the cache (higher utilization, more GPUs), a smaller cache (FP8), or fewer concurrent sequences. Which request to preempt, and when to admit new ones, is the scheduler's job (Chapter 15).

Throwing tokens away: lossy eviction

Everything so far is exact: every token's keys and values are kept, somewhere. A different family of methods deliberately drops entries the model will probably not need, trading some accuracy for a cache that stops growing.

  • StreamingLLM (Xiao et al., 2023). A plain sliding window collapses once the first tokens are evicted, because heads park unused attention on them (attention sinks, Chapter 5). Keeping just the first 4 tokens plus a recent window keeps models stable over 4 million tokens, up to 22.2× faster than recomputing a sliding window. The positional detail: positions are assigned by slot within the cache, not in the original text. If the cache holds original tokens [0, 1, 2, 3, 6, 7, 8], they get positions 0–6. So keys are cached before RoPE and rotated each step when read. The model still forgets everything outside the window; this gives endless fluent streaming, not long memory.
  • H2O (Zhang et al., 2023). A small fraction of tokens receives most of the attention. H2O accumulates the attention each cached token has received and keeps those heavy hitters plus the most recent tokens, evicting the rest as it goes. With a 20% budget it reports up to 29× higher throughput than offloading-based systems.
  • SnapKV (Li et al., 2024). The queries of the last few prompt tokens (an "observation window") already reveal which earlier positions each head will care about. At the end of prefill SnapKV scores positions with those queries, pools neighboring scores so it keeps small clusters rather than isolated tokens, and keeps the top positions per head. It reports 3.6× faster decoding and 8.2× better memory efficiency at 16K tokens, and 380K tokens on one A100-80GB with little loss on needle-in-a-haystack tests (find one planted fact in a long document).

These methods have practical costs. Fused attention kernels never write the attention weights to memory (Chapter 15), so scoring tokens needs extra work. A dropped token is gone: a later question about the middle of a document cannot be answered from a cache that discarded it. Per-head, ragged caches also fit poorly with paged blocks and prefix sharing. For these reasons production systems mostly rely on reductions trained into the architecture, such as GQA, MLA, sliding windows and learned sparse attention (Chapter 5), plus exact techniques like paging, prefix caching, FP8 and offload. Lossy eviction is used where memory is tight and approximate recall is acceptable.

Key takeaway

There are four levers on the cache: store fewer heads or a compressed latent (architecture), store fewer bytes per number (quantization), store it somewhere cheaper (offload), or store fewer tokens (windows and eviction). Only the last one changes what the model can see.
