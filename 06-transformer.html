From translation machine to text predictor

The Transformer was introduced in 2017 to translate sentences, for example French to English. That job has two different halves. First you must read the whole source sentence. Then you must write the target sentence one token at a time. So the original design had two stacks of layers.

  • The encoder reads the source. Its attention is bidirectional: every source token may look at every other source token, left and right.
  • The decoder writes the target. Its self-attention is masked (causal): a position may only look at earlier positions, because later ones do not exist yet. It has a second attention, cross-attention, whose queries come from the decoder and whose keys and values come from the encoder's output. That is how the decoder "looks at" the source sentence.

The base model in the paper had 6 encoder layers, 6 decoder layers, vectors of 512 numbers and about 65 million parameters. A year later, OpenAI's GPT-1 asked a simpler question: what if we keep only the decoder, delete cross-attention, and train it to predict the next token of ordinary text? That is a decoder-only Transformer. Google's BERT went the other way (encoder-only, trained to fill in blanks), which is great for classifying and searching text but cannot generate it fluently. Every open-weight LLM in this blog — Llama, Mistral, Qwen, DeepSeek, gpt-oss — is a decoder-only Transformer, sometimes with Mixture-of-Experts layers (Chapter 7), and the closed frontier models are generally understood to be built the same way, though their details are not public.

Why did decoder-only win for general-purpose models? The usual reasons are practical, not deep:

  • Any text is training data. There is no source/target split. Every document trains the same objective: predict the next token (Chapter 8).
  • Every position is a training example. With a causal mask, one forward pass over n tokens produces n predictions in parallel (Chapter 5 explains the mask).
  • Prompt and answer are the same kind of thing. Instructions, documents, tool results and the answer are all tokens in one sequence (Chapter 3). The model does not need to know which part is "input".
  • Causality makes caching easy. Past positions never change, so their keys and values can be stored and reused while generating (Chapter 12).

Encoder–decoder models still exist (T5, and speech models such as Whisper), but the frontier is decoder-only. The modern recipe, which Llama made standard and which we use as the running example, adds a few refinements to the 2017 block: normalization before each sublayer (pre-norm) using RMSNorm, rotary position embeddings (RoPE), grouped-query attention (GQA), a gated SwiGLU feed-forward network, and no bias vectors. The rest of the chapter assembles exactly that model.

Common misconception

"Decoder" here has nothing to do with decoding a file format or with the output layer. It is a historical name for "a stack of blocks whose attention is causal". A decoder-only model reads your prompt with the same layers it uses to write the answer.

The residual stream: one vector per token, many writers

The problem. A model with 32 blocks must carry information from the bottom to the top. If each block replaced its input with a new vector, every block would have to re-encode everything that later blocks might need, and a single bad block could destroy information. Training such a deep chain is also hard, because the learning signal has to pass back through every block (Chapter 8).

The idea. Give each token one vector of d = 4,096 numbers, and never replace it. Each block only adds something to it. This running vector is called the residual stream. It starts as the token's row of the embedding table (Chapter 3). Then each of the 64 sublayers of Llama 3.1 8B (32 attention sublayers and 32 feed-forward sublayers) does the same three things:

  1. Read: take a normalized copy of the stream (RMSNorm). The stream itself is not changed.
  2. Compute: run attention or the feed-forward network on that copy.
  3. Write: add the result back into the stream with a plain +.
Intuition

Chapter 4 described one residual connection as state += delta. What is new here is seeing the whole model that way: the stream is a shared memory region that 64 sublayers read and may only update with +=, so the final vector is the embedding plus 64 diffs.

The exact equations

Write x0 for the embedding of a token. For each layer l = 1 … L:

hl = xl−1 + Attnl( RMSNorm(xl−1) )     xl = hl + FFNl( RMSNorm(hl) ) xl−1: the stream entering layer l, shape [n, 4096] for n tokens. hl: the stream halfway through the layer. Attn mixes information across positions (Chapter 5); FFN works on each position separately. Each sublayer has its own weights, including its own RMSNorm scale vector.

Unroll the recursion and the whole model is one sum:

xL = x0 + Σl=1..L ( al + ml )     logits = WLM · RMSNorm(xL) al and ml are the vectors written by the attention and FFN sublayers of layer l. For Llama 3.1 8B that is 1 embedding + 64 writes = 65 vectors of 4,096 numbers, added together. The final norm and LM head then read the sum once.

Three consequences follow, and the rest of the blog leans on all of them.

  • All sublayers share one coordinate system. Since everything is added, each sublayer must write in a "language" that later sublayers and the LM head can read. This is what makes the interpretability tools at the end of this chapter possible.
  • Information can skip layers. If block 3 writes a fact, block 30 can read it directly. The blocks in between do not have to copy it forward. In training, the same identity path carries the learning signal back down unchanged.
  • Streams of different tokens only meet in attention. The stream of token i at layer l contains information from tokens 0 … i only, because the attention mask hides the future.

The low-level reality

The stream is the only state passed from one block to the next. Per token it is 4,096 numbers: 8 KiB in BF16 (some implementations keep it in FP32 for accuracy, 16 KiB). For a prompt of n tokens it is a [n, 4096] matrix. Compare that with the weights of one block: 218,112,000 parameters, about 436 MB in BF16. So a block is a huge, fixed function applied to a tiny piece of state. That ratio is why generating one token at a time is limited by how fast the GPU can stream weights from memory, not by arithmetic (Chapter 11).

The residual add itself is an elementwise operation: read two [n, 4096] arrays, write one. It does almost no math per byte, so on a GPU it is memory-bound. Inference engines therefore fuse "add the sublayer output to the stream" and "RMSNorm the result for the next sublayer" into one kernel that reads the data once (Chapter 15 covers fusion).

Because 65 vectors are summed, the stream's magnitude tends to grow with depth. RMSNorm at every read rescales the copy to a root-mean-square of about 1 (times a learned per-dimension scale), so each sublayer sees inputs of a predictable size no matter how deep it sits.

Key takeaway

A Transformer is a stack of 2L small functions that each read a normalized copy of a per-token vector and add a correction to it. The vector is the residual stream; it is the model's working memory for that token.

The block: read, compute, add (pre-norm)

Every one of the 32 blocks in Llama 3.1 8B has the same structure and different weights. In code:

h   = x + attention(rmsnorm(x, w_attn_norm))     # sublayer 1: mix across tokens
out = h + ffn(rmsnorm(h, w_ffn_norm))            # sublayer 2: per-token transform

This is called a pre-norm block, because the normalization sits before each sublayer, on the side branch. The 2017 paper used post-norm: x = LayerNorm(x + sublayer(x)). The difference looks cosmetic, but it decides whether a deep model trains at all.

Why pre-norm won. With post-norm, the main path passes through a normalization at every sublayer, so there is no clean route from the output back to the early layers. Xiong et al. (2020) showed that at the start of training, post-norm gradients near the output are large, which is why the original Transformer needed a careful learning-rate warm-up (very small weight updates for the first steps of training, Chapter 8). Pre-norm keeps the identity path clean: the gradient of the output with respect to x0 contains a plain "1" term from the sum. GPT-2 moved its normalization to the input of each sub-block, and almost every large model since has done the same. One cost: the stream itself is never normalized inside the stack, which is why a final norm is needed before the LM head.

RMSNorm, as used. Chapter 4 derives it; the one-line reminder is: divide the vector by its root-mean-square, then multiply each dimension by a learned scale.

RMSNorm(x) = x√( mean(x2) + ε ) ⊙ g x: one token's 4,096 numbers. mean(x²): average of the squares. ε = 1e-5 (config field rms_norm_eps) avoids division by zero. g: 4,096 learned scales (the tensor input_layernorm.weight). ⊙: elementwise multiply. Chapter 4 works a numeric example.

Each block has two of these (8,192 parameters together). They are negligible in parameter count but not in behavior: they are the only per-dimension "volume knobs" on what each sublayer sees.

Variations you will meet in configs

  • Biases. Llama's linear layers have no bias vectors (attention_bias: false, mlp_bias: false). Qwen2.5 keeps biases on the q, k and v projections (you can see q_proj.bias tensors in its weight files).
  • QK-norm. Qwen3 adds a small RMSNorm (128 weights) to each query and key head before RoPE (self_attn.q_norm.weight, self_attn.k_norm.weight). It keeps attention scores from blowing up during training.
  • Extra norms. Some families also normalize the sublayer output before adding it ("sandwich" norms). The principle is the same: keep the identity path an untouched sum.

The attention sublayer, as a black box. Input: the normalized [n, 4096] matrix. Output: a [n, 4096] matrix to add to the stream. Inside: four weight matrices (Wq, Wk, Wv, Wo), RoPE on queries and keys, 32 query heads sharing 8 key/value heads, a causal softmax. All of that is Chapter 5's subject; here we only need its shapes, which the shape trace below lists.

The feed-forward network: where most parameters live

Attention moves information between positions. The feed-forward network (FFN, also called the MLP) then processes each position on its own, with no view of other tokens. Llama uses the gated SwiGLU form (the gating idea and the SiLU curve are in Chapter 4):

FFN(x) = Wdown · ( SiLU(Wgate x) ⊙ (Wup x) ) x: one normalized token vector [4096]. Wgate and Wup: [14336, 4096] each, they map 4,096 → 14,336 numbers. SiLU(z) = z·σ(z), a smooth ReLU-like curve. ⊙: elementwise product, so the SiLU branch acts as a per-unit "gate" on the up branch. Wdown: [4096, 14336], back to 4,096. For n tokens all three are matrix multiplies on [n, ·] matrices.

Why the hidden size is 14,336

A classic, non-gated FFN expands to 4·d and back: two matrices, 8d² parameters. A gated FFN has three matrices, so to keep the parameter count the same the hidden size is cut to ⅔ · 4d (LLaMA paper). Llama 3 then scales by a multiplier and rounds up to a hardware-friendly multiple. Meta's original params.json for the 8B model stores ffn_dim_multiplier: 1.3 and multiple_of: 1024:

int(⅔ · 4 · 4096) = 10,922  →  int(1.3 × 10,922) = 14,198  →  round up to a multiple of 1,024 = 14,336 = 3.5 · d

Why 70–80% of the weights are here

Count per block in units of d² (d = 4,096):

  • Attention: Wq and Wo are d × d each (2d²). Wk and Wv are only d × d/4 each, because 8 KV heads × 128 = 1,024 = d/4 (GQA). Total 2.5 d².
  • FFN: three matrices of d × 3.5d = 10.5 d².

So the FFN is 10.5 / 13 = 80.8% of each block, and 70.2% of the whole 8B model (the embedding and LM head take most of the rest). In the classic 2017 shape (attention 4d², FFN 8d²) the FFN share was two-thirds, which is the figure the interpretability literature quotes. GQA shrank attention further, so modern dense models are even more FFN-heavy: 79.9% for Llama 3.1 70B and 81.3% for 405B. Mixture-of-Experts models attack exactly this part: they replace the one big FFN with many smaller expert FFNs and run only a few per token (Chapter 7).

What the FFN does: a key–value memory

There is a useful way to read the formula. Look at one hidden unit i out of 14,336:

  • Row i of Wgate (and of Wup) is a key: a direction in the 4,096-dim space. The dot products gi = gatei·x and ui = upi·x measure how much the input matches that key.
  • The coefficient ci = SiLU(gi) · ui says how strongly slot i fires.
  • Column i of Wdown is the value: a 4,096-dim vector that slot i writes.
FFN(x) = Σi=1..14336 ci(x) · Wdown[:, i]

So the FFN is a soft lookup table with 14,336 slots per layer: match the input against every key, then return a mix of the values whose keys matched. Geva et al. (2021) studied this view directly. They found keys that respond to human-readable patterns in the input (shallow ones such as "ends with a certain word" in lower layers, more semantic ones higher up), and values whose effect, read through the LM head, raises the probability of tokens that tend to follow those patterns. Compare attention: also a lookup, but its keys and values are computed from other tokens at run time. The FFN's keys and values are fixed weights learned in training. A common shorthand: attention moves information, FFNs store it.

Caveat

"FFN = memory" is a lens, not a full explanation. Slots are not one-fact-per-row; most facts are spread across many slots and layers, and the same slot participates in many unrelated contexts. The view is still useful for intuition and it is the starting point of knowledge-editing research.

The low-level reality

Per token, one FFN is three matrix–vector products with 58,720,256 weights each: 352 MFLOP, and 352 MB of BF16 weights to read. At batch size 1 that is about one FLOP per byte, far below what a GPU needs to be compute-bound (the roofline in Chapter 2), so FFN time is weight-reading time. Because FFNs are 70% of the bytes, they are about 70% of a decode step's memory traffic. As Chapter 4 showed, engines merge Wgate and Wup into one [28672, 4096] GEMM and compute SiLU(gate) ⊙ up in one fused kernel.

The [n, 14336] intermediate is the widest activation in the block: 3.5× the stream. For n = 2,048 tokens it is 56 MiB in BF16 per matrix — small next to the weights, but it matters for training memory (Chapter 8).

The top of the stack: final norm, LM head, logits

After block 32, each position's stream holds the model's "conclusion" for that position. Two steps turn it into a prediction:

  1. Final RMSNorm (model.norm.weight, 4,096 scales). Pre-norm blocks never normalize the stream itself, so this is where it finally gets rescaled.
  2. LM head (lm_head.weight, shape [128256, 4096]). One matrix multiply produces 128,256 numbers, one per vocabulary token. These are the logits: unnormalized scores. Row j of the LM head is an "output vector" for token j, and logitj is its dot product with the final hidden vector. A token scores high when its output vector points the same way as the stream.

Softmax turns logits into probabilities (Chapter 4), and a sampler picks one token (Chapter 14).

Tied vs untied embeddings

The embedding table E at the bottom and the LM head at the top have the same shape, [V, d]. A model may tie them: use the same matrix for both (config tie_word_embeddings: true). GPT-2 does this, and so does Llama 3.2 1B. Llama 3.1 8B does not.

  • Small models tie because the vocabulary matrix is a large share of their budget. Llama 3.2 1B's table is 128,256 × 2,048 = 262,668,288 parameters, 21% of its 1,235,814,400. A second copy would add another 21%.
  • Larger models untie because the cost is small (two tables are 13% of 8B, 3% of 70B) and the input side ("what does this token mean?") and the output side ("when should this token come next?") get their own geometry.

In the weight files, a tied model simply has no lm_head.weight tensor; the loader points the head at the embedding matrix.

The low-level reality

  • Only the last row is needed at inference. In training, every position predicts its next token, so the LM head runs on all n rows (Chapter 8). When generating, only the last position's prediction is used. Engines slice the stream to the last row before the LM head. Not doing so is costly: for an 8,192-token prompt the full [8192, 128256] logits are 1.05 billion numbers, 4.2 GB in FP32.
  • Cost per generated token. 2 × 128,256 × 4,096 = 1.05 GFLOP and 1.05 GB of BF16 weights read: 6.5% of the model's bytes for one matrix. The logits for one position are 128,256 × 4 B = 513 KB in FP32.
  • The embedding is not a matmul. At the bottom, E is used as a table: gather one 8 KiB row per token (Chapter 3). So the embedding costs memory but almost no FLOPs, while the LM head costs both. That asymmetry matters for the FLOP count below.

Low-level deep dive: views, copies and layouts

Reshaping [n, 4096] to [n, 32, 128] is free in row-major memory, and the transpose to [32, n, 128] is either a copy or folded into the kernel's indexing (Chapter 5 walks through this layout). The KV cache stores k and v in a layout chosen for the decode kernel (Chapter 12). Note also that h·dh does not have to equal d: Llama 3.1 8B has 32 × 128 = 4,096 = d, but nothing in the math requires it, and some model families pick other head sizes. The config field head_dim exists for that reason.

Parameters = bytes. Multiply the count by bytes per parameter to get the weight file: 8,030,261,248 × 2 B = 16.06 GB (14.96 GiB) in BF16. 70% of those bytes are FFN weights, 17% attention, 13% the two vocabulary matrices.

FLOPs per token: where the compute goes

The rule of thumb. In y = x · Wᵀ for one token, every weight is used in exactly one multiply and one add. So a matrix with P weights costs 2P FLOPs per token, and a whole model costs about 2N FLOPs per token. For Llama 3.1 8B that is the familiar ≈ 16 GFLOP.

The precise version. The embedding table is a lookup, not a matmul, so its 525M weights cost no FLOPs. N minus the embedding is 7,504,924,672 (that still includes 266,240 norm scales, which do almost no math). So:

FLOPsweights = 2 × 7,504,924,672 = 15.01 GFLOP per token The "2N = 16.06 GFLOP" shorthand overcounts by the embedding, about 6.5% for this model and much less for bigger ones. For a tied model, the shared matrix is still used once as a matmul (the LM head), so its V·d weights do count.

The attention term. Weights are not the whole story. Attention also multiplies activations by activations (query against keys, then weights against values). Chapter 5 counted that work; for the token at position t it is:

FLOPsattn = 4 · L · d · t = 524,288 · t 4 = 2 FLOPs per multiply-add × 2 matmuls; L·d = 32 × 4,096. GQA does not reduce this: all 32 query heads still compute their own scores. GQA reduces the bytes of K and V (Chapter 12).

At t = 131,072 (the full 128K context) that is 68.7 GFLOP, more than four times the weight FLOPs. With the precise weight term, the two are equal at t ≈ 15.01e9 / 524,288 ≈ 28,600 (Chapter 5's ≈ 30,600 uses the 2N shorthand).

From per-token to a whole prompt

Processing a prompt of n tokens in one pass sums the per-token cost over positions 1 … n:

FLOPs(n) ≈ 15.01·109 · n + 524,288 · n(n+1)/2 Example, n = 8,192: 123.0 TFLOP for the weights + 17.6 TFLOP for attention = 140.6 TFLOP. An H100's dense BF16 peak is about 989 TFLOP/s, so even at 100% utilization that prompt takes ≥ 0.14 s. Real utilization, and why generation is limited by bandwidth instead, are Chapter 11's subject. For the 5-token running sentence: 75 GFLOP, almost all weights.

Everything else — RMSNorm, RoPE, softmax, SiLU, residual adds — is elementwise work of O(n·d) per layer. It is a fraction of a percent of the FLOPs but not of the time: each such op is a full pass over memory unless it is fused into a neighbor (Chapter 15). Training costs about three times the forward pass (the backward pass is ≈ 2×), which is where the 6N FLOPs-per-token rule comes from (Chapter 8).

Key takeaway

One token through Llama 3.1 8B costs ≈ 15 GFLOP of weight math (≈ 2N) plus 0.52 MFLOP per earlier token for attention. Short prompts are dominated by the FFN; very long contexts by attention.

The whole forward pass in 40 lines of NumPy

Here is everything above as runnable code. It follows the Hugging Face LlamaForCausalLM math: the same RMSNorm, the Llama 3.1 RoPE frequency rescaling, the same GQA head mapping, SwiGLU, untied LM head. Weight names map one-to-one onto the checkpoint (loader below). It is written for clarity, not speed: full precision, no batching, no KV cache.

import numpy as np               # full precision for clarity; engines use BF16

def rmsnorm(x, w, eps=1e-5):
    return w * x / np.sqrt(np.mean(x * x, axis=-1, keepdims=True) + eps)

def rope_freqs(dh, theta=500000.0, factor=8.0, lo=1.0, hi=4.0, ctx0=8192):
    f = theta ** (-np.arange(0, dh, 2) / dh)        # [dh/2] base frequencies
    s = np.clip((ctx0 * f / (2 * np.pi) - lo) / (hi - lo), 0, 1)
    return (1 - s) * f / factor + s * f             # Llama 3.1 rescaling

def rope(x, f):                                     # x: [n, heads, dh]
    ang = np.arange(len(x))[:, None] * f[None, :]   # [n, dh/2] = pos * freq
    cos = np.cos(np.concatenate([ang, ang], -1))[:, None, :]
    sin = np.sin(np.concatenate([ang, ang], -1))[:, None, :]
    x1, x2 = np.split(x, 2, axis=-1)                # HF "rotate_half" pairs
    return x * cos + np.concatenate([-x2, x1], -1) * sin

def softmax(s):
    e = np.exp(s - s.max(-1, keepdims=True))        # subtract max: no overflow
    return e / e.sum(-1, keepdims=True)

def silu(x):
    return x / (1 + np.exp(-x))

def forward(ids, W, h=32, h_kv=8, dh=128):          # ids: n token ids
    n, f = len(ids), rope_freqs(dh)
    mask = np.triu(np.full((n, n), -np.inf), k=1)   # hide j > i (the future)
    x = W["embed"][ids]                             # [n, d]  gather rows
    for lw in W["layers"]:
        a = rmsnorm(x, lw["attn_norm"])
        q = (a @ lw["wq"].T).reshape(n, h, dh)      # [n, 32, 128]
        k = (a @ lw["wk"].T).reshape(n, h_kv, dh)   # [n,  8, 128]
        v = (a @ lw["wv"].T).reshape(n, h_kv, dh)   # [n,  8, 128]
        q, k = rope(q, f), rope(k, f)
        k = np.repeat(k, h // h_kv, axis=1)         # GQA: 4 q-heads per kv-head
        v = np.repeat(v, h // h_kv, axis=1)         # [n, 32, 128]
        s = np.einsum("qhd,khd->hqk", q, k) / np.sqrt(dh) + mask  # [32, n, n]
        o = np.einsum("hqk,khd->qhd", softmax(s), v)               # [n, 32, 128]
        x = x + o.reshape(n, h * dh) @ lw["wo"].T   # residual write #1
        m = rmsnorm(x, lw["ffn_norm"])
        g, u = m @ lw["w_gate"].T, m @ lw["w_up"].T # [n, 14336] each
        x = x + (silu(g) * u) @ lw["w_down"].T      # residual write #2
    return rmsnorm(x, W["norm"]) @ W["lm_head"].T   # [n, V] logits

def generate(ids, W, steps):                        # greedy; no KV cache (Ch 12)
    for _ in range(steps):
        ids = ids + [int(np.argmax(forward(np.array(ids), W)[-1]))]
    return ids

How it was checked. Against an independent, deliberately naive implementation (Python loops over tokens and heads, scalar RoPE written straight from the transformers llama3 rope rule) on random tiny weights: the largest difference in the logits was 9 × 10−15, i.e. float64 rounding. A causality test passes too: the logits of a prefix do not change when later tokens are appended. Finally, with the loader below, the same code was run on the real weights of SmolLM2-135M, a small model with the Llama architecture (30 layers, d = 576, 9 query and 3 KV heads, tied embeddings, rope_theta 100,000 and no rope scaling, so rope_freqs was called with those values). For The cat sat on the it ranks ␣bed first (7.2%), then ␣edge, ␣window and ␣table, and greedy generation continues "The cat sat on the bed, and the cat sat". (A small model prefers bed to mat.)

Line by line, the loop body is Figure 6.6: norm, three projections, reshape into heads, RoPE, repeat KV heads, masked softmax attention, merge heads, o_proj, add; norm, gate and up, SiLU-multiply, down, add. Details worth noticing:

  • RoPE pairing. Hugging Face checkpoints rotate dimension i together with i + 64 ("rotate half"). Meta's original code rotates adjacent pairs (2i, 2i+1). Both are correct because the conversion script permutes the rows of Wq and Wk. If you load Meta's original consolidated.00.pth, use interleaved pairs instead. Mixing these up gives a model that runs and produces garbage.
  • The mask is added before softmax, so masked scores become e−∞ = 0.
  • generate calls forward on the whole sequence for every new token, so each step redoes all previous positions. Caching each layer's k and v makes a step cost one position instead of t (Chapter 12). It also only needs the LM head for the last row.
  • Precision. Real engines keep weights in BF16 (or lower, Chapter 13) and accumulate matmuls in FP32. Running this on the 8B checkpoint needs about 32 GB of RAM for FP32 copies of the weights (NumPy has no BF16, so the loader upcasts), and it is slow, but it is the same math.

The loader is short too, because the file format is simple (next section):

import json, struct, numpy as np

def load_safetensors(path):
    with open(path, "rb") as fh:
        n = struct.unpack("<Q", fh.read(8))[0]      # u64 little-endian: header size
        header = json.loads(fh.read(n))             # name -> dtype, shape, offsets
    buf = np.memmap(path, np.uint8, "r", offset=8 + n)  # mmap: no data read yet
    out = {}
    for name, t in header.items():
        if name == "__metadata__":
            continue
        begin, end = t["data_offsets"]              # relative to start of data
        raw = buf[begin:end]                        # a view into the mapping
        if t["dtype"] == "BF16":                    # numpy has no bfloat16, but
            u32 = raw.view(np.uint16).astype(np.uint32) << 16  # BF16 = top half
            out[name] = u32.view(np.float32).reshape(t["shape"])  # of an FP32
        else:
            dt = {"F32": np.float32, "F16": np.float16}[t["dtype"]]
            out[name] = raw.view(dt).reshape(t["shape"])
    return out

def llama_weights(T, L):                            # HF names -> our dict
    def layer(i):
        g = lambda k: T[f"model.layers.{i}.{k}.weight"]
        return {"attn_norm": g("input_layernorm"),
                "wq": g("self_attn.q_proj"), "wk": g("self_attn.k_proj"),
                "wv": g("self_attn.v_proj"), "wo": g("self_attn.o_proj"),
                "ffn_norm": g("post_attention_layernorm"),
                "w_gate": g("mlp.gate_proj"), "w_up": g("mlp.up_proj"),
                "w_down": g("mlp.down_proj")}
    emb = T["model.embed_tokens.weight"]
    return {"embed": emb, "norm": T["model.norm.weight"],
            "lm_head": T.get("lm_head.weight", emb),  # tied: no lm_head tensor
            "layers": [layer(i) for i in range(L)]}

For a sharded checkpoint, call load_safetensors on each shard and merge the dicts, then forward(ids, llama_weights(T, 32)).

Model files: config.json, safetensors, shards

A downloaded model is a directory. The architecture code is not in it: it lives in the inference library (the Llama implementation in Hugging Face transformers is a few hundred lines). The directory holds the numbers that configure that code and the weights it runs on:

  • config.json — the hyperparameters: every size used in this chapter.
  • model-00001-of-00004.safetensors … — the weights, split into shards.
  • model.safetensors.index.json — which tensor lives in which shard.
  • tokenizer.json, tokenizer_config.json — the vocabulary, merges and chat template (Chapter 3).
  • generation_config.json — default sampling settings. For Llama 3.1 8B: temperature 0.6, top_p 0.9 (Chapter 14).

safetensors: the file format, byte by byte

Why a new format. PyTorch's traditional .bin/.pt checkpoints are Python pickles. Unpickling can run arbitrary code, so loading a downloaded model was equivalent to running a downloaded program. safetensors stores only data and a description of it. It is also designed so that a loader can find any tensor without reading the rest of the file.

The layout has three parts:

  1. 8 bytes: an unsigned 64-bit little-endian integer N, the size of the header.
  2. N bytes: a UTF-8 JSON object. For each tensor name: dtype, shape and data_offsets: [begin, end], measured from the start of the data section (not from the start of the file). An optional __metadata__ entry holds string-to-string pairs. The header may be padded with spaces.
  3. The data buffer: raw tensor bytes, little-endian, row-major (C order), packed with no holes.

Why the layout matters: mmap

Because the data section is raw, aligned and contiguous, a loader does not need to parse or copy it. It can mmap the file — ask the OS to map the file into the process's virtual address space — and build each tensor as a pointer plus a shape into that mapping. Nothing is read from disk until a page is touched; then a page fault makes the kernel read that page into the page cache and map it. You already know this mechanism from systems work; here is what it means for a 5 GB shard.

Low-level deep dive: the bytes are already in the right order

BF16 tensors are stored little-endian and row-major, which is the in-memory layout of x86-64 and ARM CPUs and of NVIDIA GPUs. So "deserializing" a tensor is a no-op: the bytes on disk are the bytes the matmul kernel reads. q_proj.weight, shape [4096, 4096], is 4,096 rows of 4,096 BF16 values; row r, column c is at data offset begin + (r·4096 + c)·2. The header is padded with spaces so the data section starts at an 8-byte-aligned offset (9,520 = 8 × 1,190). The one conversion our NumPy loader has to do is BF16 → FP32, because NumPy has no BF16 type: shift each 16-bit pattern left by 16 bits and reinterpret it as an FP32. That creates a copy, so it is no longer zero-copy.

Shards and the index

Large checkpoints are split into shards (typically about 5 GB each) so downloads can resume and run in parallel and so each process can load only what it needs. Llama 3.1 8B has 4 shards; 70B has 30. The index file is plain JSON:

Looking inside: logit lens, features, superposition

The residual-stream view is not only an engineering convenience. Because every sublayer reads from and adds into one shared space, and the LM head reads that same space at the end, the stream can be inspected. This is the entry point of mechanistic interpretability: reverse-engineering what the weights compute. A short tour.

The logit lens

Take the stream after some middle layer, apply the final RMSNorm and the LM head to it as if it were the last layer, and read off the top token. This is the logit lens (nostalgebraist, 2020). On GPT-2 it showed that predictions form gradually: early layers give shallow or meaningless guesses, middle layers often already hold a plausible candidate, and later layers refine it. The input token itself is rarely what you see: the stream is converted into "prediction space" almost immediately.

Here is a real run, made with the reference code above on SmolLM2-135M (the same small Llama-architecture model used to check the code), stopping after selected layers:

The lens is crude: intermediate layers were never trained to be read by the final LM head, so it can mislead, especially early in the stack and in some model families. The tuned lens (Belrose et al., 2023) fixes this by training a small affine "translator" per layer. Both rest on the same fact: all layers write into one coordinate system.

Features and superposition

Chapter 4 showed that meanings can be directions in a vector space. Interpretability research finds the same inside the stream: a "feature" (a concept such as "this is Python code", "the subject is plural" or "this text is about a bridge") corresponds to a direction, and its strength is the stream's projection onto that direction.

A model clearly represents far more concepts than its 4,096 dimensions. The answer is superposition (Chapter 4): many more almost-orthogonal feature directions than dimensions, which works because few features are active at once. The consequence for everything above: single dimensions, and single FFN slots, are polysemantic — they respond to several unrelated things. That is why the neat "one slot, one fact" picture of the FFN blurs in real models.

Sparse autoencoders

If features are directions packed in superposition, can we recover the list? A sparse autoencoder (SAE) is a second, much wider network trained on the model's stream vectors. Its encoder maps x (4,096 numbers) to m ≫ d feature activations f = ReLU(Wenc·x + b); its decoder rebuilds x̂ = Wdec·f. The loss rewards an accurate rebuild and penalizes the sum of activations, so each vector is explained by a handful of features. Each column of Wdec is then a candidate feature direction, and you interpret it by looking at the inputs that activate it most.

Anthropic's Towards Monosemanticity (2023) did this on a one-layer model. Scaling Monosemanticity (2024) trained SAEs with up to 34 million features on the middle-layer residual stream of Claude 3 Sonnet. Many features were multilingual and even multimodal, some were abstract (code errors, sycophancy, deception), and clamping a feature changed behavior in the expected way. The best known demo amplified a Golden Gate Bridge feature until the model talked about the bridge constantly. The authors are clear about limits: the dictionary is incomplete, and it is hard to prove that features are what the model actually uses rather than a convenient summary.

Key takeaway

All interpretability tools here rely on the architecture of this chapter: an additive residual stream that every component reads and writes in one shared coordinate system. The logit lens reads it with the model's own head; SAEs re-express it as a sparse sum of directions.
