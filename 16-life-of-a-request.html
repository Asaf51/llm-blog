The request we will follow

A user of a travel app types: "I land at 7 pm. Do I need an umbrella for dinner?" The app sends this to a hosted reasoning model. With it go the app's system prompt, three tool definitions, and the earlier conversation. The request sets reasoning effort to "medium", temperature to 1.0, a cap of 2,000 output tokens, and asks for a streamed response.

The model does not answer right away. It thinks, decides it needs the forecast, and calls a get_weather tool. The app runs the tool and calls the API a second time with the result. Now the model answers. One user question, two HTTP requests. Following both of them touches almost every chapter of this blog.

To talk in bytes and milliseconds we need a concrete machine. Providers do not publish their stacks, so we use a plausible stand-in built from public parts.

The trace, hop by hop

Before the GPU: steps 1–6

1 · Client. The app's SDK serializes the conversation into JSON (about 17 KB) and POSTs it over an HTTPS connection it already has open, so there is no new TLS handshake. Nothing is tokenized yet; the client only has characters. The API is stateless: each request carries the whole conversation. (Some APIs can store state for you, but the model still reads the whole history as input.) Chapter 3 explains why input grows every turn.

2 · Gateway. TLS ends here. The gateway maps the API key to an account and checks two rate limits: requests per minute and tokens per minute. It does not know the exact token count yet, so it estimates from the text and the output cap. Over a limit, the request ends right here with HTTP 429. Limits and tiers are in Chapter 15.

3 · Router. Many identical replicas serve this model. A random choice would waste the cache that one of them already holds for this conversation. A prefix-aware router keeps an approximate prefix tree of recent request text for each replica. SGLang's router, for example, stores raw characters so it never has to tokenize, sends the request to the best match if the match is above a threshold (default 50%), and otherwise to the least-loaded replica. Here replica 3 matches 91%. More in Chapter 15.

4 · Chat template and tokenizer. On the replica, the model's chat template renders the system prompt, tool schemas and messages into one string, with special marker tokens between roles. The tokenizer turns it into 4,224 token IDs. Tools are not a side channel: they are 870 tokens of JSON schema in the same sequence as everything else. See Chapter 3 for templates and Chapter 9 for how tool calling is trained.

5 · Prefix cache. The engine cuts the IDs into 16-token blocks and hashes each block together with the hash of the block before it. So a block's hash stands for the whole prefix up to and including it, the way a Merkle chain does. Blocks 0–239 are found in the hash table: their keys and values are already in GPU 3's memory from the previous turn. Only the last 384 tokens are new. Chapter 12 owns this mechanism.

6 · Scheduler. The request waits in the queue for about 15 ms while the current iteration finishes. Then the scheduler checks two things: are there 24 free KV blocks for the new tokens, and do the 384 tokens fit in this iteration's token budget next to the 31 sequences already decoding? Both yes, so the request moves to the running set. If memory runs short later, the scheduler can preempt a sequence and recompute it afterwards. The scheduler loop is in Chapter 15.

On the GPUs: steps 7–12

7 · Prefill. The 384 new tokens run through all 61 layers in one forward pass, in the same iteration as the other sequences' decode steps (chunked prefill). In each layer, attention lets the new positions read the 3,840 cached ones and each other, and writes their compressed K,V latents into the new blocks. In the 58 MoE layers, each token is sent over NVLink to the GPUs that own its 8 chosen experts, and the results come back. The work is about 2 × 37e9 × 384 ≈ 2.8e13 FLOPs, and the iteration takes about 25 ms. Without the cache, all 4,224 tokens would need prefill: three chunks of up to 2,048 tokens, roughly 100 ms. Prefill is in Chapter 11, routing in Chapter 7, MLA in Chapter 5.

8 · First token. Only the last position's vector goes through the final norm and the LM head, giving 129,280 logits. The sampler divides them by the temperature, applies softmax, keeps the top-p nucleus and draws one token. (Our generic request sets temperature 1.0, the value reasoning models are trained to sample at; several hosted APIs now reject any other value, or the parameter itself.) The draw happens 75 ms after the client sent the request; the first bytes reach the client at about 100 ms. That is the time to first token (TTFT). But this token is the start of the hidden thinking, so the user sees nothing yet. Sampling is Chapter 14; TTFT is defined in Chapter 11.

9 · Decode, with continuous batching. From now on, every iteration gives each of the 32 sequences on GPU 3 one more token. One iteration reads about 90 GB of weights and 13.5 GB of KV cache, so it takes about 22 ms no matter what any single sequence does. The weight read is paid once for all 32. Sequences join and leave between iterations, so nobody waits for the longest one. Batching is in Chapter 15; the bandwidth arithmetic is in Chapter 11.

10 · Speculative decoding. DeepSeek-V3-style models carry an MTP module that predicts one token further ahead. The engine uses that guess as a draft and checks it in the next pass, at almost no extra cost. DeepSeek reports 85–90% acceptance for this second token and 1.8× faster decoding. At 85%, each 22 ms pass yields 1.85 tokens on average, so a token arrives every 12 ms: about 83 tokens per second for this user. The acceptance rule makes the output distribution exactly the same as without speculation. See Chapter 15.

11 · Hidden thinking. The first 380 output tokens are reasoning. The user never sees them: the API streams an empty thinking block, or at most a summary. Yet each one is a full decode step, takes a KV entry, and is billed as output. At 12 ms per token, that is 4.6 seconds before any visible text. The "medium" effort setting shaped how long this phase runs. Chapter 10 explains how.

12 · Tool call. The model writes 14 visible tokens ("Let me check tonight's forecast…"), then 26 tokens that the runtime parses as a call to get_weather, then a token that ends its turn. The engine stops the sequence. The API reports the stop reason tool_use (Anthropic) or tool_calls (OpenAI Chat Completions). If the provider enforces the tool's JSON schema during sampling, the arguments are guaranteed to parse. Tool calling is in Chapter 9, constrained decoding in Chapter 14.

Back to the client, and around again: steps 13–17

13 · Detokenize and stream. Each sampled ID becomes bytes again. If a token ends in the middle of a multi-byte UTF-8 character, the detokenizer holds those bytes back until the character is complete (Chapter 3). Text leaves as server-sent events (SSE) on the HTTP response that has been open since step 1. The exact events are shown in What the client receives below.

14 · The client runs the tool. The SDK sees the stop reason, calls the weather service (about 300 ms), and builds request 2. It contains everything from request 1, the assistant's whole turn, and the tool result. The assistant's turn includes its reasoning, passed back as an opaque item: both OpenAI and Anthropic ask for this when a turn continues after a tool call, so the model can pick up its own train of thought. Total: 4,224 + 420 + 180 = 4,824 input tokens.

15 · Request 2 hits the cache. It takes the same path. The router sees an 88% match on replica 3 again. The prefix cache now matches all 264 blocks of request 1's prompt, so only 600 tokens need prefill, about 27 ms. The first token reaches the client 103 ms after it sent the request. (The engine may even still hold the KV of turn 1's output tokens. The bill does not depend on that: what counts as "cached" on the invoice follows the provider's published rules.)

16 · Answer and stop. 220 more reasoning tokens (2.6 s), then 180 visible tokens stream out over 2.2 s. The model emits its end-of-turn token. The stop reason is end_turn (Anthropic), stop (OpenAI Chat) or status completed (OpenAI Responses). The sequence leaves the batch, but its KV blocks are not wiped: they return to the pool as cached blocks, ready for turn 3, until LRU eviction reclaims them (Chapter 12).

17 · Usage and bill. The final events carry the usage counts. The meter multiplies them by prices. At our illustrative prices both requests cost 1.77 cents together; without the prefix cache they would cost 3.94 cents. The section "The bill" below does the arithmetic. Pricing logic is in Chapter 15.

Key takeaway

The model itself only ever does one thing: map a token sequence to a next-token distribution. Everything else in the trace (routing, caching, batching, speculation, streaming, billing) is systems engineering around that one function, aimed at doing it for thousands of users at once without re-reading or recomputing anything twice.

Three lessons from the clock

Plumbing is cheap. Gateway, router, template, tokenizer and cache lookup add up to about 10 ms. Network distance and queueing matter more.

The prefix cache is a latency feature. It cut prefill from about 100 ms to 25 ms here. With a 100,000-token agent context the same cut is from seconds to tens of milliseconds.

Thinking dominates. 7.2 of the 10.3 seconds were hidden reasoning (4.55 s + 2.63 s). For this user, the effort setting mattered more than the GPU model.

Three details matter for client code. The usage counts in message_delta are cumulative, not increments. Errors can arrive in the middle of a stream as an error event (for example overloaded_error, which would be HTTP 529 without streaming), after you have already shown text. OpenAI's Responses API uses the same SSE mechanism with its own event names, such as response.created, response.output_text.delta and response.completed.

Why it stopped

Every response ends with a stop reason. In the trace, request 1 stopped because the model called a tool and request 2 because the model ended its turn. Each API names the cases differently; the side-by-side table (OpenAI Chat, OpenAI Responses, Anthropic) and the way an engine detects each case are in Chapter 14.

A reasoning trap

The output cap counts reasoning and visible tokens together. If thinking uses it all, the response stops before any visible text, and you still pay for every reasoning token (Chapter 10). Our cap of 2,000 was enough only because effort was "medium" and the question was easy.

Request parameters: the knobs on an API call

"Parameters" means two different things. Model parameters are the learned weights: N numbers fixed by training. They set the memory bill (N × bytes per weight: 8.03B → 16.06 GB in BF16) and the decode speed (Chapter 1, Chapter 11). Request parameters are the settings sent with one API call, like those of our trace. They never change the weights. They change which tokens are produced, how many, and how they are billed. Rules of thumb

These are the approximations worth carrying in your head. Each is derived in the linked chapter; each is wrong at the edges.

Memory

  • One billion parameters ≈ 2 GB in BF16, 1 GB in FP8, ≈ 0.56 GB at 4-bit with scales (Ch 13).
  • Weights are shared by every request; the KV cache is per request. At long context or large batch, the KV cache dominates (Ch 12).
  • GQA models need tens to hundreds of KiB of KV per token: 128 KiB for Llama 3.1 8B, 320 KiB for 70B. A million tokens of 8B KV cache is 131 GB (Ch 12).
  • Budget VRAM as weights + KV + 10–20% headroom for activations, runtime and fragmentation (Ch 11).

Speed

  • Decode at small batch is memory-bound: tokens per second ≈ bandwidth ÷ bytes read per token. Halve the bytes (quantize), roughly double the speed (Ch 11).
  • Prefill is compute-bound and runs at thousands to tens of thousands of tokens per second per GPU. Long prompts mostly cost TTFT, and a cache hit removes most of it (Ch 11).
  • Batching raises total throughput almost for free until the batch nears the ridge point (≈ 300 sequences on an H100 in BF16) or the KV pool is full. Per-user speed falls slowly (Ch 11).
  • MoE: memory scales with total parameters, compute per token with active parameters, and at large batch bandwidth scales with total again (Ch 7).
  • Speculative decoding helps most at small batch and on predictable text. It never changes the output distribution (Ch 15).

Quality

  • 8-bit weights are nearly lossless, 4-bit costs a little, below about 3 bits quality falls fast. At equal memory, a bigger model at 4-bit often beats a smaller one at 16-bit (Ch 13).
  • Temperature changes diversity, not knowledge. Temperature 0 is still not bit-for-bit deterministic on a shared server (Ch 14).
  • More reasoning effort helps on hard, checkable problems, with roughly log-linear returns, and wastes tokens on easy ones (Ch 10).
  • Advertised context is not effective context: recall in the middle of very long prompts is weaker (Ch 5).

Money

  • Output tokens usually cost several times more than input tokens (4–6× in late-2026 list prices); cached input costs a tenth of input or less (Ch 15).
  • Reasoning tokens are output tokens: billed, slow, and invisible (Ch 10).
  • Put stable content first (system prompt, tools, documents) and variable content last. One changed early token invalidates the cache for everything after it (Ch 12).
  • Every token of the system prompt is paid on every turn, at the cached rate if you are lucky (Ch 3).

Training

  • Training ≈ 6·N·D FLOPs and ≈ 16 bytes per parameter plus activations; inference ≈ 2·N FLOPs per token (Ch 8).
  • Chinchilla-optimal is about 20 tokens per parameter. Models meant for heavy use train far longer to be cheap at inference: Llama 3 8B saw about 1,900 tokens per parameter (Ch 8).
  • Fine-tune for behavior and format; retrieve (RAG) for facts that change. LoRA trains about 0.1–1% of the parameters (Ch 9).

Self-test

One or more questions per chapter. Try to answer before you open each one; numbers use the blog's running examples.

Ch 1What does one forward pass of an LLM compute, and what turns that into text?

A probability distribution over the whole vocabulary for the next token. A sampler picks one token, it is appended to the input, and the loop repeats until a stop token or a length limit.

Ch 2Why did BF16 replace FP16 for training?

BF16 keeps FP32's 8-bit exponent, so it has the same range: gradients and activations rarely overflow or underflow, and no loss scaling is needed. It gives up mantissa bits, which training tolerates.

Ch 2The H100's BF16 ridge point is about 295 FLOPs per byte. What does that mean for a kernel at 50 FLOPs per byte?

It is memory-bound: it can reach at most 50 × 3.35 TB/s ≈ 168 TFLOPS, about 17% of the 989 TFLOPS peak. Only kernels above ≈ 295 FLOPs per byte can use the full compute.

Ch 3How many Llama 3 tokens is "The cat sat on the", and where do the spaces go?

Five: The cat sat on the. Each leading space belongs to the word that follows it.

Ch 3Why does the input token count grow every turn of a chat, even if each user message is short?

The API is stateless, so each request resends the whole history (system prompt, tools, all earlier messages, earlier answers), and all of it is input to the model again.

Ch 4Why subtract the maximum logit before computing softmax?

To avoid overflow in exp(). Subtracting the same constant from every logit does not change the result, because it cancels between numerator and denominator.

Ch 5Why are attention scores divided by √dh?

The dot product of two random dh-dimensional vectors has a standard deviation that grows like √dh. Without the division, scores get large, softmax saturates to nearly one-hot, and gradients vanish.

Ch 5Llama 3.1 8B has 32 query heads but only 8 KV heads. What does that buy?

A KV cache 4× smaller than full multi-head attention: 128 KiB per token instead of 512 KiB, with little quality loss. That means 4× more context or concurrent users in the same memory, and fewer bytes to read per decode step.

Ch 6Where do most of Llama 3.1 8B's parameters live?

In the FFNs: 176,160,768 of the 218,112,000 parameters per layer (81%), about 5.64B of 8.03B overall (70%). Attention projections take about 1.34B, and the embedding and LM head 525M each.

Ch 6About how many FLOPs does it take to generate one token with an 8B model at position 8,192?

About 2N ≈ 16 GFLOP for the matrix multiplies, plus the attention term 4·L·d·t = 4 × 32 × 4,096 × 8,192 ≈ 4.3 GFLOP. Roughly 20 GFLOP.

Ch 7Why is Mixtral 8x7B 46.7B parameters and not 8 × 7B = 56B?

Only the FFNs are replicated as experts; attention, embeddings and norms are shared. And because each token uses 2 of 8 experts, only about 12.9B parameters are active per token.

Ch 7Why does a big MoE need big batches to be served efficiently?

At batch 1 only k experts per layer are read, but at larger batch the fraction of experts touched, 1 − (1 − k/E)B, approaches 1. Then each step reads almost all the weights, and only a large batch spreads that read over enough tokens.

Ch 8How much compute does training an 8B model on 15T tokens take?

C ≈ 6 × 8.03e9 × 15e12 ≈ 7.2e23 FLOPs.

Ch 8Where does "16 bytes per parameter" for training come from?

Mixed-precision AdamW: 2 bytes BF16 weights + 2 bytes BF16 gradients + 4 bytes FP32 master weights + 4 bytes Adam first moment + 4 bytes second moment. Activations come on top.

Ch 8What is a compute-optimal number of training tokens for a 70B model, and why do labs often train far beyond it?

About 20 × 70B = 1.4T tokens (Chinchilla). Labs train longer because a smaller, longer-trained model is cheaper to serve for the same quality, and serving cost dominates over a model's life.

Ch 9What does loss masking do during supervised fine-tuning?

It computes the loss only on the assistant's tokens. The model learns to produce answers, not to imitate the system prompt or the user.

Ch 9How many trainable parameters does LoRA rank 16 add to one 4,096 × 4,096 matrix?

16 × (4,096 + 4,096) = 131,072, which is 0.78% of the matrix's 16.8M parameters.

Ch 9Mechanically, how does a model "call a tool"?

Tool schemas are tokens in its prompt. It was trained to emit a call in a specific format (special tokens or JSON). The runtime parses that, stops generation, the client runs the tool, and the result is appended as a new message; then the model continues.

Ch 10Why do reasoning tokens raise both cost and latency?

They are output tokens: each is a full decode step, each is billed at the output price, and each takes context and KV cache. And all of them come before the first visible token.

Ch 10What lets GRPO work without a value model?

It samples a group of answers to the same prompt and uses each answer's reward relative to the group's mean (divided by the group's standard deviation) as its advantage.

Ch 11What is the upper bound on decode speed for Llama 3.1 8B in BF16, batch 1, on one H100?

Bandwidth ÷ bytes per token. Rule of thumb with all the weights: 3.35e12 ÷ 16.06e9 ≈ 209 tokens per second. Strictly, a step gathers only one row of the 1.05 GB embedding table, so it reads ≈ 15.0 GB and the bound is ≈ 223 tok/s. Both ignore KV reads and overheads; measured engines reach about 150.

Ch 11Why is prefill compute-bound while decode is memory-bound?

Prefill multiplies each weight matrix by many token vectors at once (a GEMM), so every byte of weight does hundreds of FLOPs. Decode handles one new token per sequence (a GEMV), so every byte of weight read does about B FLOPs at BF16, far below the ridge point unless the batch is huge.

Ch 12How big is the KV cache for Llama 3.1 70B at 32K context and batch 4, in BF16?

320 KiB × 32,768 tokens = 10 GiB per sequence; × 4 = 40 GiB.

Ch 12Why does a prompt cache need an exact prefix match?

Under causal attention, each token's K and V depend on every token before it. Change one early token and every later K and V changes, so nothing after the change can be reused.

Ch 13What is the effective bits per weight of 4-bit weights in groups of 32 with one FP16 scale each?

4 + 16/32 = 4.5 bits per weight.

Ch 13Why are activations harder to quantize than weights?

A few activation channels carry outliers far larger than the rest. One scale for the whole tensor then wastes almost all levels on the outliers. Activations also change with every input, so their scales cannot be tuned offline like weights.

Ch 14What does temperature do to the logits, and what happens as T → 0?

It divides them by T before softmax. Lower T sharpens the distribution; as T → 0 it becomes greedy decoding (argmax). T > 1 flattens it.

Ch 14Why can temperature 0 give different answers to the same prompt on a hosted API?

Floating-point addition is not associative. Batch size and batch composition change kernel choices and reduction orders, which changes rounding, which can flip a near-tie between two tokens. MoE routing can amplify this. Determinism needs batch-invariant kernels.

Ch 15Why does continuous batching beat static batching?

Static batching keeps a batch together until its longest sequence ends, leaving slots idle. Continuous batching re-forms the batch every iteration, so finished sequences leave at once and waiting ones join.

Ch 15With acceptance rate α = 0.8 and 4 draft tokens, how many tokens does each target pass yield on average?

(1 − 0.85) ÷ (1 − 0.8) = (1 − 0.328) ÷ 0.2 ≈ 3.36 tokens, minus the cost of drafting.

Ch 15What problem does FlashAttention solve?

Naive attention writes and reads the full n × n score matrix in HBM, which makes it memory-bound. FlashAttention computes attention in tiles held in on-chip SRAM, using an online softmax, so the score matrix never touches HBM. The result is exact.

Ch 16In the trace, request 2 had 4,824 input tokens. Why was its TTFT only about 100 ms?

4,224 of them hit the prefix cache, so only 600 tokens needed prefill (about 27 ms). The rest was network (50 ms round trip) and about 26 ms of plumbing and queueing.

Ch 16Usage says: input 4,824 (cached 4,224), output 400 (reasoning 220). What is the bill at $3 / $0.30 / $15 per million?

600 × $3 + 4,224 × $0.30 + 400 × $15, per million: $0.0018 + $0.00127 + $0.006 = $0.00907.

  4. Steps 5–8: the server's half of the clock

Hints (open only when stuck)
  • The 9,216 missing Qwen3 parameters: each layer has a per-head RMSNorm on queries and one on keys (q_norm, k_norm), dh = 128 weights each. 2 × 128 × 36 = 9,216.
  • A cold run needs a cold prefix, not a restarted server. Put a random nonce in the first line of the system prompt and every block misses. A nonce at the end measures a warm prefill of a few tokens.
  • A full prefix match still computes the last prompt token, because the sampler needs its logits. So the best case reports the largest multiple of 16 below the prompt length, not the whole prompt.
  • Chat templates rewrite history. Render requests 1 and 2 and diff their token IDs: templates often drop earlier turns' thinking, and the hit stops at the first differing token. Whether request 1's output blocks also hit in request 2 depends on whether the re-rendered turn tokenizes exactly as it was generated.
  • If your reasoning counter reads zero, check the field name. Newer vLLM versions put it in reasoning, older ones in reasoning_content.
  • Do not count tokens by SSE chunks; one chunk is not guaranteed to be one token. Use the usage chunk and the tokenizer.
  • A fresh TCP connection, a tokenizer loaded inside the timed path, or the first request after startup each add tens of milliseconds that look like plumbing. Warm up, then take the median of five runs.
  • The upward bend: summed over a prompt of n tokens, the attention term 4·L·d·t becomes ≈ 2·L·d·n². Long prompts are also prefilled in chunks, one per iteration, sized by the max-num-batched-tokens setting in the startup log.
  • Under load, histogram deltas mix every request. Time your request on the client, or use per-request OpenTelemetry spans if your vLLM build has tracing.
  • Background prompts must not share a prefix. Shared blocks save memory, and with prefix-aware attention kernels they can also save reads, which breaks the simple step model.
