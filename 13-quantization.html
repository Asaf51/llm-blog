Quantization

A model is billions of numbers, and every generated token reads all of them. Quantization stores those numbers in 8, 4 or even 2 bits instead of 16, so the model fits in less memory and runs faster, at a cost in quality that you can measure. This chapter shows the math, the bytes on disk, the kernels that unpack them, and the algorithms that keep the damage small.

Why quantize: memory, bandwidth, compute

Llama 3.1 8B has 8.03 billion weights. Stored in BF16, each weight takes 2 bytes, so the model is 16.06 GB. That one number causes three separate problems.

  1. It does not fit. A 16 GB GPU cannot hold 16.06 GB of weights, and it also needs room for the KV cache and scratch buffers (Chapter 11). Llama 3.1 70B in BF16 is 141 GB: two 80 GB H100s just for the weights.
  2. It is slow to read. When the model generates text one token at a time (decode), every weight is read from memory once per token. The arithmetic is cheap; moving the bytes is the bottleneck. So the speed limit is memory bandwidth ÷ bytes per token (Chapter 11). Halve the bytes and you nearly double the speed.
  3. The math could be cheaper. GPU tensor cores (Chapter 2) multiply 8-bit numbers at twice the BF16 rate: an H100 does about 989 TFLOPS dense in BF16 and about 1,979 in FP8 or INT8. NVIDIA Blackwell (B200, RTX 50-series) adds FP4 at twice the FP8 rate. This only helps when both inputs of the multiplication are low-precision.

Quantization means storing each number with fewer bits by mapping it to one of a small set of representable values, plus a little metadata (a scale) to map it back. It is lossy compression with one special property: the GPU must be able to decompress it at full speed, a few dozen numbers at a time, in registers, right before it multiplies them. Every format in this chapter is shaped by that constraint.

Two pieces of vocabulary are used everywhere below.

  • Bits per weight (bpw): total bits of the stored tensor (or file) divided by the number of weights. It includes the metadata. A "4-bit" format is usually 4.25 to 4.9 bpw in reality.
  • WxAy: weights stored in x bits, activations (the numbers flowing between layers) in y bits. W4A16 means 4-bit weights with BF16/FP16 activations; W8A8 means both are 8-bit. A third target, the KV cache, is often listed separately (W4A16KV8).

The price is quality. A quantized model computes slightly different numbers, so its next-token probabilities drift from the original. At 8 bits the drift is almost invisible; at 4 bits it is small but measurable; below 3 bits it grows fast. Most of this chapter is about two questions: how do we lose as little as possible per bit, and how do we make the hardware go fast on the result.

Key takeaway

Quantization buys three different things: fit (fewer bytes stored), decode speed (fewer bytes read per token) and prefill speed (cheaper multiplications, only if activations are quantized too). Which of the three you get depends on what you quantize.

The core idea: snap numbers to a ruler

A 4-bit integer has 16 possible values. A weight is a real number like 0.0053 or −0.0291. To store one in the other, lay a ruler with 16 evenly spaced tick marks over the range where the numbers live, and for each number store the index of the nearest tick. To read a number back, look up where that tick sits. You need two extra facts about the ruler: the distance between ticks, called the scale s, and which tick sits at 0.0, called the zero point z.

Intuition

This is fixed-point arithmetic with a per-block exponent, or a color palette for numbers. A GIF stores an 8-bit index per pixel plus one palette; a quantized tensor stores a 4-bit index per weight plus one (scale, zero) pair per block of weights. The palette is shared, so its cost is spread over many entries.

q = clamp( round(x / s) + z,  qmin,  qmax )      x̂ = s · (q − z) x is the real number; s the scale (tick spacing); z the zero point (the integer that represents 0.0); round() goes to the nearest integer; clamp() cuts anything outside the representable integers [qmin, qmax]; q is what gets stored; x̂ ("x-hat") is the dequantized value the model actually computes with. This is called affine (or uniform) quantization.

There are two common ways to set s and z for b bits:

  • Asymmetric: the ruler spans exactly [min, max] of the data. s = (max − min) / (2b − 1), z = round(−min / s), codes 0 … 2b−1. Uses every code, but you must store z too.
  • Symmetric: z = 0 and the ruler is centered on zero. s = max|x| / (2b−1 − 1), codes −7 … +7 for 4 bits. Cheaper to compute with (no zero-point term in the dot product), but if the data is lopsided, half the ruler covers empty space.

Two kinds of error, one knob

Quantization makes two kinds of error, and the scale trades one for the other.

  • Rounding error applies to every value inside the range. It is at most s/2. If values land at random positions between ticks, the error is uniform on [−s/2, s/2] and its mean square is s2/12.
  • Clipping error applies only to values outside the range: a value of 9.0 on a ruler that ends at 3.3 is stored as 3.3, an error of 5.7.
The math: 6 dB per bit

With b bits over a fixed range R, s ≈ R / 2b, so the rounding MSE is about R2 / (12 · 4b). Each extra bit halves s and divides the MSE by 4: the signal-to-quantization-noise ratio (SQNR = 10·log10(signal power / error power)) improves by 10·log104 ≈ 6.02 dB per bit.

Numeric check with the symmetric ruler above: s = 0.471, so the predicted RMS error is 0.471/√12 = 0.136. The eight numbers actually gave MSE 0.0149, RMS 0.122. Close: eight samples are not a uniform distribution.

So choosing the scale is choosing the clip range. Make the range smaller and every ordinary value gets a finer ruler, but the extremes are clipped. Common rules:

  • absmax (or min/max): never clip. Simple and the default in most formats.
  • percentile: clip at, say, the 99.9th percentile of |x|.
  • MSE search: try a few dozen clip ratios and keep the one with the lowest error, optionally weighted by how much each weight matters. llama.cpp's k-quant quantizers and AWQ's scale search both work this way.

For bell-shaped data the best clip depends on the bits. Simulating 2 million standard-normal samples (standard deviation σ = 1), the MSE-optimal symmetric 4-bit clip is about 2.5σ, and the optimal 8-bit clip is about 3.9σ. Now compare that with absmax: the largest of 32 random normal values is about 2.35σ on average, close to optimal; the largest of 4,096 values is about 3.8σ, far too wide for 4 bits. Small groups make plain absmax nearly optimal. This is the first hint of why formats use small blocks.

The ruler does not have to be uniform

Trained weights are roughly bell-shaped: many values near zero, few large ones. A uniform ruler spends as many ticks on the empty tails as on the crowded middle. Two alternatives put more ticks where the data is:

  • Floating-point elements such as FP8 (E4M3) and FP4 (E2M1). The bit layouts and the full list of values are in Chapter 2; the point here is that their ticks are dense near zero and sparse far away. E2M1 can represent ±{0, 0.5, 1, 1.5, 2, 3, 4, 6}.
  • Lookup-table codes such as NF4 ("NormalFloat 4", from QLoRA): 16 values chosen so that each bin holds the same share of a normal distribution. The 4-bit code is just an index into a 16-entry table, which a kernel keeps in registers or shared memory.
Key takeaway

Every quantizer is: a ruler (uniform, float or table), a scale (and maybe a zero point) per group, round, clamp. Rounding error shrinks 4× per extra bit; clipping error appears when the range is too small. Outliers force a choice between the two.

Granularity: who shares a scale

Step 7 above is the whole problem in miniature: one large value sets the step for everything that shares its scale. The fix is to share scales among fewer numbers. That costs metadata, so the design question is how many weights share one scale. This is called the granularity of quantization.

A weight matrix of a linear layer (Chapter 4) has shape [dout, din]: one row per output channel, one column per input channel. The common choices are:

  • Per-tensor: one scale for the whole matrix.
  • Per-channel: one scale per output row.
  • Per-group (also "block-wise"): one scale per g consecutive weights along a row, with g typically 16 to 128.
  • 2-D blocks: one scale per tile, for example 128×128 in DeepSeek-V3's FP8 weights.

The real size of a quantized tensor follows directly:

bpw = b + bits of scale + bits of zero pointg b = bits per element; g = weights per group. Example: 4-bit elements, groups of 32, one FP16 scale: 4 + 16/32 = 4.5 bpw (llama.cpp Q4_0). Groups of 128 with an FP16 scale and a 4-bit zero point (a typical GPTQ/AWQ checkpoint): 4 + 20/128 = 4.16 bpw.

Why groups run along the input dimension

Granularity is not only about accuracy. It decides where the multiplications by the scale go inside the kernel. Look at one output of a linear layer, yj = Σk Wjk xk:

  • With a per-output-channel scale, Wjk = sj qjk, so yj = sj · Σk qjk xk. The scale leaves the sum: one multiply per output, not per weight.
  • With groups along k, yj = Σgroups G sjG · Σk∈G qjk xk. One multiply per group partial sum: cheap.
  • A scale per input channel k would sit inside the sum on every term. For weight-only quantization that is tolerable (we dequantize each weight anyway), but it rules out pure integer matrix multiplies.

The same logic applies when activations are quantized too. For Y = X WT with an integer GEMM (general matrix multiply), a scale per row of X (one per token) and per row of W (one per output channel) factor out cleanly: Y = diag(sx) · (Qx QwT) · diag(sw). The integer product runs on the tensor cores, and the two scale vectors are applied once per output element. A scale per column of X (per input channel) does not factor out. Remember this: it is exactly where activation outliers live.

Outliers: why activations are harder than weights

Weights and activations look similar (both are matrices of real numbers) but they are very different to quantize.

  • Weights are fixed after training. You can study them offline for minutes or hours, pick the best scales, and store the result. Their distribution is bell-shaped with mild tails.
  • Activations are produced fresh for every token. A scale must either be computed on the fly from the current values (dynamic quantization, which costs a max-reduction per row) or fixed in advance from sample text (static quantization, which can be wrong for unusual inputs). And activations contain outliers: a few channels that are tens or hundreds of times larger than the rest.

LLM.int8(): the first systematic look

Tim Dettmers and coauthors found this structure in 2022 while trying to run OPT-175B and BLOOM in 8 bits. They reported outlier features up to 20× larger than other dimensions. These features first appear in about 25% of layers and, at around 6.7B parameters, become systematic: about 150,000 outliers per 2,048-token sequence, concentrated in only 6 feature dimensions. Setting those few dimensions to zero dropped the top-1 softmax probability from about 40% to about 20% and raised perplexity by 600–1000%. Removing the same number of random dimensions changed perplexity by about 0.1%.

Their method, LLM.int8(), has two parts:

  1. Vector-wise quantization: a scale per row of X (per token) and per output channel of W (the factorable scales from the granularity section).
  2. Mixed-precision decomposition: any input channel with a value above a threshold α = 6.0 is pulled out and multiplied in FP16 together with the matching weights; everything else goes through INT8. More than 99.9% of the values are multiplied in 8 bits.

It works, but the gather/scatter of outlier columns is slow, so LLM.int8() is mainly a memory saver (the load_in_8bit option of bitsandbytes) rather than a speed-up.

Common misconception

"8 bits is always safe." It is safe for weights with per-channel scales. For activations, a per-tensor 8-bit scale can wreck a modern model, as the table shows. The difficulty is not the bit count; it is the range of the data that shares one scale.

There are four ways to handle outliers, and production systems combine them:

  1. Finer scales: per-token for activations, small groups for weights.
  2. Keep them in high precision: LLM.int8's decomposition, or simply leaving sensitive layers unquantized.
  3. Move the difficulty from activations into weights with a per-channel rescaling (SmoothQuant, AWQ).
  4. Rotate the space so that no single channel is extreme (QuaRot, SpinQuant).

Items 3 and 4 are covered in the PTQ section.

What gets quantized, and what each choice speeds up

"Quantize the model" can mean three different things. They save different resources and speed up different phases of inference (prefill processes the prompt in parallel and is compute-bound; decode produces one token at a time and is memory-bound; see Chapter 11).

  • Weight-only (W4A16, W8A16). Weights are stored in 4 or 8 bits and turned back into BF16 inside the kernel, in registers, just before the multiply. Memory and bytes-per-token shrink, so batch-1 decode gets faster roughly in proportion. The FLOPs are unchanged, so compute-bound prefill does not get faster, and can get slightly slower because of the unpacking work. This is what GGUF files, GPTQ/AWQ checkpoints, bitsandbytes NF4 and MLX mostly do.
  • Weights and activations (W8A8, W4A4). Both operands of the matrix multiply are low-precision, so it runs on INT8/FP8 (or FP4) tensor cores at 2× (or 4×) the BF16 rate. Prefill and large-batch decode get faster, and weights still shrink. The cost is everything in the outlier section: activation scales must be computed per token on the fly or calibrated in advance. FP8 (E4M3) tolerates outliers better than INT8 because its ticks spread out logarithmically, which is a big reason FP8 W8A8 became the standard datacenter path on H100-class GPUs.
  • KV cache (FP8, INT8, INT4). The keys and values stored for every past token (Chapter 12) are written in 8 or 4 bits with small per-head or per-token scales, and the attention kernel dequantizes them as it loads them. FP8 halves KV memory: twice the context or twice the batch in the same VRAM, and faster long-context decode, where KV reads dominate.

Low-level deep dive: how Meta served Llama 3 405B in FP8

The Llama 3 paper describes a careful W8A8 FP8 deployment on H100s. They quantized most parameters and activations of the feed-forward layers (about 50% of inference compute) but not the attention projections, and left the first and last transformer layers in BF16. Scales were computed dynamically and row-wise (per token for activations, per output channel for weights). High-perplexity tokens such as dates produced large activations and large scales, which caused underflows, so they capped the dynamic scale factor at 1,200. Standard benchmarks looked fine even without these fixes, yet the model occasionally produced corrupted answers; they caught this by comparing reward-model scores over 100,000 responses instead. The payoff: up to 50% higher prefill throughput and a better throughput–latency trade-off in decode than BF16 across two machines.

GGUF and llama.cpp quant types, byte by byte

GGUF is the single-file format used by llama.cpp, Ollama and LM Studio. Its layout is simple: a 4-byte magic number (the ASCII bytes GGUF), a version (3), the tensor count, a list of typed key-value metadata (architecture, hyperparameters, the whole tokenizer, the chat template), a table of tensor descriptors (name, shape, type, offset), and then the raw tensor data, each tensor aligned to 32 bytes by default. Like safetensors (Chapter 6) it can be memory-mapped directly. The important detail for quantization: every tensor has its own type, so one file can mix 4-bit, 6-bit and 8-bit tensors.

Q4_0: the simplest real format

Q4_0 is the original llama.cpp 4-bit type and the clearest example of a block format. The definition, from ggml-common.h:

#define QK4_0 32
typedef struct {
    ggml_half d;            // scale ("delta"), FP16
    uint8_t   qs[QK4_0/2];  // 32 weights, two 4-bit codes per byte
} block_q4_0;               // sizeof = 2 + 16 = 18 bytes

The quantizer finds the weight with the largest magnitude in the block, keeping its sign, and sets d = max / −8. That weight then lands exactly on code −8, the extra level that a 4-bit two's-complement range [−8, 7] has on its negative side, so all 16 codes are usable. Each weight is stored as min(15, ⌊x/d + 8.5⌋), an unsigned nibble with an offset of 8. Below is a real block from Llama 3.1 8B.

The other "legacy" types follow the same pattern with blocks of 32: Q4_1 adds an FP16 minimum m so w = d·q + m (asymmetric, 20 bytes, 5.0 bpw); Q5_0 and Q5_1 store the fifth bit of each code in a separate 32-bit word (22 and 24 bytes, 5.5 and 6.0 bpw); Q8_0 is an FP16 scale plus 32 signed bytes (34 bytes, 8.5 bpw).

K-quants: blocks of blocks

An FP16 scale per 32 weights costs 0.5 bpw, which is a lot of overhead at 4 bits. The k-quants (2023) use super-blocks of 256 weights split into sub-blocks of 16 or 32. Each sub-block gets its own scale (and for some types a minimum), but those sub-scales are themselves quantized to 6 or 8 bits relative to one FP16 super-scale. Scales of scales: the same "double quantization" idea QLoRA used for NF4.

The importance matrix (imatrix)

Plain quantizers minimize the error on the weights, Σk (wk − ŵk)2. But what matters is the error on the layer's output, y = Σk wk xk. A weight error ek changes the output by ek xk; if the inputs were uncorrelated, the expected squared output error would be Σk ek2 · E[xk2]. So errors on weights that see large inputs hurt more.

llama-imatrix runs the model over some calibration text and, for every linear layer, accumulates Σ xk2 per input column (the source literally does acc[j] += x[j] * x[j]). llama-quantize --imatrix then minimizes the weighted error Σk impk (wk − ŵk)2 when it searches for each block's scales. This is the diagonal of the same matrix GPTQ uses (next sections), and the same signal AWQ uses. On Llama 3 8B it lowers the KL divergence of Q4_K_M from 0.031 to 0.028 and of Q2_K from 0.445 to 0.332. At 2 bits it is mandatory: llama.cpp refuses to make IQ2_XXS without one.

I-quants: vector quantization on lattices

Below about 3.5 bpw, rounding each weight to its own grid wastes bits. The i-quants (2024, by Iwan Kawrakow) borrow ideas from the QuIP# paper and quantize groups of weights jointly:

  • IQ2_XXS encodes the magnitudes of 8 weights as one index into a codebook of 256 points from the E8 lattice (a famously dense packing of 8-dimensional space). Signs are stored separately with a trick: force an even number of negative signs per group of 8 (flip the least important weight if needed), so 8 signs need only 7 bits. Result: 2.0625 bpw including a 16-bit scale per 256 weights.
  • IQ3_XXS uses 256 points of the D4 lattice for groups of 4: 8×8 bits of indices + 4×7 bits of signs = 92 bits per 32 weights, plus a 4-bit block scale = 96 bits, plus the super-block scale: 3.0625 bpw.
  • IQ4_NL and IQ4_XS are scalar but non-linear: each 4-bit code indexes a 16-entry table (−127, −104, −83, …, 89, 113) that is denser near zero, like NF4. IQ4_XS packs the scales into super-blocks: 4.25 bpw.

The cost is decoding speed: codebook lookups are cheap on GPUs but slower than shifts on some CPUs. There are also ternary types, TQ1_0 (1.6875 bpw: five ternary digits per byte, since 35 = 243 ≤ 256) and TQ2_0 (2.0625 bpw), for models trained with ternary weights.

Block floating-point formats: FP8 blocks, MX and NVFP4

GGUF formats are designed for software kernels. The newest GPU generations instead build block scaling into the tensor cores themselves, so the scale multiply costs nothing. These formats use small floating-point elements (FP8, FP6, FP4, whose bit layouts are in Chapter 2) plus one shared scale per small block.

FP8 with block scales (DeepSeek-V3)

FP8 E4M3 covers a much wider range than INT8 (its largest value is 448 and its ticks are logarithmic), but one scale per tensor is still exposed to outliers. DeepSeek-V3 was trained and released in FP8 with fine-grained scales: activations get one scale per 1×128 tile (per token, per 128 channels) and weights one per 128×128 block, all in E4M3. Because those scales vary along the inner dimension K of the matrix multiply, they cannot be applied after the multiply as one number. DeepSeek also found that H800 (export-market H100) tensor cores accumulate FP8 products with only about 14 bits of precision (a maximum relative error near 2% for K = 4,096). Their kernel fixes both at once: every NC = 128 elements (4 WGMMA instructions, Hopper's warp-group matrix-multiply operations), partial sums are copied to FP32 registers on the regular CUDA cores, multiplied by the two block scales and accumulated there. FP8 training itself is covered in Chapter 8.

OCP Microscaling (MX)

The Open Compute Project's MX specification (v1.0, 2023, authored by AMD, Arm, Intel, Meta, Microsoft, NVIDIA and Qualcomm) standardizes the idea. An MX block is 32 elements sharing one E8M0 scale: 8 exponent bits, no sign, no mantissa, so the scale is always a power of two, 2e−127, from 2−127 to 2127 (the all-ones byte means NaN). The element types are FP8 (E4M3 or E5M2), FP6 (E3M2 or E2M3), FP4 (E2M1) and INT8. Size is d + 8/32 bits: MXFP8 8.25 bpw, MXFP6 6.25, MXFP4 4.25.

The spec's conversion rule: set the scale X to the largest power of two ≤ max|v|, divided by the largest power of two the element type can represent (4 for E2M1); then round each v/X to the element type and clamp to its largest normal value (6 for E2M1).

Worked example: one block, two formats

Take a block whose largest magnitude is 2.6.

MXFP4: the largest power of two ≤ 2.6 is 2, so X = 2/4 = 0.5. Then 2.6/0.5 = 5.2, which rounds to the E2M1 value 6, so 2.6 is stored as 3.0: a 15% error on the most important value of the block. If the maximum were 3.5, it would scale to 7.0 and be clipped to 6: stored as 3.0 again (−14%). With a power-of-two scale, the block maximum lands anywhere in [4, 8) on the element grid, and the part above 6 is clipped.

NVFP4: the scale is max/6 = 0.4333, rounded to the nearest E4M3 value. In [0.25, 0.5) E4M3 steps by 2−5 = 0.03125, so the scale becomes 14 × 0.03125 = 0.4375. Then 2.6/0.4375 = 5.94 rounds to 6, stored as 2.625: a 1% error.

NVFP4

NVIDIA's NVFP4 (introduced with Blackwell) changes two things relative to MXFP4. Blocks are 16 elements instead of 32, and the block scale is an E4M3 FP8 number, so it has 3 mantissa bits: 8 steps per factor of two instead of 1. E4M3 has a much smaller range than E8M0 (about 2−9 to 448), so NVFP4 adds a second-level FP32 scale per tensor that shifts all block scales into range. Size: 4 + 8/16 = 4.5 bpw (plus 32 bits per tensor). NVIDIA reports about 3.5× less memory than FP16 and 1.8× less than FP8, with 1% or less accuracy loss versus FP8 on DeepSeek-R1-0528.

On random matrices, my simulation gives these relative RMS errors (lower is better) for a Gaussian matrix / a heavy-tailed one (Student-t, 5 degrees of freedom): Q4_0-style INT4 with groups of 32 and FP16 scales 8.6% / 10.8%; NVFP4 9.5% / 9.2%; NF4 with groups of 64 9.2% / 10.5%; INT4 with groups of 128 10.3% / 15.1%; MXFP4 11.5% / 12.6%; INT4 per-channel 13.8% / 31.0%. MXFP4's coarse scale costs about 2 percentage points; NVFP4's float elements shine when the tails are heavy. The real reason to pick a format, though, is the hardware: on Blackwell, NVFP4 and MXFP4 matrix multiplies run on the FP4 tensor-core path at about twice the FP8 rate.

MXFP4 is also where training and formats meet. OpenAI post-trained gpt-oss with its mixture-of-experts weights already quantized to MXFP4 (4.25 bpw). Those weights are over 90% of the parameters, which is why gpt-oss-120b (117 B parameters) fits on one 80 GB GPU and gpt-oss-20b runs in 16 GB. llama.cpp stores them as block_mxfp4 (one E8M0 byte + 16 bytes of codes = 17 bytes per 32 weights), and its MXFP4_MOE recipe keeps everything else in Q8_0.

Inside the kernel: dequantize on the fly

A quantized model is never expanded back to BF16 in memory; that would erase the savings. The kernel loads the compressed bytes and expands them in registers, a few dozen at a time, right before the multiply. GPUs have done this for decades with compressed textures: the texture unit decompresses a small block when it is sampled, and the full image never exists uncompressed in DRAM.

Here is the reference logic for one output of a Q4_0 matrix-vector product (GEMV), the core operation of batch-1 decode. Real kernels vectorize it, but the arithmetic is exactly this:

// y_j = sum_k W[j][k] * x[k]   with row j of W stored as Q4_0 blocks
float dot_q4_0(const block_q4_0 *row, const float *x, int n) {
    float acc = 0.0f;                          // FP32 accumulator
    for (int b = 0; b < n / 32; b++) {         // one 18-byte block per iteration
        const float d = fp16_to_fp32(row[b].d);
        const float *xb = x + b * 32;
        float s = 0.0f;                        // partial sum for this block
        for (int j = 0; j < 16; j++) {
            const uint8_t byte = row[b].qs[j];
            const int lo = (byte & 0x0F) - 8;    // weight j
            const int hi = (byte >> 4)   - 8;    // weight j + 16
            s += lo * xb[j] + hi * xb[j + 16];
        }
        acc += d * s;                          // the scale is applied once per block
    }
    return acc;
}

Note where the scale goes: outside the inner loop, once per 32 weights, exactly as the granularity section predicted. On a GPU the same work is spread over a warp, and two tricks make it fast:

  • Wide loads. One 128-bit load brings in 16 bytes, which is 32 weights. The memory system is used at full width even though each weight is only half a byte.
  • Integer-to-float conversion without a convert instruction. The FP16 bit pattern 0x6400 is 1024.0, and at that magnitude one unit of the 10-bit mantissa is exactly 1.0. OR-ing a 4-bit code q into the low mantissa bits gives the FP16 number 1024 + q. Subtracting 1032.0 (1024 + 8) yields q − 8 exactly. With 32-bit logic operations this handles two FP16 values per instruction (pattern 0x64006400). For the high nibble, left in place, the same OR gives 1024 + 16q, and one fused multiply-add by 1/16 with −72 yields q − 8. This is the trick used by FasterTransformer-style and Marlin-style kernels.

Why 4-bit decode is about 2.5–3× faster, not 4×

Q4_0 stores 4.5 bits per weight instead of 16, so a decode step reads 3.6× fewer weight bytes; Q4_K_M reads 3.3× fewer. Measured speed-ups are lower for three reasons: some traffic does not shrink (the KV cache, activations, the small tensors kept at higher precision); the unpacking instructions start to matter once the bytes are few; and smaller transfers achieve a lower fraction of peak bandwidth. Batching changes the picture (Chapter 11). With B sequences per step, each loaded weight is used B times, so the arithmetic grows while the bytes stay fixed. The Marlin paper showed that a carefully pipelined W4A16 kernel keeps close to the ideal 4× speed-up up to batch 16–32, with gradually smaller gains up to 64–128, and up to 2.8× end-to-end in vLLM. Past that point the GEMM is compute-bound, the unpacking is pure overhead, and a W8A8 FP8 (or FP4 on Blackwell) kernel that makes the math itself cheaper wins. This is why local inference favors weight-only 4-bit while large-batch servers favor FP8 or NVFP4.

Low-level deep dive: llama.cpp is secretly W4A8

On CPUs and in its CUDA matrix-vector kernels, llama.cpp does not multiply 4-bit weights by float activations. It first quantizes the activation vector on the fly to 8-bit blocks (Q8_0 for Q4_0 weights, Q8_K for k-quants, Q8_1 on CUDA), then computes integer dot products: vpdpbusd (AVX-VNNI) or maddubs (AVX2) on x86, sdot/i8mm on ARM, dp4a on NVIDIA GPUs (a 4-way int8 dot product with an int32 accumulator). Each block contributes dw · dx · Σ qwqx. The Q8_1 block even stores d·Σq so that the minimum term of Q4_1 (m · Σx) costs one multiply instead of a loop. Integer SIMD is faster and denser than float SIMD on these units, and 8-bit activation blocks of 32 are fine-grained enough that the extra error is small.

Smarter rounding: calibrated post-training quantization

Everything so far used round-to-nearest (RTN): each weight independently snaps to its closest grid point. That is optimal for the weights in isolation, but the goal is different. We want the layer's outputs to stay the same. Post-training quantization (PTQ) methods use a small set of calibration data (a few hundred sequences of ordinary text run through the model to record real activations) to choose better integers or better scales. They take minutes to hours and need no training. The alternative, quantization-aware training, comes in the next section.

GPTQ: fix the error you just made

GPTQ (Frantar et al., 2022) quantizes one linear layer at a time. Let X be the layer's calibration inputs (shape din × tokens). The goal is the quantized Ŵ that minimizes the output error ‖WX − ŴX‖2. Each output row is independent, and for one row w the error is a quadratic form:

error(ŵ) = (w − ŵ) H (w − ŵ)T / 2,    H = 2 X XT H is the Hessian of the layer's squared error: a din × din matrix of input correlations, the same for every row. Its diagonal is exactly the llama.cpp importance matrix; its off-diagonal terms say which inputs move together.

If inputs k and k' are correlated, an error on weight k can be partly cancelled by nudging weight k'. GPTQ builds on the Optimal Brain Quantization method: quantize one weight wq, then update all not-yet-quantized weights F by the closed-form optimal correction

δF = − wq − quant(wq)[HF−1]qq · (HF−1):,q The rounding error of wq, divided by a diagonal entry of the inverse Hessian, times the corresponding column of the inverse Hessian: weights correlated with input q move to compensate. Then q leaves the set F and the process repeats.

The original method was far too slow for LLMs (cubic in din per row). GPTQ made three changes:

  1. Same column order for all rows. The original chose a greedy order per row. GPTQ showed that a fixed order works almost as well on large layers, so the inverse-Hessian updates are shared by all rows and done once.
  2. Lazy batch updates. Updating the whole matrix after every column is memory-bound. GPTQ quantizes 128 columns, accumulates their corrections, and applies them to the rest of the matrix in one GEMM.
  3. Cholesky form. Repeatedly updating H−1 is numerically unstable at this scale. GPTQ precomputes the needed rows from a Cholesky factorization of H−1, after adding 1% of the mean diagonal to H ("dampening").

The calibration set in the paper was 128 random 2,048-token segments of C4 web text. The result: a 175B-parameter model quantized to 3–4 bits in about four GPU-hours with negligible loss. Memory-wise, H for a 4,096-wide input is 4,0962 × 4 bytes = 64 MiB; for Llama's 14,336-wide down_proj input it is 822 MB. A common option, act-order, quantizes the columns with the largest Hkk first, while many weights remain to absorb their errors.

AWQ: protect the weights that see big inputs

AWQ (Lin et al., 2023) starts from an observation: not all weights matter equally, and the important ones are found by looking at the activations, not the weights. Keeping just 1% of weight channels (the ones multiplied by the largest activations) in FP16 recovers most of the loss of 3-bit RTN. Mixed precision is awkward for kernels, so AWQ uses an equivalent transformation instead: multiply the important input channel of W by s > 1 and divide the matching activation by s. The product is unchanged, but the weight is now larger relative to its group's quantization step (which barely changes, because one channel rarely sets the group maximum), so its relative rounding error shrinks by about 1/s.

AWQ searches the scale per input channel as s = sXα, where sX is the average activation magnitude of that channel and α ∈ [0, 1] is chosen by grid search to minimize the layer's output error. The 1/s is folded into the previous operation (an RMSNorm weight or the previous linear layer), so inference cost is zero. On OPT-6.7B with INT3 and groups of 128, scaling the salient channels by s = 2 improved perplexity from 23.54 to 11.92. No backpropagation and no reconstruction are involved, which makes AWQ hard to overfit to its calibration set.

SmoothQuant: move the outliers into the weights

SmoothQuant (Xiao et al., 2022) uses the same equivalence, Y = (X diag(s)−1) · (diag(s) WT), for the opposite purpose: making activations quantizable for W8A8. Activation channel j is divided by

sj = max|Xj|α / max|Wj|1−α max|Xj| is measured on calibration data; max|Wj| is the largest weight in input channel j; α (the "migration strength") is usually 0.5. With α = 0.5 both sides end up with the same maximum, √(max|Xj| · max|Wj|).

Example: an activation channel with maximum 40 meets weights with maximum 0.1. s = √40 / √0.1 = 20, after which both maxima are 2. The activation outlier has become a mild weight outlier, which per-channel weight scales handle easily. The paper reports up to 1.56× speed-up and 2× memory reduction with negligible accuracy loss, enough to serve a 530B model on a single node. Its limit showed up in the W8A8 table in the outlier section: it fixes channel outliers, not one huge token such as BOS, where per-token scales work far better.

Rotations: QuaRot and SpinQuant

Scaling handles one channel at a time. A rotation handles all of them at once. For any orthogonal matrix Q (one with QQT = I), Y = XWT = (XQ)(WQ)T. Fold Q into the weights offline and rotate the activations online (or fold that too, where the architecture allows). A random rotation spreads any single large coordinate over all coordinates. Hadamard matrices (entries ±1/√d) are orthogonal and can be applied in O(d log d) with a butterfly network, like an FFT, so the online rotation is cheap.

  • QuaRot (2024) applies randomized Hadamard rotations to the residual stream, inside the feed-forward block, to attention and to the KV cache, and then quantizes everything to 4 bits: weights, activations and KV cache, with every matrix multiply in INT4. Llama-2-70B loses at most 0.47 WikiText-2 perplexity and keeps 99% of its zero-shot accuracy, with up to 3.33× faster prefill and 3.89× less decode memory. At 6 and 8 bits it is lossless with plain RTN.
  • SpinQuant (2024) noticed that some random rotations are much better than others (up to 13 points of zero-shot accuracy apart) and learns the rotation matrices. With W4A4KV4 it narrows the gap to full precision to 2.9 points on Llama-2 7B, and on the harder-to-quantize Llama 3 8B it closes up to 45% of the gap that QuaRot leaves.

The same "incoherence processing" idea powers the best 2-bit weight-only methods (QuIP#, QTIP, and EXL3, which is based on QTIP) and MXFP4 training recipes.

My own measurement on Llama 3.1 8B (table below) makes the point. W4A4 with per-token activation scales and per-channel weight scales, plain RTN, breaks the model. Adding a randomized Hadamard rotation in front of every linear layer (random sign flips, then a Walsh–Hadamard transform of size 4,096, or blocks of 2,048 for the 14,336-wide down_proj input), with nothing else changed, cuts the KL divergence 8.5×. The rotation also helps weight-only W4, because the weights' own outlier columns get spread out too, and adding 8-bit per-token activations on top costs nothing measurable. QuaRot and SpinQuant add GPTQ-quality weight rounding, which closes most of the remaining gap.

HQQ: no calibration data at all

HQQ (Half-Quadratic Quantization, Badri and Shaji, 2023) asks whether you can get close to calibrated quality without any data. It minimizes the error between W and its dequantized version directly, but with a sparsity-promoting ℓp loss (p < 1) instead of squared error, which tolerates a few large errors (outliers) instead of letting them dominate. The optimization of the zero point (and optionally the scale) is done with half-quadratic splitting: alternating closed-form updates, no gradients. It quantizes Llama-2-70B in under 5 minutes, more than 50× faster than GPTQ.

Training for low precision: QAT and native low-bit models

Post-training methods hit a wall at around 3–4 bits for weights and 8 bits for activations. Beyond that, the model itself has to adapt. Quantization-aware training (QAT) runs training (often a short continued-training phase) with quantization inside the forward pass, so the weights learn to work despite rounding.

The mechanism is fake quantization. The master weights stay in FP32 or BF16 and are updated by the optimizer as usual (Chapter 8). In the forward pass, each weight is replaced by x̂ = s·clamp(round(x/s)), computed in floating point, so the loss "sees" the rounded model. The problem is the backward pass: round() is a staircase, and its derivative is zero almost everywhere, so no gradient would reach the weights. The fix is the straight-through estimator (STE): in the backward pass, pretend round() is the identity, passing the gradient through unchanged inside the clip range and blocking it outside. Scales can be learned the same way.

Why this works: with the rounding in the loop, training pushes weights toward configurations whose rounded versions perform well, and it discourages the outliers that ruin scales. The cost is training compute and data. Three examples show where the field went:

  • gpt-oss (OpenAI, 2025) was post-trained with its MoE weights already in MXFP4 (see the block-format section). The released checkpoint is the 4.25-bpw model; there is no larger original being degraded on your machine.
  • BitNet b1.58 (Microsoft, 2024) trains from scratch with every weight in {−1, 0, +1}: log23 ≈ 1.58 bits of information. Its quantizer is absmean: divide the weight matrix by its mean absolute value γ, round, and clip to [−1, 1]. Activations use 8 bits. A matrix multiply becomes additions and subtractions of activations. The authors report matching a full-precision Llama-style model of the same size and training tokens at 3B parameters and above, and released BitNet b1.58 2B4T (2B parameters, 4T training tokens). llama.cpp's TQ1_0 and TQ2_0 types store such weights. The open question is whether this holds at frontier scale; the published evidence is at a few billion parameters.
  • FP8 and FP4 training: DeepSeek-V3 was trained with FP8 matrix multiplies using the block scales described above, and research recipes now train with MXFP4 matrix multiplies (using stochastic rounding and random Hadamard transforms). Training precision is covered in Chapter 8.
Key takeaway

PTQ adapts the numbers to a fixed model; QAT adapts the model to the numbers. The trend is toward models that are born in low precision (FP8 training, MXFP4 post-training, ternary pretraining), which removes the gap between "the model" and "the quantized model".

The wider zoo: bitsandbytes, GPTQ/AWQ checkpoints, EXL2/EXL3, MLX

Every inference stack has its own format family. The ideas are all ones you have seen; only the packing differs.

  • bitsandbytes (Hugging Face Transformers' load_in_8bit / load_in_4bit): LLM.int8() for 8 bits, and NF4 or FP4 with blocks of 64 for 4 bits. Optional double quantization stores the FP32 block scales themselves as FP8 in groups of 256, cutting scale overhead from 32/64 = 0.5 to 8/64 + 32/(64·256) = 0.127 bits per weight. This is the frozen base model in QLoRA fine-tuning (Chapter 9); compute is done in BF16 after dequantizing.
  • GPTQ and AWQ checkpoints on Hugging Face: INT4 codes packed eight per int32, an FP16 scale and a packed zero point per group of 128. vLLM and similar engines run them with Marlin-family W4A16 kernels.
  • FP8 checkpoints: E4M3 weights with per-tensor, per-channel or 128×128 block scales, run natively on Hopper and Blackwell GPUs; increasingly the format in which open models are released.
  • EXL2 (ExLlamaV2): GPTQ-style optimization, but it mixes 2-, 3-, 4-, 5-, 6- and 8-bit quantization within and across layers to hit any average bitrate between 2 and 8 bpw (for example 4.65). EXL3 (ExLlamaV3) is a streamlined version of QTIP (trellis-coded quantization with incoherence processing); it computes Hessians on the fly and converts small models in minutes, 70B-class models in hours, on one consumer GPU.
  • MLX (Apple silicon): affine group quantization, by default 4 bits with groups of 64 and one scale plus one bias per group in the model's float type (4 + 32/64 = 4.5 bpw), codes packed eight per uint32 from the low bits up. It also supports mxfp4, mxfp8 and nvfp4 modes.

Measuring the damage

A quantized model never fails loudly. It produces fluent text that is slightly different. To measure "slightly", there are four common tools, from cheapest to most meaningful.

  • Perplexity (Chapter 8): the exponential of the average negative log-probability that the model gives to the real next token of a test text, usually WikiText-2. Lower is better, and it is cheap. But it only looks at the probability of one token per position, and errors in different directions can cancel.
  • KL divergence (KLD) to the original model: at every position, compare the whole next-token distributions. With p from the original model and q from the quantized one, KLD = Σv p(v) · ln(p(v)/q(v)). It is 0 only if the distributions are identical, and it does not need the "right answer", only the original model's logits (llama.cpp stores them: 37 GiB for Llama 3 over WikiText-2).
  • Top-token agreement and "flips": how often the most likely token is the same, and on benchmarks, how many answers change from right to wrong and wrong to right. A 2024 study ("Accuracy is not all you need") showed that accuracy can stay the same while many individual answers flip, and that KLD tracks flips well.
  • Task evaluations: benchmarks for knowledge, math, code and long context, chat-quality judges, or, as Meta did for Llama 3 405B, comparing reward-model scores of many generated answers.
Worked example: KL divergence

Three candidate tokens. The original model gives p = [0.70, 0.20, 0.10]; the quantized model gives q = [0.60, 0.25, 0.15].

KLD = 0.70·ln(0.70/0.60) + 0.20·ln(0.20/0.25) + 0.10·ln(0.10/0.15) = 0.70·0.154 − 0.20·0.223 − 0.10·0.405 = 0.108 − 0.045 − 0.041 = 0.023 nats (a nat is the unit you get when KL uses the natural log). Rules of thumb, with the evidence behind them

  • 8-bit weights are effectively lossless (Q8_0, FP8, INT8 per-channel): KLD around 0.001, the same top token about 98% of the time.
  • 5–6 bits are near-lossless (Q6_K: KLD 0.005, perplexity +0.3%).
  • 4 bits is the sweet spot with a small, real loss (Q4_K_M: perplexity +2.8%, top token changes about 1 time in 12). Calibration (imatrix, GPTQ, AWQ) and good formats matter here.
  • 3 bits and below degrade quickly: Q3_K_M is about 3× worse in KLD than Q4_K_M, Q2_K is 14× worse, and 1.5-bit types are mostly experiments for very large models. Lattice i-quants and an imatrix are what make 2–3 bpw usable at all.
  • Activations are harder than weights: W8A8 needs per-token scales or smoothing; W4A4 needs rotations or QAT.
  • Heavily trained models are harder to quantize. At Q4_K_M, Llama 3 8B (trained on about 15T tokens) has a KLD of 0.031 versus 0.013 for Llama 2 7B (2T tokens); at Q2_K, 0.445 versus 0.109. The "Scaling Laws for Precision" paper (2024) found the same trend in controlled runs: post-training quantization hurts more as pretraining data grows, to the point where extra data can make the quantized model worse. The more information packed into each weight, the less rounding it tolerates.

Bigger and quantized, or smaller and exact?

With a fixed memory budget, the usual answer is: take the bigger model at about 4 bits. When the k-quants were introduced, perplexity across LLaMA 7B to 65B turned out to be a fairly smooth function of the quantized file size: what mostly matters is how many bytes you can afford, and a larger model at fewer bits is a good way to spend them (the author's 16 GB GPU could run the 30B model only at about 2–3 bits). HQQ's authors make the same point: their 2-bit Llama-2-70B beats a full-precision Llama-2-13B of similar memory footprint. Two cautions. First, below about 2.5 bpw the cliff can erase the advantage. Second, the same k-quant measurements showed that the relative quantization error did not shrink for the larger models; big models "tolerate" quantization because they start from a better place, not because they lose less.

Common misconception

"The benchmark score did not change, so the quant is lossless." Benchmarks average away individual flips, and WikiText perplexity says little about long-context retrieval, code or rare languages. Meta saw FP8 benchmarks hold up while some responses were corrupted. Measure KLD or flips against the original, and test the tasks you care about.

What fits where

The arithmetic is one line: weight bytes ≈ parameters × bpw / 8. Then leave room for the KV cache (for Llama 3.1 8B, 128 KiB per token in BF16, so 1 GiB per 8K tokens; Chapter 12) and for runtime buffers (Chapter 11). Sizes marked ≈ are computed from parameter counts, not measured files.

Hints (open only when stuck)
  • Q4_0 is not bit-exact? Convert BF16 to FP32 first. Keep the sign of the largest-magnitude weight (on ties, the first one wins). Compute d = max/−8 and id = 1/d in FP32, and round with the FP32 d, not the FP16 value you store. Codes are min(15, trunc(x·id + 8.5)). Dividing by d instead of multiplying by id flips a few codes per million.
  • Q8_0 is off by one on some codes? The C code uses roundf, which rounds halves away from zero. torch.round and np.round round halves to even. gguf-py ships np_roundf for exactly this reason.
  • The file disagrees but gguf-py agrees? Convert with --outtype bf16, not f16: FP16 can flush tiny BF16 values to zero. GGUF lists shapes as [din, dout], the reverse of PyTorch. The converter permutes the rows of attn_q and attn_k to suit llama.cpp's RoPE layout, so compare those as sets of rows (for example, sorted row hashes).
  • Q4_K scales. Sub-blocks 0–3 keep their 6-bit scale and min in the low 6 bits of bytes 0–3 and 4–7. Sub-blocks 4–7 take their low 4 bits from bytes 8–11 (scale in the low nibble, min in the high nibble) and their top 2 bits from the spare top bits of bytes 0–7. Read get_scale_min_k4 in ggml-quants.c. In qs, each 32 bytes hold two sub-blocks: low nibbles for the first, high nibbles for the second.
  • NVFP4 and MXFP4. The per-tensor scale is amax/(6·448), so that the largest block scale lands on 448. Casting to torch.float8_e4m3fn does not saturate (values that are too large become NaN), so clamp before you cast. For MXFP4 the shared exponent is floor(log2 amax) − 2, and elements clip at ±6. gguf-py's MXFP4.quantize_blocks is a reference you can diff against.
  • RMS table off by about 1 point? The chapter's INT4 rows use the Q4_0 rule (signed max/−8, 16 levels), not max/7. Express errors as ‖W − Ŵ‖ / ‖W‖.
  • Harness noise. Quantize-dequantize in FP32 and cast to BF16 once. Keep the original linear weights on the CPU so restore is exact. Compute log_softmax in FP32, never in BF16. Score the same positions in every configuration.
  • W8A8 per-tensor looks fine? Then your scale did not see the BOS row. The massive activation is the point of the experiment, so keep BOS in every window and include it when you compute the scale.
  • GPTQ blows up. Accumulate H in FP32 as a running mean. Set dead inputs (Hkk = 0) to 1 and zero their weights. Use the upper Cholesky factor of H−1, not of H. Compute each group's scale from the updated weights when you reach its first column. For AWQ, normalize s (for example, divide by √(max · min)). Under GQA, skip folding v → o, as AutoAWQ does (Llama 3.1's v_proj has 1,024 outputs, but o_proj has 4,096 inputs).
  • Too-good kernel numbers. L2 is 50 MB on an H100, 40 MB on an A100 and 72 MB on an RTX 4090. A 4,096 × 4,096 Q4_0 matrix is 9.4 MB and fits. Time a full 32-layer set of distinct matrices (about 3.9 GB of Q4_0) with triton.testing.do_bench.
